# Данные для кабинета владельца в Cloud — проект решения

Дата: 2026-11-03. Статус: локальная очередь и Cloud-код реализованы и проверены изолированно; удалённое развёртывание и Telegram-доставка остаются отдельными этапами.

## Цель и границы

Локальная SQLite филиала остаётся источником истины. Cloud хранит проверенные проекции для сайта владельца. Отсутствие интернета или Telegram никогда не блокирует продажу и закрытие смены. Сайт показывает время последнего подтверждённого обновления по каждому разделу и отмечает неполную синхронизацию.

## Надёжная доставка

1. Отдельная SQLite-очередь для закрытого отчёта и снимков журнала: `eventId`, `kind`, `branchId`, `shiftId`, версия формата, payload или ссылка на неизменяемый снимок, hash, время создания, состояние, попытки и последняя ошибка. В одной транзакции с закрытием сохраняются отчёт и задания; запрос в интернет в эту транзакцию не входит.
2. Один фоновый worker отправляет небольшие ограниченные пакеты. После подтверждения Cloud фиксирует курсор/ack локально. При таймауте повторяет с тем же ключом идемпотентности; Cloud принимает тот же ID и hash один раз, конфликтующий hash отклоняет.
3. Запускать worker после успешного закрытия, при запуске сервера и периодически во время работы. При ошибке применять паузу с увеличением интервала. Отправлять накопленные старые смены по порядку без ожидания закрытия следующей смены. Свежий отчёт имеет приоритет перед массовой обратной загрузкой журнала.
4. Для аналитики сохранять существующий фоновый поток подтверждённых фактов; не задерживать его до закрытия смены. Улучшить текущий периодический опрос: будить worker после появления нового факта, делать короткую периодическую проверку для восстановления, не посылать пустой пакет каждые 30 секунд. База получает короткие чтения и одну фоновую отправку за раз. При большой истории применять порционную обратную загрузку и лимит времени/размера пакета.
5. Cloud возвращает подтверждение для каждого события или пакета. Отчёт отображается как «в очереди», «получен Cloud»; Telegram отдельно как «ожидает», «отправлен», «ошибка/неизвестно». Не смешивать эти состояния.

## Telegram

Cloud создаёт одно логическое задание уведомления по `branchId + reportId` после принятия отчёта. Bot token и привязка получателя хранятся только в Cloud. Сообщение содержит краткие итоги и ссылку на отчёт сайта; отсутствие Telegram не меняет статус закрытой смены. Сетевой таймаут после отправки означает неопределённый результат: повтор может создать дубль сообщения, поэтому нужно хранить ID попытки и показывать этот случай честно.

## Доступ, дата, сверка

- Все чтения сайта ограничиваются организацией владельца и выбранным филиалом. Локальный сервер отправляет данные подписанным устройством; клиент сайта не пишет в таблицы фактов. Доступ к сотрудникам не превращается в Cloud-учётные записи сотрудников.
- Для календарных графиков и рейтинга использовать дату филиала (`Asia/Bishkek` сейчас); отчёт смены связывать по `shiftId`, даже если смена пересекла полночь. День возврата определяется временем возврата, история проданных блюд сохраняется.
- Проверять равенство количества и сумм между закрытым отчётом, журналом и аналитическими фактами за смену. Различие показывать как ошибку синхронизации, а не исправлять молча. Смешанная оплата: один заказ, несколько способов оплаты.
- Сайт сообщает `lastSyncAt`, наличие долга в очереди и неполную обратную загрузку отдельно для аналитики, журнала и отчётов. При отсутствии данных показывает нули и пустое состояние.
- Если кассовый компьютер выключен до передачи очереди, Cloud и Telegram не получат новые данные до его следующего запуска и подключения. Сайт продолжает показывать последнюю полученную версию со временем обновления.

## Порядок работ

1. Подтвердить контракт Cloud аналитики и блюд: локальные миграции/код есть, но развёртывание удалённых миграций, функции и веб-чтения нужно проверить отдельно. Добавить проверку сверки и полноты загрузки.
2. Реализовать очередь и Cloud-приём закрытых отчётов; затем сайт истории смен и Cloud Telegram worker.
3. Добавить журнал оплаченных заказов и поздние возвраты, небольшими пакетами и с обратной загрузкой.
4. Добавить снимки вклада сотрудников и исторические столы/зоны внутри заказов и отчётов. Не создавать отдельный Cloud-справочник персонала/столов в MVP.

## Что пока не нужно

Не отправлять стоп-лист, живой статус столов, PIN/пароли, телефоны персонала, внутренний аудит всех действий, задания печати, склад, расходы и себестоимость. Для сайта владельца это не требуется в текущем MVP и увеличивает объём, риск утечки и стоимость синхронизации.

## Состояние реализации 2026-11-03

- Схема локальной базы 26 и фоновый worker: очередь закрытых отчётов, оплаченных снимков заказов, возвратов и снимков сотрудников. Временные сетевые ошибки оставляют запись в очереди; подтверждение Cloud фиксируется отдельно. Рабочий профиль `fresh-20261103` мигрирован после резервной копии.
- Cloud SQL `20261103000300`–`20261103000600` и подписанная функция `menu-sync` готовы в коде. Они ещё не применены на удалённом проекте; накопленные записи остаются в локальной очереди.
- Статический кабинет владельца содержит чтение блюд, отчётов смен, журнала и снимков сотрудников. Проверен на ширинах 1536 и 390 px с перехваченными Cloud ответами.
- Telegram пока создаёт только логическое задание `WAITING_CONFIGURATION`. Привязка получателя, секрет бота и доставляющий worker не реализованы. Сверка отчёта с журналом и аналитикой тоже остаётся.
- Для обратной загрузки установлен интервал минимум 500 мс после успешной отправки: отдельные записи отчётов/журнала уходят не чаще 2 в секунду, аналитические пакеты — не чаще 2 в секунду. Реальная скорость ниже при медленном Cloud. Нельзя обещать порог лагов по числу записей без измерения на кассовом оборудовании.
