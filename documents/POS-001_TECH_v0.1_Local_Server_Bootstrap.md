## 1. Цель и границы

### 1.1. Цель

Создать технический фундамент Windows-приложения Bashkar POS: независимо работающий Local POS Server, операционное хранилище SQLite, конфигурацию и диагностику, базовые защищённые HTTP/WebSocket-интерфейсы и управляемый жизненный цикл службы. После завершения первого этапа функциональные серверные модули можно развивать и тестировать **без интерфейса кассира**.

### 1.2. Входит в первую часть ТЗ

- платформенные и технологические ограничения;
- организационная структура репозитория, зависимостей и процессов;
- пакетирование серверного процесса и служба Windows;
- сценарии установки, первого запуска и повторного запуска;
- местоположение данных, конфигурации и секретов;
- безопасная инициализация/подключение SQLite;
- запуск HTTP/WebSocket-инфраструктуры и минимальные диагностические контракты;
- режимы готовности сервера, отказоустойчивое поведение;
- базовая информационная безопасность;
- журналирование, метрики состояния, проверка живости;
- стратегия тестирования и критерии приемки Bootstrap.

### 1.3. Не входит в первую часть ТЗ

- пользовательские экраны POS Desktop и Waiter Web, их UX/дизайн;
- полная физическая схема SQLite и точные SQL-индексы бизнес-сущностей;
- полные прикладные API заказов, смен, платежей, каталога и персонала;
- драйверные протоколы и печатные шаблоны;
- облачный протокол синхронизации и окончательная схема TLS/DNS в локальной сети;
- онлайн-эквайринг, склад, доставка, фискализация, KDS;
- реализация многокассового режима, выделенного резервного сервера или передачи столов в MVP.

**Важно:** перечисленные бизнес-модули обязательны для завершения *всего серверного этапа MVP*, но их детальная реализация оформляется в отдельных частях BACKEND-001 / смежных ТЗ. Готовность Bootstrap не равна готовности всего POS.

## 2. Архитектурные инварианты

**POS-TECH-ARCH-001 [Основание].** Bashkar POS Desktop и Local POS Server — независимые процессы на одном Windows-компьютере.

**POS-TECH-ARCH-002 [Основание].** Local POS Server является единственным авторитетным исполнителем локальных бизнес-команд и проверок прав; POS Desktop, Waiter Web и будущие клиенты не открывают SQLite напрямую.

**POS-TECH-ARCH-003 [Основание].** SQLite — локальный операционный источник истины филиала; наличие Supabase, интернета и Telegram не является условием обычных заказов, оплат, смен и печати после активации.

**POS-TECH-ARCH-004 [Основание].** В MVP один локальный сервер, одна авторитетная операционная БД и одно кассовое Desktop-рабочее место на филиал; до 10 одновременно подключённых официантов и до 50 столов — предварительная целевая нагрузка.

**POS-TECH-ARCH-005 [Основание].** Отсутствие ответа клиенту не равнозначно отсутствию сохранённой команды; для изменяющих команд требуется устойчивая идемпотентность по `command_id`.

**POS-TECH-ARCH-006 [Основание].** Закрытие интерфейса Desktop не останавливает сервер, не закрывает смену и не освобождает столы.

**POS-TECH-ARCH-007 [Основание].** Подтверждение локальной бизнес-операции даётся только после успешного локального commit, а не после облачной синхронизации либо физической печати.

**POS-TECH-ARCH-008 [Основание].** Серверная архитектура — Modular Monolith. Модульность — разделение ответственности внутри одного серверного приложения, а не отдельные микросервисы.

**POS-TECH-STACK-001.** Нельзя устанавливать Node.js или npm глобально на компьютер ресторана как обязательную часть штатного запуска. Установщик поставляет проверенные исполняемые компоненты.

**POS-TECH-STACK-002.** Все production-зависимости фиксируются в `pnpm-lock.yaml`; разрешения на автоматическое обновление major-версий в распространяемой сборке нет.

**POS-TECH-STACK-003.** Сборка должна быть воспроизводимой и сопровождаться ведомостью версий, включая Node runtime, WinSW, Electron и бинарные нативные зависимости.

**POS-TECH-STACK-004.** Нативный модуль SQLite собирается/подбирается под **встроенный Node.js серверного процесса**; не допускается неявно считать ABI Electron и отдельного Node.js одинаковым.

**POS-TECH-STACK-005.** Сборка проверяется на Windows 10/11 x64; Windows x86 не является целью MVP. Совместимость с указанными в ARCH-001 редакциями Windows подтверждается тестами.

### 3.2. Серверные зависимости

**Предлагаемый набор**, точные patch-версии уточняются при подготовке репозитория:

- runtime: `fastify`, `@fastify/websocket`, `@fastify/helmet`, `@fastify/rate-limit`, `@fastify/cookie`, `zod`, `fastify-type-provider-zod`, `better-sqlite3`, `drizzle-orm`, `argon2`, `pino`;
- development: `typescript`, `tsx` (только dev), `drizzle-kit`, `vitest`, `@types/node`, `@types/better-sqlite3`, линтер, форматтер;
- системные средства: WinSW, встроенный Node runtime, Windows Service Control Manager, Windows Event Log/файловый журнал при необходимости.

Пакеты подключаются только по реальной потребности этапа. Например, `argon2` нужен модулю Auth, а не для самого HTTP Bootstrap.

## 4. Размещение и ответственность процессов

```text
Windows 10 / Windows 11 (POS-компьютер филиала)
│
├── Bashkar POS Desktop (Electron, процесс пользователя)
│       │
│       └── HTTP(S) / WebSocket → Local POS Server
│
└── Bashkar POS Local Server (Windows Service, независимый процесс)
        ├── HTTP API и WebSocket Gateway
        ├── Auth / Permissions
        ├── Shifts / Tables / Menu / Orders / Payments
        ├── Print Queue Worker / адаптеры
        ├── Sync Worker / Outbox-Inbox
        ├── Backup / Recovery / Audit / System
        └── SQLite (локальный диск)

Waiter Web (смартфоны в LAN) → тот же Local POS Server
Supabase / Cloud Backend ←→ Sync Worker (асинхронно)
Kitchen Printer ← Print Queue Worker
```

**POS-TECH-PROC-001.** Запускаемый Windows Service процесс не зависит от процесса Electron и пользовательской сессии Windows.

**POS-TECH-PROC-002.** Для филиала допускается только один активный экземпляр серверного процесса, имеющий доступ к рабочей БД. Второй запуск должен корректно завершаться с диагностикой `INSTANCE_ALREADY_RUNNING`, а не пытаться обслуживать параллельные запросы.

**POS-TECH-PROC-003.** Print, Sync и Backup реализуются как управляемые фоновые подсистемы сервера (либо дочерние процессы под его наблюдением, если это будет доказано необходимым), не как зависимости существования окна кассира.

**POS-TECH-PROC-004.** Сервер не должен обращаться к Electron IPC, renderer-процессу или React-компонентам для принятия ресторанных решений.

## 6. Windows Service и управление жизненным циклом

### 6.1. Регистрация службы

**POS-TECH-SVC-001 [Основание].** Local POS Server устанавливается как отдельная Windows Service с автозапуском при старте Windows.

**POS-TECH-SVC-002 [Проектное предложение].** Предлагаемое имя службы: `BashkarPOSLocalServer`; отображаемое имя: `Bashkar POS Local Server`. Имена уточняются при утверждении установщика.

**POS-TECH-SVC-003.** Установка/удаление службы допускаются только из доверенного инсталлятора или уполномоченного административного обслуживания; обычному сотруднику не предоставляется право управлять службами Windows.

**POS-TECH-SVC-004.** Для процесса применяется минимально достаточная Windows-учётная запись; запуск с правами LocalSystem **не должен быть вариантом по умолчанию**. Доступ к директориям, LAN и принтерам проверяется на целевом оборудовании.

**POS-TECH-SVC-005.** При аварийном завершении процесса Windows/WinSW выполняет управляемый перезапуск с защитой от бесконечного быстрого цикла. Частота/максимум попыток — конфигурация инсталлятора и предмет тестирования.

**POS-TECH-SVC-006.** Команда остановки инициирует graceful shutdown: запрет новых изменяющих команд, завершение или атомарный откат незавершённых транзакций, прекращение новых попыток печати/синхронизации, освобождение SQLite-подключения и порта.

**POS-TECH-SVC-007.** Если graceful shutdown не успел завершиться, повторный старт обязан восстановить состояние из устойчивой БД; память и локальные in-memory очереди не считаются источником истины.

**POS-TECH-SVC-008.** Смена Windows-пользователя, выход из учётной записи и закрытие Electron не останавливают Local POS Server.

### 6.2. Сценарии запуска

**UC-POS-TECH-001: Обычный старт компьютера**
1. Windows запускается.
2. SCM запускает WinSW/Local POS Server.
3. Сервер считывает конфигурацию, открывает SQLite, выполняет проверки и применимые миграции.
4. Сервер определяет состояние активации филиала и активной смены.
5. Запускаются разрешённые серверные интерфейсы и фоновые компоненты.
6. При допустимом состоянии сервер сообщает готовность.
7. Запущенный позднее POS Desktop подключается к готовой службе.

**UC-POS-TECH-002: Кассир закрывает окно Desktop**
1. Закрывается процесс Electron.
2. Windows Service продолжает работу.
3. Сессии остальных клиентов, Print Jobs, состояние смены и Outbox сохраняются независимо от окна.
4. При повторном открытии Desktop загружается действительное состояние из API.

**UC-POS-TECH-003: Незавершённая транзакция во время отключения питания**
1. Windows/сервер неожиданно останавливается.
2. После перезапуска SQLite восстанавливает согласованное состояние по журналу.
3. Сервер читает сохранённые результаты команд и очередей, не повторяя бизнес-действия только из-за рестарта.
4. Если клиент не получил ответ, он выясняет итог по прежнему `command_id`.

## 7. Первый запуск, активация и повторный запуск

### 7.1. Состояния развертывания

**POS-TECH-FIRST-001 [Основание].** Новый, неактивированный филиал требует первичной интернет-активации через Supabase Auth владельца. Владелец выбирает организацию и филиал, после чего задаёт отдельный локальный пароль Owner.

**POS-TECH-FIRST-002 [Основание].** После активации локальные логин/пароль, смены, операции заказов и оплат не требуют постоянного интернета. Локальный и облачный пароль Owner — разные секреты.

**POS-TECH-FIRST-003 [Основание].** Не допускается заводской универсальный пароль вроде `admin/admin`.

**POS-TECH-FIRST-004 [Проектное предложение].** Сервер различает: `UNPROVISIONED` (новая установка), `NEEDS_ACTIVATION` (инфраструктура создана, филиал ещё не активирован) и `ACTIVATED` (установлена допустимая локальная привязка). Данные статусы **не являются** статусами кассовой смены.

### 7.2. Защита от потери существующей БД

**POS-TECH-FIRST-005 [Основание].** Отсутствующий файл SQLite на компьютере, который уже обслуживал филиал, считается инцидентом. Автоматически создавать новую пустую рабочую БД на его месте запрещено.

**POS-TECH-FIRST-006 [Проектное предложение].** Создание новой БД разрешается только в явно подтверждённом режиме первичной установки при отсутствии свидетельств прежнего активированного экземпляра. Используется отдельный защищённый маркер установки/привязки инстанса.

**POS-TECH-FIRST-007 [Основание].** При повреждённой БД, неверной схеме или неудачной миграции сервер переходит в ограниченное диагностическое состояние. Не происходит скрытого сброса истории или автоматического восстановления из непроверенной старой копии.

## 8. Локальные каталоги и конфигурация

### 8.1. Пути Windows (проектное предложение)

| Назначение | Предварительное размещение |
|---|---|
| Исполняемые файлы | `%ProgramFiles%\BashkarPOS\` |
| Постоянные данные | `%ProgramData%\BashkarPOS\` |
| Рабочая SQLite | `%ProgramData%\BashkarPOS\data\pos.db` |
| Журналы | `%ProgramData%\BashkarPOS\logs\` |
| Backups | `%ProgramData%\BashkarPOS\backups\` |
| Общая конфигурация | `%ProgramData%\BashkarPOS\config\` |
| Защищённые локальные секреты | защищённое Windows-хранилище / отдельный ACL-каталог, без открытого текста |

**POS-TECH-CONF-001.** Рабочая SQLite размещается на локальном диске; сетевой SMB-доступ нескольких компьютеров к одному активному SQLite-файлу запрещён.

**POS-TECH-CONF-002.** Исполняемые каталоги отделены от изменяемых данных, чтобы обновление/переустановка не удаляли финансовую историю.

**POS-TECH-CONF-003.** Данные защищены NTFS ACL, доступ имеют только служебная учётная запись и уполномоченные администраторы/средства обслуживания.

**POS-TECH-CONF-004.** Секреты и пароли не хранятся в исходном `.env` production-поставки, не попадают в логи и не встраиваются в Electron renderer. Применяются защищённые механизмы Windows и минимум облачных привилегий.

**POS-TECH-CONF-005.** Конфигурация содержит версии формата и валидируется до старта подсистем; неизвестные/критически некорректные значения не должны молча заменяться небезопасными умолчаниями.

**POS-TECH-CONF-006.** Изменение критичных сетевых параметров и путей БД не является обычной ресторанной операцией; требуется административный регламент и диагностика после применения.

### 8.2. Параметры конфигурации (предварительный набор)

`server.instance_id`, `branch.id`, `network.loopback_bind`, `network.lan_bind`, `network.https`, `db.path`, `db.migration_policy`, `logging.level`, `backup.policy`, `print.worker_enabled`, `sync.worker_enabled`, `installation.schema_version`.

Владельцем бизнес-состояний остаётся SQLite; конфиг не служит заменой таблиц сотрудников, заказов или смен.

## 9. SQLite: инициализация, миграции, целостность

**POS-TECH-DB-001 [Основание].** Использовать SQLite в режиме WAL, `PRAGMA synchronous=FULL`, атомарные транзакции и ограничения целостности.

**POS-TECH-DB-002 [Проектное предложение].** При каждом открытии соединения включать и проверять `PRAGMA foreign_keys=ON`; значение `busy_timeout` установить по итогам тестирования (начальная техническая гипотеза: 5000 мс).

**POS-TECH-DB-003.** При обычном запуске система проверяет доступность файла, принадлежность филиалу, версию схемы, критические признаки повреждения и возможность корректной записи до объявления готовности к мутациям.

**POS-TECH-DB-004.** Для существующей БД применять только явно совместимые, версионированные миграции. Стратегия создания резервной копии и транзакционность миграции описываются в DB-SCHEMA-001.

**POS-TECH-DB-005.** Если требуемая миграция невозможна, сервер не запускает изменяющие команды и сообщает код причины. Нельзя игнорировать несовместимость схемы.

**POS-TECH-DB-006.** Работающий филиал не имеет права открыть пустую БД вместо существующей, даже при отсутствии текущего SQLite-файла.

**POS-TECH-DB-007.** При успешном восстановлении сервер загружает сохранённые смены, заказы, платежи, Print Jobs, Outbox и идентификаторы ранее принятых команд; не создаёт их повторно.

**POS-TECH-DB-008.** Сохранение бизнес-операции, необходимых задач печати, аудита и Outbox должно выполняться как согласованный транзакционный результат; полный SQL-контракт определяется в DB-SCHEMA-001 / BACKEND-001.

**POS-TECH-DB-009.** Backups активной SQLite выполняются SQLite Online Backup API или эквивалентным безопасным механизмом, не обычным копированием открытого `.db`.

**POS-TECH-DB-010.** График резервирования из ARCH-001 остаётся предварительным: каждые 30 минут, после закрытия смены, ежедневно и перед обновлением; внешняя зашифрованная копия при доступной связи. Проверка возможности восстановления обязательна.

## 10. Состояния и диагностика Local POS Server

### 10.1. Предлагаемая диагностическая модель

**Не заменяет** состояния заказа, смены или сущностей CORE-001.

| Состояние | Значение | Допустимые операции |
|---|---|---|
| `STARTING` | Сервер загружается и проверяет окружение | Только ограниченная диагностика, если слушатель уже запущен |
| `NEEDS_ACTIVATION` | Новый экземпляр готов к предусмотренной процедуре активации | Активация/диагностика; обычные ресторанные мутации запрещены |
| `READY` | Локальная БД и критический набор подсистем пригодны к операциям | Операции по правам/CORE-001 |
| `READ_ONLY` | Изменяющие операции запрещены из-за установленного риска; допустимо безопасное чтение | Только явно безопасные чтения и диагностика |
| `BLOCKED` | Данные/схема/инстанс в критическом состоянии; обычная работа недопустима | Безопасная диагностика и контролируемое восстановление |
| `STOPPING` | Управляемое завершение работы | Новые мутации не принимаются |

**POS-TECH-STATE-001.** Потеря внешнего интернета или Supabase **не** переводит исправный локальный сервер в `BLOCKED` и не запрещает приём заказов.

**POS-TECH-STATE-002.** Неисправный кухонный принтер не отменяет принятые заказы и не блокирует их сохранение; статус принтера ведётся как отдельное состояние компонента.

**POS-TECH-STATE-003.** Запрет операций, связанных с закрытой/отсутствующей сменой, — бизнес-отказ, а не общая неработоспособность Local POS Server.

**POS-TECH-STATE-004.** Нестабильность/повреждение SQLite или невозможность надёжной записи приводит к запрету подтверждений изменяющих операций до устранения причины.

**POS-TECH-STATE-005.** Диагностика различает как минимум: Windows Service, SQLite, локальный API, LAN, печать, Backup, Sync, интернет, Supabase. Одного поля `online: true/false` недостаточно.

### 10.2. Минимальные служебные маршруты (проектное предложение)

Маршруты перечислены для Bootstrap, **не являются окончательным публичным контрактом BACKEND-001**.

| Маршрут | Доступ | Назначение |
|---|---|---|
| `GET /api/v1/system/health/live` | Ограниченный локальный health-check | Процесс отвечает и event loop доступен |
| `GET /api/v1/system/health/ready` | Ограниченный локальный health-check | Готовность к обычным операциям в данном экземпляре |
| `GET /api/v1/system/version` | Локально или по авторизованному запросу | Версия сервера, протокола и схемы без секретов |
| `GET /api/v1/system/status` | Авторизованный администратор либо системный локальный диагностический канал | Детальное состояние подсистем и коды причин |

**POS-TECH-API-001.** Все обычные изменяющие эндпоинты требуют проверенную сервером сессию, контекст филиала, права, условия CORE-001 и проверки идемпотентности.

**POS-TECH-API-002.** Факт доступности `live` не означает `ready`; HTTP-коды и машиночитаемый статус должны согласованно выражать запрет мутаций.

**POS-TECH-API-003.** Общий формат ошибки предусматривает стабильный `error.code`, `message`, `request_id`, необязательные безопасные `details`; стеки, ключи и SQL не передаются обычным клиентам.

**POS-TECH-API-004.** WebSocket получает разрешённые серверные события; после разрыва клиент получает актуальный снимок состояния из API, не полагаясь на пропущенные события как на единственную историю.

## 11. Сеть, локальная безопасность и HTTPS

**POS-TECH-NET-001 [Основание].** POS Desktop подключается к Local POS Server на том же компьютере; официанты — через служебную локальную сеть. Выход в интернет не нужен для LAN-операций.

**POS-TECH-NET-002 [Проектное предложение].** Локальный диагностический интерфейс привязывать к loopback. LAN-интерфейс открывать отдельно только на необходимом сетевом интерфейсе/порту с применёнными правилами брандмауэра.

**POS-TECH-NET-003 [Основание].** Предпочтительная цель для смартфонов: HTTPS + WSS, единый origin сайта/API/WebSocket и локальное DNS-разрешение. Конкретный DNS/TLS-механизм требует испытаний Android и iPhone **без интернета**.

**POS-TECH-NET-004.** До проверки TLS/локального DNS запрещено объявлять небезопасный HTTP на доступном гостям Wi-Fi полноценным production-решением.

**POS-TECH-NET-005.** Не использовать открытый CORS `*` с пользовательскими учётными данными; проверять origin WebSocket и защищать cookie-сессии от CSRF в зависимости от выбранного транспорта и схемы авторизации.

**POS-TECH-NET-006.** При изменении IP POS-компьютера, перезапуске роутера, нестандартном Private DNS/VPN должны быть тестируемые состояния диагностики; принудительная зависимость от внешнего DNS без проверенной offline-работы запрещена.

**POS-TECH-NET-007 [Основание].** Административные ключи Supabase не упаковываются в распространяемый POS Desktop; обмен с облаком использует ограниченные привилегиями device credentials.

## 12. Ошибки, восстановление и идемпотентность

**POS-TECH-REC-001 [Основание].** Перезапуск серверной службы не создаёт новую смену, не переоткрывает закрытую смену и не повторяет уже зарегистрированные оплаты.

**POS-TECH-REC-002 [Основание].** Если `command_id` уже зафиксирован с тем же содержимым, возвращается сохранённый результат или статус выяснения. Использование того же `command_id` с другим содержимым отклоняется.

**POS-TECH-REC-003 [Основание].** Физическая печать и синхронизация выполняются асинхронно после локального commit; ошибка принтера не откатывает продажу.

**POS-TECH-REC-004 [Основание].** Неизвестный результат печати (`UNKNOWN`) не запускает безусловную автоматическую повторную печать. Такие попытки требуют отдельного регламента PRINT-001.

**POS-TECH-REC-005 [Основание].** При повреждённой БД или нехватке места новые оплаты/заказы не получают подтверждение успеха. Диагностика позволяет отличить эту неисправность от отсутствия интернета.

**POS-TECH-REC-006 [Основание].** При подозрительном изменении системного времени фиксируется отдельная диагностика; порог и алгоритм определяются в BACKEND-001. Старые записи не переписываются бесследно.

**POS-TECH-REC-007 [Основание].** Обновление и установка миграций автоматически не выполняются во время открытой кассовой смены; rollback приложения разрешён только при совместимости актуальной базы и бинарной версии.

**POS-TECH-REC-008 [Основание].** Нельзя автоматически восстанавливать прошлую базу и объявлять незасинхронизированные события восстановленными без проверки.

## 13. Логирование, наблюдаемость, поддержка

**POS-TECH-LOG-001.** Технические логи сохраняются локально независимо от доступности облака и содержат timestamp, level, component, request_id/command_id (когда есть), error_code, версии ПО и безвредный контекст.

**POS-TECH-LOG-002.** Бизнес-аудит заказов, оплат, входов и административных действий **не заменяется** файловым техническим логом; Audit — отдельная устойчивая подсистема.

**POS-TECH-LOG-003.** Пароли, временные пароли, session tokens, cloud credentials, секреты TLS и платёжные секреты исключаются из логов, диагностических выгрузок и сообщений API.

**POS-TECH-LOG-004.** Поддерживаются ротация технических логов, безопасная очистка по утверждённой политике хранения и запрет удаления важных финансовых записей ради освобождения места.

**POS-TECH-LOG-005.** Фиксируются как минимум: запуск/завершение службы, этапы Bootstrap, миграции, ошибки SQLite, состояние очередей, отклонённые опасные операции, состояние Backup/Sync/принтеров и причины переходов `READY / READ_ONLY / BLOCKED`.

**POS-TECH-LOG-006.** Диагностика должна выдавать понятный стабильный код неполадки для поддержки, не раскрывая низкоуровневые секреты сотруднику.

## 14. Нефункциональные требования и производительность

**POS-TECH-NFR-001 [Основание].** Windows 10/11 x64; тестирование целевых редакций (в том числе Pro, Enterprise, IoT Enterprise LTSC по ARCH-001).

**POS-TECH-NFR-002 [Основание].** Минимальная целевая RAM — 4 ГБ, рекомендуемая — 8 ГБ. Electron остаётся предварительным выбором до испытания на 4 ГБ.

**POS-TECH-NFR-003 [Основание].** Сценарная целевая нагрузка: 1 касса, 10 официантов, 50 столов, один или несколько кухонных принтеров.

**POS-TECH-NFR-004 [Основание].** При исправном оборудовании и LAN: P95 обычного подтверждения заказа сервером ≤ 1 с; P95 доставки события подключённым клиентам ≤ 1 с. Физическая печать не входит в этот показатель.

**POS-TECH-NFR-005.** Sync, Backup и Print Workers не должны блокировать сохранение обычного заказа в допустимой нагрузке.

**POS-TECH-NFR-006.** Время запуска службы, CPU/RAM на 4 ГБ, устойчивость на низком свободном пространстве и режим частых рестартов измеряются в тестах. Конкретный SLA старта в предыдущих документах не утверждён — не вводится произвольная гарантия.

| AT-POS-BOOT-13 | Попытка доступа к секретам обычным пользователем | Нет доступа к секретам/паролям без необходимых полномочий |
| AT-POS-BOOT-14 | Изменение IP и перезапуск роутера | Диагностируется LAN-состояние, данные не повреждаются |
| AT-POS-BOOT-15 | Windows 10 x64 / 4 ГБ RAM | Нет критической потери работоспособности; измерены показатели |
| AT-POS-BOOT-16 | Автоматический старт после сбоя процесса | Управляемый restart; восстановление текущей БД и очередей |

| AT-POS-BOOT-18 | Попытка сделать запрос с чужим branch_id | Не предоставляется доступ к другим филиалам; атрибуты клиента не принимаются на веру |

**Критерий завершения части 1 (Bootstrap):** сервер устанавливается и самостоятельно функционирует как Windows Service, имеет безопасные начальные состояния и проверенную SQLite-инициализацию, предоставляет диагностику/минимальный API, независим от Electron и восстанавливает состояние после перезапуска. Отдельно фиксируются пройденные тесты Windows 10/11, 4 ГБ RAM и отсутствие необоснованного сброса данных.

**Критерий завершения полного серверного этапа (позже):** серверные API и тесты реализуют весь согласованный AUTH-001 и обязательные CORE-001, включая TABLE/COUNTER, меню, смены, оплаты, корректировки, печать, инциденты и синхронизацию. Первый критерий не следует выдавать за второй.

## 17. Вопросы, оставленные открытыми намеренно

1. **Service identity:** итоговая ограниченная Windows-учётная запись и права на конкретные модели принтеров.
2. **Дистрибутив:** финальный способ упаковки Node runtime, WinSW и Electron в один Installer, в том числе требования подписания и обновления службы.
3. **TLS/LAN:** промышленный локальный DNS, выдача/обновление сертификатов и тест работы без интернета на Android/iPhone; схема `r001.pos.bashkar.kg` в ARCH-001 была примером, а не подтверждённым работающим адресом.
4. **Схема данных и миграции:** окончательная транзакционная модель, таблицы и стратегии отката в DB-SCHEMA-001.
5. **Ресурсные пороги и время старта:** измерить на целевых Windows 10/11 POS, не утверждать без испытаний.
6. **Версионирование API:** согласовать точные DTO/endpoint названия и ошибки в BACKEND-001.

Эти вопросы не меняют фундаментальные решения Local-First, отдельной службы Windows, SQLite как операционного источника истины и общей бизнес-логики всех клиентов.
