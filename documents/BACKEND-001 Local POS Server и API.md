# 1. Назначение и границы

## 1.1. Назначение

BACKEND-001 определяет, **как** локальный сервер Bashkar.kg принимает, валидирует и исполняет ресторанные команды, обеспечивает безопасность и согласованность данных, взаимодействует с POS Desktop, Waiter Web, SQLite, печатью и синхронизацией, восстанавливается после отказов и возвращает однозначные результаты.

Local POS Server — единственный авторитетный исполнитель операционных команд конкретного филиала. POS Desktop и Waiter Web отображают состояние и направляют команды, но не определяют успешность сделки, права сотрудника, итоговую цену, действительность оплаты или факт завершения смены.

## 1.2. Включено в BACKEND-001

- процесс Local POS Server, сервисный запуск Windows, локальное HTTPS/API и WebSocket/WSS;
- модули и зависимости, границы ответственности, server-side use cases;
- идентификация сессий, локальная авторизация, RBAC, области `organization_id`/`branch_id`;
- HTTP-контракты: запросы, ответы, ограничения, коды ошибок и версионирование;
- команды Shift, Table Session, TABLE/COUNTER Order, Batch, Correction, Payment, Refund, Reversal, Menu, Employee и Recovery;
- атомарные транзакции, конкуренция, идемпотентность и история действий;
- связность с SQLite, Print Jobs, Realtime, Outbox/Inbox и Backup;
- диагностика, безопасный запуск, аварийные режимы и испытания.

## 1.3. Не включено

BACKEND-001 **не подменяет**: бизнес-правила CORE-001; матрицу доступа AUTH-001; окончательные физические SQL-таблицы, индексы и миграции DB-SCHEMA-001; UI-макеты POS-001 и WAITER-001; команды и форматы печати PRINT-001; протокол облачной доставки SYNC-001; облачный Backend и Owner Dashboard как самостоятельные приложения; юридическую спецификацию ККМ и фискализации.

Тем не менее серверные **границы интеграции** с этими компонентами входят в BACKEND-001.

# 2. Неизменяемые архитектурные и бизнес-инварианты

**BE-INV-001 [ИСТОЧНИК].** Для каждого филиала MVP один основной Local POS Server, одна авторитетная локальная SQLite и одно рабочее место кассира. Несколько официантов обслуживаются одновременно; поддержка нескольких касс Post-MVP.

**BE-INV-002 [ИСТОЧНИК].** Подтверждение заказа, платежа, коррекции и закрытия смены не требует Supabase/Telegram. Без работающего локального сервера **не бывает подтверждённой новой серверной продажи**.

**BE-INV-003 [ИСТОЧНИК].** Только `TABLE` и `COUNTER`; COUNTER — самостоятельный заказ на вынос **без** `table_session_id`, `table_id` и TABLE-сборов.

**BE-INV-004 [ИСТОЧНИК].** У TABLE: физический стол → посещение → один основной Order, создаваемый при первом успешном Batch → любое допустимое число последовательных Batch до расчёта. У COUNTER: отдельный Order, также появляющийся после первого принятого непустого пакета.

**BE-INV-005 [ИСТОЧНИК].** Принятый Batch и исторические Order Items/цены/модификаторы не изменяются бесследно. Исправления — отдельные события.

**BE-INV-006 [ИСТОЧНИК].** Полный положительный расчёт — один действительный Settlement на Order, с одним или несколькими Payment; `ZERO_SETTLED` — отдельный результат при действующих позициях и сумме 0 **без** Payment; обычных частичных платежей нет.

**BE-INV-007 [ИСТОЧНИК].** Для TABLE оплаченный либо нулевой расчёт атомарно закрывает посещение и освобождает стол. Полная разрешённая отмена до оплаты также закрывает TABLE. Для COUNTER завершение не затрагивает физический стол.

**BE-INV-008 [ИСТОЧНИК].** Одновременно не более одной открытой кассовой смены; закрытие не допускается при активных TABLE/COUNTER, известных неурегулированных денежных инцидентах или несверенных бумажных продажах, относящихся к смене. `CLOSED → OPEN` запрещён.

**BE-INV-009 [ИСТОЧНИК].** Сервер определяет исполнителя только по действительной локальной сессии. Клиентский `employee_id`, `role`, `permissions`, `branch_id` не расширяет полномочия.

**BE-INV-010 [ИСТОЧНИК].** `STRICT/SHARED` применяется к TABLE; `opened_by_employee_id`, `responsible_waiter_id`, фактический `submitted_by_employee_id` не смешиваются. Передача ответственности в MVP **не реализуется**.

**BE-INV-011 [ИСТОЧНИК].** Каждая принятая команда с данным `command_id` исполняется как одно логическое действие: повтор не создаёт дубль; тот же ID с другим содержимым отклоняется.

**BE-INV-012 [ИСТОЧНИК].** Бизнес-результат + необходимые Print Jobs + аудит + Outbox сохраняются согласованно; физическая печать, внешнее получение денег, облачная доставка и Telegram — асинхронные внешние эффекты.

**BE-INV-013 [ИСТОЧНИК].** При печати `UNKNOWN` и неопределённом результате платежной/локальной команды запрещено объявлять ложный успех/ошибку и запрещён неконтролируемый повтор.

**BE-INV-014 [ИСТОЧНИК].** После закрытия исходный отчёт смены не переписывается; поздние возвраты, восстановления и исправления показываются отдельными операциями текущего периода со ссылками на оригиналы.

# 3. Размещение и технологическая архитектура

## 3.1. Физическая топология

```text
                         СЛУЖЕБНАЯ LAN / Wi-Fi
  POS Desktop (Windows) -----------┐
                                    ├--> HTTPS + WSS --> Local POS Server
  Waiter Web (телефон/браузер) ----┘                      (Windows Service)
                                                         |
                                  +----------------------+----------------+
                                  |                      |                |
                                SQLite             Print Worker      Sync Worker
                                  |                      |                |
                            Backup / Audit        Kitchen/Customer    Cloud Backend
                                                                            |
                                                                        Supabase
```

Для MVP POS Desktop, Local POS Server, SQLite, Print Worker, Sync Worker и статические ресурсы Waiter Web развёрнуты на **одном** POS-компьютере. UI и Windows Service запускаются отдельными процессами. Закрытие UI не выключает службу.

## 3.2. Архитектурный стиль

- `[ИСТОЧНИК]` Modular Monolith: функционально отдельные модули в одном серверном процессе, не набор микросервисов.
- `[ИСТОЧНИК]` предварительный стек: Node.js + Fastify, TypeScript, Zod, SQLite, WebSocket; адаптер печати и Outbox/Inbox. Стек предварительный — совместимость и потребление памяти необходимо проверить.
- `[ПРОЕКТ]` слои `transport → application commands/queries → domain policies → repository/transaction → infrastructure adapters`; отдельные типы DTO и доменных объектов.
- `[ПРОЕКТ]` один управляемый канал записи SQLite на уровне серверного процесса и согласованная стратегия коротких транзакций, без доступа UI к DB-файлу.
- `[ПРОЕКТ]` все внешние side effects запускаются **после** commit, на основе durable jobs/outbox; исключения должны иметь собственную запись состояния.

## 3.3. Предлагаемые модули

| Модуль | Прикладные обязанности |
|---|---|
| `Auth` | login/logout, смена пароля, жизненный цикл сессий |
| `Employees` | карточка, статусы, архив, сброс временного пароля |
| `Permissions` | RBAC, делегирование Manager, проверки scope и STRICT/SHARED |
| `Shifts` | open/close, отчёт, проверка блокирующих операций |
| `Tables` / `TableSessions` | столы, открытие, пустое закрытие, текущая ответственность |
| `Orders` / `OrderBatches` | TABLE/COUNTER, неизменяемые пакеты и позиции |
| `Menu` | каталог, редакции, стоп-лист, snapshots, конфликт публикации |
| `Pricing` | централизованный расчёт размеров, модификаторов, скидки и TABLE-сборов |
| `Corrections` | отмены количества, групповые отмены, замену, комментарии |
| `Payments` | Settlement, Payment, ZERO_SETTLED, Refund, Reversal |
| `PrintingGateway` | создание job, предъявление job исполнителю, статусы, ручное урегулирование |
| `Realtime` | маршрутизация WSS, ревизии, ограничение доступа к событиям |
| `SyncGateway` | durable Outbox/Inbox, технические статусы интеграции |
| `Recovery` | инциденты, бумажная сверка, безопасная восстановительная регистрация |
| `Audit` | критические бизнес-/административные/безопасностные события |
| `Backup` | снимки SQLite, метаданные, проверка копий и доступ к восстановлению |
| `System` | safe start, health, readiness, диагностика, конфигурация сервиса |

Модули не должны напрямую перезаписывать таблицы друг друга вне единого согласованного application-use-case/transaction context. `Pricing` — единый вычислительный сервис для TABLE, COUNTER, коррекции и Settlement.

## 3.4. Запуск Windows Service

**BE-SYS-001 [ИСТОЧНИК].** Служба автоматически запускается после старта Windows без открытия POS Desktop; интерфейс может подключиться позднее.

**BE-SYS-002 [ПРОЕКТ].** Readiness последовательно проверяет конфигурацию филиала/активации, доступ к диску, целостность и совместимость схемы SQLite, запрет второго активного авторитетного экземпляра, состояние миграций и тестовую возможность безопасной записи (без подмены бизнес-операций).

**BE-SYS-003 [ИСТОЧНИК].** Если состояние БД повреждено/неподдерживаемо, сервер переходит в ограниченный режим диагностики, **не создаёт автоматически пустой ресторан**.

**BE-SYS-004 [ПРОЕКТ].** Технические режимы: `STARTING`, `READY`, `DEGRADED_READ_ONLY`, `MAINTENANCE`, `STOPPING`; это не статусы Shift или Order. Значения и диагностический протокол нужно утвердить.

**BE-SYS-005 [ИСТОЧНИК].** Завершение службы останавливает приём новых команд, не обрывает начатый commit неконтролируемо; существующие задачи восстанавливаются из SQLite.

**BE-SYS-006 [ИСТОЧНИК].** Автоматическая установка обновления во время активной смены запрещена.

# 4. Сетевой контур и общие требования к API

## 4.1. Входные каналы

- POS Desktop и Waiter Web обращаются **к одному Local POS Server**.
- Waiter Web раздаётся локальным сервером, локальные API и WSS доступны через служебную сеть.
- Предпочтителен **единый HTTPS origin** для веб-клиента, API и WebSocket, локальный DNS и сертификат для домена Bashkar.kg.
- Внешний интернет не нужен для уже работающей сети после первоначальной активации; внешнее API не должно быть публично доступным напрямую.
- QR подключения содержит **только адрес сайта**, без сотрудника, привилегий, токенов и пароля.

`[РЕШИТЬ]` Реализуемость TLS + DNS на типовых роутерах, Android/iPhone, VPN/Private DNS, при смене IP и без интернета проверяется реальным прототипом; окончательное hostname/сертификат/обновление выбираются по итогам (§20-D01).

## 4.2. Предлагаемый HTTP-контракт

**BE-API-001 [ПРОЕКТ].** Версия API в префиксе `/api/v1` либо равноценном заголовке; критическое изменение контрактов требует новой версии.

**BE-API-002 [ПРОЕКТ].** Для каждой mutating command объявить уникальный `command_id` (UUID) и `correlation_id` для трассировки; сервер хранит fingerprint содержимого.

**BE-API-003 [ИСТОЧНИК].** Все входные данные валидируются: типы, границы количества, строк, валюты, актуальные version/revision, существование связей и область филиала. Запрошенные цены и итоги — только ориентир для контроля ожиданий клиента, **не доверенное значение**.

**BE-API-004 [ПРОЕКТ].** Успешный ответ содержит server-side `resource_id`, `resource_version`, `server_time`, фактическое состояние, `command_id`, а при необходимости `change_cursor`.

**BE-API-005 [ПРОЕКТ].** Отказ возвращает `error.code`, безопасный `message`, `correlation_id`, необязательные `details`/`current_version`/`current_total`. Секреты, чужие записи и парольные поля не разглашаются.

**BE-API-006 [ИСТОЧНИК].** При сомнительном сетевом исходе клиент выясняет результат прежнего `command_id`, а не создаёт новый заказ/Payment с новым ID.

**BE-API-007 [ПРОЕКТ].** Оптимистические версии (`expected_revision`) используются для защиты от устаревшего экрана и конкурентного расчёта; одного сравнения версии недостаточно без транзакционной проверки бизнес-инвариантов.

## 4.3. Предлагаемые классы ошибок

| HTTP-класс (проект) | Машинный код (пример) | Применение |
|---|---|---|
| `400` | `INVALID_REQUEST` | невалидный формат/обязательное поле |
| `401` | `AUTH_REQUIRED`, `SESSION_EXPIRED` | отсутствие/недействительность сессии |
| `403` | `FORBIDDEN`, `ROLE_DISALLOWS` | недостаточно прав или системный запрет роли |
| `404` | `NOT_FOUND` | отсутствующий или не раскрываемый объект чужого scope |
| `409` | `SHIFT_ALREADY_OPEN`, `TABLE_OCCUPIED`, `ORDER_FINALIZED`, `STATE_CONFLICT` | конфликт состояний |
| `409` | `PRICE_CHANGED`, `MENU_REVISION_CONFLICT`, `IDEMPOTENCY_MISMATCH` | требование явного согласования или конфликт повторного ID |
| `422` | `BUSINESS_RULE_VIOLATION`, `SETTLEMENT_MISMATCH` | корректный формат, недопустимая бизнес-команда |
| `423/503` | `WRITE_UNAVAILABLE` | безопасно ограниченная работа/нет устойчивой записи |
| `429` | `RATE_LIMITED` | ограничение перебора логина/нагрузки |
| `500` | `INTERNAL_ERROR` | непредвиденная ошибка без раскрытия стека клиенту |

**Важно:** соответствие конкретных кодов и HTTP-статусов ещё не утверждено. Ошибки уровня транспорта, отсутствия связи и неизвестного исхода команды на клиенте должны различаться.

## 4.4. Чтение и команды

`[ПРОЕКТ]` Запросы чтения могут возвращать проекции и списки с пагинацией; операции изменения выполняются отдельными командами (command-style API). Не смешивать «редактирование черновика клиента» с принятием серверного Order. Серверный поиск финансовой/персональной истории фильтруется по scope и permissions.

# 5. Авторизация, сотрудники и RBAC

## 5.1. Два контекста идентичности

**[ИСТОЧНИК]** `Cloud Owner Identity` через Supabase Auth используется для первой активации и Owner Dashboard; у каждого филиала отдельная `Branch Local Identity`, включая локального Owner с независимым паролем. После начальной активации сотрудники и владелец работают локально без интернета. Облачные пароли не приравниваются к локальным.

## 5.2. Вход, первый пароль, сессии

- Локальный вход **только логин + пароль**, без PIN, биометрии или обязательной регистрации доверенного телефона.
- Сервер создаёт криптографически случайный временный пароль для нового сотрудника, показывает один раз; до установки личного пароля доступ ограничен сменой пароля.
- Постоянный пароль минимум 8 символов, без обязательного набора классов символов; распространённые пароли запрещены; проверка перебора обязательна.
- Локальные password hashes защищены и **не** синхронизируются в Supabase, не передаются в аудит.
- Сессии: POS Desktop **3 часа бездействия**; Waiter Web **6 часов**; абсолютный предел для обеих — **12 часов**. Фоновые heartbeats не должны бесконечно продлевать idle expiry.
- Смена пароля, сброс, приостановка или деактивация отзывают соответствующие сессии; обычное переключение сотрудника на кассе не закрывает Shift.
- Архивный `DEACTIVATED` сотрудник не удаляется и не получает новых операций, даже если ранее создавал заказы.

`[ПРОЕКТ]` Для Waiter Web предпочтительна защищённая HTTP-only cookie-сессия с применимыми SameSite/Secure/CSRF правилами; для Desktop — защищённое хранение сессионного секрета. Способ и защита от CSRF требуют отдельного security-review (§20-D02). Параметры Argon2id и rate limits тестируются на 4 ГБ RAM.

## 5.3. Проверки прав на **каждой** защищённой команде

`session_valid ∧ employee.ACTIVE ∧ correct_branch_scope ∧ role_allows ∧ permission_granted ∧ object_access_allows ∧ CORE_business_preconditions`.

- Роли: `OWNER`, `MANAGER`, `CASHIER`, `WAITER`.
- Модель: **ролевые шаблоны + индивидуальные grants**, с жёсткими верхними границами роли.
- `WAITER` не получает COUNTER, открытие/закрытие смены и право полной отмены по умолчанию; системные запреты роли не снимаются grants.
- Manager делегирует только права в Owner-approved перечне и не может сам себе расширить права.
- `STRICT`: чужое TABLE без деталей и без отправки пакета, если нет специального разрешения; `SHARED`: работа с доступными общими столами при нужном разрешении. Ответственный не изменяется при чужом Batch.
- Для COUNTER `STRICT/SHARED` не применяется.
- `employee_id` действия определяется сервером, а `branch_id` — активированной инсталляцией и защищённым контекстом.
- Владелец через Owner Dashboard может управлять меню по отдельным правилам, но **не** локальными сотрудниками в MVP.

## 5.4. Стабильные ключи разрешений

`[ПРОЕКТ]` Взять логические ключи из AUTH-001 §6.5 как первую редакцию `permission catalog`: `table.open`, `table.batch.submit`, `table.access_others`, `order.discount.set`, `order.correction.apply`, `order.cancel_full`, `counter.create`, `counter.settle`, `payment.refund`, `payment.reversal`, `shift.open`, `shift.close`, `employee.permissions.manage`, `menu.edit`, `menu.stoplist.manage`, `print.redirect`, `recovery.reconcile`, `audit.security.view` и т. д. Полный перечень и соответствие маршрутам — отдельное приложение/контракт перед кодированием.

## 5.5. Первичная активация

Локальный сервер нельзя штатно активировать в чужом филиале. `[ИСТОЧНИК]` первый старт привязывается к Cloud Owner и конкретному branch после проверки облачной идентичности. Повторная привязка после восстановления не должна создавать второй «авторитетный» сервер по той же базе. `[РЕШИТЬ]` конкретная криптографическая регистрация филиального узла, rotation и scope sync-credential (§20-D10) относятся к BACKEND/SYNC.

# 7. Предметные обработчики ресторанных операций

## 7.1. Столы и посещения (`TABLE`)

**BE-TABLE-001 [ИСТОЧНИК].** Чтение полного перечня столов с состоянием `FREE/OCCUPIED` разрешено по действующим правам. В `STRICT` чужие активные посещения не раскрывают состав/сумму заказа; в `SHARED` доступ определяется разрешениями.

**BE-TABLE-002 [ИСТОЧНИК].** Открытие: проверить auth, role, permission, branch, shift `OPEN`, стол свободен, idempotency; создать одну `Table Session` с `opened_by_employee_id` и отдельно `responsible_waiter_id`, меткой времени сервера, связью shift и аудитом.

**BE-TABLE-003 [ИСТОЧНИК].** Конкурентное открытие одного стола приводит к одной успешной Session; другой запрос получает состояние занятого стола. В рамках одной Session ответственное лицо в MVP не передаётся другому официанту.

**BE-TABLE-004 [ИСТОЧНИК].** Пустое посещение можно закрыть только без ранее принятых пакетов и при соответствующем праве, с причиной `EMPTY` и освобождением стола.

**BE-TABLE-005 [ИСТОЧНИК].** TABLE с принятыми позициями завершается после успешного полного/нулевого расчёта или отдельной разрешённой полной отмены; обычной произвольной команды «Закрыть занятой неоплаченный стол» нет.

## 7.2. Принятие первого и следующих Order Batch

**BE-ORD-001 [ИСТОЧНИК].** До первого успешно принятого непустого Batch `Order` не существует, даже если Table Session открыта. Неподтверждённый телефонный Draft хранится в IndexedDB браузера, не является серверной продажей.

**BE-ORD-002 [ИСТОЧНИК].** Команда Batch проверяет: действующую сессию и права; смену OPEN; активное посещение/COUNTER; доступ по STRICT/SHARED; подходящую редакцию меню, товар и stop-list; выбранный размер, модификаторы, комментарии и количество; актуальную цену и требуемое согласование; неизменность статуса заказа; отсутствие повторного command_id.

**BE-ORD-003 [ИСТОЧНИК].** Для каждого Order Item сохраняются исторические name/price/size/modifiers/comment, quantity, menu revision, принтерное назначение, отправитель и время. Разные комментарии/варианты у единиц блюда требуют отдельных логических позиций.

**BE-ORD-004 [ИСТОЧНИК].** При первом TABLE Batch фиксировать применимые TABLE-сборы/проценты и названия на весь Order; поздние настройки меню эти снимки не изменяют.

**BE-ORD-005 [ИСТОЧНИК].** В одном атомарном commit сохранить Batch и items, заказ (при первом Batch), audit, Outbox, необходимые Kitchen Print Jobs. Для непечатаемых товаров Kitchen Job **не создавать**. Сервис доставки в принтер запускается после фиксации.

**BE-ORD-006 [ИСТОЧНИК].** При изменившейся цене или недопустимом старом варианте **отклонить** текущую команду и вернуть данные для явного повторного подтверждения актуальных условий; сервер не подменяет цену молча.

**BE-ORD-007 [ИСТОЧНИК].** Отправитель нового Batch фиксируется фактически. При SHARED он может отличаться от открывшего стол и ответственного.

**BE-ORD-008 [ИСТОЧНИК].** Комментарий к позиции — свободный текст до **300 символов** по правилам CORE, может быть на RU/KY, не изменяет цену, проходит нормализацию/экранирование; не заменяет платный модификатор.

## 7.3. COUNTER (заказы на вынос)

**BE-CTR-001 [ИСТОЧНИК].** Первый непустой пакет создаёт Order `type=COUNTER` и первый Batch; номер для персонала последовательный в границах **филиал + текущая смена**. Пустой Draft не резервирует номер, отдельного Table Session нет.

**BE-CTR-002 [ИСТОЧНИК].** Возможны несколько `ACTIVE/UNPAID` COUNTER одновременно, дозаказы новыми Batch до оплаты, необязательное имя/пометка гостя.

**BE-CTR-003 [ИСТОЧНИК].** Fast checkout (`create + first batch + settlement + payment(s) либо zero settlement + print jobs + audit + outbox`) — **одна атомарная операция**: не допускается Pay без Order и подтверждённого Batch.

**BE-CTR-004 [ИСТОЧНИК].** После `COMPLETED/PAID` или `COMPLETED/ZERO_SETTLED` новые Batch и обычные корректировки запрещены; `CANCELLED` необратим в обычном workflow. COUNTER нельзя конвертировать в TABLE.

**BE-CTR-005 [ИСТОЧНИК].** Скрытие завершённой карточки переводит её видимость `VISIBLE → HIDDEN` (общую для филиала); событие аудируется и доступно после рестарта. Это не факт выдачи, возврата или отмены. Завершённая видимая карточка **не** блокирует Shift Close.

**BE-CTR-006 [ИСТОЧНИК].** Контейнер (упаковка) может быть *предложен* в интерфейсе для COUNTER; без явного подтверждения не добавляется. Принятый контейнер — обычная отдельная позиция с собственной ценой. Недоступность контейнера сама по себе не блокирует доступное блюдо. Никакого предложения для TABLE по этому правилу.

**BE-CTR-007 [ИСТОЧНИК].** Kitchen-чек COUNTER имеет крупное «НА ВЫНОС» и номер заказа; в TABLE на кухонном чеке крупный номер стола. Номер Batch на бумаге KITCHEN не печатается. Формат — PRINT-001.

## 7.4. Меню, редакции и стоп-лист

**BE-MENU-001 [ИСТОЧНИК].** Каталог изолирован по филиалам, один уровень категорий в MVP; основной язык + необязательные переводы. Внутренние интерфейсы RU/KY; меню гостя предусматривает RU/KY/EN с fallback на основной язык.

**BE-MENU-002 [ИСТОЧНИК].** Размеры имеют **собственные конечные базовые цены**, а не надбавку поверх единой цены. Дополнительные варианты — модификаторы, платные/бесплатные, с ограничениями min/max и доступностью.

**BE-MENU-003 [ИСТОЧНИК].** Локальная публикация ревизии — атомарное целостное применение; отдельный оперативный stop-list имеет собственную ревизию/историю. Новая цена вступает в силу после локального commit, в том числе при открытой Shift.

**BE-MENU-004 [ИСТОЧНИК].** Owner Dashboard вправе предлагать обновлённые редакции, однако облачная публикация **не равна** успешному локальному применению. При конкурирующих правках одной сущности нет last-write-wins; фиксируется конфликт, локальные продажи продолжаются на последней применённой редакции.

**BE-MENU-005 [ИСТОЧНИК].** Архивирование не удаляет исторические ссылки. `Availability=unavailable` не равнозначна архиву: блюдо видно с отметкой, но новое подтверждение запрещено.

`[РЕШИТЬ]` Структура diff/revision, критерий «одна сущность изменена обеими сторонами», алгоритм совместимых слияний и порядок подтверждения локального применения — вместе с SYNC-001 (§20-D07).

## 7.5. Корректировки и отмены

**BE-COR-001 [ИСТОЧНИК].** До серверного принятия редактирование Draft не создаёт Order Correction, не требует причины отмены и не изменяет историю.

**BE-COR-002 [ИСТОЧНИК].** После принятия только отдельные корректировки: `CANCEL_QUANTITY`, `REPLACE_ITEM`, `CHANGE_COMMENT`, `REPLACE_MODIFIERS` (через замену платного варианта), `GROUP_CANCEL`, `CANCEL_ORDER`.

**BE-COR-003 [ИСТОЧНИК].** Каждая отмена исходного действующего количества требует причины, ссылки на конкретный item, положительного допустимого количества. Отмена последних действующих порций заказа дополнительно требует права **полной отмены** — нельзя обойти через серию мелких отмен.

**BE-COR-004 [ИСТОЧНИК].** Увеличение количества принятых блюд — **новый Batch** по актуальной цене; исходные позиции не «инкрементируются» на месте. Замена блюда/платного модификатора — атомарная отмена старой и создание новой позиции с полной валидацией.

**BE-COR-005 [ИСТОЧНИК].** Комментарий принятой позиции изменяется отдельной корректировкой; может касаться части порций; исторический комментарий сохраняется. Изменение платной опции не маскируется произвольным комментарием.

**BE-COR-006 [ИСТОЧНИК].** Групповая отмена либо вся принята, либо полностью отвергнута. Полная отмена неоплаченного TABLE закрывает Table Session с `CANCELLED`, освобождает стол и создаёт необходимые связанные Kitchen-коррекции. Полная отмена COUNTER завершает заказ без Table Session.

**BE-COR-007 [ИСТОЧНИК].** Отмены уже оплаченного заказа обычными правилами недоступны; Refund/Reversal — отдельный финансовый поток.

**BE-COR-008 [ИСТОЧНИК].** Kitchen-коррекции создаются по назначению **исходного** печатаемого item, в логическом порядке за оригиналом. Отмена непечатавшегося товара не создаёт Kitchen Correction Job.

# 8. Единый серверный расчёт денег

## 8.1. Единицы и арифметика

**BE-PRICE-001 [ИСТОЧНИК].** Все денежные значения целочисленные в минимальных единицах (для KGS — тыйыны) либо в другой точно представимой модели, утверждаемой DB-SCHEMA-001. `float`/IEEE754 для конечных денежных результатов запрещён.

**BE-PRICE-002 [ИСТОЧНИК].** `unit_base_price` = цена выбранного размера либо цена товара без размера; модификаторы добавляются; итог позиции = (base + сумма применимых modifiers) × quantity.

**BE-PRICE-003 [ИСТОЧНИК].** Обычный сотрудник не вводит произвольную цену Order Item. Нулевая цена **допустима**, отсутствие цены не равняется нулю, отрицательная цена запрещена.

## 8.2. Подтверждённая формула CORE «Меню и ценообразование»

Для действующих позиций заказа из исторических снимков:

```text
S = сумма действующих подтверждённых позиций с учётом корректировок
D = одна фиксированная скидка на заказ, 0 <= D <= S
B = S - D

TABLE:   F_i = ROUND_HALF_UP(B * P_i / 100) для каждого активного на первом Batch сбора i
         T = B + SUM(F_i)
COUNTER: T = B
```

- Каждый TABLE-сбор независим и рассчитывается **от той же базы B**, а не поверх предыдущих сборов.
- Сборы **по умолчанию выключены**; набор их ставок и имён фиксируется при первом принятом TABLE Batch для всего этого заказа.
- Если позиционная сумма после отмен уменьшилась и старая скидка стала больше S, скидка автоматически уменьшается до S **с сохранением события/аудита**.
- Каждый сбор округляется отдельно `ROUND_HALF_UP` **до одного тыйына**, не до целого сома. Общий итог до целого сома не округляется.
- Для COUNTER никакие дополнительные процентные сборы не применяются.
- После полного расчёта исходные скидка, ставки и сумма сохраняются исторически, не переписываются вследствие настроек меню.

**BE-PRICE-004 [ПРОЕКТ].** Реализовать чистую функцию `calculateOrderTotal(pricedItems, corrections, discount, feeSnapshots)` с набором золотых тестовых векторов; запрет на вычисление критических сумм в UI.

## 8.3. Settlement

**BE-PAY-001 [ИСТОЧНИК].** Оплата — на всю актуальную серверную сумму после пакетов, корректировок, скидки и TABLE-сборов; стандартный UX не требует ввода суммы. Внутренний факт `CARD_MANUAL`/`QR_TRANSFER_MANUAL` не равен автоматическому подтверждению банка.

**BE-PAY-002 [ИСТОЧНИК].** Методы: `CASH`, `CARD_MANUAL`, `QR_TRANSFER_MANUAL`. Смешанная оплата двух методов — один Settlement с двумя Payment, суммы строго положительные и в точности дают актуальный Total. Для второго метода сумму определяет сервер.

**BE-PAY-003 [ИСТОЧНИК].** Три метода одновременно в UX не входят без отдельного утверждения; архитектурная модель не должна этому мешать в будущем.

**BE-PAY-004 [ИСТОЧНИК].** Полный положительный расчёт атомарно создаёт Settlement + Payment(s), фиксирует финансовый результат `PAID`, для TABLE — закрытие Session + освобождение стола, для COUNTER — `COMPLETED`; создаёт Customer Print Job, аудит и Outbox.

**BE-PAY-005 [ИСТОЧНИК].** Сумма 0 при действующих позициях оформляется `ZERO_SETTLED`: логический Settlement/result **без Payment**, но с Customer Job (итог 0), аудитом и соответствующим завершением TABLE/COUNTER.

**BE-PAY-006 [ИСТОЧНИК].** Для одной успешной команды расчёта существует ровно один действительный результат; если Payment и Batch меняются конкурентно, действует последовательный порядок, не допускающий оплаты устаревшего итога. Отдельный checkout с подменённым `client_total` не авторитетен.

**BE-PAY-007 [ИСТОЧНИК].** После успешной оплаты обычный новый Batch, изменение скидки, корректировка исходного состава запрещены.

## 8.4. Refund и Payment Reversal

**BE-PAY-008 [ИСТОЧНИК].** Refund относится к исходному **конкретному Payment**; поддерживается **полный возврат этого Payment**, не частичный. Причина обязательна, нужна открытая текущая смена, повторный Refund того же полного Payment запрещён. Для смешанной оплаты возврат составляющих — отдельно.

**BE-PAY-009 [ИСТОЧНИК].** Обычная роль Cashier имеет базовое право оформлять допустимый возврат; запись сохраняет фактического исполнителя. Сам внешний возврат денег выполняется вне Bashkar POS и не проверяется автоматически.

**BE-PAY-010 [ИСТОЧНИК].** Payment Reversal — **исправление ошибочной учётной регистрации**, а не возврат средств. Должны сохраняться исходные записи и новая корректирующая история; старый закрытый Shift Report не переписывается.

**BE-PAY-011 [СОГЛАСОВАНО / ДЕТАЛИ ОТКРЫТЫ].** Reversal требует отдельного права: по умолчанию оно есть у Owner и может быть выдано Manager; у Cashier по умолчанию отсутствует. Причина обязательна, исходный Payment не изменяется и не удаляется; сохраняется связанная корректирующая запись. Состав корректирующего Settlement, условия нового расчёта по закрытому заказу, смешанная оплата и отражение в истории требуют отдельного финансового согласования (§20-D05).

# 9. Кассовые смены, отчёт и Telegram

## 9.1. Открытие смены

**BE-SHIFT-001 [ИСТОЧНИК].** Активная смена одна на филиал. Открытие — локальная проверка логина и пароля заново (не только наличие ранее выданной сессии), permission `shift.open`, отсутствие OPEN; сохранение opened-by, device, времени и Outbox/Audit.

**BE-SHIFT-002 [ИСТОЧНИК].** Если две команды одновременно открывают Shift, только одна становится OPEN. Повтор той же команды не создаёт второй Shift.

**BE-SHIFT-003 [ИСТОЧНИК].** Shift может работать через полночь, не закрывается по времени, при закрытии POS Desktop или выходе кассира. Начальный/конечный физический остаток денег в MVP не вводится.

## 9.2. Закрытие смены

**BE-SHIFT-004 [ИСТОЧНИК].** Требует новой проверки логина/пароля и права `shift.close`.

**BE-SHIFT-005 [ИСТОЧНИК].** Проверяет **в той же согласованной операции**, что нет:

1. любых активных TABLE Session, в том числе пустых;
2. подтверждённых `COUNTER ACTIVE/UNPAID`;
3. незавершённых критических финансовых операций и известных инцидентов реально полученных, но неурегулированных денег;
4. известных несверенных бумажных продаж соответствующей смены.

Не блокируют закрытие сами по себе: старые Kitchen Jobs со сбоем, `COUNTER COMPLETED` со всё ещё видимой карточкой, завершённые нулевые расчёты, отменённые COUNTER, непринятые Draft, незавершённая доставка Telegram или Outbox.

**BE-SHIFT-006 [ИСТОЧНИК].** Запись CLOSED + closed_by/time + один исходный Shift Report + Outbox/Report Delivery фиксируются согласованно; повтор команды не пересоздаёт отчёт. При ошибке сохранения не объявлять закрытие успешным.

**BE-SHIFT-007 [ИСТОЧНИК].** Факт внешней доставки отчёта не является условием закрытия; Telegram и Owner Dashboard видят его позднее по durable delivery/sync. Ошибка уведомления не меняет `CLOSED`.

## 9.3. Отчёт

- Данные: branch, id смены, время открытия/закрытия, сотрудники; число TABLE/COUNTER заказов и посещений; суммы подтверждённых продаж; скидки/сборы; нулевые завершения; способы зарегистрированных Payment; возвраты, корректировки и их связь с периодом.
- Внутренние банковские методы — **ручная регистрация**, а не подтверждение эквайера.
- Исторический исходный отчёт **immutable**; поздний возврат и recovery привязан к текущей смене с ссылкой на исходную.
- Завершённые продажи учитываются отдельно от фактически зарегистрированных оплат; оплаты разбиваются по методам, а нулевой расчёт входит в количество завершённых заказов без денежного поступления. Отмены и возвраты показываются отдельно; предусмотрены общие показатели и разбивка TABLE/COUNTER. Точные формулы выручки и чистого итога, включая смешанную оплату, исправления и Recovery, требуют финансового согласования (§20-D08).
- `[ПРОЕКТ]` создавать детерминированный `report_snapshot_version` и машинно читаемые агрегаты; формулы отдельных KPI предварительно согласовать с CORE-001/Owner Dashboard (§20-D08).

# 10. Транзакции, идемпотентность и конкуренция

## 10.1. Правило commit-before-ack

**BE-TX-001 [ИСТОЧНИК].** Сервер подтверждает успех критической команды только после успешного локального commit. Событие WebSocket, job физической печати и начало облачной доставки не могут заменить сохранение SQLite.

**BE-TX-002 [ПРОЕКТ].** Единая структура обработки:

```text
1. Проверить форму запроса, сессию, scope и предварительные права
2. Найти command_id и проверить fingerprint предыдущего исполнения
3. Начать согласованную короткую транзакцию записи
4. Повторно проверить права, состояния, версии и финансовые инварианты
5. Выполнить domain change и расчёты
6. Сохранить command-result / audit / print-jobs / outbox / прочие обязательные записи
7. COMMIT
8. Вернуть фактический результат; после commit оповестить Realtime и workers
```

Точки проверки и способ хранения command-result требуют технического согласования; существующий результат из пункта 2 не должен стать ложноположительным при несоответствии fingerprint.

## 10.2. Отложенные внешние эффекты

**BE-TX-003 [ИСТОЧНИК].** Физическая печать, внешняя банковская операция (её подтверждает сотрудник) и внешняя доставка Telegram не входят в транзакцию SQLite. Их история живёт отдельными надёжными сущностями.

**BE-TX-004 [ИСТОЧНИК].** Transactional Outbox записывается в той же SQLite транзакции, что изменяемое доменное состояние. Поэтому потеря сети не может уничтожить событие о уже подтверждённой продаже.

## 10.3. Контроль конкуренции

**BE-TX-005 [ИСТОЧНИК].** Два одновременных открытия Table, две Shift Open, Settlement vs Batch, Settlement vs Correction, Shift Close vs новая продажа и два Refund одного Payment — сериализуются до одного допустимого результата.

**BE-TX-006 [ПРОЕКТ].** На одном авторитетном локальном узле использовать SQLite transaction-bound writes и уникальные ограничения в DB-SCHEMA-001; дополнительно `expected_revision` для человеко-понятного конфликта. Не допускать долгой транзакции при ожидании сети, принтера или работы сотрудника.

**BE-TX-007 [ПРОЕКТ].** Перед важным commit повторно прочитать релевантное актуальное состояние (Shift, order revision, employee grants, menu revision, суммы) внутри транзакции; не доверять захваченному ранее UI-snapshot.

**BE-TX-008 [РЕШИТЬ].** Схема сериализации записей: bounded write queue, transaction locking mode, busy timeout, retries `SQLITE_BUSY`, атомарность мультиобъектных операций и протокол transaction-result — согласовать с DB-SCHEMA-001 (§20-D04).

## 10.4. Обязательные тесты гонок

- два официанта одновременно открывают один Table — одна Session;
- официант отправляет Batch одновременно с расчётом — либо Batch раньше и вся сумма включена, либо Settlement раньше и Batch отклонён;
- Shift Close одновременно с Counter Fast Checkout — недопустимы успешно закрытая Shift и новый заказ в ней после закрытия;
- два Checkout с разными `command_id` — только один Settlement;
- тот же `command_id` с тем же содержимым — тот же результат, а с другим — конфликт;
- две отмены одной исходной порции — одна действительная, итог не отрицателен;
- отзыв permission конкурентно с командой — результат соответствует установленному линейному порядку;
- меню публикуется во время подтверждения Batch — сервер выбирает целиком одну применённую редакцию, никогда смесь цен;
- UNKNOWN Print Job конкурирует с redirect/manual handoff — не запускаются две независимые неконтролируемые физические попытки.

# 11. Realtime / WebSocket

**BE-RT-001 [ИСТОЧНИК].** При доступной служебной сети сервер доставляет обновления подключённым POS/Waiter-клиентам: состояния Shift, Tables, Table Sessions, Orders, меню, финансовых результатов, печати и актуальных прав.

**BE-RT-002 [ИСТОЧНИК].** WebSocket не является источником истины. Потерянное событие не должно скрыть подтверждённый заказ после следующей полной/частичной загрузки серверного состояния.

**BE-RT-003 [ПРОЕКТ].** Защита соединения: WSS через тот же origin, проверка сессии при подключении, повторная проверка прав при подписках и перед выдачей чувствительной информации; закрытие/re-auth при отзыве сессии или Employee `SUSPENDED`.

**BE-RT-004 [ПРОЕКТ].** События несут тип, stable ID, `revision`, `server_time` и минимальный безопасный payload; при `revision gap` клиент извлекает текущую проекцию HTTP. Пример:

```json
{
  "type": "table_session.updated",
  "entity_id": "<UUID>",
  "revision": 23,
  "server_time": "<RFC3339 timestamp>"
}
```

**BE-RT-005 [ИСТОЧНИК].** Отдельные `STRICT`-ограничения применяются не только к HTTP query, но и к потоку реального времени. Чужое посещение в STRICT может раскрывать лишь допустимое состояние стола, но не закрытую сотруднику сумму и позиции.

**BE-RT-006 [ПРОЕКТ].** Подключение после обрыва: клиент читает current snapshot, возобновляет подписку и при необходимости сверяет последние ревизии. Гарантия доставленного и прочитанного клиентом события должна быть отлична от гарантии SQLite commit.

# 12. Print Job, печать, UNKNOWN и ручное урегулирование

## 12.1. Разделение ответственности

- **Backend** решает, *нужно ли* создать `KITCHEN` или `CUSTOMER` Print Job, фиксирует его связь с Batch/Correction/Settlement и предоставляет защищённые команды управления и статусы.
- **PRINT-001 / Print Service** определяет формат бумаги, драйверы, ESC/POS, реальные повторы, acknowledgement, выбор принтера, spooler и аппаратную проверку.
- В MVP только **два типа документов**: `KITCHEN` и `CUSTOMER`. «Отмена/изменение» — смысл Kitchen-уведомления, не третий тип документа.

## 12.2. Создание job

**BE-PRINT-001 [ИСТОЧНИК].** При подтверждении Batch создавать Kitchen Job **лишь для включённых в печать товаров**. Не создавать Kitchen Job для пустого кухонного поднабора. Для корректировок использовать историческую настройку печати затронутых позиций.

**BE-PRINT-002 [ИСТОЧНИК].** После полного/нулевого расчёта создать `CUSTOMER` Job, включая нулевой расчёт. При полной отмене без Settlement фиктивный Customer Job не создавать.

**BE-PRINT-003 [ИСТОЧНИК].** Бизнес-операция и необходимые job-ссылки сохраняются вместе. Ошибка/отсутствие принтера **не откатывает** сохранённый Batch или оплату.

## 12.3. Попытки и исходы

**BE-PRINT-004 [ИСТОЧНИК].** Различать смысл `PENDING`, `IN_PROGRESS`, `SENT/ACKNOWLEDGED`, `FAILED_SAFE`, `UNKNOWN`, `MANUAL_HANDOFF`, `RESOLVED_NO_PRINT`. Названия enum и полный граф переходов утверждает PRINT-001.

**BE-PRINT-005 [ИСТОЧНИК].** Автоматический безопасный повтор допустим только при доказанном `FAILED_SAFE` (отказе до передачи). `UNKNOWN` **никогда автоматически не перепечатывать**. `SENT` не приравнивать без технического основания к физическому выходу бумаги.

**BE-PRINT-006 [ИСТОЧНИК].** При устной/ручной передаче уже сохранённого заказа на кухню фиксировать `Manual Kitchen Handoff` с исполнителем, временем, ссылкой и причиной; автоматические повторы соответствующего job остановить.

**BE-PRINT-007 [ИСТОЧНИК].** Поздний Kitchen Job после закрытия относящейся к нему смены не печатать автоматически; предоставить ответственному сотруднику проверку актуальности и контролируемую команду решения. Оригинал и коррекция должны иметь понятный причинно-хронологический порядок.

**BE-PRINT-008 [ИСТОЧНИК].** Перенаправление на заранее предусмотренный запасной принтер не стирает исходный Job, первичные попытки и историю решений.

**BE-PRINT-009 [РЕШИТЬ].** Достоверный критерий `FAILED_SAFE`, поддержка подтверждений драйверов, статусы при аварии spooler, допустимость повтора и взаимодействие с резервным принтером нуждаются в испытании PRINT-001 (§20-D06).

# 13. Синхронизация, Cloud Owner и Inbox/Outbox

## 13.1. Authority и границы

**BE-SYNC-001 [ИСТОЧНИК].** Local POS Server/SQLite — авторитетный источник заказов, оплат, смен, истории персонала данного филиала. Supabase хранит подтверждённую синхронизированную копию и обслуживает Owner Dashboard.

**BE-SYNC-002 [ИСТОЧНИК].** Синхронизация **асинхронна**. Ошибки интернета/Supabase/Telegram не останавливают локальный приём заказов и оплат. После восстановления сети передаются события из сохранённой очереди без дублирования.

**BE-SYNC-003 [ИСТОЧНИК].** Облачная сторона не может записать в локальную финансовую историю ранее устаревший результат. Облачные изменения меню/конфигурации идут через проверяемый Inbox, revision/conflict policy и подтверждение реального применения.

**BE-SYNC-004 [ИСТОЧНИК].** Пароли сотрудников, password hashes, локальные sessions и сервисные секреты не отправляются в облачную аналитику. Персонал в облаке — разрешённая безопасная копия; статистика рассчитывается в Supabase и доступна Owner.

## 13.2. Предлагаемые технические контракты

**BE-SYNC-005 [ПРОЕКТ].** Для Outbox-события: `event_id`, `branch_id`, `entity_type/id`, entity revision/sequence, `event_type`, safe payload или ссылка на snapshot, `created_at`, delivery status/attempts. Для входящего: внешний message ID, предназначенный филиал, версия/основание, подпись/верификация, результат применения/конфликта.

**BE-SYNC-006 [ПРОЕКТ].** Отправитель повтора допускает at-least-once delivery; получатель обеспечивает idempotent apply. Конкретный protocol handshake, deduplication retention, order sequencing и конфликтный merge задаёт SYNC-001.

**BE-SYNC-007 [ИСТОЧНИК].** В Owner Dashboard версия меню не отображается как «применено», пока соответствующий филиал не подтвердил фактический локальный commit. Статистика имеет показатель времени последней синхронизации.

## 13.3. Telegram

`[ИСТОЧНИК]` После закрытия смены регистрируется задание доставки краткого отчёта владельцу в Telegram, если интеграция настроена; отсутствие интернета/ошибка доставки не пересоздаёт Shift и не отменяет сохранённый отчёт. Повторы доставки должны быть контролируемыми и проверяемыми. Секрет Telegram не хранится в доступных клиентам ресурсах.

# 14. SQLite, миграции и DB-SCHEMA-001

## 14.1. Основное хранилище

**BE-DB-001 [ИСТОЧНИК].** На каждый филиал отдельная SQLite на локальном диске Windows POS; не допускается параллельное открытие активного файла несколькими компьютерами через общую файловую папку.

**BE-DB-002 [ИСТОЧНИК].** Для MVP предварительно установлены `journal_mode=WAL`, `synchronous=FULL`, ограничения целостности, атомарные транзакции, проверенные миграции и регулярная диагностика.

**BE-DB-003 [ИСТОЧНИК].** Данные включают как минимум: организации/филиал, сотрудников/права/сессии, Shift, Tables/Sessions, Menu/Revisions, Orders/Batches/Items, Payments/Settlements/Refunds, Print Jobs/Attempts, Sync Outbox/Inbox, Audit, Recovery и Backup metadata. **Точный SQL — DB-SCHEMA-001**, а не эта глава.

## 14.2. Необходимые инварианты хранения

`[ПРОЕКТ]` Схема БД должна уметь доказуемо обеспечить:

- не более одной Shift `OPEN` на филиал;
- не более одной ACTIVE Table Session на физический стол;
- не более одного действительного полного расчёта на Order;
- уникальность `command_id` внутри выбранного contract scope и сопоставление с результатом/fingerprint;
- уникальность `COUNTER` человекочитаемого номера в `branch+shift`;
- не более одного полного действительного Refund на исходный Payment;
- ненулевые суммы/количества там, где этого требуют бизнес-правила;
- исторические внешние ключи к архивированным сотрудникам и меню;
- транзакционное создание Print Job/Outbox/Shift Report и корректировок;
- revision/cursor, пригодные для конфликтов и восстановления клиентов.

Не следует считать этот список физическими `UNIQUE`-индексами до определения схемы конкретных жизненных циклов и технической реализации.

## 14.3. Миграции и обновления

**BE-DB-004 [ИСТОЧНИК].** До миграции требуется проверка пакета обновления и безопасная предварительная резервная копия; автоматическая установка посреди активной смены запрещена.

**BE-DB-005 [ИСТОЧНИК].** При неподдерживаемой/частично мигрированной схеме write операции блокируются до безопасной диагностики/восстановления. Автоматический откат бинарной версии не может незаметно откатить более новые данные.

**BE-DB-006 [ПРОЕКТ].** Миграции имеют monotonic `schema_version`, журнал применения, контроль допустимого upgrade/downgrade, preflight проверки свободного места и тестовый путь восстановления. Версионирование конкретизирует DB-SCHEMA-001.

# 15. Аварийные операции, инциденты и безопасное восстановление

## 15.1. Классы ошибок

**BE-REC-001 [ИСТОЧНИК].** Раздельно показывать: локальный сервер, SQLite/write readiness, сеть официанта, внешний интернет, Supabase, Telegram, Print Queue/Printer. Общее «нет связи» без идентификации проблемы недостаточно.

**BE-REC-002 [ИСТОЧНИК].** При недоступности локального сервера/БД телефон может редактировать IndexedDB Draft, но **не** подтверждает новый заказ/платёж. Если доступен POS Desktop, кассир может оформить отдельную серверную операцию с проверкой, что заказ уже не принят.

**BE-REC-003 [ИСТОЧНИК].** Если POS остановлен, а ресторан физически способен работать, допускается отдельный **бумажный аварийный порядок**; бумага сама по себе не создаёт подтверждённую SQLite-продажу.

## 15.2. Денежные инциденты

**BE-REC-004 [ИСТОЧНИК].** Если деньги реально получены, но сервер не подтвердил полный Settlement, не превращать это молча в `PAID` или `PARTIALLY_PAID`. Создаётся отдельная запись `Unsettled Receipt Incident`; требуется выяснить исход сохранённого `command_id` и выполнить разрешённую сверку.

**BE-REC-005 [ИСТОЧНИК].** При смешанном расчёте с фактически полученной одной составляющей до успешного полного commit нельзя создать фиктивный отдельный Payment без завершённого Settlement; хранится факт инцидента и дальнейшая сверка.

**BE-REC-006 [ИСТОЧНИК].** Известные неурегулированные денежные инциденты блокируют нормальное закрытие относящейся Shift.

## 15.3. Бумажная сверка и MANUAL_RECOVERY

**BE-REC-007 [ИСТОЧНИК].** Нумерованная бумажная запись содержит фактическое время, сотрудника, состав/количество, согласованные цены и скидки, способ/сумму фактически полученных денег, факт выдачи и сверки.

**BE-REC-008 [ИСТОЧНИК].** После восстановления сервер сначала проверяет старые Order, Batch, Settlement, Payment и command IDs; лишь отсутствующие факты можно отражать специальной уполномоченной `MANUAL_RECOVERY`, без автоматического повторного приготовления/печати.

**BE-REC-009 [ИСТОЧНИК].** Если исходная Shift уже `CLOSED`, её не переоткрывать и исходный отчёт не менять. Сверка/корректирующая регистрация отражается в разрешённом действующем периоде со ссылкой на старый документ.

**BE-REC-010 [ИСТОЧНИК].** Исходное время бумажного действия **не** подменяет время серверной регистрации. Если реальный факт поступления денег не доказан, статус подтверждённой оплаты не устанавливается.

**BE-REC-011 [СОГЛАСОВАНО / ПРОВЕРКА ОТКРЫТА].** Каждую финансовую MANUAL_RECOVERY оформляют и подтверждают два разных уполномоченных сотрудника. При отсутствии второго сотрудника запись остаётся на рассмотрении. Сохраняются бумажное основание, участники, фактическое время операции и время регистрации. Бухгалтерская и фискальная допустимость процедуры и формы документов требуют отдельной проверки (§20-D09, D16).

## 15.4. Запуск после сбоя

**BE-REC-012 [ИСТОЧНИК].** При перезапуске Windows сервер восстанавливает из SQLite существующую Shift, Orders, Settlement, Print Queue и Outbox, а не создаёт новые операции. Commit завершённого запроса не повторяется.

**BE-REC-013 [ИСТОЧНИК].** При повреждении DB запрещено автоматически «создать чистую БД», подменить её произвольной облачной записью или слепо воссоздать оплаченные продажи из догадок.

**BE-REC-014 [ИСТОЧНИК].** Восстановление SQLite проводится при исключительном обслуживающем доступе после проверки пригодной копии, с аудитом и сверкой операций после точки резервирования. Если пригодной копии нет — контролируемая процедура без ложного автоматического восстановления.

**BE-REC-015 [СОГЛАСОВАНО / ДЕТАЛИ ОТКРЫТЫ].** Предусмотрены локальные копии и дополнительная шифрованная копия вне основного POS-компьютера, ответственный за доступ к копиям и ключам, регулярная проверка восстановления на отдельной тестовой базе и предупреждение о просроченной или непроверенной копии. RPO/RTO, расписание, носитель и управление ключами определяются после испытаний; 30 минут между копиями **не означают** гарантированную потерю не более 30 минут (§20-D11).

## 15.5. Часы Windows

**BE-REC-016 [ИСТОЧНИК].** Выявленные существенные скачки системного времени требуют предупреждения и, если риск влияет на безопасность/корректность, ограничений; старые timestamps не переписываются.

**BE-REC-017 [РЕШИТЬ].** Технический порог отклонения, локальные свидетельства стабильного времени и условия возврата READY не определены (§20-D12).

# 16. Backup и жизненный цикл обновления

**BE-BACKUP-001 [ИСТОЧНИК].** Предварительный график из ARCH-001: автоматическая резервная копия каждые **30 минут**, после закрытия Shift, ежедневно, перед обновлением; по возможности зашифрованное внешнее сохранение.

**BE-BACKUP-002 [ИСТОЧНИК].** Предварительная ротация: **48 последних получасовых** и **30 ежедневных** копий; хотя бы одна актуальная копия вне основного диска. Окончательная политика определяется тестированием и объёмом.

**BE-BACKUP-003 [ИСТОЧНИК].** Копирование «голого» SQLite файла во время работы недопустимо; нужен безопасный консистентный механизм, например SQLite Online Backup API.

**BE-BACKUP-004 [ПРОЕКТ].** Для каждой копии фиксировать snapshot ID, branch/database/schema version, время, криптографическую проверку целостности, verification status, storage location (без разглашения секретов) и данные о пригодности для восстановления.

**BE-BACKUP-005 [ИСТОЧНИК].** Перед возвращением к работе после восстановления проверить согласованность сохранённой Shift, заказов/расчётов, Print Queue и Outbox. Автоматическая регенерация отсутствующих поздних финансовых данных из облака не допускается без сверки.

**BE-BACKUP-006 [РЕШИТЬ].** Носители, retention, ключи шифрования, custody прав поддержки, проверка восстановления и обновление ключей определяются отдельно (BACKUP-001/SEC-001), с учётом оборудования ресторанов (§20-D11, D18).

# 17. Безопасность, аудит, мониторинг

## 17.1. Граница безопасности

**BE-SEC-001 [ИСТОЧНИК].** Local API не публикуется напрямую в интернете. Применяются HTTPS/WSS, Windows Firewall, служебная сеть, права Windows Service и защита SQLite и локальных ключей.

**BE-SEC-002 [ИСТОЧНИК].** Клиент не может получить доступ к закрытым данным сотрудника/другого филиала/чужого STRICT посещения, подставив ID в URL или body. Authorize **object-level** даже для reads и websocket-subscribes.

**BE-SEC-003 [ИСТОЧНИК].** Service role Supabase, пароль Owner, локальные password hashes, сессионные токены и Telegram secrets не размещаются в публичной сборке клиента и не выводятся в логах, QR или диагностических сообщениях.

**BE-SEC-004 [ПРОЕКТ].** Для cookie model требуется CSRF защита, корректный SameSite/CORS/origin allowlist; WebSocket origin и session handshakes проверяются. Параметры хеширования и логин rate limit выбираются после тестов нагрузки, чтобы злоумышленник не мог массово заблокировать сотрудников или заполнить аудит.

## 17.2. Аудит

**BE-AUDIT-001 [ИСТОЧНИК].** Хранить отдельный защищённый Audit Log для критических действий: исполнители заказа, открытия/закрытия, Batch, discounts, corrections, settle/refund/reversal, прав и статусов сотрудников, menu publication, печати, восстановления, ошибок и мер безопасности.

**BE-AUDIT-002 [ИСТОЧНИК].** Типовая запись: event ID; org/branch; реально проверенный employee либо NULL для анонимной попытки; command/correlation ID; target; time; action; result; reason; безопасные before/after.

**BE-AUDIT-003 [ИСТОЧНИК].** Хранить неизменяемость/объяснимость истории, но не включать password, временные секреты, tokens, хеши, CVV/PIN и платёжные реквизиты, не требуемые бизнес-моделью.

**BE-AUDIT-004 [ПРОЕКТ].** Поиск аудита — фильтры по времени, исполнителю, типу, объекту, результату, пагинация, отдельное право `audit.security.view`. Логи технической диагностики отделяются от первичных бизнес-аудит-событий.

## 17.3. Readiness/Health

`[ПРОЕКТ]` Отображать структурированный статус: `service.ready`, `database.readable`, `database.writable`, `schema.compatible`, `shift.status`, `printer.queue_status`, `sync.outbox_backlog`, `internet.reachability`, `cloud.reachability`, `telegram.delivery_state`, `last_backup_verified_at`, `clock_risk`. Публичный health не раскрывает секреты/чужие записи.

## 20.1. P0 — критические продуктовые / эксплуатационные / правовые решения

### D01 — HTTPS в локальной сети без интернета

- **Вопрос:** как POS и телефон официанта разрешают локальное имя и доверяют HTTPS/WSS на типовых Android/iPhone и роутерах без внешнего интернета?
- **Вариант A:** локальный DNS → заранее установленный HTTPS-домен Bashkar.kg + безопасный выпуск/renewal сертификатов по DNS-01. **Вариант B:** альтернативный проверенный механизм безопасного локального origin.
- **Рекомендация:** A только при успешном аппаратном PoC; заранее определить документированную B fallback-схему, а не запускать недоверенный HTTP как «постоянное решение».
- **Ответственные:** технический архитектор + инфраструктура; владелец утверждает стоимость эксплуатации.
- **Источник:** ARCH-001 §7; AUTH-001 §9, §22.3. **Статус: направление A согласовано; PoC, fallback и окончательная схема OPEN / P0.**

### D03 — Идемпотентность и долговечность `command_id`

- **Вопрос:** на какой области уникален ID (`branch`, `client`, `command`), сколько хранится результат, чем проверяется fingerprint, как выясняется результат после рестарта/архивации?
- **Вариант A:** durable journal + восстановимый результат для всех финансово значимых команд на срок сохранения соответствующей истории. **Вариант B:** ограниченная по времени таблица ключей с дополнительным долговременным dedup-инвариантом на доменных сущностях.
- **Рекомендация:** долговечная проверяемая связь `command_id` ↔ исходный результат; не полагаться на краткоживущий in-memory cache или TTL, который позволяет повторить Payment после восстановления.
- **Ответственные:** backend + DB архитектор. **Источник:** ARCH-001 §14; CORE-001 REC BR-REC-004, AUTH-001. **OPEN / P0.**

### D04 — Конкурентные транзакции SQLite и порядок результатов

- **Вопрос:** как доказуемо сериализуются `Close Shift ↔ Checkout`, `Settlement ↔ Batch`, `Open Table ↔ Open Table`, `Refund ↔ Refund` без блокировки GUI и потери атомарности?
- **Вариант A:** единый контролируемый writer + краткие SQLite-транзакции с доменными ограничениями и optimistic revision. **Вариант B:** иная доказуемо эквивалентная схема конкурентной сериализации.
- **Рекомендация:** A для одного authoritative server MVP при обязательных race tests и тестах на 4 ГБ RAM; конкретная механика `BEGIN`/`busy_timeout` — DB-SCHEMA-001.
- **Ответственные:** backend + DB архитектор. **Источник:** ARCH-001 §5, §8; все CORE-001. **OPEN / P0.**

### D05 — Правила и права `Payment Reversal`

- **Вопрос:** кто исправляет ошибочно зарегистрированный метод/Settlement; как сформировать новый зачтённый расчёт без изменения старого; что разрешено после закрытия старой смены?
- **Вариант A:** отдельное высокорисковое разрешение, по умолчанию у Cashier отсутствует; менеджер/владелец выполняет по специальной процедуре. **Вариант B:** кассир с явно выданным `payment.reversal`, но с теми же дополнительными финансовыми проверками/аудитом.
- **Согласовано:** A: отдельное право по умолчанию у Owner, может быть выдано Manager; у Cashier по умолчанию отсутствует. Причина обязательна; исходный Payment сохраняется без изменения, создаётся связанная корректирующая запись.
- **Остаётся открытым:** финансовая процедура замещающего расчёта, в том числе после закрытия смены и при смешанной оплате. Произвольный update исходного Payment запрещён.
- **Ответственные:** финансы + backend. **Источник:** CORE-001 «Оплаты» §15, §24 (`OPEN-PAY-07`), AUTH-001 §6. **Статус: права и принципы согласованы; процедура OPEN / P0.**

### D09 — Ручная аварийная регистрация продаж и второй подтверждающий

- **Вопрос:** какая форма бумажной сверки допускается, как подтверждается фактически полученная сумма и когда нужен независимый проверяющий? Как провести событие, если его исходная Shift уже CLOSED?
- **Вариант A:** два разных уполномоченных сотрудника при всех финансовых MANUAL_RECOVERY. **Вариант B:** один при низком риске, два для определённых сумм/типов с документированными порогами.
- **Согласовано:** A: для каждой финансовой MANUAL_RECOVERY нужны два разных уполномоченных сотрудника; без второго запись остаётся на рассмотрении. Сохраняются инициатор, подтверждающий, бумажное основание, фактическое время и время регистрации.
- **Остаётся открытым:** бухгалтерская и фискальная допустимость, форма документов и технический формат связанной корректировки. Не создавать фиктивные Payment задним числом.
- **Ответственные:** бухгалтер/комплаенс + backend. **Источник:** CORE-001 «Нестандартные ситуации» §11, §25 (REC-OPEN-001/002/003); AUTH-001. **Статус: принцип двух сотрудников согласован; процедура OPEN / P0.**

### D11 — Проверяемые копии, RPO/RTO и ключи восстановления

- **Вопрос:** где физически находятся копии, как обеспечивается действительно независимый носитель, кто владеет ключами, как часто проверяется восстановление, какая приемлемая потеря/простой после разрушения POS-компьютера?
- **Вариант A:** локальные безопасные периодические snapshots + шифрованная offsite-копия, тестовое восстановление по расписанию. **Вариант B:** другой проверяемый storage/retention режим, пригодный для слабых POS и offline эксплуатации.
- **Согласовано:** локальные копии, дополнительная зашифрованная копия вне основного POS-компьютера, ответственный за доступ и ключи, регулярная проверка восстановления на отдельной тестовой базе и предупреждение о просроченной или непроверенной копии.
- **Остаётся открытым:** измеримые цели RPO/RTO, расписание и носитель, конкретные ответственные и хранение ключей; установить после испытаний. Интервал 30 минут не является гарантией RPO.
- **Ответственные:** владелец по RPO/RTO/затратам, эксплуатация + DB по механизму. **Источник:** ARCH-001 §17; CORE-001 Recovery §13–14, §25. **Статус: направление согласовано; параметры и проверка OPEN / P0.**

### D16 — ККМ / фискальный документ / правовые ограничения

- **Вопрос:** как Bashkar POS сосуществует с обязательной фискальной инфраструктурой Кыргызстана при реальной продаже, возврате, смене и аварийной бумажной регистрации?
- **Вариант A:** зафиксированная схема параллельного использования действующей ККМ и Bashkar POS до отдельной интеграции. **Вариант B:** отдельный утверждённый проект интеграции, если он обязателен для выбранного сценария внедрения.
- **Согласовано:** A как предварительное направление: отдельное параллельное использование действующей ККМ и Bashkar POS; интеграция рассматривается отдельным этапом. Внутренний Kitchen/Customer чек не объявлять фискальным.

- **Ответственные:** владелец + юридический/налоговый специалист + продукт. **Источник:** ARCH-001 §12.5, §24; CORE-001 Recovery §25. **Статус: направление A согласовано; правовая проверка OPEN / P0 перед реальной продажей.**

# 21. Известные коллизии версий и контроль согласованности

1. **ARCH-001 и передача между сменами.** В предварительной архитектуре упоминается будущая возможность переноса обязательств между сменами. CORE-001 «Кассовые смены» и «Нестандартные ситуации» устанавливают MVP: завершить открытые TABLE/COUNTER до штатного Shift Close; **перенос как обычный MVP workflow не реализовать**.
2. **ARCH-001 про регистрацию устройств.** В разделе безопасности предварительно упоминалась device registration. Позднее AUTH-001 Q09/Q19 **не требует доверенных устройств, PIN и подтверждения нового телефона**. Сохраняются QR-адрес, логин/пароль, HTTPS и права.
3. **Универсальный Kitchen Job.** Общие ранние фразы про печать «при отправке пакета» уточнены CORE «Меню», «COUNTER», «Recovery»: Kitchen Job требуется **только для печатаемых кухней позиций**, а не для каждого Batch.
4. **Старые открытые вопросы оплаты.** CORE «Оплаты» §24 ещё содержит ранние вопросы по фиксированной скидке и сбору COUNTER; позднее CORE «Меню» §13 закрепляет одну фиксированную скидку, независимые TABLE-сборы и запрет сборов COUNTER. Эти параметры не открывать заново без явной инициативы владельца.
5. **COUNTER как отдельный процесс.** Более поздний CORE «Заказы Counter» подробно зафиксировал quick checkout, номер `branch+shift`, hide/visible и финальный статус. BACKEND обязан опираться на эти уточнения, а не на старый упрощённый абзац.
6. **Refund ≠ Payment Reversal.** Refund отдельного Payment полным объёмом согласован, а процедура ошибочной регистрации/замещающего расчёта **остаётся частично открытой**. Не смешивать это в одном «отменить платёж».
7. **Исходный Shift Report.** Даже аварийная поздняя регистрация не должна задним числом открывать/пересчитывать закрытую смену. Нужны link-объекты и корректировки текущего периода.
8. **Owner Dashboard.** Владелец может управлять облачной редакцией меню, но локальное редактирование сотрудников выполняется через POS Desktop филиала; облачный owner имеет read-only статистику персонала.
9. **Передача TABLE.** `responsible_waiter_id` хранится для расширяемости, но **ни UI, ни API передачи ответственности в MVP нет**. При `SHARED` чужой Batch не меняет ответственного.
10. **Фискальность.** Печатный внутренний `CUSTOMER` не равен автоматически фискальному документу ККМ. До коммерческого внедрения требуется отдельная согласованная инструкция.
