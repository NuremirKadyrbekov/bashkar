# Официант: Roadmap подключения и рабочего экрана для HTTP MVP

Дата: 27.10.2026. Статус: **согласовано; реализация по этапам**. Область: один локальный филиал, POS Desktop, Waiter Web на телефоне, служебный Wi-Fi и включаемый HTTP listener. Переход на HTTPS — отдельный следующий этап.

## Отправная точка

- Сотрудники уже создаются в Desktop с ролью WAITER, логином и временным паролем; личный PIN выдаётся отдельной командой. Страница «Официанты» уже показывает общий URL и QR действующего HTTP listener. Это рабочие технические части, но сценарий подключения разорван между страницами.
- Waiter Web уже умеет PIN-вход, список столов с «Мои / Все», открытие разрешённого стола, меню и поиск, локальный зашифрованный черновик, отправку партии, историю, разрешённые корректировки/расчёт и восстановление неопределённого ответа. Нужны продуктовая компоновка, состояния и проверка на настоящих телефонах.
- Основные действующие контракты: [BLOCK-C-TECH-UI-SPEC-001](BLOCK-C-TECH-UI-SPEC-001.md) §5–6, [API-WAITER-009](API-WAITER-009.md), [WAITER-SCREEN-017](WAITER-SCREEN-017.md), [WAITER-HTTP-MVP-018](WAITER-HTTP-MVP-018.md). Правило HTTP reload из WAITER-HTTP-MVP-018 позднее старого memory-only правила BLOCK-C.

## Этапы

| Этап | Результат | Критерий завершения |
|---|---|---|
| 1. Сотрудники | При создании CASHIER или WAITER сервер сразу генерирует личный PIN в одной атомарной операции; форма по роли и список сотрудников показывают результат. | Создание не оставляет активного кассира/официанта без PIN; код показан один раз, повтор команды не создаёт дубль или новый PIN; запреты и аудит сохранены. |
| 2. Подключение официантов | Отдельная страница подключения: готовность сервера, один общий QR/ссылка филиала, список активных официантов и их статус PIN, инструкция «Wi-Fi → QR → личный PIN». | QR не содержит PIN; вход работает на телефоне; выключенный listener, смена IP и ошибка сети показываются понятным состоянием. Доступ к PIN соответствует действующим правам. |
| 3. Столы | Удобный мобильный старт: зоны, «Мои / Все», поиск/фильтр, свободен/занят/мой/чужой, явное открытие свободного стола и доступные действия занятого. | На 360×640 и 390×844 официант быстро находит стол; STRICT не раскрывает чужой заказ; состояние смены/сети понятно. |
| 4. Заказ | Посещение → меню → состав новой партии → проверка цен/сбора → явная отправка → результат. Удобные варианты, модификаторы, количество, комментарии, стоп-лист и дозаказ. | Черновик не путается с принятым заказом; обновление HTTP-вкладки сохраняет действующий вход и черновик; двойной заказ при потере ответа не возникает. |
| 5. Остальные разрешённые функции | История партий, перенос/ответственный по действующим правам, скидка, коррекция, закрытие пустого визита, TABLE-расчёт только при grant, сообщения о печати и UNKNOWN. | Каждое действие видно только по праву, сервер повторно проверяет права и состояние; кассовые/финансовые функции не появляются автоматически. |
| 6. Пилот и переход на HTTPS | Испытание Android/iPhone, Windows/роутера/отключения сети, инструкция смены адреса, затем доверенное HTTPS без переноса ошибок HTTP в новый режим. | Проверены реальные телефоны и Wi-Fi; до смены origin разобраны локальные drafts/pending; QR и URL обновлены согласованно. |

Этапы 1–2 дают работающий путь подключения. Этапы 3–4 — основной повседневный путь официанта. Этап 5 выполнять после удобного и проверенного основного пути; не включать все сложные финансовые сценарии в первую мобильную итерацию.

**Срез реализации 28.10.2026:** этап 1 и Desktop-часть этапа 2 внесены в код; на телефоне добавлены поиск/зона/сортировка столов, индикация закрытой смены/чужого стола и мобильные вкладки меню/партии. Базовые открытие, состав и отправка уже существовали. Автотесты и Electron browser QA пройдены, физический Android/iPhone и ресторанная сеть ещё не проверены. Остальные UX-состояния и функции этапов 3–5 остаются в работе; этап 6 не начат.

## Правила срезов

1. Для создания CASHIER/WAITER расширить серверную команду `employee.create`: подготовить уникальный четырёхзначный PIN и его hash/ciphertext вне writer, затем в одной транзакции CommandBus сохранить сотрудника и PIN. Существующая `employee.pin.issue` остаётся для ранее созданных сотрудников без PIN; `reset` — для замены кода. Для MANAGER PIN не создаётся, так как текущая PIN-политика его не допускает.
2. На CASHIER/WAITER-создание требовать одновременно `employee.create` и `employee.pin.issue`; если нельзя подготовить PIN/ключи или нет права, не создавать сотрудника. Сбой транзакции откатывает обе записи. При повторе с тем же commandId не выдавать секрет заново и не генерировать второй PIN; при утрате одноразового результата уполномоченный сотрудник выполняет отдельный reset существующего сотрудника.
3. Ссылка/QR общие для филиала; личность задаёт индивидуальный PIN. Не размещать PIN, токен или идентификатор сессии в URL/QR.
4. Сохранять авторитет Local POS Server: цены, права, открытие стола, отправка и расчёт подтверждаются сервером. UI не выводит чужие детали при STRICT.
5. Приёмку разделять на код/автотесты, browser QA и физическую проверку на Android/iPhone/сети ресторана. Тестовый QR со временной БД не является подключением рабочего филиала.
