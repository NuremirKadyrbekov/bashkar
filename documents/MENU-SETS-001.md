# MENU-SETS-001 — фиксированные сеты и развитие типов позиций

Дата: 24.10.2026. Статус: реализация согласована пользователем и выполнена 24.10.2026. Ниже сохранено исходное ТЗ; фактический контракт и проверки указаны в разделе 12.

## 1. Решение

Рекомендуется сет из реальных позиций каталога с заданными количествами и самостоятельной конечной ценой. Связь с блюдами не обязывает складывать их розничные цены.

Пример: бургер × 2, картофель × 1, напиток 400 мл × 2. Цена сета задаётся владельцем, например 750 сом, независимо от суммы отдельных покупок. Кассир не вводит её заново при каждой продаже. Себестоимость не равна сумме розничных цен и в этом этапе не рассчитывается.

Свободный текст быстрее, но не позволяет надёжно проверять доступность компонентов, связывать их с отчётами и будущими рецептурами. Существующее поле описания обычного товара можно использовать для временного информационного состава, явно без этих возможностей. Не создавать второй полноценный механизм текстовых сетов рядом со связанными сетами в первом этапе.

## 2. Что существует в текущем Bashkar

Проверено по catalog.ts, pricing.ts, order-service.ts, printing/render.ts и CORE-001:

- Обычные позиции, размеры и обязательные группы выбора с полной ценой сочетания MATRIX; старый аддитивный контракт также читается.
- Флаги кухни/контейнера, предложение контейнера, черновики и публикация редакций, отдельный стоп-лист.
- Серверное принятие заказа с историческим снимком состава/цен и кухонным payload.
- Количество продаваемой позиции сейчас целое. Денежные значения — целые минимальные единицы.
- Полноценного связанного состава сета, разворачивания его для кухни, складского списания и расчёта себестоимости в проверенной модели меню нет.

Следовательно, связанный сет требует согласованных изменений сервера, Desktop, Waiter, снимков заказов, печати, отмен/корректировок и отчётов. Одной вкладки в редакторе недостаточно.

## 3. Границы первого этапа

Включено: фиксированный состав из обычных активных позиций, целые количества, самостоятельная конечная цена, переводы названия сета, доступность по составу, печать и исторические снимки, продажа в TABLE/COUNTER.

Не включено: выбор гостем состава, замены компонентов, вложенные сеты, разные составы по размерам одного сета, частичный возврат компонента, весовые компоненты, автоматическая скидка, склад и рецептуры, распределение выручки по компонентам.

Для разных составов «Сет на двоих» / «Сет на четверых» в первом этапе создаются отдельные сеты. Это предотвращает перемножение выбора компонентов в общей матрице вариантов.

## 4. Экран редактирования

### 4.1. Основное

При создании выбирать «Обычная позиция» / «Сет». Для сета доступны:

- Основное название, категория, описание, переводы.
- Отдельное обязательное поле «Цена всего сета, сом».
- Вкладка «Состав сета» вместо «Варианты и размеры».
- Управление собственной доступностью и архивом через существующие операции и права.
- Настройка предложения контейнера для заказа на вынос по существующей модели.

После первой публикации тип позиции не меняется. Для превращения обычного блюда в сет создавать новую позицию, чтобы сохранить смысл истории.

### 4.2. Состав

Кнопка «Добавить блюдо» открывает поиск реального каталога. Для каждой строки:

1. Выбрать блюдо.
2. Если есть размеры/обязательные группы — выбрать точное готовое сочетание. Нельзя оставлять выбор на потом.
3. Указать количество на один сет.
4. Показать название выбранного сочетания и состояние доступности.
5. Предоставить удаление строки с подтверждением при потере данных.

Состав фиксируется владельцем в редакторе. Кассир выбирает только количество целых сетов и общий комментарий. Компоненты не редактируются отдельно в заказе первого этапа.

### 4.3. Ограничения состава

Предлагаемые начальные лимиты: 1–30 строк, количество каждой строки 1–99. Эти лимиты требуют согласования. Все умножения дополнительно проверяются сервером на допустимый предел количества и переполнение.

- Только активные обычные позиции этого же каталога/филиала; контейнеры и сеты не являются пищевыми компонентами.
- Ссылка включает стабильный ID блюда и выбранного сочетания; для старой схемы — конкретный размер и полный допустимый набор опций.
- Совпадающие блюда с одинаковым сочетанием объединяются количеством. Разные сочетания — отдельные строки.
- Основное имя компонента берётся из каталога, ручная подмена не допускается.
- Черновик может содержать неразрешённую ссылку после редактирования компонента, но публикация такого черновика запрещена с указанием проблемного сета/строки.

## 5. Цена и финансовая модель

`Стоимость строки заказа = цена одного сета × количество сетов`.

- Компоненты не добавляют свою розничную стоимость к цене сета.
- Цена меняется только через публикацию редакции. Изменение розничной цены компонента не меняет цену сета автоматически.
- Цена не может быть пустой или отрицательной. Явный ноль допускается по действующим правилам нулевого расчёта, без фиктивной оплаты.
- Разница с розничной суммой не создаёт скидку заказа. Существующая скидка заказа и сборы TABLE применяются к стоимости сета обычным серверным механизмом.
- Автоматическую надпись «выгоднее на X сом» в первом этапе не показывать. Для неё позже потребуется сравнение с точно теми же доступными сочетаниями и количествами в той же редакции.
- Выручка учитывается по сету. Количества компонентов могут показываться отдельно как состав сетов, но не как самостоятельные продажи с собственной выручкой. Нельзя удваивать итог.

## 6. Доступность и публикация

Сет продаётся, если доступен сам сет и все входящие блюда/точные сочетания с учётом их размеров и опций.

- Стоп-лист одного компонента делает зависимые сеты недоступными без публикации каталога. Показывается причина: «Нет в наличии: картофель».
- Включение сета не обходит стоп-лист компонентов. Собственный выключатель сета сохраняется отдельно; возвращение компонента не включает сет, выключенный вручную.
- Сервер перепроверяет зависимости при предварительном расчёте и окончательном принятии. Если условия изменились — понятная ошибка, без автоматического списания/замены.
- При архивировании блюда показать зависимые активные сеты. Опубликовать можно после замены компонента либо архивирования этих сетов в той же редакции.
- Это проверка стоп-листа, а не резервирование остатков. Складских гарантий наличия в первом этапе нет.
- До активации филиала действуют существующие ограничения. Клиенты работают через Local POS Server, без прямого SQLite и без зависимости от внешнего интернета.

## 7. Заказ, кухня и упаковка

### 7.1. Продажа

В гостевом заказе — одна платная строка сета с раскрываемым составом. Например:

Сет на двоих × 2 — 1500 сом
- Бургер × 4
- Картофель × 2
- Напиток 400 мл × 4

Состав не становится набором отдельных платных order_items. Сервер хранит одну денежную позицию и вложенный снимок компонентов. Структура снимка должна быть согласована с отменами и печатью до разработки.

### 7.2. Кухня

- Отправлять заголовок сета, количество сетов и фактические количества компонентов. Количество компонента = количество на сет × количество сетов.
- Печатаемые компоненты определяются их признаком кухни, а не одним вручную заданным флагом родительского сета. Сет без печатаемых компонентов кухонного задания не создаёт.
- Заголовок сохраняет связь компонентов с сетом. Повтор и отмена используют исходный снимок, а не актуальное меню.
- Текущую доставку/очередь печати переиспользовать. Новую многокухонную маршрутизацию в этот этап не включать.

### 7.3. Контейнеры

Только для COUNTER. Предложение контейнера настраивается на самом сете и использует существующую отдельную платную строку упаковки. Не запускать автоматически предложения каждого компонента — иначе появляются дубли.

Первый этап сохраняет текущую модель одного связанного вида контейнера на сет. Если требуется три разных коробки на один сет или количества коробок отличаются от количества сетов, нужна отдельная модель упаковки; это вопрос согласования, не скрытое допущение реализации. Ручное добавление упаковки остаётся возможным.

## 8. История, отмены и безопасность

- В принятый снимок включить тип позиции, цену сета и список компонентов: стабильные ссылки, названия/переводы, выбранные сочетания, количество на сет и кухонные признаки.
- Изменение названия, цены, состава и архивирование в новой редакции не меняет принятые позиции, повторные чеки и отмены.
- Отмена/возврат разрешены только целыми сетами. Из двух сетов можно отменить один с корректным уменьшением компонентов кухни по исходному составу.
- Отдельно отменить бургер из принятого сета в первом этапе нельзя. Для этого нужна согласованная модель распределения цены и частичного исполнения; нулевые цены дочерних строк этого не решают.
- Сервер подтверждает права menu.edit / menu.stoplist.manage и существующие права финансовых операций. Запросы проверяются независимо от видимости кнопок.
- Сохранить действующие CAS-конфликты, атомарность публикации, подтверждение цены/состава, идемпотентность финансовых команд и правила неизвестного результата.
- Новые поля имеют обратную совместимость: старая позиция без типа читается обычной. Старые снимки не переписываются. Потребность в миграции/версии API определяется при проектировании, перед выпуском обновляются совместимые Desktop/Waiter/Local Server.

## 9. Какие типы и свойства предусмотреть дальше

Не превращать каждый признак в новый взаимоисключающий тип. Разделять состав, единицу продажи, способ цены и операционные признаки.

| Сценарий | Пример | Что подготовить | Приоритет |
|---|---|---|---|
| Обычная штучная позиция | Суп, бутылка воды | Текущая модель | Уже есть |
| Вариант обычной позиции | Большой чай с молоком | Текущая MATRIX-модель полной цены | Уже есть |
| Фиксированный сет | Суши-сет, завтрак | Связанный состав + своя цена + снимок | Следующий этап |
| Комбо с выбором | Один бургер + один напиток на выбор | Слоты выбора, ограничения, серверная проверка выбранного состава | После сетов |
| Дополнительные ингредиенты/пожелания | Сыр, без лука, прожарка | Отличать доплату от бесплатной инструкции; не превращать все независимые добавки в декартову матрицу | Отдельный этап |
| Вес/объём | Салат за 100 г, напиток на розлив | Единица, точность количества, целочисленный масштаб, округление, тара/весы | Подготовить контракт, не включать сейчас |
| Половинки/сборная позиция | Пицца из двух половин | Отдельный состав и явная политика конечной цены | Позже |
| Открытая цена | Блюдо дня по согласованной цене | Отдельное право, пределы и аудит; не обычное поле кассира | Позже |
| Упаковка/покупной товар | Контейнер, салфетки, вода | Отдельные операционные признаки; приготовление не обязательно | Упаковка уже есть |
| Рецептура/полуфабрикат | Тесто, соус, ингредиенты | Внутренняя сущность склада/производства, единицы и списание; не обычный сет | Отдельный модуль |
| Подарочный сертификат/депозит | Предоплаченный номинал | Баланс, погашение, возвраты; отдельный финансовый процесс | Отдельное согласование |

Бизнес-ланч — фиксированный сет либо комбо с выбором. Сезонное/завтрак — расписание доступности. «Популярное» — метка/подборка. Кухня и контейнер — операционные свойства. Это не новые типы расчёта цены.

## 10. Проверки перед приёмкой

1. Сохранение/открытие черновика сета не меняет опубликованное меню.
2. Публикация состава и ручной конечной цены; отклонение неполных ссылок, вложенности, контейнеров и неверных количеств.
3. Цена сета 750 при иной розничной сумме; две единицы стоят 1500 до обычных скидок/сборов.
4. Для MATRIX-компонента выбран один точный вариант; его розничная цена не добавляется к сету.
5. Изменение розничной цены компонента сохраняет цену сета.
6. Стоп-лист компонента блокирует зависимые сеты без публикации; собственная блокировка сета не теряется.
7. Конкурентное изменение состава/доступности до принятия отклоняется и требует новой проверки.
8. Два сета печатают правильные количества компонентов с заголовком; непечатаемые компоненты не уходят на кухню.
9. TABLE/COUNTER, Desktop/Waiter, RU/KY/другие настроенные языки дают одинаковый состав и расчёт.
10. Изменение меню после принятия не меняет историю, перепечатку и отмену.
11. Отмена одного из двух сетов уменьшает кухонные количества ровно на состав одного; отдельный компонент отменить нельзя.
12. Скидки, сборы, нулевая цена, финансовые лимиты и отчёты не удваивают сумму компонентов.
13. Упаковка предлагается один раз на уровне сета, только COUNTER, с существующей обработкой количества/удаления.
14. Серверная проверка прав, потеря соединения, неизвестный результат и перезапуск проходят существующие сценарии без автоматического повтора опасной команды.
15. Обратная совместимость старого меню/снимков и отсутствие регрессий обычных позиций подтверждены тестами на одноразовых данных.

## 11. Согласованные границы первого этапа

1. Связанный фиксированный состав + вручную заданная конечная цена, без автоматического пересчёта по рознице.
2. Нет замен и вложенных сетов; отмена только целыми сетами.
3. Любой недоступный компонент блокирует продажу сета.
4. Достаточен ли один тип контейнера на сет по текущей модели; примеры реальной упаковки.
5. Лимиты 30 строк и 99 единиц компонента на один сет.

## 12. Фактическая реализация и проверка — 24.10.2026

### Контракт

- В `Item` добавлены `kind?: ITEM | SET` и `components?: SetComponent[]`. Отсутствие kind означает обычную позицию. SET использует собственный `price`, пустые variants/groups, без MATRIX. Смена типа опубликованного ID запрещена сервером, включая историю редакций.
- Компонент содержит `{itemId, variantId, modifierIds, quantity, combinationId?}`. Для MATRIX обязателен стабильный ID точного сочетания; для старой схемы используются точные размер/модификаторы. Дубликаты в редакторе объединяются, сервер отклоняет дублирующие строки. Ограничения: 1–30 строк, 1–99 единиц на сет; произведение на число сетов не превышает существующий MAX_QUANTITY=9999.
- Ссылки и структура проверяются сервером при сохранении черновика и публикации. Неисправленный состав можно держать в рабочей форме, но сервер не принимает его как сохранённый валидный черновик. Вложенные сеты, контейнеры как компоненты и недопустимые выбранные варианты отвергаются.
- Расчёт проверяет доступность каждого компонента, его опций, размера и комбинации. Отказ компонента возвращает SET_COMPONENT_UNAVAILABLE. Розничная цена компонента не участвует в цене сета.
- Сервер сохраняет одну денежную строку с `kind: SET` и `components`, содержащими снимки названий/переводов, выбранных вариантов, количества **на один сет** и кухни. Компоненты не становятся отдельными order_items и не увеличивают выручку. Печатное представление умножает количество компонента на количество сета в исходной строке/отменяемой порции.
- Использованы существующие меню API/IPC, редакции/черновики, стоп-лист, TABLE/COUNTER, подтверждения/идемпотентность и корректировки. Новые endpoint-адреса и SQL-миграции не требуются. Старые снимки читаются без переписывания. Для выпуска должны обновляться совместимые Local Server/Desktop/Waiter.

### Интерфейс

Создать товар → «Тип позиции: Сет» → указать цену в «Основное» → «Состав сета» → выбрать блюда и точные сочетания → сохранить изменения → сохранить черновик / опубликовать.

- Есть поиск блюда, добавление/редактирование/удаление строк, количество, объединение одинаковых сочетаний и защита несохранённой формы.
- После публикации тип показан без редактирования. Для архива/контейнера, используемого активными сетами, показываются зависимые сеты; сервер независимо проверяет каталог.
- Касса и Waiter показывают раскрываемый фиксированный состав. Опубликованная доступность сета учитывает компоненты, собственный стоп-лист остаётся отдельным.
- Для COUNTER используется один связанный вид контейнера с текущей логикой количества. Предложение срабатывает один раз на уровне сета. Несколько видов коробок и отдельная схема количеств упаковки остаются будущим расширением; самостоятельное добавление упаковки доступно.

## 13. Открытый вопрос после MVP — способ ведения состава сета

**Зафиксировано 02.11.2026 по решению владельца.** После MVP спросить ресторан, как персоналу удобнее вести состав сета: выбирать связанные блюда каталога, вводить состав вручную как текст или использовать оба представления. До ответа ресторана не менять текущий контракт связанного состава, его проверку доступности, снимки заказа и печать.

В разговоре уточнить, должен ли текстовый состав показываться только гостю на публичном сайте или также кассиру, официанту и кухне; кто и как обновляет текст при изменении рецепта; должна ли недоступность компонента автоматически блокировать продажу сета. По результату отдельно согласовать требования и оценить изменения сервера, редактора меню, публичного сайта, заказов и печати. Решение о текстовом составе пока **не принято**.
