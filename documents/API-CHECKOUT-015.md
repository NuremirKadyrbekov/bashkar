# API-CHECKOUT-015 — назначения посещения и атомарная оплата

Дополнение 26.10.2026: [POS-008](POS-ORDER-FIRST-CART-008.md) переносит выбор типа в табы нового черновика и раскрывает пакет на высоту корзины без анимации. Общий checkout не меняется. Native `cashReleaseEmpty` использует существующий close-empty с защищённым переносом draft и минимальным replay собственной квитанции; новых HTTP-полей и миграции нет.

Дата: 25.10.2026. Реализовано в исходниках Local POS Server `0.14.0-order-first`, схема **15**. Дополнение к API-TABLES-004, API-ORDERS-005, API-FINANCE-007 и API-CASH-WORKSPACE-014. Фактическая установка требует отдельного штатного обновления; рабочие профили этой поставкой не мигрировались.

## Назначения

- `POST /api/v1/tables/move`: `{commandId, sessionId, tableId, revision}`.
- `POST /api/v1/tables/responsible`: `{commandId, sessionId, responsibleWaiterId, revision}`.
- Ответ обоих: `{sessionId, revision}`. После подтверждения клиент перечитывает доступные ему данные; ответ смены ответственного не раскрывает новое посещение после потери доступа.
- Отдельные права `table.move` и `table.responsible.change`: по умолчанию OWNER/MANAGER/CASHIER. Дополнение 29.10.2026: права также включены в исходный шаблон WAITER; официант выполняет их только в `SHARED` и только над своим открытым посещением. Явный отзыв через матрицу ролей действует для всех официантов. Права не заменяют объектный доступ STRICT/SHARED. Список кандидатов для передачи в Waiter Web доступен в `SHARED` при `table.responsible.change`.
- Только OPEN посещение в своей текущей OPEN смене; CAS по ревизии, активная свободная цель того же филиала, активный официант роли WAITER. NULL ответственный допустим только при отсутствии действующих официантов. Перенос на занятый стол, объединение и снятие назначенного стола не добавлены.
- Прежний `tables/assign` остаётся совместимым: только первоначальное назначение NULL → стол с прежним правом `table.open`; теперь также записывает событие назначения.
- Миграция 015 добавляет неизменяемые `table_assignment_events`, усиливает соответствие события состояниям до/после и меняет только триггеры назначения. Автор/время открытия, смена и закрытые посещения остаются защищены. ID заказа/посещения, номер, пакеты, скидка и снимок сборов сохраняются. Старые print/settlement snapshots не переписываются. Новые снимки TABLE включают текущее назначение и неизменяемого автора.
- Повтор собственной завершённой команды возвращает минимальную исходную квитанцию даже после потери объектного доступа; актуальные роль/право проверяются снова. Другой commandId не даёт обхода доступа. Собственный неотправленный дозаказ не передаётся новому ответственному.

## Общий checkout

`POST /api/v1/cash/checkout/prepare` принимает строго:

```json
{
  "orderId": null,
  "type": "TABLE",
  "sessionId": null,
  "opening": { "tableId": null, "responsibleWaiterId": null },
  "draft": {
    "draftId": "UUID",
    "draftRevision": 1,
    "menuRevision": 1,
    "lines": [],
    "discount": 0
  },
  "payment": { "kind": "SINGLE", "method": "CASH" }
}
```

`lines` в настоящем новом заказе содержит хотя бы одну валидную позицию по API-ORDERS-005/014; пустой пример показывает только форму. Суммы — целые тыйыны. UUID/ревизии/состав не назначаются сервером из примера.

Контексты:

- Новый TABLE: `orderId/sessionId=NULL`, `opening` с необязательным столом и действующим назначением ответственного. Проверяется будущий объектный доступ кассира до создания посещения.
- Уже открытое пустое посещение: `orderId=NULL`, `sessionId` существующего OPEN посещения, `opening=NULL`. Если заказ уже появился, клиент получает конфликт, а не оплачивает неизвестные принятые позиции.
- Существующий TABLE: реальные `orderId/sessionId`, `opening=NULL`.
- COUNTER: `sessionId/opening=NULL`, `orderId` реальный либо NULL.
- `draft=NULL` означает расчёт только принятых позиций существующего заказа. Право приёма новых позиций здесь не требуется. Новый заказ без непустого draft запрещён.

Prepare возвращает авторитетные новые `lines`, `batchSubtotal`, общие `subtotal/discount/base/fees/total`, снимок сборов, `menuRevision/menuChanged`, разложение `payments`, `expectedOrderRevision`, `expectedVisitRevision`, `shiftId`, `confirmationHash`. Для нового TABLE в hash включается разрешённый план открытия с ревизиями конфигурации/режима; секретов сотрудника в нём нет. Для существующего заказа учитываются действующие порции после коррекций, а не первоначальная сумма пакетов. Обычный TABLE batch prepare также связывает hash с `visitRevision`.

`POST /api/v1/cash/checkout/commit` принимает тот же исходный запрос плюс `commandId`, `expectedOrderRevision`, `expectedVisitRevision`, `shiftId`, `confirmationHash`. `localScopeId` — только native Desktop поле; в HTTP body не передаётся. Произвольные поля полномочий/цены обычного блюда отвергаются.

Commit повторяет prepare и сверку внутри одного `CommandBus`/SQLite writer transaction. Используются общие тела приёма TABLE/COUNTER, текущий priceLine/totals и существующий finalize Settlement/Payments; вложенных команд, промежуточного HTTP submit или отдельного завершения нет. При необходимости в этой же транзакции создаётся посещение, выдаётся общий номер смены, принимается один пакет, создаются кухонные и клиентские задания, закрываются заказ/посещение. Ошибка любого обязательного write откатывает весь новый граф и номер. Старые пакеты и платежи не меняются.

Методы:

- SINGLE: CASH, QR_TRANSFER_MANUAL или существующий CARD_MANUAL. Кнопка перевода фиксирует ручное подтверждение уже полученного перевода, не банковскую операцию.
- MIXED: два различных разрешённых метода, положительная целая первая сумма и положительный автоматически рассчитанный остаток.
- ZERO: только при полном нулевом итоге; Settlement ZERO_SETTLED без фиктивного Payment.

Проверяются текущая смена, права расчёта, объектный доступ, при наличии draft — права приёма/произвольной цены/первой скидки, меню, ревизии и hash. Повтор своего commandId возвращает ту же квитанцию; изменения payload вызывают COMMAND_ID_CONFLICT. Отзыв действующих прав не обходится replay. Исторический fee snapshot TABLE сохраняется после переноса; COUNTER продолжает без TABLE-сборов.

Квитанция: прежние поля расчёта (`commandId/orderId/orderNumber/revision/result/settlementId/paymentIds/sessionId/printJobIds/counterNumber`) плюс `batchId` либо NULL и `kitchenJobIds`. TABLE освобождает стол; оплаченный COUNTER сохраняет прежнюю отдельную видимость рабочего списка до ручного скрытия. Выдача не блокирует оплату и не выводится из статуса печати.

## Native и интерфейс

FAST_FIRST использует checkoutPrepare/checkoutCommit, верхние назначения, нижнюю шторку и три способа расчёта. TABLE_FIRST и TABLE_QUICK сохраняют прежние сценарии. Неизменившийся пакет FAST_FIRST отправляется без обычного подтверждающего диалога; изменившиеся деньги/ревизии требуют нового нажатия.

До отправки checkout main process атомарно сохраняет pending commandId/исходный запрос; непустой draft замораживается с проверкой точного состава, ревизии, скидки и меню. После валидной квитанции очищается только его draft и соответствующий workspace. Неизвестный ответ/невалидная успешная квитанция оставляют команду для точного retry. Принятый заказ без draft также имеет pending/recovery; закрытое сервером состояние не мешает восстановить потерянную квитанцию. До recovery повторная новая оплата/смена контекста запрещены.

Дозаказы другого заказа/сотрудника не стираются. При потере доступа к выбранному посещению оно снимается с экрана, а личный защищённый draft остаётся на своём scope. Поддержка повторной печати/возврата и закрытия смены переиспользует прежние контракты.
