## 1. Как читать документы

1. Позднее явно согласованное решение пользователя уточняет раннее ТЗ в своей области. Сохранять другие ограничения, права и исторические данные.
2. Реализованное поведение подтверждают исходники, миграции и тесты; номер версии старой поставки не является текущей версией всей платформы. Код не превращает неутверждённое бизнес-изменение в согласованное правило.
3. CORE/AUTH описывают требования, API — конкретные контракты поставок, ROADMAP/POS/DB-SCHEMA — план или проект. Физическая SQLite определяется миграциями, а не концептуальной диаграммой.
4. PROGRESS — датированный журнал. «Ещё нет» в старой записи означает состояние на ту дату. Актуальные исключения собраны здесь; новый код не означает обновление работающей установки.
5. Документы и примеры не являются разрешением запускать миграцию рабочего филиала, менять его ключи или отправлять секреты. Решения о доступе берутся из запроса пользователя и действующих процедур.

Текущий source: **0.11.0-menu-sync**, **SQLite schema 12**, миграции **001–012**. Общий серверный idle POS и Waiter — **3 часа**, absolute — **12 часов**. Clean-preview — изолированный fixture, не обход активации рабочего филиала.

## 3. Заказ, оплата и выдача — действующее правило

| Событие | TABLE | COUNTER |
|---|---|---|
| Принят первый Batch | Заказ OPEN, посещение OPEN | Заказ OPEN, без Table Session |
| Отправлено на печать | Кухонное задание/эффективный dispatch; состояние приготовления неизвестно | То же |
| Полный расчёт | COMPLETED/PAID, посещение CLOSED/PAID, стол свободен в той же транзакции | COMPLETED/PAID, карточка VISIBLE в рабочем списке |
| Нулевой расчёт с действующими позициями | COMPLETED/ZERO_SETTLED, посещение CLOSED/ZERO_TOTAL; Payment не создаётся | COMPLETED/ZERO_SETTLED, карточка VISIBLE; Payment не создаётся |
| Полная отмена | CANCELLED; посещение закрыто | CANCELLED |
| Пустое посещение без принятого Batch/оплаты | Отдельное закрытие EMPTY | Неприменимо |
| Ручное скрытие карточки | Неприменимо | Только COMPLETED, отдельная CAS-операция; запись сохраняется в истории |
| «Готово / Подано / Выдано» | Таких команд и достоверных отметок пока нет | Таких команд и достоверных отметок пока нет |

Текущие оплаченные видимые COUNTER **не блокируют** закрытие смены. OPEN заказы, активные посещения и предусмотренные денежные/восстановительные инциденты блокируют. Ошибка печати сама по себе не отменяет оплату и не блокирует финансовое закрытие.

**Исправление пояснения в чате:** оплата не убирает COUNTER из рабочего списка автоматически. Ручное скрытие — организационная памятка, а не доказанная выдача. Код и CORE Counter в этом месте совпадают.

## 4. Что остаётся решить отдельно

Это список открытых решений, а не утверждённое изменение MVP.

1. **Подача TABLE:** нужна ли частичная отметка количества по строке/партии, кто ставит, кто исправляет ошибку, как учитывается отмена и дозаказ. Предложение: отдельные события actor/time/quantity, не редактировать историческую принятую строку.
2. **Выдача COUNTER:** весь заказ или частичные выдачи; кассир/официант и разрешения; независимость от оплаты. Предложение: отдельное состояние выполнения, оплаченные невыданные остаются в отдельной очереди.
3. **Занятость TABLE при предоплате:** сохранять действующее автоматическое освобождение либо отдельно фиксировать уход гостя. Второй вариант меняет закрытие посещения и blockers смены, требует ТЗ и миграций.
4. **Смена и невыданные оплаченные заказы:** разрешать перенос выполнения через смены или блокировать close. Это не следует автоматически из новых кнопок «Выдан».
5. **Кухонная готовность:** кухонный экран/кто отмечает «Готово» или MVP только «Подано/Выдано». Статусы spooler для этого непригодны.
6. **Cloud Owner:** refresh/relogin и политика онлайн-доступа администратора. Срок локальной сессии 3/12 часов сам по себе не продлевает access token Supabase.
7. **Эксплуатация:** согласовать backup/restore и перенос ключей, RPO/RTO, контролируемые обновления, ККМ/юридические требования. Не закрывать эти вопросы отметкой «183 теста прошли».

Для DOC-14/18 принято решение сохранить действующее согласованное поведение до отдельного утверждения модели выдачи. Уже оплаченные заказы и старые отчёты не переписываются.

## 5. Физическое хранение и транспорт

| Концепция ранних документов | Текущая реализация |
|---|---|
| Журнал команд / command_journal | `commands`, scoped branch + command ID, canonical fingerprint включает API/type/actor/payload; доступ повторно проверяется внутри writer, тот же результат в транзакции |
| Версия каталога / статус редакции | `menu_revisions` (immutable), `menu_current`, `menu_drafts`; метаданные sync отдельно в `menu_sync_versions/state`, редактор/draft lease в schema 12 |
| Автор входящей Cloud-редакции | `created_by=NULL` для системного применения, реальное происхождение/автор в metadata; фиктивного сотрудника нет |
| Структурированные строки модификаторов/сборов | Принятые `order_items.snapshot`, снимки заказа/Settlement и связанные immutable факты; старое меню не перечитывается для истории |
| Изменение принятой позиции | `order_corrections`, portions/события; исходная строка не редактируется бесследно |
| Печать | Immutable `print_jobs` + отдельная фактическая dispatch/attempt/event модель из migration 010 |
| Сессии | Локальные `auth_sessions`; native bearer защищён main; Waiter HttpOnly cookie + CSRF/memory unlock; Cloud Owner proof в памяти сервера |
| Меню Cloud | Supabase Edge `menu-sync` + таблицы migration 20261024000100; отдельная подпись ответа и proof устройства; renderer не пишет в Cloud/SQLite |
| Официант в сети | Явно настроенный HTTPS private IPv4/IP-SAN; DNS/WSS в целевой архитектуре не доказан фактом этой реализации |
| Настройки и обновления | Без автоматического upgrade старых DB при startup; явная миграция запрещена при OPEN-смене |

`DB-SCHEMA-001` остаётся полезной моделью связей и инвариантов, но не описанием каждой фактической таблицы. Сравнение физической схемы и миграционных checksum выполняет код `migrations/index.ts`.

## 7. Что изменено и как проверено

- Во всех 42 исходных документах добавлены дата сверки и границы актуальности; исторические версии и результаты тестов не выданы за текущие.
- Исправлены непосредственные противоречия PIN, новой активации Owner, сроков idle, закрытия смены, наличия HTTPS Waiter и области формул цены. Добавлены пояснения к CORE оплаты/Counter и ограничениям проекта БД/стека.
- PROGRESS оформлен как журнал с актуальным указателем; старые свидетельства не удаляются. Добавлен индекс всех документов с классификацией.
- Изменения только документационные. Код, миграции, Cloud, рабочие профили, БД, смены и исторические финансовые записи этим аудитом не менялись.
- Проверка после сверки: `pnpm test` — **32 файла / 183 теста PASS**; 117 локальных Markdown-ссылок проверены на существование файлов (результат также в PROGRESS). Ранее зафиксированная реальная Cloud QA подтверждает только указанный поток меню, не всю архитектуру.
