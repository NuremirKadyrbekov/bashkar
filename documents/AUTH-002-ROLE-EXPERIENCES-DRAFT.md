## 2. Целевая модель

| Контур | Вход | Необходимая связь | Основной исполнитель |
|---|---|---|---|
| Owner Dashboard — отдельный облачный сайт | Облачный email как логин + пароль через Supabase Auth | Интернет и доступность облачного сервиса обязательны | Cloud Backend с проверкой Owner и organization/branch scope |
| Cashier POS — Electron на кассовом компьютере | По умолчанию PIN из 4 цифр; альтернативная вкладка логин/пароль | Доступный локальный сервер; интернет не нужен после активации | Local POS Server и SQLite |

Один облачный Owner может владеть несколькими филиалами. Сотрудник и его PIN относятся к одному филиалу. В другом филиале нужна самостоятельная локальная запись. Аккаунт Owner не является активацией кассы: один филиал по-прежнему имеет один активный авторитетный сервер.

Owner Dashboard не является офлайн-копией админки кассира. Waiter Web не является публичным облачным сайтом, который обязан ходить в интернет для каждого заказа. Посетительский QR-сайт не входит в эту задачу.

## 3. Общие экраны входа

### 3.1. Запуск POS

1. Desktop подключается к настроенному локальному серверу.
2. Если нужна первичная активация — отдельный мастер активации Owner с обязательным интернетом. Его нельзя перепутать с ежедневным входом сотрудника.
3. Если сервер активирован — сразу открывается **«Вход кассира»** с цифровой клавиатурой и четырьмя скрытыми ячейками PIN.
4. Ссылка **«Войти по логину и паролю»** переключает форму. Ссылка **«Кабинет владельца»** открывает отдельный облачный сайт в браузере, не меняя привязку филиала.
5. После входа явно показать имя/роль/филиал; «Сменить сотрудника» завершает текущую сессию и возвращает PIN-экран. Смена, открытые столы и принятые заказы остаются открытыми.

В ежедневном сценарии не предлагать выбор облачного Owner/организации/филиала. Подключение другого сервера — административная операция, не пункт PIN-формы.

### 3.2. Форма PIN

PIN — строка **ровно из четырёх цифр 0–9**, включая начальные нули. Не преобразовывать его в число. Клавиатура, ввод с физической клавиатуры, очистить и удалить последнюю цифру. Автоматически проверять при вводе четвёртой цифры; блокировать повтор до завершения одной попытки. После неуспеха очистить поле, показать общую ошибку и время доступной следующей попытки.

Не требуется выбирать сотрудника перед PIN: сервер определяет его по уникальному PIN данного филиала. PIN официанта не открывает Cashier POS, а PIN кассира не открывает Waiter Web. Отказ не раскрывает, принадлежит ли введённый код другой роли или заблокированному сотруднику.

PIN не хранится в localStorage, URL, логах, аналитике, HTML-атрибутах или списке сотрудников. Не отображать введённый PIN открытым текстом после успешного входа.

## 4. Owner Dashboard

### 4.1. Вход и потеря интернета

Owner использует только облачный email/пароль. Нет PIN, локального Owner-пароля и режима входа по ранее закешированным реквизитам. Облачная сессия не принимается локальным API как сессия кассира.

При открытии Dashboard и каждом защищённом API-запросе backend проверяет текущую облачную личность и принадлежность организации/филиала. Сохранённый refresh token не даёт офлайн-доступа: при новом открытии страницы нужна успешная онлайн-проверка. При установленной потере связи блокировать действия и скрывать рабочие данные за экраном «Для кабинета владельца нужен интернет»; не использовать Service Worker для офлайн-аналитики. Восстановление требует успешной проверки облачной сессии. Флаг browser.online сам по себе не является доказательством доступности сервера.

Физически полученные раньше данные нельзя «отозвать» из памяти внешнего браузера или скриншотов; речь о поведении приложения и авторизации API.

### 4.2. Разделы

- **Обзор:** выручка/расчёты/средний чек и другие показатели только после согласования D08 и появления настоящих финансовых фактов; выбор периода/филиалов.
- **Организации и филиалы:** список своих заведений, филиалов, состояние сервера, последнее соединение/последняя синхронизация, статус активации. Организация «MANGO», филиалы «MANGO — Каракол», «MANGO — Бишкек».
- **Сотрудники:** состав персонала, роль/статус, принадлежность филиалу и разрешённая статистика. Пароли/хеши не показывать. PIN созданных локально сотрудников своих филиалов разрешено повторно посмотреть отдельной кнопкой по правилам §9.3. Создание/блокировка/изменение прав удалённо — только с контрактом §9 и явным применением филиалом.
- **Меню:** категории, блюда, размеры, модификаторы, цены, переводы, архив, kitchen flag, стоп-лист в допустимом контуре.
- **Настройки меню:** разрешённые настройки каталога и TABLE-сборов, сохранение целой редакции, сравнение конфликтов. Настройки не переписывают исторические цены и сборы уже принятых заказов.

У каждого набора данных показать **«Данные филиала на …»**, состояние доставки и отставание. Интернет у Owner не означает, что филиал сейчас доступен или что сведения свежие. Отсутствие синхронизации не отображать как нулевую выручку.

Облачное создание организации/филиала не активирует POS автоматически и не переносит прежнюю регистрацию. Установка/замена сервера остаётся отдельной процедурой D10.

## 5. Кабинет кассира

После входа открыть операционную рабочую область. Рекомендованные основные вкладки:

1. **Столы:** зоны, карточки свободен/занят, свои/доступные посещения; действующие STRICT/SHARED и права. Первый выпуск использует карточки, геометрический редактор карты зала не является обязательной частью этого ТЗ.
2. **POS / Продажа:** открытые TABLE-заказы, черновик, первый пакет/дозаказ, скидка по праву; затем после финансового этапа — оплата, COUNTER и разрешённые корректировки. До реализации этих операций не показывать фиктивную успешную оплату.
3. **История за 24 часа:** подтверждённые продажи филиала в серверном скользящем окне; контракт §8.
4. **Меню:** просмотр актуального локального меню, размеров/модификаторов/цен/доступности. Редактирование каталога/настроек кассиру не выдаётся; стоп-лист — только если отдельно разрешён.
5. **Смена:** состояние и разрешённые операции. Начало/закрытие по отдельным правам и предметным проверкам, без автоматического закрытия при выходе.
6. **Связь / кухня:** понятное состояние локального сервера и доступные статусы заданий. PENDING не означает напечатано.

Отдельная небольшая панель **«PIN сотрудников»**: кассир видит свой код и коды официантов только своего филиала по кнопке «Показать PIN». PIN других кассиров, Manager и Owner недоступны, включая запрос по известному employee ID. Панель не даёт права создавать сотрудников, менять роль/права или сбрасывать PIN.

Не показывать административные вкладки Owner, межфилиальную аналитику и чужие организации. Скрытие вкладки дополняется проверкой роли/прав/филиала на каждом серверном запросе. Смена метода входа PIN↔пароль не расширяет права.

Существующий Manager сохраняется отдельной ролью: рекомендованный первый вариант — локальный вход логин/пароль в POS с операционными и только явно выданными административными разделами, без облачной аналитики Owner. PIN для Manager не выдаётся автоматически; возможное добавление потребует той же филиальной уникальности и отдельного правила допуска в POS. Новые client-audience проверки должны явно поддержать этот сценарий, а не случайно заблокировать Manager вместе с Owner.

## 6. Waiter Web

1. Сотрудник подключает телефон к служебной Wi-Fi-сети ресторана.
2. Открывает локальный защищённый адрес или сканирует QR в POS. QR содержит только адрес филиального интерфейса, не PIN/пароль/token и не является разрешением работать.
3. Видит название филиала и **«Вход официанта»**, вводит личный PIN.
4. После входа доступны «Все столы / Мои», состояние столов, открытие разрешённого посещения, черновик, выбор размеров/модификаторов/комментария, отправка пакетов и история доступного заказа.
5. STRICT/SHARED проверяет сервер; работа другого официанта в SHARED не изменяет ответственного, автор каждого пакета реальный.
6. Локальные черновики сохраняются в IndexedDB с scope server instance/branch/employee/device/session. Чужой сотрудник на том же телефоне не получает доступ к ним. Неизвестная отправка повторяется прежней командой, без автоматического дублирования после возвращения Wi-Fi.

Официант не получает POS кассира, COUNTER, историю всех продаж филиала, администрирование меню/сотрудников, кассовую смену и облачную аналитику. Остальные уже согласованные разрешения TABLE, включая скидку и отдельно выдаваемые финансовые права, не меняются молча: перед реализацией зафиксировать обновлённую матрицу ролей. UI не должен выдавать недействующее право финансового этапа за готовую операцию.

При отсутствии интернета, но работающем Wi-Fi/сервере, вход и ресторанные операции работают. При потере связи с локальным сервером отправка блокируется, локальный черновик сохраняется. После очистки браузерного хранилища восстановление несинхронизированного черновика не гарантируется.

## 7. PIN: выдача, уникальность и защита

### 7.1. Правила

- Уникальность **среди всех неархивных сотрудников одного филиала**, включая Cashier/Waiter/Manager. Это позволяет вводить только PIN без выбора имени и исключает разную роль у одинакового кода.
- Между разными филиалами одинаковые PIN допустимы. Для истории идентификатор сотрудника остаётся UUID, а не PIN.
- Заблокированный сотрудник сохраняет резерв своего PIN до явной смены/архивирования. После архива запись/история сохраняются, PIN-вход отключён; освобождённый код может быть выдан другому сотруднику с новым ID и без доступа к старым черновикам/сессиям.
- PIN генерирует локальный сервер случайно, с проверкой уникальности в одной транзакции; не использовать номер телефона, позицию в списке или общий код по умолчанию. Начальные нули допустимы. Пространство — максимум 10 000 комбинаций; при исчерпании отказ, не дублирование.
- PIN можно повторно посмотреть в разрешённом кабинете по §9.3. Просмотр не генерирует новый код, не является сбросом и не отзывает сессии. Копировать открытый PIN в обычный command journal/result нельзя; потеря ответа на просмотр допускает новый авторизованный запрос актуального кода.
- Cashier сохраняет отдельный локальный логин/пароль как альтернативу. Waiter может работать только по PIN; отдельный вход по паролю для него не требуется новым UX.
- До явной выдачи PIN вход по нему недоступен; при переходе нет массового назначения `0000`. Существующие пароли не превращаются в PIN.

### 7.2. Техническая защита

Четыре цифры дают лишь 10 000 вариантов: это быстрый вход для контролируемого рабочего контура, а не эквивалент стойкого пароля. Использовать только на native loopback кассы и защищённой локальной сети официантов; публичный доступ к PIN API из интернета запрещён.

Нужны стойкий salted hash для проверки и защищённый keyed lookup для поиска сотрудника/уникальности без перебора всех хешей на каждой попытке. Для разрешённого повторного просмотра дополнительно хранить PIN в локальной SQLite только как аутентифицированный шифротекст. Один хеш не позволяет восстановить код для показа. Lookup key и отдельный ключ шифрования хранятся вне SQLite в системном защищённом хранилище филиального сервера, не в Desktop/Waiter/облаке; не использовать открытый SHA-256 четырёх цифр и не переиспользовать приватный ключ подписи активации как PIN-secret. Шифротекст привязать к branch/employee/PIN version, чтобы перестановка записей не раскрыла чужой код. Hash/lookup/ciphertext/version обновляются атомарно при выдаче/сбросе. До кода закрепить параметры хеширования/шифрования, provisioning, ротацию и поведение при утрате ключей в техническом приложении. Утрата ключа не разрешает пустой PIN или автоматическое отключение проверок; парольный вход кассира остаётся отдельным методом, если сервер в целом исправен.

Ограничение попыток обязательно: per-source/pre-auth challenge, per-code/employee при возможности, bounded verification queue и аудит без PIN. Новый cookie или новая страница не должны сбрасывать лимит. Одновременно один атакуемый сотрудник не должен надолго блокировать весь персонал. В распределённой атаке с доступом к служебной сети ограниченность четырёх цифр остаётся реальным риском; stronger password для кассира сохраняется.

Для первого технического приложения рекомендованы: 5 неудач с одного источника за минуту → пауза 60 секунд, повторные превышения с нарастающей паузой до 15 минут; дополнительно per-code/employee и ограничение параллельных проверок. Точные независимые лимиты, proxy/IP attribution и устойчивость к DoS утверждаются и испытываются до включения PIN, без бесконечной глобальной блокировки.

Для операций повышенного риска быстрый вход не отменяет отдельное право/основание/подтверждение. Существующее повторное подтверждение открытия смены логином/паролем сохраняется, пока не согласовано его изменение. Парольный fallback не должен обходить блокировку сотрудника или отзыв прав.

PIN reset, блокировка/архив, изменение роли и изменение пароля отзывают соответствующие старые сессии по явно согласованной политике. Рекомендация: сброс PIN отзывает все локальные сессии данного сотрудника, без закрытия смены/столов и без изменения исторического авторства.

## 8. История кассира «последние 24 часа»

Рекомендация: кассир с правом `sales.history.view_recent` видит продажи **своего филиала**, а не других филиалов, за непрерывные последние 24 часа по серверному времени. Все продажи филиала, включая смену другого кассира, — предложенный default для передачи смены; если нужен только собственный автор, это отдельная настройка/решение.

Граница времени: `serverNow − 24h ≤ financialFactTime ≤ serverNow`; единая UTC-арифметика, отображение Asia/Bishkek. Это не календарный день и не только текущая смена. Ограничение действует и в list, details, search/export/reprint API, а не только в фильтре интерфейса. Старый известный ID не обходит окно.

Списки показывают время, тип TABLE/COUNTER, стол/номер, исполнителя, подтверждённую сумму и разрешённые подробности. Доступ к финансовым операциям определяется отдельными правами; просмотр не разрешает возврат/отмену/перепечатку.

Принятый Order Batch не считается продажей. Полную семантику финансового факта закрепить вместе с Payment/Settlement/ZERO_TOTAL и D08: рекомендуемый якорь — время окончательного подтверждённого расчёта, а события возврата/исправления показывать отдельно со ссылкой на оригинал. Пока этих сущностей нет, раздел не выдаёт сумму пакетов за выручку. Обновление записи не переносит старую продажу в новое окно.

Открытые посещения и неоплаченные заказы старше 24 часов остаются доступными в операционном контуре по правам: фильтр истории не скрывает незавершённую работу и не закрывает её. Для легитимной работы с более старой финансовой историей нужен отдельный Owner/Manager-сценарий, не лазейка cashier API. D12 времени Windows остаётся обязательной эксплуатационной зависимостью.

## 9. Данные Owner и удалённые изменения

Owner Dashboard нельзя наполнить актуальной аналитикой только сменой экрана входа. Сейчас настоящее облако обслуживает активацию; полной доставки продаж/персонала/редакций в Dashboard ещё нет.

### 9.1. Чтение

Филиал асинхронно отправляет разрешённые события/срезы через Outbox; облако принимает их идемпотентно и хранит tenant-scoped проекции. Owner видит только свои организации/филиалы. Имена/роли/статусы передаются согласно политике персональных данных; пароли/PIN/хеши/local session tokens/PIN lookup/encryption keys не включаются в обычные синхронизированные проекции. Отдельный авторизованный запрос показа PIN Owner описан в §9.3 и не превращается в постоянную облачную копию кодов.

Существующие очереди не считать доставленными без ack. Потеря интернета не останавливает локальные операции. При сверке авторство открывшего, ответственного и отправителя пакета остаётся раздельным; выручка не вычисляется из неподтверждённых черновиков.

### 9.2. Меню и конфигурация

Owner сохраняет административную команду с commandId, branch/organization scope, base revision и проверенным issuer. Филиальный сервер сам устанавливает исходящее защищённое соединение, забирает адресованную ему команду и повторно проверяет полномочия/версию/предметные правила перед локальным commit. Публичный входящий порт в ресторан не открывается.

Статусы в Dashboard: «Ожидает филиал», «Применено филиалом», «Конфликт», «Отклонено», «Исход уточняется». Без локального ack нельзя писать «Меню обновлено на кассе». Копия в облаке не заменяет авторитетную локальную редакцию. При конфликте — сравнение и явное разрешение, без last-write-wins.

При отозванном Owner/смене прав старые необработанные команды не применяются только по факту давней постановки в очередь; контур должен проверить актуальную авторизацию/срок/получателя. Точный protocol/credentials/revoke/retention — обновлённые D07/D10/D15 и SYNC-приложение до реализации.

### 9.3. Персонал и выдача PIN

**Уточнение пользователя:** PIN генерируется и назначается локальным сервером, но для удобства доступен повторный просмотр в Owner Dashboard и кабинете кассира. Кассир видит **свой PIN и PIN официантов своего филиала**. Просмотр кода не даёт права сбрасывать/менять его.

| Кто смотрит | Какие коды доступны |
|---|---|
| Cloud Owner | PIN сотрудников принадлежащих ему филиалов при актуальной облачной авторизации и подтверждённой принадлежности филиала |
| Cashier | Собственный PIN и PIN сотрудников с текущей ролью WAITER того же филиала; не коды других кассиров/Manager |
| Waiter | Панель просмотра кодов не предоставляется; чужие PIN недоступны |
| Manager | Новое право показа PIN автоматически не выдаётся; возможное делегирование — отдельное решение |

Отдельное право `employee.pin.view` дополняется серверной областью Owner/Cashier из таблицы; общий grant не снимает ограничение цели. Для Cashier право входит в предлагаемый шаблон и может отзываться. Нельзя получить чужой PIN через общий список/экспорт персонала или прямой запрос ID. Для заблокированной/архивной цели показ не предоставляется; старые версии PIN не показываются.

По умолчанию в списке только маска `••••` и кнопка «Показать PIN». После нажатия сервер проверяет действующую сессию, текущие права/роль/статус/филиал сотрудника и принадлежность целевой записи; результат выводится в отдельной небольшой карточке на 20 секунд с возможностью скрыть раньше. При выходе/смене пользователя, уходе с экрана или истечении сессии код убирается. Массового раскрытия всех кодов при открытии страницы нет. Имя сотрудника и филиал видны рядом с показанным кодом.

Каждый просмотр фиксируется в защищённом аудите: кто, чей код, филиал, время, результат. Сам PIN, расшифрованный ответ и ключи в аудит/logs/обычные commands/results не попадают. Ошибка аудита не должна приводить к неучтённой выдаче. На клиенте открытый PIN существует только в памяти/DOM карточки показа, не сохраняется в localStorage/IndexedDB/файлы/session history/аналитику; ответы не кешируются. Автоматического копирования в буфер обмена нет.

Кассир получает код по локальной защищённой связи без интернета. Owner запрашивает актуальный PIN у филиального сервера через защищённый канал Cloud Backend, с отдельным конфиденциальным ответом для авторизованного получателя. Прямой публичный PIN endpoint в ресторане не открывается. PIN нельзя передать через обычный Outbox как открытое поле сотрудника. Рекомендован зашифрованный конверт для получателя с проверкой адресата, ограниченным сроком и защитой от replay; точный протокол/ключи обязательны до реализации показа в Dashboard.

Если сервер филиала не имеет связи с облаком, Owner видит «PIN сейчас недоступен: филиал не на связи»; старый PIN из кеша не показывается. Повторный просмотр после восстановления связи делает новый авторизованный запрос текущей версии. Если безопасная доставка ещё не готова, кнопка Owner явно недоступна, а не изображает успешный показ. Локальное отображение у кассира от облака не зависит.

Просмотр PIN официанта позволяет кассиру знать его реквизит входа. Поэтому авторство бизнес-команд подтверждает использованную учётную запись, а не доказывает, какой человек физически ввёл код. Это осознанное следствие согласованного доступа к кодам, фиксируемое вместе с аудитом просмотров.

Просмотр персонала и разрешённых PIN входит в уточнённый кабинет. **Удалённое создание/блокировка/сброс PIN/назначение прав** по-прежнему предлагаются расширением R-05; доступ к просмотру сам по себе не утверждает эти изменяющие операции.

Если расширение принято, команды изменяют локальные записи лишь после принятия филиальным сервером. Owner должен видеть, что команда блокировки ещё не дошла до офлайн-филиала; нельзя обещать мгновенный удалённый отзыв в отключённом ресторане.

При первичной установке первый код можно показать Owner в online activation wizard на кассовом компьютере. Генерация и сброс остаются локальными атомарными операциями; повторное чтение существующего кода — отдельный сценарий. Ни один из этих путей не создаёт облачную таблицу открытых PIN.

## 10. Активация и переход с текущего Owner

В новом мастере Owner подтверждает облачную идентичность и доступ к филиалу, привязывает сервер и создаёт первого локального кассира с отдельным логином/паролем и PIN. Опциональный Manager создаётся явно; не назначать кассиру скрытые права Owner. Незавершённый provisioning имеет durable ID/повтор и не создаёт дубли регистрации/первых сотрудников.

Запись облачного Owner и локальный служебный actor для истории могут существовать в БД, но это не локальная учётная запись для входа. Удалять прежние Employee/Audit/Batch/Order ID нельзя. Команды Owner должны сохранять облачное происхождение, а не притворяться локальным входом кассира.

Порядок перехода существующего филиала:

1. Проверить identity/активацию/схему, backup и ограничения обновления; не мигрировать OPEN-смену обходным путём.
2. При доступном интернете подтвердить настоящего Owner и создать/проверить хотя бы одного действующего кассира с локальными реквизитами. Рекомендуется явно назначить локального Manager с ограниченными административными правами для аварийных случаев.
3. Проверить PIN и парольный вход кассира, принадлежность филиала и дальнейшую локальную работу без интернета.
4. После готовности необходимых online Owner-функций отключить локальный интерактивный вход прежних OWNER и отозвать их локальные сессии, сохранив всю историю/идентификаторы. Не оставлять скрытый обход через старый `/auth/login`.
5. Проверить, что сотрудники не потеряли доступ к работе и что кассир не получил чужие Owner-права.

Если Manager не назначен, а интернет отсутствует, обычные кассиры/официанты продолжают работу, но управление персоналом/утраченным PIN может ждать восстановления связи. Не создавать универсальный мастер-PIN или незадокументированный offline Owner-пароль. Конкретную аварийную процедуру закрепить отдельно до коммерческого пилота.

Исходные MANGO/macOS/Windows и их ключи этим документом не меняются; новая модель не повод переактивировать уже занятый филиал на другом сервере.

## 11. Сеть и границы безопасности

Текущий API разрешает native loopback и намеренно отклоняет browser/LAN. Для Waiter нужен отдельный защищённый web transport: TLS, допустимые Host/Origin, серверные защищённые HttpOnly/SameSite cookies и CSRF, срок/отзыв сессий, защищённый realtime или polling. Разрешение CORS `*`, токен в localStorage и `ignore certificate errors` не являются решением.

До сетевой реализации закрыть D01/D02 на реальном роутере и Android/iPhone: имя локального сервера, DNS без интернета, доверенный сертификат, доставка/обновление/истечение сертификата, смена IP, изоляция гостевой сети. Домен и инфраструктура ещё не подтверждены; не считать бренд BASHKAR.KG доказательством владения доменом/готового DNS. Выбранный способ сертификатов фиксируется отдельным техническим приложением и hardware QA.

Разные страницы/порты сами по себе не ограничивают доступ. Ключевой инвариант: authenticated actor + client audience + роль + grant + organization/branch/object scope + предметные условия. Cloud Owner session, Cashier POS session и Waiter Web session не взаимозаменяемы. Будущие изменения не отключают существующие sandbox/CSP/native protected storage/CommandBus/commit-before-ack.

A–D можно готовить отдельными вертикальными срезами, сохраняя рабочую старую модель до управляемого перехода. Целевой пользовательский сценарий — только после завершения необходимых зависимостей, а не сразу после A. Физическая печать и финансы не становятся готовыми из-за разделения кабинетов.

Это существенное расширение продукта на несколько этапов. Переписывать CommandBus, TABLE/Order/Menu/Pricing с нуля не требуется. Точную календарную оценку давать после выбора D01/D02 и объёма cloud administration; без этих решений обещать срок полного выпуска было бы недостоверно.

## 13. Приёмка

- Cloud Owner не входит по PIN или локальному паролю; без интернета новый вход/открытие Dashboard невозможны, рабочий offline cache не выдаётся за кабинет.
- Кассир входит четырьмя цифрами без выбора имени и по логину/паролю; оба метода ведут в один и тот же профиль/права своего филиала. Официантский код отклоняется в Cashier POS и наоборот.
- PIN уникален в выбранной области, включая гонки выдачи/сброса. Начальные нули сохраняются; ни старый код после reset, ни универсальный default не работают.
- Долговременный brute force, новые cookies, role probing и многократные ошибки не обходят ограничения; загрузка хеширования ограничена, один сотрудник не создаёт бесконечную блокировку всех.
- Блокировка/архив/reset отзывают сессии, не удаляя историю/столы/пакеты. Cloud queued block не показывается применённым до ack филиала.
- После отключения интернета Cashier и Waiter продолжают разрешённые операции через Local Server; после потери Wi-Fi отправки не получают ложного success.
- Waiter работает на Android и iPhone по HTTPS без отключения проверки сертификата; браузерные сессии/CSRF/audience/branch/object scope испытаны.
- История 24 часа отсекает старые записи во всех серверных маршрутах; открытые заказы не скрываются. Batch/черновик не считается оплаченной продажей.
- Owner видит только свои организации/филиалы и время актуальности; потерянные/повторные sync-команды не дублируют операции, конфликт меню не разрешается автоматически.
- PIN/пароли/локальные хеши/ключи отсутствуют в постоянном renderer storage/URL/logs/обычных cloud projections. Разрешённый PIN выводится только в краткоживущей карточке по новому авторизованному запросу, с аудитом без секрета. Cashier не раскрывает код другого кассира/Manager/чужого филиала; смена роли/отзыв права немедленно учитываются сервером. Шифротекст нельзя переставить другой цели; сброс не оставляет доступной старую версию.
- Переход сохраняет identity, данные и авторство; прежний локальный Owner не остаётся доступен через альтернативный API. Рабочие кассиры проверены до отключения старого входа.
- Windows native storage/service/ACL, локальная сеть/телефоны, отсутствие интернета, облако, финансовые факты, принтеры и restore фиксируются раздельно. Неисполненные проверки — NOT RUN.

## 14. Решения для утверждения

| Код | Рекомендация |
|---|---|
| R-01 | Отдельный облачный сайт Owner; в Desktop только ссылка на него и отдельный мастер первичной активации |
| R-02 | PIN — 4 цифры, уникален среди неархивных сотрудников одного филиала; один код определяет сотрудника без выбора имени |
| R-03 | Cashier: PIN + парольный fallback; Waiter: PIN; системный audience не позволяет войти не в свой интерфейс |
| R-04 | Cashier история: все подтверждённые продажи своего филиала за скользящие 24 часа; не только личные и не календарный день |
| R-05 | В Owner Dashboard сначала достоверный просмотр персонала; удалённые создание/блокировка/права/reset PIN — отдельное расширение после защищённого command/секретного result контракта |
| R-06 | Сохранить Manager как отдельную явно назначаемую локальную роль с ограниченными правами; не делать кассира скрытым администратором |
| R-07 | Прежний локальный Owner отключить только при управляемом переходе после готовности online-замены и проверенного кассира; без скрытого offline Owner |
| R-08 | Сохранить idle POS 3 часа / Waiter 3 часа, absolute 12 часов; PIN не упрощает подтверждения рискованных действий автоматически |
| R-09 | Уточнено пользователем: PIN выдаётся локально и повторно показывается Owner по своим филиалам, Cashier — свой и официантов своего филиала; остальные границы показа, шифрование и аудит — §7/§9.3 |

Пользователь явно подтвердил все R-01…R-09 и разрешил продолжать. Начать срез A по UI §3/§5; до включения PIN закончить его техническое приложение о лимитах/ключах/миграции и проверки. Повторное утверждение уже описанного UI и решений не требуется; новые продуктовые решения и ещё не выбранная инфраструктура согласуются отдельно по необходимости. На момент передачи реализация A не начата: код, данные, облако и существующие установки под AUTH-002 не менялись.

Обновление реализации A: локальный PIN/кассир добавлены в source 0.6.0-pin/schema 6. Исторические формулировки о неначатой реализации выше относятся к моменту передачи. Облачные/сетевые/финансовые B–F не объявляются готовыми; локальный Owner сохранён.
