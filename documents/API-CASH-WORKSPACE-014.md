# API-CASH-WORKSPACE-014 — поставка единой корзины Кассы

**Дополнение 25.10.2026:** [API-CHECKOUT-015](API-CHECKOUT-015.md) реализует перенос/смену ответственного с историей и атомарную оплату с новым пакетом. Прежние ограничения неизменяемого назначения и запрет оплаты с дозаказом ниже описывают предыдущий этап; FAST_FIRST теперь использует новый контракт. TABLE_FIRST/TABLE_QUICK сохраняют свои сценарии.

Дата: 25.10.2026. Реализовано в source **0.13.0-cash-workspace / SQLite 14** по согласованному [POS-CASH-UX-004](POS-CASH-UX-004-DRAFT.md). Этот документ уточняет прежние CORE/API в перечисленной области; старые снимки расчётов и кухонной печати не переписываются.

## Модель и совместимость

- TABLE по-прежнему обязательно связан с реальным серверным контекстом `table_sessions`. Теперь `table_sessions.table_id` может быть NULL: это «Зал · Без стола», с настоящими сменой, автором, ответственным и временем. Фиктивные столы и подмена TABLE на COUNTER не используются.
- STRICT/SHARED применяются прежним `TableService`: ответственный сохраняется, право отмечать выдачу не открывает чужое посещение. Все открытые контексты, включая неназначенные и пустые, входят в действующие blockers смены. SQL-защита открытия в закрытой смене сохранена.
- Физический стол до назначения остаётся FREE. Назначение свободного активного стола выполняется один раз, атомарно, с CAS посещения и аудитом. Занятый стол отклоняется; объединения/переноса между занятыми столами нет. Старые кухонные снимки сохраняют прежнюю надпись, новые используют назначенный стол.
- Полный/нулевой расчёт и полная отмена сохраняют прежнюю семантику. Закрывается контекст; назначенный физический стол освобождается. Номера TABLE/COUNTER остаются общими в рамках смены, пакеты не получают новый номер заказа.

## HTTP Local POS Server

Все маршруты — `/api/v1`, с действующей авторизацией, проверкой филиала и строгим набором полей.

| Маршрут | Контракт |
|---|---|
| POST `/tables/open` | `commandId, tableId: UUID|null, responsibleWaiterId: UUID|null`; обязательный ответственный определяется прежними правилами |
| POST `/tables/assign` | `commandId, sessionId, tableId, revision`; table.open + объектный доступ, OPEN посещение/смена, стол свободен/активен |
| POST `/cash/draft-context` | `draftId, type: TABLE|COUNTER`; контекст защищённого локального нового черновика, не создание заказа/номера |
| GET `/orders/:id/batches?after=0&limit=20` | Общая история TABLE/COUNTER, limit≤100; автор/время/сумма пакета, неизменяемые строки, действующие количества/порции/комментарии, отметки выдачи, реальные состояния кухонной печати, next |
| POST `/orders/:id/fulfillment` | `commandId, itemId` (UUID принятой строки), `issued: boolean, expectedRevision, expectedOrderRevision`; отдельное событие выдачи |
| GET `/orders/:id/fulfillment/events?after=0&limit=50` | Аудируемая последовательность отметок/снятий с серверным курсором, сотрудником, временем и количеством; limit≤100 |

Существующие prepare/submit TABLE и COUNTER принимают новые пакеты в том же заказе. При изменении меню, суммы, скидки, сборов или принятой ревизии между просмотром и подтверждением требуется повторный просмотр. Desktop не подписывает автоматически изменившуюся сумму за кассира.

## Неизвестный товар

Новый вид строки `CUSTOM_AMOUNT`. Минимальный выбор для quote: `{kind:'CUSTOM_AMOUNT', unitPrice:12345, quantity:1}`. Сумма — целые тыйыны, цена 1…999999999, количество 1…9999, произведение и итог ограничены общим денежным лимитом. В пакете добавляется UUID `lineId`; нормализованный локальный формат также содержит `itemId:'CUSTOM_AMOUNT', variantId:null, modifierIds:[], comment:''`. Этот идентификатор обозначает вид строки и не ссылается на вымышленную запись меню.

- Серверный снимок: «Неизвестный товар», явный kind, введённая цена/количество/итог, `kitchen:false`, без вариантов/модификаторов/комментария. Автор и время сохраняются в принятом пакете и аудите команды.
- Цена обычного товара по-прежнему определяется меню; произвольные поля цены обычной строки не принимаются. Для неизвестного товара чужие варианты, непустой комментарий и серверная коррекция комментария отвергаются.
- Применяются общие скидки/сборы TABLE, расчёт, отмены, возврат Payment, журнал продаж и финансовая печать. Кухонные задания, включая отмены и повторную печать их снимков, не содержат неизвестных строк. Полностью некухонный пакет принимается без kitchen job.
- Новое право `order.custom_item.create`: по умолчанию OWNER/MANAGER/CASHIER; WAITER запрещено потолком роли. Проверяется на quote и при приёме/замене позиции сервером.
- Продажа использует действующий опубликованный каталог и серверный quote; отдельного обхода требования публикации меню нет.

## Выдача

Отдельная append-only таблица `order_fulfillment_events`: заказ/строка, ревизия, issued, количество, автор/имя, серверное время, commandId. Финансовая ревизия заказа не меняется от выдачи. Внешняя уникальность строки/заказа проверяется, UPDATE/DELETE событий запрещены.

Право `order.fulfillment.mark` доступно OWNER/MANAGER/CASHIER/WAITER по умолчанию, с обязательным объектным доступом. Отмечать можно действующие строки только OPEN заказа в открытой смене. Команды идемпотентны, сверяют ревизию заказа и отметки. При изменении количества перечитывается серверное состояние. Одна отметка относится ко всему действующему количеству строки конкретного пакета. После уменьшения количества подтверждение сохраняется для оставшегося количества; полностью отменённая строка не отмечается. Новая/заменённая строка начинает без отметки. Снятие — отдельное подтверждённое действие с новым событием.

Выдача не влияет на оплату, дозаказ, полную отмену, завершение, свободность столов или blockers смены. `SENT` печати не означает выдачу. В завершённой продаже отметки доступны для чтения, а не редактирования. Наличие/отсутствие отметки не доказывает физическую передачу блюда.

## Desktop и восстановление

- SVG стола/пакета, режимы переключаются без подтверждения. Новый черновик сохраняет строки/количество/комментарии, цену пересчитывает сервер. Назначения зала скрыты в COUNTER и сохраняются для возврата.
- Тип принятого заказа переключателем не изменяется: другой режим открывает новый черновик, исходный дозаказ остаётся за своим заказом. Карточки активных заказов открывают ту же правую корзину, без перехода в старый редактор.
- Принятые пакеты свёрнуты, имеют независимые чекбоксы и реальную печатную информацию. Новый пакет редактируется отдельно. Расчёт из этой корзины не разрешается, пока в ней есть неотправленные позиции. После расчёта Касса остаётся открытой.
- Очистка — иконка, рядом жёлтый плюс неизвестного товара. Ввод суммы использует виртуальную клавиатуру; неизвестная строка имеет количество/удаление, без комментария/вариантов. Добавление любого товара остаётся без success-toast.
- Локальные черновики и выбранный контекст находятся в защищённом атомарном состоянии main process, разделены по установке/филиалу/сотруднику/заказу. Состав, произвольная цена и назначения восстанавливаются после перезагрузки. Новый COUNTER освобождает отдельный scope для следующего нового заказа.
- Открытие посещения из новой корзины — отдельное защищённое native-действие `cashVisitOpen`: до запроса замораживается исходный черновик, неизвестный результат требует повтора той же команды. Подтверждённый ответ атомарно связывает workspace с посещением. Потеря ответа submit также сохраняет прежний frozen/retry механизм и не создаёт повторный пакет.
- Неизвестный результат выдачи восстанавливается отдельно и не блокирует дозаказ/оплату; конфликт повторной отметки той же строки защищён отдельно от финансовых команд.
- WebSocket и явная перерисовка сериализованы; восстановление одного черновика не выполняется конкурентно. При закрытии заказа другим клиентом дозаказ сохраняется для явного переноса в новый заказ.
- Сообщения — общий [UI-MESSAGES-001](UI-MESSAGES-001.md). Потеря связи/неизвестный результат имеют постоянный путь восстановления.

## Обновление и границы

Миграция 014 перестраивает только контекст посещения с отложенной проверкой FK, сохраняет существующие строки и восстанавливает его триггеры, включая запрет INSERT в закрытую смену. Создаёт таблицу событий выдачи. Штатный механизм не разрешает миграцию при OPEN смене; рабочие установки автоматически не мигрируются.

Не входят: частичная выдача внутри количества строки, редактирование выдачи после расчёта, отдельная очередь оплаченных невыданных, смена типа принятого заказа, объединение заказов/перенос занятого стола, NFC/QR-запросы гостей. Windows/физическая бумага и реальный сенсор требуют отдельной аппаратной приёмки.
