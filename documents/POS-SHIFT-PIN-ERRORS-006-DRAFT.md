# POS-SHIFT-PIN-ERRORS-006 — ошибки PIN и восстановление открытия смены

Дата: 25.10.2026. Статус: **Согласовано пользователем и реализовано.** Имя DRAFT сохранено для прежних ссылок. Фактические файлы, проверки и границы — в §7.

Область: открытие смены из Header, при выборе свободного стола и из каталога/быстрой продажи, в обоих видах Кассы. OWNER/MANAGER сохраняют подтверждение логином/паролем; способы авторизации и серверные ограничения не меняются.

## 1. Что установлено и зачем существует блок

1. `apps/pos-desktop/main.cjs` до отправки мутации записывает команду в защищённое `state.pending`. При потере ответа запись сохраняет исходный commandId и позволяет повторить именно ту же команду, не создавая вторую операцию.
2. После серверной ошибки native-обработчик сейчас не удаляет pending для HTTP 401/403/429. Поэтому новый `shiftOpen`, явно отклонённый из-за неверного PIN, тоже остаётся в очереди.
3. `shiftCommit()` уже записывает часть ошибок в модальный `note`, но затем повторно выбрасывает ошибку. Общий `run`/`handleError` выводит её в фоновый `#status` и вызывает `pendingPanel()`. В «Заказы сначала» дополнительно работает общий toast, но фоновый блок всё равно создаётся.
4. `pendingPanel()` вставляет старую карточку «Открыть смену», поле повторного PIN и кнопку в `#screen`, за модальным окном. Это не доказательство открытия смены и не отдельное обязательное подтверждение неверного PIN.
5. В серверном `POST /shifts/open` метод `proveForShift()` проверяет PIN **до** вызова `ShiftService.open()` и `CommandBus`. Новый запрос с неверным PIN получает `INVALID_CREDENTIALS` / HTTP 401 до создания смены. Ошибка при этом записывается в аудит авторизации.

**Вывод:** ложную pending-запись новой попытки с подтверждённо неверным PIN можно и нужно удалять. Удалять весь механизм восстановления нельзя: при тайм-ауте/обрыве ответа сервер мог уже открыть смену.

Важное исключение: если команда **раньше уже имела неизвестный результат**, последующий неверный PIN не доказывает, что предыдущая отправка не выполнилась. Такой pending удалять нельзя.

## 2. Сообщение непосредственно в модальном окне

- Для подтверждённо неверного PIN показать **«Неверный PIN. Попробуйте ещё раз.»** внутри открытого диалога, рядом с вводом PIN и перед действиями подтверждения.
- Применить минималистичное оформление Bashkar: мягкий красный фон/акцент, читаемый текст, небольшой значок ошибки. Сообщение остаётся видимым, пока сотрудник исправляет ошибку; не исчезает через 1,5 секунды. Использовать доступное объявление ошибки (`role=alert`), не менять размеры окна скачком и не перекрывать клавиатуру.
- Не отправлять эту обработанную ошибку повторно в фоновый `#status`, старую карточку pending или дополнительный toast. Для данного случая достаточно ошибки поля внутри диалога.
- После отказа очищать PIN, возвращать фокус к вводу, разрешать цифровую клавиатуру. «Открыть смену» доступна только после нового ввода четырёх цифр и завершения серверной блокировки, если она есть. Восстановление прежних disabled-состояний не должно включать кнопку с пустым PIN.
- При новом вводе убрать устаревшее сообщение о неверном PIN. Подтверждение успеха — только после реального серверного результата; использовать действующий success-toast.
- Для OWNER/MANAGER ошибка их полей называется **«Неверный логин или пароль»**, а не «Неверный PIN». Сохранить существующую модель проверки их личности.
- Одинаковое поведение для Header, карточки стола и вложенного PIN над полноэкранной быстрой продажей. Исправить оба вида Кассы через общий компонент, без отдельной копии логики.

## 3. Разделение результатов команды в native-слое

| Ситуация | Pending открытия смены | Представление |
|---|---|---|
| Новая попытка; получен корректный серверный ответ `INVALID_CREDENTIALS` | Удалить только эту подтверждённо отклонённую попытку | Ошибка PIN/пароля в модальном окне |
| Новая попытка; получен подтверждённый отказ до операции `PIN_RATE_LIMITED` / `PIN_WORK_LIMIT` | Не оставлять как неизвестное открытие смены | Ограничение попыток внутри диалога; пауза по серверному контракту |
| Тайм-аут, потеря/неполный ответ, ошибка связи, результат которой нельзя подтвердить | Сохранить исходный commandId и неопределённость | Восстановление в том же модальном сценарии |
| Повтор ранее неизвестной команды; PIN неверен/действует лимит | **Сохранить предыдущую неизвестную команду** | Ошибка ввода плюс пояснение, что исходный результат ещё не проверен |
| Повтор исходной команды вернул подтверждённый результат | Удалить восстановленную запись после надёжного сохранения результата | Обновить Header и продолжить сценарий по реальному состоянию |
| Сессия истекла, права отозваны или пришла другая критическая ошибка | Сохранить действующие защитные правила; не считать это просто неверным PIN | Штатная блокировка/повторный вход, без раскрытия чужого состояния |

- Native-слой должен различать первую отправку и существовавшую неопределённость **до** текущего запроса. В защищённом состоянии сохранять достаточные метаданные для этого различия, включая перезапуск приложения во время запроса.
- Очистка — узкая классификация для открытия смены и доказанных отказов проверки личности. Не применять правило «все 401/403/429 можно удалять» к оплатам, возвратам, закрытию смены и остальным мутациям.
- Не хранить PIN/пароль в pending, метаданных, DOM-подсказках или журналах. Сохранить аудит неверных попыток, серверные лимиты и объектные/ролевые проверки.
- Для HTTP 429 показывать отдельное сообщение об ограничении, а не утверждать, что PIN неверен. Использовать `retryAfterSeconds`, если сервер его возвращает; для `PIN_WORK_LIMIT` сохранить штатную короткую паузу/повтор без отключения серверной защиты.

## 4. Что убрать с фона и чем заменить настоящее восстановление

- Записи **`shiftOpen` не выводить в старом блоке «Действия без подтверждённого результата»** на странице под модальным окном — ни в «Столы сначала», ни в «Заказы сначала».
- После обычного неверного PIN в `pending` этой новой попытки уже нет. Если других неизвестных действий нет, фонового блока вообще нет.
- Реальную неизвестную попытку показывать в модальном открытии смены: **«Не удалось подтвердить открытие смены. Проверьте результат исходного действия.»**, ввод подтверждения личности и кнопка «Проверить открытие смены». Повтор использует прежний commandId, не создаёт новую команду открытия.
- Если сотрудник закрыл диалог при настоящей неопределённости, сохранять доступный из Header устойчивый индикатор необходимости проверки. При следующем нажатии на смену открывать её восстановление внутри диалога. Не скрывать неопределённость бесследно и не показывать неподтверждённый успех.
- Реальный статус смены в Header получать с сервера. Если она уже OPEN, не подписывать её как CLOSED из-за локального pending; дать проверить исходную операцию внутри диалога текущей смены.
- При восстановлении сверять возвращённую квитанцию с текущей сменой. Старый receipt может относиться к уже закрытой смене: он не означает, что сейчас открыта новая. Успешно выполненное исходное действие и текущее состояние показывать корректно, без автоматического создания новой смены.
- Остальные неизвестные действия, в особенности финансовые, не прятать и не очищать этой правкой. Если они есть, их действующий блок восстановления сохраняется.

## 5. Ранее сохранённые записи и границы

- Старые pending без классификации нельзя массово удалить: по имеющимся полям не отличить прошлый неверный PIN от потерянного ответа.
- Для старого `shiftOpen` предложить тот же модальный путь проверки с повтором исходной команды после явного действия сотрудника. Получить квитанцию, сверить текущую смену и затем убрать подтверждённую запись. Отсутствие открытой смены само по себе не доказывает, что исходная команда никогда не выполнялась.
- При новой успешной попытке не оставлять ложные карточки подтверждённых отказов. При неизвестном исходе продолжать восстановление после перезапуска и только в контексте соответствующего сотрудника.
- Не менять бизнес-логику смен, серверный аудит/лимиты, OWNER/MANAGER-авторизацию и финансовую идемпотентность. Новая бизнес-сущность или миграция SQLite для описанного исправления не предполагается.

## 6. Приёмка

1. В обоих видах и во всех трёх точках запуска новый неверный PIN остаётся ошибкой внутри диалога; за ним нет ни фонового сообщения этого отказа, ни `shiftOpen`-карточки pending. Смена не создаётся.
2. После ошибки PIN очищен, фокус возвращён, новая попытка невозможна до четырёх цифр; правильный PIN открывает ровно одну смену и продолжает исходное действие.
3. Лимиты 429 отображаются внутри окна корректно; ограничения не сбрасываются локальной очисткой записи. OWNER/MANAGER получают ошибку своих полей, а не PIN.
4. При потерянном ответе после фактического открытия команда сохраняется; закрытие/повторное открытие окна и перезапуск не теряют её. Проверка повторяет тот же ID, не создаёт вторую смену.
5. Неверный PIN при повторе такой неизвестной команды не стирает исходную неопределённость. Последующий правильный повтор восстанавливает исходный результат.
6. Проверены старый pending без метаданных, уже закрытая исходная смена и открытие смены другим сотрудником. Header показывает факты сервера; текущую смену не приписывать новой команде ошибочно.
7. Pending оплаты/возврата/закрытия смены остаются доступны и не удаляются новой классификацией. При истёкшей сессии/отзыве прав сохраняется защита.
8. Проверить RU/KY, вложенные диалоги и 1366×768 / 1920×1080; выполнить релевантные серверные/native и Electron-регрессии на временном профиле. Не изменять рабочую базу/смены для QA.

Ожидаемые области изменения после согласования: `main.cjs` (классификация pending), `shift-finance.js` (общая ошибка/восстановление и валидация ввода), `renderer.js` (фоновый pending и сообщения), стили модального окна, тесты и стандарт [UI-MESSAGES-001](UI-MESSAGES-001.md). Точный список файлов фиксируется в отчёте реализации.


## 7. Фактическая реализация — 25.10.2026

### Поведение

- Новый `shift-open.js` управляет общим открытием/восстановлением смены во всех точках входа. Ошибка PIN/пароля остаётся в самом диалоге, без повторного проброса ожидаемого отказа в глобальные сообщения. Под ошибку зарезервировано место, поэтому неверный PIN не меняет высоту окна. PIN очищается, фокус возвращается, кнопка недоступна до нового полного ввода.
- Ограничения попыток показываются отдельным текстом. При `retryAfterSeconds` работает обратный отсчёт; input/цифровая клавиатура/подтверждение недоступны до окончания паузы. Серверные ограничения не сбрасываются. `PIN_WORK_LIMIT` без срока использует короткую локальную паузу; отсутствие серверного срока не выдаётся за подтверждённое окончание его блокировки.
- В native-слое сохраняется `IN_FLIGHT` перед первой отправкой и `UNKNOWN` при неоднозначном результате. Любой существующий record, включая старый без метаданных или оставшийся IN_FLIGHT после прерывания, трактуется как прежняя неопределённость. Только новая подтверждённо отклонённая попытка `shiftOpen` очищается по узкому списку proof-ошибок. Политика выделена в `pending-policy.cjs` и покрыта тестами.
- Неполный JSON либо некорректная успешная квитанция открытия не удаляют запись и возвращаются как неизвестный результат. Восстановление сохраняет исходный commandId; секреты в record не записываются.
- `shiftOpen` исключён из старого фонового `pendingPanel`. Для настоящей неопределённости Header сохраняет «Требует проверки» рядом с фактическим состоянием смены, а нажатие открывает проверку в модальном окне. Pending остальных операций остаются в прежнем финансовом восстановлении.
- Старые записи не удаляются автоматически. Несколько старых записей проверяются последовательно. В восстановлении открытия можно заново ввести собственный логин/пароль или PIN: это proof, а не изменение бизнес-команды. Сервер по-прежнему связывает proof с текущим авторизованным сотрудником; исходные ID/actor и серверная идемпотентность сохраняются. Это позволяет исправить старый ошибочный логин, не создавая новую команду.
- После получения исходной квитанции выполняется чтение текущей смены. Если она уже закрыта, диалог сообщает это и предлагает отдельное новое открытие, без автоматического действия. Если открыта другая смена, Header показывает её реальные данные; новый дубликат не создаётся.
- У OWNER/MANAGER сохранены логин/пароль. В UI QA отдельно подтверждён пароль OWNER; MANAGER использует тот же существующий парольный путь, без введения PIN-сценария.
