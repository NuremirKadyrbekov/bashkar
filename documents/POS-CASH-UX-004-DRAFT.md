# POS-CASH-UX-004 — режимы продажи, произвольный товар и пакеты в корзине

Дата: 25.10.2026. Статус: **Согласовано пользователем и реализовано 25.10.2026**. Фактическая поставка, схема 14, API, проверки и границы: [API-CASH-WORKSPACE-014](API-CASH-WORKSPACE-014.md). Имя DRAFT сохранено для совместимости прежних ссылок.

Дополняет [POS-CASH-UX-003](POS-CASH-UX-003.md), [общие номера заказов](API-ORDER-NUMBERS-013.md) и [стандарт уведомлений](UI-MESSAGES-001.md). Правила ARCH-001, CORE-001 и AUTH-001 сохраняются; изменения предметной модели ниже являются предложением и требуют подтверждения этого ТЗ.

## 1. Что установлено по текущему коду

- В `fast-sales.js` режимы переключаются с подтверждением при непустой корзине; TABLE требует `tableId`. Карточки действующих заказов переводят в прежний редактор.
- TABLE создаётся через реальное посещение; проверка доступа в `TableService` использует ответственного/открывшего посещение, STRICT/SHARED и право доступа к чужим посещениям. Ограничение БД в миграции 007 требует у TABLE `table_session_id`.
- Закрытие смены учитывает открытые посещения и неоплаченные COUNTER. Простое разрешение TABLE без посещения оставит такой заказ вне текущего контроля блокировок.
- Сервер уже принимает последующие пакеты TABLE и COUNTER. Пакет хранит автора, время, строки и номер последовательности; кухонные задания создаются только для кухонного подмножества строк.
- Текущий `Selection` поддерживает только позиции опубликованного меню. Нет произвольной цены товара и отдельной сохраняемой модели выдачи. Эти функции нельзя реализовать только локальными флажками интерфейса.
- Номер заказа общий для TABLE и COUNTER внутри смены; новый пакет не получает новый номер заказа. UUID остаётся техническим идентификатором.

Источники: `apps/pos-desktop/fast-sales.js`, `cash-items.js`; `apps/local-server/src/modules/tables/table-service.ts`, `orders/order-service.ts`, `orders/finance-service.ts`, `shifts/shift-finance-service.ts`, `menu/pricing.ts`, `migrations/007-finance.ts`. Текущая семантика расчёта и отсутствующая модель выдачи также описаны в [DOCS-AUDIT-001](DOCS-AUDIT-001.md).

## 2. Необязательный стол: риски и предлагаемое решение

| Риск простой отмены обязательности | Требование к полноценному решению |
|---|---|
| Сервер/БД отклоняют TABLE без посещения | Расширить серверную модель заказа в зале, API и схему; не ограничиваться интерфейсом |
| STRICT/SHARED привязаны к посещению | У заказа без стола хранить открывшего сотрудника и ответственного; применять те же объектные правила доступа на сервере |
| Незакрытый заказ может не заблокировать закрытие смены | Учитывать все открытые заказы зала без стола в блокировках и восстановлении, без двойного подсчёта назначенных |
| В зале физически сидят гости, но на карте стол остаётся свободным | Показывать «Зал · Без стола» в активных заказах; явно объяснить, что такой заказ не резервирует физический стол |
| Позднее назначение занятого стола создаёт конфликт | Назначать свободный стол атомарно, с проверкой ревизии и прав; конфликт не переносит и не объединяет заказы |
| Ошибочное использование COUNTER меняет сборы и отчёты | Сохранять тип TABLE, его сборы, финансовые правила и аналитику |
| Кухня не знает, куда отдавать заказ | В заданиях указывать «Зал · Без стола», номер заказа и ответственного; не печатать вымышленный стол |

**Предлагается включить полноценный сценарий «Зал · Без стола» в этот этап.** Он требует серверной доработки до включения кнопки создания. Скрытый технический стол или подмена на COUNTER запрещены.

Серверный контекст обслуживания заказа в зале должен существовать независимо от назначения физического стола. У него сохраняются филиал, смена, открывший, ответственный, время, ревизия и правила доступа. Конкретная миграция связей заказа/посещения определяется по всем текущим ограничениям и триггерам до изменения схемы; исторические финансовые снимки не переписываются. Старые TABLE продолжают работать без изменения их смысла.

- Разрешить создание непустого TABLE без выбранного стола после подтверждения сервером. Ответственный выбирается/определяется по действующим правилам, включая самостоятельную работу официанта; отсутствие стола не обходит их.
- Для заказа без стола показывать кнопку «Выбрать стол», впоследствии разрешающую назначить свободный стол через зоны и компактные карточки. Создание посещения/привязка происходят атомарно; сохранены ответственный, номер заказа, пакеты и финансовые условия. Объединение с существующим заказом занятого стола не входит в этап.
- Оплата/полная отмена закрывают контекст; физический стол освобождается только при наличии его привязки. Отсутствие стола не мешает расчёту.
- После назначения ранее созданные кухонные снимки остаются историческими; новые пакеты содержат актуальный стол. Автоматическая повторная печать старых пакетов не выполняется, изменение назначения видно сотрудникам через WebSocket.

## 3. Режимы и верхние действия корзины

- Добавить согласованные SVG-иконки: стол для «Зал», пакет для «На вынос». Сохранить мягкое различие цветовых акцентов, выбранное состояние и читаемые подписи. Иконки не заменяют название режима.
- Переключать режим нового заказа сразу, без подтверждения. Сохранять состав, количества и комментарии; пересчитывать скидку/сборы сервером. Выбранный стол и ответственного зала сохранять как настройки черновика зала, скрывать в COUNTER. При непригодных условиях серверного расчёта показать предупреждение и запретить отправку до исправления.
- Тип уже принятого заказа не менять переключателем. При открытом существующем заказе переход на другой режим сразу открывает отдельный новый черновик нужного типа, сохраняя незавершённый дозаказ исходного заказа. Возврат по карточке восстанавливает его. Не преобразовывать существующий TABLE в COUNTER или наоборот.
- Очистку показать SVG-иконкой корзины/удаления с `aria-label` и подсказкой «Очистить корзину». Она очищает только новый неподтверждённый пакет; подтверждённые строки и историю не затрагивает. Существующую защиту от случайной очистки сохранить.
- Рядом разместить жёлтую кнопку `+` с подсказкой «Неизвестный товар». Все области нажатия не меньше 44×44 px, фокус доступен с клавиатуры.

## 4. Неизвестный товар

Название в интерфейсе и финансовом снимке: **«Неизвестный товар»**. Это отдельный вид серверной строки с произвольной ценой, а не фиктивный товар меню и не отдельная платёжная операция.

1. Жёлтый `+` открывает модальное окно «Неизвестный товар»: сумма в сомах, виртуальная цифровая клавиатура, кнопка «Продолжить», закрытие/отмена. Поддержать физическую клавиатуру и десятичные доли до тыйынов; хранить целые тыйыны. Пустые, нулевые, отрицательные и превышающие денежный лимит сервера значения недопустимы. Ошибки остаются видимыми в диалоге до исправления.
2. «Продолжить» получает серверный расчёт и добавляет строку в текущий новый пакет: введённая сумма — цена единицы, начальное количество 1. Повторное добавление создаёт отдельную строку; изменение количества работает как у обычного товара и не теряет введённую цену.
3. Строка имеет название, цену, количество, итог и удаление. Нет вариантов, `⋯`, комментария и кнопки комментария; API также отвергает комментарии такой строки.
4. Действуют скидки, сборы TABLE, расчёт, отмены, возвраты, журнал продаж и финансовая печать по общим правилам. Произвольный товар отдельно различим в деталях/аналитике, без вымышленной категории меню.
5. Неизвестный товар **никогда не попадает в задания кухни**, включая повторную печать и кухонные отмены. Смешанный пакет отправляет на кухню только подходящие обычные позиции. Пакет только из неизвестных товаров принимается без кухонного задания и остаётся виден в истории.
6. Сервер проверяет разрешение на произвольную цену, сумму и доступ к заказу. Предлагаемое отдельное право выдаётся owner/manager/cashier; официанту по умолчанию не выдаётся. Клиент не может подменить цену обычного товара этим полем. Каждая принятая строка содержит автора, время и ценовой снимок.
7. Расширить общий контракт строки, quote/prepare/submit, защищённые локальные черновики, восстановление, снимки расчёта/возврата и печатные шаблоны. Цена остаётся действительной независимо от будущих изменений меню. Не добавлять второй независимый калькулятор в Desktop.

При закрытой смене запуск добавления использует действующий сценарий открытия смены с PIN либо логином/паролем для owner/manager. Без подтверждения сервера строка не считается принятой. Уведомление «Товар добавлен» не показывать.

## 5. Существующий заказ в правой корзине

- Нажатие карточки TABLE/COUNTER загружает его в «Текущий заказ» на этом же экране. Показывать номер заказа, «С10»/«Зал · Без стола»/«На вынос», ответственного и актуальный финансовый итог. Не переходить в прежний редактор.
- Сверху корзины — подтверждённые пакеты, каждый по умолчанию свёрнут: «Пакет №N», время, автор, число позиций, сумма. Раскрытие показывает позиции, варианты, комментарии и актуальные отмены/корректировки. Страницы истории загружать из существующей серверной пагинации.
- Заголовок истории — «Принятые пакеты». Принятие пакета и передача бумаги кухне различаются: кухонная печать может отсутствовать, ожидать или завершиться ошибкой. Состояние печати отображать только по реальным данным; `SENT` не означает физическую выдачу.
- Ниже — отдельный редактируемый «Новый пакет». Добавление из каталога относится только к нему. Основное действие для существующего заказа — «Отправить пакет»; для нового — «Создать заказ». Пустой пакет отправить нельзя.
- При подтверждении сервер добавляет пакет к тому же заказу, обновляет сумму и ревизию, создаёт необходимые задания кухни; только после подтверждения новый пакет очищается и появляется в истории. Номер заказа прежний, номер пакета следующий.
- Сохранять отдельные защищённые черновики по сотруднику и контексту заказа. При переходе на другую карточку дозаказ не исчезает и не переходит в другой заказ; при смене сотрудника черновики не раскрываются постороннему.
- Суммы принятого заказа, нового пакета и предполагаемый итог различимы. Окончательная сумма всегда серверная. Не представлять сумму локального дозаказа как уже принятую задолженность.
- Сохранить доступные по правам действия расчёта, коррекции и отмены. При неопубликованном новом пакете расчёт блокируется с выбором: отправить пакет или удалить черновик явным действием; не оплачивать его незаметно и не терять позиции.
- Если заказ закрыт другим сотрудником, редактирование/отправка прекращаются, показывается актуальное состояние. Локальный дозаказ сохраняется для явного переноса в новый заказ, без автоматической повторной отправки.

## 6. Независимые отметки выдачи по позициям

Это новая сохраняемая сервером операционная отметка **«Выдано»**, а не новый финансовый статус заказа, не статус кухни и не подтверждение печати.

- В раскрытом принятом пакете у каждой действующей позиции, включая неизвестный товар, показать чекбокс. В новом неподтверждённом пакете чекбоксов нет.
- На первом этапе один чекбокс относится ко всему действующему количеству данной строки данного пакета: например, «Выдано 3 из 3». Частичная выдача 1 из 3 отдельным вводом в этот этап не входит. Позиции следующих пакетов имеют независимые отметки.
- Записывать на Local POS Server ссылку на заказ/пакет/строку, действующее количество, сотрудника, серверное время и ревизию. История отметок и снятий сохраняется отдельно от неизменяемых финансовых снимков. После перезапуска состояние восстанавливается; WebSocket обновляет другие рабочие места.
- Право отмечать выдачу — отдельное разрешение, предлагаемое owner/manager/cashier/waiter, с обязательной проверкой доступа к самому заказу по STRICT/SHARED. Разрешение не даёт права открыть чужой заказ в STRICT.
- Чекбокс изменяется после подтверждения сервера; во время запроса недоступен. Повторная доставка команды идемпотентна, конфликт ревизии приводит к обновлению данных. При ошибке состояние не показывается как сохранённое.
- Снятие уже подтверждённой отметки — отдельное подтверждённое действие с записью автора/времени. Корректировка количества или отмена сохраняет прежние события в аудите; текущая отметка пересчитывается для оставшегося состава. Полностью отменённая строка помечается отменённой, чекбокс недоступен; замена блюда создаёт самостоятельную строку без унаследованной выдачи.
- Отметки **не запрещают дозаказ, оплату, полную отмену или закрытие заказа/смены**, не списывают деньги и не освобождают стол. Оплата сохраняет текущую семантику завершения, даже если не все отметки стоят.
- В деталях завершённой продажи показывать историю выдачи только для чтения. Отдельная очередь оплаченных, но не выданных заказов и редактирование выдачи после расчёта не входят в этот этап; текущую видимость COUNTER до ручного скрытия сохранить.

## 7. Общие ограничения и порядок реализации после согласования

- Все новые данные — Local POS Server; работа без внешнего интернета, прежние проверки активной смены и прав. При недоступном сервере не показывать успешное сохранение.
- Применять единые всплывающие сообщения справа на 1,5 секунды; для потери связи и неизвестного результата операции сохранять постоянный понятный статус/восстановление. Добавление обычного и неизвестного товара — без success-toast.
- Не вводить статусы «Готовится/Готов» на основании чекбоксов. Не менять общий счётчик заказов смены.
- Миграции схемы выполнять штатным защищённым механизмом; не мигрировать рабочую базу с открытой сменой. QA — изолированный профиль, рабочие базы и настройки MANGO не затрагивать.
- Сначала серверная модель и миграции TABLE без стола, произвольных строк и выдачи; затем API/драфты/события; затем единая корзина и интерфейс. Сохранять совместимость прежнего редактора и вида «Столы сначала».

## 8. Критерии приёмки

1. SVG и немедленный переход режимов работают; непустая корзина сохраняется, сборы меняются по серверному quote, принятый тип заказа не преобразуется.
2. TABLE без стола создаётся без фиктивного стола и COUNTER, доступ ограничен STRICT/SHARED, заказ виден в активных и блокирует закрытие смены. Поздняя привязка конкурентно занятого стола безопасно отклоняется.
3. Неизвестная позиция валидируется сервером, правильно участвует в количестве, скидке, сборах, оплате/возврате и никогда не печатается на кухне. Подмена прав/цены/комментария отвергается.
4. Обе карточки открываются в той же корзине; история сворачивается, новый пакет изолирован, повтор команды не дублирует заказ, номер, пакет или печать.
5. Несколько черновиков не смешиваются; поиск, категории, переходы и перезапуск не теряют их; смена сотрудника соблюдает изоляцию.
6. Отметки выдачи сохраняются между клиентами и после перезапуска, защищены правами и ревизиями; не влияют на дозаказ и финансовое завершение. Проверены количество >1, повтор, снятие, корректировка и полная отмена строки.
7. Проверены потеря ответа submit/settlement, отключение Local Server и одновременное закрытие заказа другим клиентом. Неподтверждённые действия не выглядят успешными.
8. Серверные тесты контрактов/денег/доступа/миграций, статические проверки Desktop и UI QA на 1366×768 и 1920×1080; диалоги с виртуальной клавиатурой без переполнения. Физическая Windows-печать и сенсорная приёмка фиксируются отдельно от программных тестов.
