# BASHKAR.KG — ТЗ 4.2: черновик TABLE, пакеты заказа и задания кухни

Дата: 22.10.2026. Версия: 1.0. **Статус: утверждено пользователем «Подтверждаю начинай»; реализовано в исходном коде и проверено локально.**

## 1. Цель и основания

Сотрудник собирает локальный черновик для доступного посещения, явно подтверждает условия и отправляет первый пакет либо дозаказ. Сервер атомарно принимает позиции, создаёт/обновляет один заказ посещения и сохраняет необходимые задания кухни. Неопределённый результат восстанавливается по исходной команде без дубля.

Источники и трассируемость:

## 2. Текущее состояние и границы

Есть Local POS Server, CommandBus, auth, смена OPEN, опубликованное меню/стоп-лист, точный расчёт, TABLE-зоны/посещения/STRICT/SHARED и EMPTY-закрытие. Desktop хранит сессию и pending-команды зашифрованно в main process. Есть тестовые расчёты QUOTE_ONLY, но нет принятых заказов/пакетов, сохранённых операционных черновиков и очереди кухни.

Расхождение, исправляемое этим подэтапом: `modules/menu/pricing.ts` сейчас допускает комментарий до 2000 UTF-16 единиц; CORE/BE-ORD-008 требуют до 300 символов. Операционный ввод и общую проверку quote следует привести к 300 символам, не изменяя исторические записи.

Включить:

- Desktop RU/KY: меню для выбора, локальный черновик, серверное предварительное подтверждение, первый пакет/дозаказы, история принятых пакетов, отдельная фиксированная скидка, видимый статус задания кухни.
- Backend/SQLite: один TABLE Order на посещение; неизменяемые Batch/Item; fee snapshots; текущие агрегаты/revision заказа; discount events; постоянные KITCHEN jobs; аудит/outbox/результат команды.
- Надёжное сохранение и восстановление черновиков и неизвестных результатов в Desktop.

Не включать: Payment/Settlement, возвраты, COUNTER, отмену/замену принятых строк, перенос столов/пакетов, передачу ответственного, полное закрытие смены, облачную синхронизацию, Waiter Web, LAN/HTTPS/WSS, драйвер/worker/физическую печать, перепечатку и перенаправление принтера. Эти части требуют своих контрактов/проверок. Сохранение outbox не является доставкой в облако.

**Практическое ограничение:** после первого принятого пакета посещение нельзя закрыть через EMPTY. До следующего финансового подэтапа оно останется открытым. Разработка и QA 4.2 идут на одноразовых стендах; не активировать такие заказы в рабочем ресторане и не обходить ограничение SQL-очисткой.

## 3. Предлагаемый UI для утверждения

### 3.1. Рабочий экран посещения

Из доступной карточки стола открыть экран заказа: вверху стол/зона, открывший, ответственный, текущая смена; ниже две явно разделённые части «Принято» и «Черновик».

«Принято»: пакеты по порядку, автор/время каждого, строки со снимками названий/размера/модификаторов/комментария и суммы. Общий подтверждённый итог заказа отдельно: товары, одна фиксированная скидка, каждый сохранённый сбор и итог. Номер пакета показывается в UI/истории, не на бумажном KITCHEN-документе.

«Черновик»: каталог по категориям и поиск по доступным названиям; выбор товара открывает размер, группы модификаторов, количество и комментарий. Недоступные товары/опции обозначены и не выбираются. Пустое опубликованное меню не заменяется демонстрационным.

Изменение языка не меняет выбранные ID, комментарии и историю. Снимки хранят исходное название и доступные переводы; отображение использует существующий fallback языка меню. RU/KY — языки интерфейса, не ограничение языка данных.

### 3.2. Редактирование черновика

Каждая строка имеет локальный UUID. Количество, размер, модификаторы и комментарий можно менять; строку можно удалить. Новое добавление создаёт отдельную строку: автоматического объединения, способного смешать пожелания гостей, нет. Разные комментарии/варианты всегда остаются разными строками.

Показывать «Черновик — не принят» и состояние локального сохранения. Расчёт при подборе ориентировочный; подтверждённый счёт не меняется. Перед отправкой сервер возвращает точный расчёт.

Переход к другому столу сохраняет черновик прежнего посещения. Возвращение восстанавливает его только для того же сотрудника/устройства/филиала/экземпляра/посещения. «Очистить черновик» — отдельное подтверждение. При закрытии пустого посещения с локальными строками предупредить об их потере; неизвестную отправку сначала разрешить.

### 3.3. Отправка первого пакета и дозаказа

«Проверить и отправить» доступно для непустого сохранённого черновика при доступном сервере и нужных правах. Открывается подтверждение: все строки и комментарии, сумма новых товаров, текущий подтверждённый итог и итог заказа после добавления, скидка и сборы отдельными строками. Для первого пакета виден фиксируемый набор сборов, в том числе отсутствие сборов.

Кнопка окончательного действия: **«Принять пакет»**. Подпись поясняет: приёмка сохраняет заказ и задание кухни; фактическая печать проверяется отдельно. В этой поставке постоянное заметное сообщение: **«Печать не подключена. Задания кухни сохраняются в очереди»**. Не показывать «напечатано»/«на кухне» как подтверждённый факт.

На время отправки зафиксированный черновик нельзя редактировать или отправлять второй новой командой. После commit показать принятый пакет; убрать из активного черновика только соответствующую сохранённую редакцию. Последующий набор создаёт новый Draft/Batch того же Order.

Если сервер сообщает новые цены/условия, не принимать пакет автоматически: сохранить черновик, показать сравнение было/стало, обновлённые недоступные позиции и дать повторное явное подтверждение. Недопустимую строку сотрудник исправляет или удаляет сам; частичного принятия нет.

### 3.4. Неизвестный результат, закрытие и отзыв доступа

При timeout/разрыве/неопределённом 5xx: «Результат неизвестен», исходный пакет заморожен, кнопка **«Проверить исходную отправку»** повторяет тот же ID и точное тело. Новый пакет из этого же черновика заблокирован до разрешения. Не повторять отправку автоматически после восстановления связи.

Если исходная команда принята — восстановить успех; если достоверно отклонена без commit — вернуть редактирование. Отказ в доступе не доказывает отсутствие прежнего commit: сохранить pending и показать необходимость восстановить доступ, без создания нового ID.

Если посещение закрыто/право отозвано, скрыть недоступные подробности, остановить новые операции. Локальный черновик не переносить в новое посещение этого же стола и не удалять молча. После повторного входа разрешать доступ только владельцу черновика при действующих правах.

### 3.5. Фиксированная скидка и очередь кухни

На доступном заказе с `order.discount.set` — отдельная форма фиксированной суммы в сомах/тыйынах, явное подтверждение старого/нового значения и итогов. До первого пакета скидка задаётся в черновике и фиксируется при приёмке; после — отдельной серверной командой с order revision и аудитом. Начальное значение 0. Процентных и построчных скидок нет.

У пакета отображать «Не требуется» при отсутствии кухонных строк либо «Ожидает печати — печать не подключена» для PENDING job. Состав задания доступен только при доступе к исходному посещению; название экрана не даёт новых прав. Полноценную панель управления принтерами не добавлять.

## 4. Права и серверная область

Добавить `table.batch.submit` и `order.discount.set`: включены по умолчанию Owner/Manager/Cashier/Waiter согласно AUTH-001 §6.3; могут отзываться в допустимом диапазоне. Действующие overrides, ролевые запреты и ограничения делегирования Manager сохраняются. Прежние права не сбрасывать миграцией.

Просмотр заказа/пакетов/jobs требует `table.view_details` и доступа к конкретному посещению по действующему TableService. Подготовка и приёмка требуют `table.batch.submit` и того же объектного доступа; изменение скидки — `order.discount.set` и объектного доступа. Ненулевая скидка первого пакета дополнительно требует это право; отправка нового пакета к заказу с уже установленной скидкой не считается её изменением.

STRICT/SHARED и `table.access_others` применяются одинаково в reads, quote, commands и replay. Owner не получает неявного обхода. Автор каждого Batch определяется сессией сервера; opened_by и responsible_waiter не меняются. Нельзя передать branchId/actorId/role/признак принятия/ставки/цены как авторитетные данные.

Сессия и парольные ограничения проверяются на каждой защищённой операции; фоновые опросы не продлевают idle. Отзыв доступа после уже сделанного commit не разрешает утечку результата через replay.

## 5. Бизнес-правила заказа и расчёта

1. До первой успешной непустой приёмки Order отсутствует. Первый Batch создаёт ровно один TABLE Order; дальнейшие Batch принадлежат ему. Уникальность — в SQL и транзакции.
2. Для новой приёмки нужны OPEN-смена, то же посещение в той же смене, OPEN-посещение и заказ, допускающий добавление. Закрытие/EMPTY и приёмка сериализуются одной моделью записи.
3. Проверять все строки целиком: опубликованное меню, архив/стоп-лист, принадлежность размера/опций товару, доступность, min/max, уникальность опции, количество и переполнение. Клиентская цена не является источником истины.
4. Снимки Item: товар/название/переводы, размер и его конечная цена, модификаторы с названиями/ценами, base/unit/line amount, количество, комментарий, menu revision, kitchen flag, источник Batch, время. Batch хранит фактического отправителя и снимок его имени. Предыдущие строки не пересчитываются по новому меню.
5. При первом Batch фиксируются имена и ставки активных TABLE-сборов, а также revision настройки, включая явный пустой набор. Поздняя смена настройки влияет лишь на новые заказы. Дозаказ и скидка пересчитывают суммы по сохранённым ставкам.
6. `S` — сумма подтверждённых исторических строк; `D` — одна фиксированная скидка `0≤D≤S`; `B=S−D`; каждый сбор независимо `ROUND_HALF_UP(B×rate/10000)` при rate в сотых процента; `T=B+ΣF`. BigInt для промежуточных значений; деньги — integer tyiyn. Не складывать предварительно округлённые «сборы пакетов» вместо пересчёта всего заказа.
7. Сумма Batch — сумма его новых товарных строк до общей скидки/сборов; это не отдельная оплаченная продажа. Агрегаты Order и новая revision обновляются в той же транзакции. Нельзя суммировать totals всех исторических состояний заказа.
8. Положительное количество при нулевой цене допускается. Нулевая стоимость принятого пакета не делает посещение EMPTY и не создаёт автоматический Settlement/Payment или закрытие.
9. Нельзя редактировать/удалять принятый Batch/Item/снимки. Исправления — будущие отдельные корректировки с правами. Изменение скидки записывает before/after/actor/time и не переписывает снимки строк.

Технические пределы: существующие цена/итог ≤999999999 тыйынов, количество 1–9999, ставки 0–10000 сотых процента, сумма ставок ≤10000. Максимум 1000 строк одного пакета — сохранить предел текущего quote. Итог проверять для всего накопленного заказа, не только нового Batch; отказ по лимиту не оставляет частичных записей. Искусственного бизнес-лимита на число пакетов посещения не вводить; чтение истории — постраничное.

Комментарий: простой текст, максимум 300 Unicode code points, RU/KY и другие обычные символы; CRLF привести к LF, управляющие команды/ESC/NUL отклонять, перенос LF разрешён. Проверять после нормализации. В UI вставлять как текст, не HTML. Сохранённый комментарий не меняет цену; печатный адаптер в будущем обязан отдельно безопасно кодировать его для принтера. Конкретное Unicode-считание — техническое предложение этого ТЗ.

## 6. Предлагаемый API и защита подтверждения

Пути относительно `/api/v1`; существующая Authorization, loopback/Host/Origin/JSON защита и строгие DTO сохраняются. LAN или browser CORS не открывать.

| Метод / путь | Назначение |
|---|---|
| GET `/tables/visits/:id/order` | Order либо null, подтверждённые итоги/revision и небольшая первая страница Batch |
| GET `/tables/visits/:id/batches?after=…&limit=…` | История по серверной последовательности, snapshot-строки и ссылки/статусы jobs; рекомендуемый limit 20, максимум 100 |
| POST `/tables/visits/:id/batches/prepare` | Read-only пересчёт для подтверждения; ничего не принимает/не резервирует |
| POST `/tables/visits/:id/batches/submit` | Идемпотентная приёмка целого пакета |
| POST `/orders/:id/discount` | Идемпотентная CAS-команда изменения фиксированной скидки |
| GET `/tables/visits/:id/kitchen-jobs` | Сохранённые jobs этого посещения, доступ по TableService; без команд физической печати |

Prepare: draftId/draftRevision, выбранные строки с local lineId, ожидаемая menu revision; для первого пакета — предлагаемая фиксированная скидка, для существующего — текущий Order. Ответ содержит авторитетные новые строки/цены, текущий order revision (0 при отсутствии), итог после добавления, набор сборов, revision меню и `confirmationHash`.

Рекомендуемый `confirmationHash` — SHA-256 канонического полного серверного предложения: branch/actor/session, draftId/revision/line IDs и selections, menu revision, существенные снимки/доступность выбранных строк, order revision, существующая скидка, применимый набор сборов и новые суммы. Хеш не является credential, авторизацией или резервом цены. Клиент отображает именно это предложение.

Submit: commandId, тот же draftId/revision и неизменные selections, menu revision, ожидаемый order revision, first-order discount при отсутствии Order, confirmationHash. Внутри writer повторно вычислить предложение из текущих серверных данных и сравнить. Изменение цены/редакции/сборов первого заказа/скидки/состава заказа → `CONFIRMATION_STALE` 409 без записи, с безопасным актуальным предложением при сохранённом доступе. Недоступная строка → отклонение всего пакета. Нельзя принять старую клиентскую сумму или молча изменить условия.

Prepare после изменения цены возвращает информацию для явного сравнения/подтверждения. Даже изменение меню между prepare и submit обнаруживается. Консервативный конфликт всей menu revision допустим; UI сохраняет черновик. Транзакция не ждёт решения сотрудника.

Успех Submit: минимальный receipt {commandId, sessionId, orderId, batchId, batchSequence, orderRevision, kitchenJobIds}. Подробный состав/актуальный итог перечитывается защищённым GET; это не Payment/Settlement. Для скидки: commandId, expectedRevision, amount; результат orderId/revision, история before/after и полный серверный перерасчёт.

Основные новые ошибки: `EMPTY_BATCH`/`INVALID_COMMENT`/`INVALID_LINES` 400; `CONFIRMATION_STALE`, `ORDER_REVISION_CONFLICT`, `ORDER_NOT_OPEN`, `SHIFT_REQUIRED`, `VISIT_CLOSED`, недоступность товара/опции и лимиты — предметный отказ без commit; `VISIT_ACCESS_DENIED`/`PERMISSION_DENIED` 403; объект вне филиала не выдаёт подробностей. Существующие `COMMAND_ID_CONFLICT`, `STORAGE_BUSY`, `WRITE_QUEUE_FULL`, ошибки сессии и сохранности остаются. Точные денежные коды сохраняют текущую семантику валидатора, не переименовываются ради нового экрана.

## 7. Транзакция, конкуренция и повтор

Все изменяющие операции — через существующий branch-scoped CommandBus/BEGIN IMMEDIATE. Внутри транзакции: актуальная авторизация → проверка journal/fingerprint → для новой команды проверка состояния/подтверждения → создание/обновление Order → Batch/Items/Modifiers → fee snapshot при первом → монотонный `table_sessions.has_accepted_batch=1` с revision+1 → KITCHEN job/items при необходимости → аудит/outbox → минимальный результат команды → commit → HTTP success.

Не выполнять HTTP, принтер, ожидание пользователя и асинхронные действия внутри SQLite-транзакции. Сбой на любом участке откатывает весь набор. Повтор прежнего ID с тем же actor/type/payload возвращает исходный receipt после проверки текущих прав/объектного доступа, без повторной проверки цен или состояния OPEN, способной спрятать уже сделанный commit. Иной payload того же ID → конфликт.

Два независимых пакета не теряются и не заменяют друг друга. При изменившейся order revision второй получает конфликт подтверждения, повторно готовится и явно подтверждается; после этого оба могут быть приняты последовательно. Две первые отправки не создают два Order. Одинаковый command ID даёт один Batch/job. Порядок пакетов определяется серверной последовательностью, не временем клиентского устройства.

Гонка EMPTY/submit: EMPTY первым — пакет отклонён; submit первым — защитный признак запрещает EMPTY. Нулевые суммы и будущее удаление действующих строк не обнуляют факт принятого пакета.

При достоверном отклонении без commit и изменении условий сформировать новую попытку с новым ID после исправления/подтверждения. При неизвестном результате **нельзя менять тело или ID**. После отзыва права pending сохраняется; невозможность повторить по правам не означает отсутствие принятого заказа. Retention успешных команд текущего D03 не сокращать; восстановление из старой копии остаётся отдельным D11 и не получает новых обещаний exactly-once.

## 8. Локальные черновики Desktop

Рекомендация: отдельное защищённое native-хранилище в main process через Electron safeStorage; renderer обращается только через whitelist IPC. Это конкретизация для Desktop. Требование IndexedDB из CORE относится к браузерному/мобильному клиенту; Waiter Web здесь не подменяется Desktop.

Ключ: server instance + branch + employee + device/profile + tableSession + draftId. Не связывать только с номером стола. Хранить revision, local line IDs/selections/comments, состояние отправки, неизменный frozen payload/commandId для pending. Не хранить пароли, облачные credentials или произвольные исполняемые данные.

На каждое изменение — сериализованное сохранение версии; UI показывает успешное сохранение только после записи. Защита от старой асинхронной записи: CAS/revision и единый writer. Один активный Desktop на профиль либо блокировка второго writer; нельзя получить два независимых процесса, перетирающих черновик. Недоступное protected storage/повреждение/полный диск не заменять молча пустым: показать ошибку, запретить отправку несохранённой редакции, сохранить имеющиеся файлы. Нативное сохранение должно исключать частично записанный финальный файл; интерфейс не обещает аппаратную power-loss гарантию без испытаний.

Pending и черновик связать durable commandId до сети. При падении между commit, ответом и очисткой черновика после рестарта сопоставить исходный frozen draft revision/commandId с результатом. Очищать только принятую редакцию; сбой очистки не должен давать возможность отправить её как новый пакет. Не допускать редактирование frozen-редакции до разрешения исхода.

При выходе/смене сотрудника черновики сохраняются за прежним сотрудником, но не выдаются новому. Чтение/запись IPC проверяет текущую сессию и предметный доступ; renderer не задаёт путь файла/actor/branch. Восстановленный черновик требует нового серверного подтверждения, а не старой сохранённой цены. Автоматической отправки и синхронизации между устройствами нет.

## 9. SQLite и задания кухни

Планируется отдельная миграция **005-orders-batches**, schema 5, без изменения 1–4. Конкретный SQL следует контрактам, а не названиям таблиц из предварительного проекта.

| Сущность | Минимальное содержание / ограничения |
|---|---|
| orders | branch/shift/session/type TABLE, OPEN, revision, discount и рассчитанные агрегаты; UNIQUE branch+table_session; scoped FK к посещению/смене |
| order_batches | order/session/branch, sequence, commandId, sender ID/name/time, menu revision, сумма новых товаров; UNIQUE order+sequence и branch+commandId |
| order_items / order_item_modifiers | Исторические snapshots и происхождение Batch, local lineId; положительное количество; суммы integer; никаких joins к текущему меню ради исторической цены |
| order_fee_snapshots | Сохранённый набор имён/ставок первого Batch; отсутствие сборов тоже зафиксировано на Order |
| order_discount_events | Отдельная история назначения/изменения скидки, before/after/actor/time/command; первоначальная ненулевая скидка также имеет событие |
| print_jobs / print_job_items | KITCHEN + назначение NEW_BATCH, snapshotVersion, branch/order/session/batch, внутренний batchSequence, payload только кухонных строк, status PENDING; UNIQUE источник+назначение для одного логического направления |

Защитить scoped FK, обязательность происхождения и неизменяемость принятых фактов SQL-ограничениями/триггерами. Агрегаты Order пересчитывать только с revision и историей команды; не замораживать весь Order, мешая разрешённым дозаказам/скидке. Индексы по branch/session/order/sequence. Историю не удалять штатным API.

Один логический KITCHEN job на кухонный поднабор Batch; пустой поднабор не создаёт job. Физический принтер не назначается фиктивным ID. Будущая маршрутизация по принтерам — отдельное расширение, не причина отправлять принтеру весь смешанный Batch.

Payload: стол/зона, время отправки, фактический отправитель, только kitchen Items с количеством/размером/модификаторами/комментариями и ссылками на исходные снимки. Внутренние batch IDs/sequence нужны для трассировки, но номер Batch не включать в бумажные строки. Формат бумаги, кодировка и ESC/POS пока не формируются.

Этот подэтап создаёт и читает только PENDING. Не добавлять переходы в COMPLETED/SENT/FAILED_SAFE/UNKNOWN без worker и D06/PRINT-001. Разные предварительные enum CORE и BACKEND не смешивать в фиктивную «готовую печать». UNKNOWN никогда не повторяется автоматически; SENT не доказывает выход бумаги — обязательные ограничения будущего адаптера. Аппаратная часть остаётся OPEN, полная готовность этапа 4 не заявляется.

## 10. Обновление существующих стендов

Сохраняется обычный отказ `SCHEMA_UPGRADE_REQUIRED` без автоматической миграции. Явная миграция — только остановленная изолированная установка по существующим правилам, с сохранением identity и проверкой структуры/checksums. Pending upgrade при OPEN-смене запрещён.

MANGO/macOS, MANGO—Windows и архив iteration-002 не обновлять автоматически. Открытую смену не закрывать SQL, не удалять базы/marker/key и не подменять архив под прежним именем. Для QA создать новые одноразовые данные; настоящий облачный филиал нужен лишь для отдельного real-cloud прогона, если он будет согласован. Синтетическая активация допустима только явно изолированным harness, не в production entrypoint.

Проверить миграцию schema 4 без OPEN и отказ при OPEN без изменения данных. Будущий Windows-пакет выпускать под новым именем с manifest/checksum; не называть старый ZIP проверкой новых заказов.

## 12. Приёмка

| Группа | Обязательный результат |
|---|---|
| Первый/следующие пакеты | Открытие не создаёт Order; первый непустой создаёт один; дозаказ добавляет Batch к нему; отправители различаются, ответственный неизменен |
| Снимки | Старые строки/комментарии/цены/кухонный признак неизменны после публикации меню, стоп-листа и смены режима |
| Сборы/скидка | Набор фиксируется первым Batch; дальнейшие суммы от общего B по прежним ставкам; скидка одна, CAS+audit; нулевые цены и лимиты корректны |
| Атомарность | Искусственный сбой при Item/job/audit/outbox/result не оставляет ни Order, ни Batch, ни защитного признака; последующий успешный повтор допустим |
| Конкурентность | Первые параллельные пакеты — максимум один Order; нет потерянного Batch; EMPTY против submit; публикация меню/стоп-лист/скидка против submit |
| Повторы | Один ID → один Batch/job; иной payload → конфликт; потеря ответа, рестарт сервера и Desktop не создают дубль; старый frozen Draft не отправляется новым ID |
| Права | Все роли/defaults/revokes/Manager restrictions; чужой branch/visit/batch/job/draft недоступен; STRICT/SHARED меняется между prepare и submit; replay не обходится через старое право |
| Комментарии | 300/301 Unicode символов, RU/KY, разные пожелания отдельными строками; HTML/ESC не исполняются; комментарий не меняет сумму |
| Черновики | Восстановление точного scope, смена сотрудника, закрытый и новый visit одного стола, потеря соединения, сбой сохранения, гонка редакций/второй writer, повреждённое storage без молчаливого сброса |
| Кухня | Смешанный Batch сохранён полностью; job только kitchen-строки, без предыдущего Batch; все non-kitchen → нет job; PENDING переживает restart; никакого ложного printed |
| UI | Выбор/редактирование/удаление Draft, явное подтверждение новых условий, UNKNOWN recovery, история/discount, раздельные суммы, RU/KY, отсутствие секретов в renderer/logs |
| Регрессия | Существующие auth/activation/menu/pricing/shift/table tests и Electron-сценарии сохраняются |
| Миграция | Новая установка/schema 4→5; checksum 1–4 неизменен; OPEN блокирует upgrade; identity/данные сохранены |

Доступно на macOS без нового облака/Windows: код, SQLite/API/отказные тесты, native safeStorage и настоящий Electron на изолированной fixture. Реальное облако/отключённый интернет, Windows-служба/DPAPI/ACL, целевой POS 4 ГБ, router/телефоны, реальный принтер и power loss отмечаются отдельными результатами только после проведения.
