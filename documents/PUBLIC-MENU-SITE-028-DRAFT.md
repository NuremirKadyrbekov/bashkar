# PUBLIC-MENU-SITE-028 — публичное меню филиала и вход по ссылке стола

**Статус:** 01.11.2026 Cloud-миграция `20261101000400_public_menu.sql`, Edge `menu-sync` и `public-menu`, адаптивный сайт и переключатель Owner реализованы. Сайт опубликован на `https://bashkar-menu.gigglycomet1.chatgpt.site`; маршруты филиала и стола отвечают HTTP 200. Публикация тестового филиала пока выключена, полный URL/QR в POS ещё не подключены. Реальный каталог в опубликованном браузере ожидает включения Owner и сквозной проверки.
**Связано:** [TABLE-PUBLIC-LINKS-027](TABLE-PUBLIC-LINKS-027-DRAFT.md), [API-MENU-SYNC-012](API-MENU-SYNC-012.md), [TABLES-ZONES-MAP-026](TABLES-ZONES-MAP-026-DRAFT.md).

## 1. Решение и порядок работ

Сначала создать **один публичный сайт меню**. У каждого филиала на нём одна опубликованная версия меню, приходящая из базы Bashkar через контролируемую синхронизацию. Затем подключить к сайту конкретные филиалы и их столы. Ссылки всех столов одного филиала открывают **одинаковый каталог**; код стола задаёт только контекст («Вы за столом № …») и пригодится для будущего заказа. Сайт и отдельные меню не копируются на каждый стол. Названия и переводы, описания, фотографии и цены выводятся из опубликованных данных филиала, без вручную заполненного каталога в коде сайта.

Маршруты одного сайта:

| Адрес | Содержимое |
|---|---|
| `/b/{branchId}` | Публичное меню филиала без выбранного стола. |
| `/b/{branchId}/t/{tableCode}` | То же меню и подтверждённый сервером стол этого филиала. |

Прямой вход на `/b/{branchId}` нужен для проверки сайта до подключения столов. В будущем переход по ссылке стола создаст гостевой контекст, но сейчас не отправляет заказ. Другой филиал выбирает другое меню по `branchId`.

## 2. Откуда берётся меню

Источник текстов и цен — **опубликованный каталог, реально применённый локальным сервером филиала**, а не черновик, произвольный последний Cloud head или тестовые данные. В проекте уже есть `menu_revisions`/`menu_current` и Cloud-синхронизация нормализованного каталога. Cloud-версия может быть архивирована или ожидать локального применения; поэтому публичный сайт использует отдельный branch-scoped `public_menu_snapshot` с `branchId`, `versionId`, `localRevision`, `contentHash`, `publishedAt`, `appliedAt`, `publicUpdatedAt`, `catalog` и статусом публикации. Снимок записывается только после подтверждения, что именно эта версия применена филиалом, и с проверкой hash/версии. Более старая или конфликтная доставка не перезаписывает новый публичный снимок. Фото присоединяются при публичном чтении из отдельных Cloud-таблиц по `(branchId,itemId)` и имеют независимую `photoRevision`.

Для филиала требуется явное включение «Показывать меню на сайте» уполномоченным Owner. До включения, без применённого опубликованного каталога или при ошибке проверки сайт показывает понятное состояние «Меню пока недоступно». На странице персонала видны версия, время последнего обновления и ошибка/ожидание синхронизации. Если локальный сервер временно офлайн, сайт может показывать **последний подтверждённый снимок** с отметкой времени, но не заявляет текущую доступность блюд и не принимает заказ.

Общий каталог содержит категории, товары, описания, переводы, варианты, модификаторы, наборы и цены по текущей схеме `catalog.ts`. Публичная проекция скрывает архивные категории/товары, упаковочные служебные позиции и внутренние поля (`kitchen`, author, device, drafts и др.). Для матричных цен брать реальные допустимые комбинации; если без выбора невозможно назвать одну цену, показывать «от X» по минимальной доступной комбинации, затем точную цену после выбора. Цены хранятся в тыйынах и форматируются в сомах без чисел с плавающей точкой. Оперативный стоп-лист сейчас не входит в menu-sync; до отдельной синхронизации доступности публичный сайт не обещает, что позиция есть в наличии.

**Открытый вопрос после MVP:** формат состава сета на публичном сайте и в операционной работе определить после разговора с рестораном. Текущий связанный состав сохраняется; ручной текстовый состав не утверждён. Вопросы для ресторана и границы будущего решения — в [MENU-SETS-001 §13](MENU-SETS-001.md#13-открытый-вопрос-после-mvp--способ-ведения-состава-сета).

### Поля меню, которые сайт получает из данных

| Поле сайта | Источник и правило |
|---|---|
| Название категории, блюда, варианта и модификатора | `name` и `translations` опубликованного каталога. Язык берётся из `catalog.languages`; если перевода нет, показывать основное название, не машинный перевод. |
| Описание блюда | Сейчас есть только одно поле `description`. Добавить в модель и редактор `descriptionTranslations` по тем же языкам; при отсутствии перевода использовать основное описание. Пустое описание скрывать. |
| Цена | `price`, цена варианта/модификатора или конкретной `combinationPrices` из опубликованного каталога. Никаких цен в коде сайта; цена и валюта форматируются из целого количества тыйынов. |
| Фото блюда | Владелец/кассир загружает из Desktop или владелец из удалённого кабинета напрямую в Cloud media API; связь `(branchId,itemId) → assetId` и ревизия хранятся только в Cloud-таблицах, файл — только в Bunny Storage. Local Server не получает байты, локальный каталог фото не содержит. Отсутствие фото показывать нейтральной заглушкой, не случайной картинкой. |

Для фотографий **Cloud-БД** хранит связь с филиалом и товаром, идентификатор файла, тип, размер, размеры изображения и историю изменений; оптимизированные файлы хранятся в **Bunny Storage** и выдаются через Bunny Pull Zone. Байты и метаданные фото не хранятся в локальном POS, его JSON каталога или SQLite. Desktop отправляет файл напрямую в доверенный Cloud media API по короткоживущему разрешению, выданному Local Server после проверки права; удалённый Owner использует Cloud Auth. Local Server не принимает байты. Публичный API выдаёт адрес только подтверждённого фото своего филиала; замена получает новый путь, чтобы кеш не показывал старую картинку. Описания и цены следуют ревизии локального каталога, фото — независимой Cloud-ревизии. Подробный контракт — [MENU-PHOTO-DESCRIPTION-029](MENU-PHOTO-DESCRIPTION-029-DRAFT.md).

## 3. Сайт и публичный API

- Адаптивная страница для телефона в первую очередь: название филиала, категории, поиск, карточка блюда с фото, переведённым названием и описанием, ценой, вариантами/модификаторами и переключением доступных языков каталога (RU/KY по возможности данных). Пустое меню, отсутствие сети, загрузка и ошибка — отдельные состояния.
- Сайт читает только публичную проекцию через серверный/Edge API по `branchId`. Браузер не получает служебный ключ, токены POS, доступ к таблицам заказов, сотрудников или черновиков. Разрешены только опубликованные поля; произвольный ID версии/филиала не даёт доступа к приватному каталогу. API возвращает `menuVersionId`, `photoRevision`, `updatedAt` и кеширует по этой паре; после новой применённой версии каталога или изменения фото кеш инвалидируется.
- Для ссылки стола публичный API разрешает `(branchId,tableCode)` только после синхронизации реестра столов, проверяет активность стола и зоны и возвращает публичные `tableName`, `zoneName`, `tableId` для внутреннего контекста страницы. Код не принимается как подтверждение присутствия гостя. Неизвестный/отключённый стол получает состояние «Стол недоступен» и не может создать заказ. Никаких подробностей текущего посещения гостю не раскрывать.
- Оба маршрута филиала получают **один `public_menu_snapshot` и один Cloud-манифест фото по `branchId`**. Табличный маршрут не создаёт и не меняет копию меню; при обновлении каталога или фото все столы видят новую пару версий после обновления/истечения кеша.

## 4. Подключение филиала и адреса

1. Разработать сайт и API на изолированном тестовом филиале; локальный preview может использовать тестовые данные, явно отмеченные как тестовые. До подключения рабочего филиала не показывать его Cloud-историю через публичный API.
2. Разместить сайт на стабильном публичном HTTPS-адресе хостинга. Собственный домен можно подключить позже; до готовности постоянного адреса QR для печати не создавать. Если печатать QR на адресе провайдера, после смены домена поддерживать перенаправление с этого адреса.
3. Owner включает публичное меню своего филиала. Система проверяет соответствие `branchId` в реестре активации, статус применённой версии и синхронизации, публикует проверенный снимок. Отключение публикации закрывает публичное меню без удаления локального каталога.
4. После готовности меню подключить реестр публичных кодов столов по [TABLE-PUBLIC-LINKS-027](TABLE-PUBLIC-LINKS-027-DRAFT.md), включая существующие столы. Подтвердить полный снимок `(branchId,tableId,code,active,zoneActive)` и последующие изменения. Только тогда выдавать POS полные ссылки и QR на столы.

## 5. Заказ гостем — следующий этап

В этом ТЗ сайт **только показывает меню**. Корзина, гостевая сессия, подтверждение присутствия/одобрение персоналом, отправка в локальную кассу, кухня, оплаты и статусы заказа требуют отдельного API и отдельной приёмки. Публичный сайт не может напрямую вызывать локальный сервер по адресу ресторана. До подтверждения локальным сервером нельзя показывать «Заказ принят»; ссылка стола сама по себе не даёт доступ к чужим заказам.

## 6. Критерии приёмки по этапам

**A. Сайт меню:** тестовый филиал с опубликованным и локально применённым каталогом виден по `/b/{branchId}`; черновик, конфликтная/неприменённая Cloud-версия, архивные и служебные позиции не появляются. Новая подтверждённая версия обновляет страницу без ручного копирования меню. Названия, переводы описаний и цены изменяются через локальный редактор/БД; фото загружается из Desktop или удалённого кабинета через Cloud media API в Bunny и связывается в Cloud-таблицах. Изменение одного филиала не меняет другой. Проверить отсутствие перевода/фото, замену фото и кеш, варианты, матричные цены и точность тыйынов. Филиал без публикации недоступен; публичный API не раскрывает персонал, заказы и служебные ключи. Проверить мобильный экран, язык, пустые/ошибочные состояния.

**B. Подключение столов:** два стола одного филиала показывают одинаковые `versionId` и состав меню, но разные подписи стола; другое отделение имеет свой каталог. Переименование/смена зоны не меняет ссылку. Неизвестный, отключённый и перевыпущенный код не активирует гостевой сценарий. QR выдаётся только для работающего HTTPS-адреса.

**C. Заказы:** отдельное ТЗ после завершения A/B.

Миграции и проверки выполнять сначала на изолированном филиале/копии БД. Рабочий MANGO и его смену это ТЗ не меняет.

## 7. Реализация и включение

- `20261101000400_public_menu.sql` создаёт снимок после подписанного ACK применённой версии меню. Старый ACK не заменяет снимок с большей локальной ревизией. Публикация выключена по умолчанию; включить её может Owner через Desktop «Меню и Cloud» или удалённый кабинет через owner RLS.
- `public-menu` Edge Function отдаёт только очищенную публичную проекцию каталога и проверяет активность стола/зоны. Фото получает как URL Bunny по Cloud-связке; сервисный ключ остаётся в Edge. Ошибки отсутствующего или выключенного меню не раскрывают каталог.
- `apps/public-menu/dist` — мобильная страница для `/b/{branchId}` и `/b/{branchId}/t/{tableCode}`. Локальный предпросмотр: `pnpm run preview:public-menu` (порт 4175). Сайт читает `config.json` с публичным адресом API и publishable key; служебных ключей в нём нет.
- До выдачи полных ссылок и QR нужно включить публичное меню тестового филиала через Owner, проверить живой каталог и Bunny-фото на опубликованном сайте, затем настроить `publicBaseUrl` для POS. Гостевой заказ этим этапом не включается.
