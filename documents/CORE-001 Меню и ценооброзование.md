# 1. Назначение и цели

## 1.1. Назначение

Раздел определяет бизнес-правила каталогизации блюд и товаров, многоязычного представления меню, выбора платных и бесплатных вариантов, управления ценами и доступностью, публикации обновлений, локального/облачного редактирования и формирования достоверной суммы заказа.

Главная задача — сделать меню удобным для персонала и гостей и при этом гарантировать, что изменения ассортимента не искажают уже принятые пакеты, счета, отмены и финансовую историю.

## 1.2. Принципы

1. **Local-First:** Local POS Server хранит и применяет действующий каталог филиала; интернет не нужен для просмотра и принятия заказов по ранее применённому меню.
2. **Единые правила:** POS Desktop и Waiter Web Client используют одни цены, доступность и серверные проверки.
3. **Сохранение истории:** опубликованные изменения каталога не переписывают уже принятые Order Item и Order Batch.
4. **Прозрачная цена:** размер, платные модификаторы, скидка и дополнительные сборы рассчитываются и показываются отдельно в установленном порядке.
5. **Контролируемая публикация:** обновление каталога активируется целостной проверенной редакцией.
6. **Без скрытых конфликтов:** параллельные изменения через POS и Owner Dashboard не перезаписывают друг друга по принципу «последний победил».
7. **Минимум лишних действий:** ручные стоп-листы и доступность модификаторов работают быстро; сложные рецептуры и склад не входят в MVP.

## 1.3. Входит в раздел

- категории, блюда и товары; базовые карточки и архивирование;
- языки, переводы и локализация представления меню;
- размеры/варианты, модификаторы, правила выбора и ценообразования;
- ручная доступность товара и отдельных модификаторов;
- цены для TABLE и COUNTER, разделение по филиалам;
- редакции каталога, публикация и конфликты изменений;
- взаимодействие со скидками, сборами, кухней, пакетами, оплатами и отменами;
- полномочия, история, отказоустойчивость, критерии приёмки.

## 1.4. Не определяются здесь

HTTP API, структура SQL-таблиц, компоненты конкретных экранов, драйверы принтеров, механизм формирования переводов, интерфейс QR/NFC-меню и его срок выпуска, расширенная логика COUNTER, способы банковской оплаты, рецептуры и складская себестоимость.

# 2. Уже принятые зависимости от других разделов

- Один TABLE Session содержит один основной Order и несколько принятых Order Batch; COUNTER не создаёт Table Session.
- Draft может редактироваться до подтверждения; Order Batch и исторический Order Item после принятия нельзя бесследно изменять.
- При отправке пакета сервер проверяет товар, актуальную цену, модификаторы, активную смену, полномочия и идемпотентность.
- При расхождении цен устаревшего черновика сервер не повышает итог молча: сотрудник подтверждает актуальные условия.
- После полной оплаты TABLE автоматически закрываются посещение и стол; обычные изменения позиций и скидки прекращаются.
- Обычная оплата полная; смешанная оплата — единое завершение расчёта; частичные оплаты исключены.
- Скидка для MVP одна фиксированная сумма на весь заказ, изменяемая до оплаты; изменение истории скидки сохраняется.
- Дополнительные процентные сборы изначально отключены, применяются только к TABLE, на COUNTER не начисляются.
- Сохранение принятого пакета и необходимого задания печати не зависит от физической доступности принтера; в этом разделе уточняется, **когда кухонное задание требуется**.
- Корректировки принятых позиций фиксируются отдельными событиями; принятые пакеты не переписываются.
- Локальный сервер — источник операционной истины филиала, Supabase/Owner Dashboard получают его фактическое состояние через асинхронную синхронизацию.

# 3. Бизнес-сущности и логическая модель

| Сущность | Бизнес-значение | Примечание |
|---|---|---|
| **Menu Category** | Одноуровневая категория товаров | Без подкатегорий в MVP |
| **Menu Item** | Карточка блюда или товара | Уникальная логическая сущность филиала |
| **Menu Content Translation** | Локализуемые названия/описания блюда, категории, размера и модификаторов | Значение на основном языке обязательно; остальные переводы необязательны |
| **Menu Language** | Язык клиентского меню, включённый заведением | Базовые: русский, кыргызский, английский; возможно добавить другие |
| **Size Variant** | Вариант блюда с собственной конечной ценой базового изделия | Например 250/400 мл; выбор из группы размеров |
| **Modifier Group** | Группа допустимых дополнительных вариантов | Требования min/max и связь с блюдом |
| **Modifier Option** | Конкретная платная или бесплатная опция | Один вариант в одной позиции не выбирается многократно |
| **Menu Revision** | Проверенная редакция каталога конкретного филиала | Используется для последовательности и публикации |
| **Availability** | Текущая возможность заказывать блюдо/опцию | Ручное управление; не равна архивированию |
| **Menu Change / Conflict** | Предложенное изменение, его автор, происхождение, состояние применения или конфликт | Не самостоятельное изменение операционного заказа |
| **Fee Configuration** | Настройка именного процентного сбора для TABLE | Набор ставок фиксируется при первом принятом пакете TABLE |
| **Order Item Price Snapshot** | Исторический состав и цена принятой позиции | Защищён от заднего изменения каталога |

Это **логические понятия**, а не утверждённые таблицы базы данных. Реальная схема — DB-SCHEMA-001.

## 3.1. Отношения

**Branch → Menu Revision → Category → Menu Item → (Size Variants, Modifier Groups, Translations, Availability).**

Menu Item принадлежит ровно одной категории; у каждой товарной позиции есть собственная карточка и ID. Связи с историческими Order Item сохраняются после архивирования товара.

# 4. Структура каталога и карточка товара

## 4.1. Категории

- Только один уровень категорий, например «Горячее», «Напитки», «Десерты».
- Нет подкатегорий и неограниченной вложенности.
- Одно действующее блюдо находится в одной категории.
- Для практической навигации допускается управляемая последовательность показа категорий и товаров.

## 4.2. Карточка блюда или товара

Минимальная бизнес-информация:

- стабильный идентификатор и филиал;
- одна категория;
- основное название и основной язык;
- базовая цена для блюда без размерных вариантов **либо** доступные размеры со своими конечными базовыми ценами;
- необязательное описание и фотография;
- переводы названия/описания на дополнительные языки; названия категории, размеров и модификаторов также могут локализоваться;
- связанные модификаторы и допустимые размеры;
- состояние архивирования и доступности;
- необходимость кухонной печати (настройка «Готовится на кухне»);
- необязательная связь блюда с одним товаром-контейнером для предложения в COUNTER;
- версия последнего применённого изменения и история авторов.

Фото, рецепт, пищевая ценность и складские показатели **не являются обязательными данными MVP**.

## 4.3. Бизнес-правила каталога

**BR-MENU-001.** Меню каждого филиала имеет собственный каталог товаров и категорий.

**BR-MENU-002.** В MVP разрешён ровно один уровень категорий; подкатегории не создаются.

**BR-MENU-003.** Каждый действующий Menu Item принадлежит одной категории.

**BR-MENU-004.** У товара обязателен стабильный ID, основное название, ценовое основание и состояние доступности/архивирования; описание и фотография необязательны.

**BR-MENU-005.** Порядок показа категорий и товаров может управляться уполномоченным редактором и не изменяет цены или историю заказов.

**BR-MENU-006.** Категория с действующими товарами не должна бесследно исчезнуть, сделав эти товары некорректными; перед архивированием категории связанные позиции должны быть явно обработаны уполномоченным сотрудником. Точный UX обработки относится к POS-001/Owner Dashboard.

# 5. Многоязычность

## 5.1. Разделение языков интерфейсов

- **Внутренние интерфейсы POS Desktop и Waiter Web Client** поддерживают русский и кыргызский языки пользовательских элементов.
- **Меню для гостей, в том числе клиентское QR/NFC-меню**, предусматривает русский, кыргызский и английский, а ресторан вправе дополнительно включать нужные языки.
- Языки интерфейса сотрудников и языки клиентского меню — разные настройки.
- Для меню на основном языке обязательны названия показанных гостю категорий, блюд, размеров и модификаторов; переводы этих текстов на другие языки необязательны согласно M01=B.
- При отсутствии перевода любого гостевого элемента меню (названия категории, блюда, размера, модификатора или описания) показывается его значение на основном языке, если оно предусмотрено. Не предполагается автоматический машинный перевод.

**Важное уточнение:** при неполных переводах конкретное название блюда может отобразиться на основном языке даже тогда, когда у сотрудника выбран русский/кыргызский, а у гостя — другой язык. Это следствие M01=B, не ошибка расчёта цены. Интерфейсные подписи POS/Waiter при этом остаются на выбранном русском или кыргызском.

## 5.2. Бизнес-правила языков

**BR-MENU-007.** Гостевое меню предусматривает RU, KY, EN и возможность добавить другие языки по выбору ресторана.

**BR-MENU-008.** Обязательны названия на выбранном основном языке для элементов, видимых в гостевом меню (категории, товары, размеры, модификаторы); переводы этих элементов на остальные языки необязательны.

**BR-MENU-009.** Если перевод гостевого элемента меню на выбранный язык отсутствует, отображается значение на основном языке без выдуманного автоматического перевода.

**BR-MENU-010.** POS Desktop и Waiter Web Client поддерживают русский и кыргызский интерфейс; произвольное добавление языков для этих интерфейсов не входит в MVP.

**BR-MENU-011.** Переключение языка не изменяет ID товара, цену, размер, модификаторы, доступность или состав заказа.

**BR-MENU-012.** Переводы и основной язык должны быть доступны без интернета через применённый локальный каталог для соответствующих локальных интерфейсов.

**BR-MENU-013.** Обновление любого перевода не переписывает исторические снимки наименования уже принятого Order Item.

**BR-MENU-014.** Публикация новой редакции переводов проходит контроль версий и правил конфликтов, как и остальные изменения каталога.

**BR-MENU-015.** Поддержка переводов в данных не означает автоматическую реализацию всех расширенных возможностей клиентского QR/NFC-меню в MVP: границы выпуска такого интерфейса определяются отдельным документом в соответствии с ARCH-001.

# 6. Размеры и модификаторы

## 6.1. Различия понятий

- **Размер/вариант** — выбор одной конкретной базовой версии товара, например «Капучино 250 мл = 180 сом» и «Капучино 400 мл = 230 сом». Согласно M03=A, каждый размер имеет **свою конечную цену базового блюда**, а не прибавку к общей цене.
- **Модификатор** — дополнительный заранее настроенный выбор (например «Овсяное молоко +40 сом», «Без сахара +0 сом»), который может быть платным или бесплатным.
- **Комментарий** — свободный текст о пожелании гостя, не являющийся источником цены и не заменяющий структурированный платный модификатор.

Блюдо может не иметь размеров и модификаторов. Если группа размера настроена как обязательная, заказ без выбранного размера не принимается.

## 6.2. Группы модификаторов

- Группы могут быть обязательными либо необязательными.
- Для каждой группы устанавливаются допустимые минимум и максимум выбранных **различных** опций.
- Один и тот же вариант внутри одной позиции можно выбрать не более одного раза (Q07=A).
- Стоимость одной и той же логической опции может быть различной для разных блюд (Q08=B).
- При добавлении нескольких единиц одного блюда с разными вариантами или комментариями соответствующие комбинации сохраняются раздельными позициями.

## 6.3. Цена позиции

**Дополнение 24.10.2026 (согласованный MVP новых товаров).** Для вновь создаваемого товара разрешён режим полной цены комбинации: выбирается ровно один размер, если размеры заданы, и ровно один вариант из каждой дополнительной группы. Для каждой комбинации хранится самостоятельная конечная цена одной единицы. Размер и дополнительные варианты в этом режиме не добавляют к ней отдельную стоимость. Пустая цена недопустима, ноль указывается явно. Опубликованная комбинация имеет стабильный ID; её доступность можно менять отдельной командой стоп-листа с правом `menu.stoplist.manage`, не публикуя весь каталог. Старые опубликованные товары без указания нового режима продолжают рассчитываться по следующим ниже правилам сложения; они не преобразуются автоматически. Это решение закрывает `MENU-OPEN-005` для нового режима.

Для товара прежнего режима без полной цены комбинации при принятии пакета рассчитывается:

`Базовая цена единицы = цена выбранного размера либо цена блюда без размерных вариантов`.

**Только additive:** `Цена единицы с модификаторами = базовая цена единицы + сумма цен выбранных платных/бесплатных модификаторов`. Для MATRIX цена единицы берётся из выбранной комбинации.

`Стоимость позиции = цена единицы с модификаторами × количество`.

Бесплатный модификатор имеет цену 0. Избранный размер учитывается **вместо** базовой цены товара, а не дважды. Денежные значения не могут быть отрицательными. Процентные скидки на отдельные позиции не вводятся.

## 6.4. Бизнес-правила модификаторов

Правила о доплате и произвольных min/max ниже относятся к прежнему additive-режиму. Для новых MATRIX товаров действуют §6.2 и MENU-VARIANT-MATRIX-TECH-001: ровно один выбор из каждой группы, полная цена сочетания, максимум 64 сочетания; доплаты не складываются.

**BR-MENU-016.** В MVP поддерживаются заранее настроенные бесплатные и платные модификаторы и отдельные группы размеров.

**BR-MENU-017.** Группа модификаторов имеет допустимый минимум и максимум вариантов, проверяемые сервером при отправке пакета.

**BR-MENU-018.** Сервер отклоняет выбор, не удовлетворяющий обязательному минимуму или превышающий максимум группы.

**BR-MENU-019.** Один вариант модификатора нельзя выбрать несколько раз внутри одной позиции.

**BR-MENU-020.** Цена модификатора может зависеть от блюда; цена для конкретного блюда берётся из действующей проверенной конфигурации.

**BR-MENU-021.** Размеры одного блюда задаются как его варианты с самостоятельными конечными базовыми ценами; выбирается один применимый размер.

**BR-MENU-022.** Размер не оформляется как отдельный самостоятельный Menu Item исключительно ради различия в миллилитрах/массе, если это варианты одного блюда.

**BR-MENU-023.** Бесплатные варианты разрешены; выбор такого варианта не должен менять стоимость.

**BR-MENU-024.** Произвольный комментарий к блюду не может сам изменять цену заказа.

**BR-MENU-025.** Для additive цена единицы равна цене размера/блюда плюс выбранные модификаторы; для MATRIX берётся только конечная цена выбранного сочетания. Стоимость позиции равна цене единицы × количество.

**BR-MENU-026.** При сохранении принятой позиции фиксируются выбранный размер, модификаторы, их фактические цены, количество, итоговая сумма и редакция действовавшего каталога.

**BR-MENU-027.** После принятия пакета изменение текущей цены размера/модификатора в меню не изменяет сохранённую цену этой позиции.

**BR-MENU-028.** Платный модификатор ранее принятой позиции меняется только по согласованным правилам корректировки/замены, не путём тайного изменения исторического снимка.

**BR-MENU-029.** При групповых количествах блюда с различными модификаторами или комментариями каждая различающаяся конфигурация учитывается отдельно.

# 7. Нулевая цена и недопустимые суммы

**BR-MENU-030.** Для блюда или варианта допускается установленная цена **0 сом**; отсутствие заполненной цены не должно неявно интерпретироваться как ноль.

**BR-MENU-031.** Бесплатная базовая позиция может иметь платные модификаторы: их сумма рассчитывается обычным способом.

**BR-MENU-032.** Отрицательные цены блюда, размера и модификатора не допускаются в обычном каталоге MVP.

**BR-MENU-033.** Официант/кассир не может менять цену отдельной позиции непосредственно при оформлении заказа; доступны предусмотренные размеры, модификаторы и разрешённая фиксированная скидка на весь заказ.

**BR-MENU-034.** Нулевая итоговая сумма при сохранённых действующих блюдах не считается полной отменой: нулевой расчёт завершается без Payment с клиентской печатью согласно CORE-001 «Оплаты и расчёты» §6.4.

# 8. Стоп-лист, доступность и архивирование

## 8.1. Операционная доступность

- Недоступное блюдо остаётся видимым персоналу с отметкой «Нет в наличии», но добавить его в новую принятую позицию нельзя.
- Доступность модификатора изменяется отдельно. Недоступный вариант не запрещает заказ всего блюда, если существует другая допустимая комбинация. Если обязательный выбор невозможен, сервер не может принять некорректную комбинацию.
- В MVP доступность меняется вручную, без расписаний и складских остатков.
- Быстрое изменение стоп-листа выполняется локально через сервер и вступает в действие после успешной фиксации.
- Размерные варианты блюда имеют собственную доступность в оперативном стоп-листе. Отключение блюда блокирует все размеры; отключение одного размера не меняет остальные. Если остановлены все размеры, блюдо нельзя заказать. Возврат блюда сохраняет ранее установленные стопы отдельных размеров; возврат размера действует только при доступном блюде.

## 8.2. Архивирование

Архивирование убирает товар из новой продажи, но не удаляет его ID, исторические связи, стоимость, уже принятые пакеты и историю корректировок. Исторические оплаченные заказы не зависят от того, остаётся ли товар в действующем каталоге.

## 8.3. Бизнес-правила доступности

**BR-MENU-035.** Для нового принятого заказа недоступный товар запрещён, но виден сотрудникам как недоступный.

**BR-MENU-036.** Уполномоченные кассир, менеджер и владелец могут изменять стоп-лист в пределах прав, проверяемых сервером. Официант только видит недоступные товары и не может изменять стоп-лист.

**BR-MENU-037.** Доступность модификатора регулируется независимо от доступности самого блюда.

**BR-MENU-038.** Выбранная недоступная опция, а также отсутствие допустимого выбора в обязательной группе блокируют принятие соответствующей позиции.

**BR-MENU-039.** Ручной стоп-лист в MVP не содержит автоматических периодов по дням/часам и автоматического списания складских остатков.

**BR-MENU-040.** Состояние доступности применяется к новым принятым пакетам, но не отменяет автоматически уже принятые пакеты.

**BR-MENU-041.** Уже сформированный Draft после изменения доступности не подтверждается без проверки актуального каталога; клиент должен исправить недоступный выбор и повторно подтвердить пакет.

**BR-MENU-042.** Архивированный товар недоступен для новых заказов, но сохраняется в исторических заказах, финансовых и аудиторских данных.

**BR-MENU-043.** Архивирование и включение стоп-листа — разные операции; простое временное отсутствие блюда не требует архивирования.

**BR-MENU-044.** Операции изменения доступности доступны локально без внешнего интернета, фиксируются в истории и впоследствии синхронизируются.

**BR-MENU-044a.** POS и Waiter Web получают изменения доступности через локальный WebSocket и перечитывают актуальное меню. При отправке пакета сервер повторно проверяет блюдо, выбранный размер, модификаторы и сочетание; уже принятые пакеты не изменяются.

# 9. Филиалы, цены TABLE/COUNTER и вступление цен в силу

## 9.1. Концепция

Каждый филиал MVP самостоятельно ведёт свой каталог и цены. Не требуется единый каталог организации с принудительно общими ценами всех филиалов. Внутри филиала действуют одинаковые базовые цены для TABLE и COUNTER; дополнительные сборы применяются по особым правилам TABLE.

## 9.2. Бизнес-правила цен и филиалов

**BR-MENU-045.** Каталог и цены изолированы по филиалам; изменение одного филиала не изменяет автоматически другой.

**BR-MENU-046.** Базовая цена одного и того же товара в данном филиале одинакова для TABLE и COUNTER.

**BR-MENU-047.** Различия общей суммы TABLE и COUNTER могут определяться утверждёнными дополнительными сборами, которые запрещены для COUNTER, и допустимыми скидками.

**BR-MENU-048.** Новая цена применяется сразу после успешной локальной публикации проверенной редакции каталога, в том числе во время открытой смены.

**BR-MENU-049.** У ранее принятых позиций остаются цены и модификаторы на момент их принятия, независимо от последующего изменения меню.

**BR-MENU-050.** Дозаказ через новый Order Batch рассчитывается по редакции меню, действующей на Local POS Server в момент принятия нового пакета.

**BR-MENU-051.** Если исходный черновик содержит устаревшую цену или конфигурацию, сервер возвращает конфликт и сведения об актуальных условиях; без явного подтверждения сотрудника новый пакет не принимается по изменённой цене.

**BR-MENU-052.** Если при публикации новая цена действительна лишь для отдельного филиала, остальные филиалы продолжают работать по своим действующим редакциям.

# 10. Управление каталогом, права и каналы редактирования

## 10.1. Два канала

Каталог можно редактировать:

1. через **Owner Dashboard**, с доставкой проверенной редакции на соответствующий локальный сервер через синхронизацию;
2. непосредственно через **POS Desktop**, с локальной проверкой, публикацией и последующей синхронизацией.

Обычная офлайн-работа с каталогом не требует доступности облака. Owner Dashboard не имеет права объявлять облачную редакцию применённой локально до соответствующего подтверждения фактического состояния филиала.

## 10.2. Права

- **Owner**: редактирование меню и назначение разрешений;
- **Manager**: редактирование меню только при предоставленном разрешении;
- **Cashier**: не получает общего права редактирования каталога по умолчанию, но может управлять стоп-листом при соответствующих правах;
- **Waiter**: использует действующее меню, не редактируя каталог и цены.

Права изменять конфигурацию дополнительных сборов определяются ранее утверждённым BR-SERVICE-008: владелец или отдельно уполномоченный администратор. Их не следует автоматически приравнивать ко всем правам редактирования меню.

**BR-MENU-053.** Owner Dashboard и POS Desktop являются допустимыми каналами управления каталогом MVP.

**BR-MENU-054.** Меню/цены редактирует владелец либо менеджер с отдельным правом; полномочия проверяются сервером или соответствующей доверенной системой управления, а применение изменения подтверждает Local POS Server.

**BR-MENU-055.** Кассир с правом управления стоп-листом не получает из этого право изменять цену, архивировать товар или публиковать произвольную редакцию каталога.

**BR-MENU-056.** Официант не может произвольно менять цены или правила модификаторов через заказ или подмену клиентских данных.

**BR-MENU-057.** Результат локального изменения применим только после успешного сохранения и серверной проверки; закрытый POS Desktop не должен отменять уже применённую редакцию.

# 11. Редакции меню, публикация и конфликты

## 11.1. Жизненный цикл предложения изменения

Редакция каталога проходит логические этапы: **редактирование → проверка → применение** либо **отклонение/конфликт**. Эти этапы не предписывают конкретную схему таблиц или экранов.

При одной команде публикации обновлённый набор данных проверяется и становится активным **целиком**, либо прежняя редакция остаётся действующей. Промежуточная полуприменённая версия недопустима. Оперативный стоп-лист является отдельным локальным изменением доступности с собственной историей/ревизией и не требует повторной публикации всего каталога.

## 11.2. Одновременные POS/Owner Dashboard правки

Если одна и та же сущность меню изменена независимо локально и в облаке до согласования изменений, система фиксирует конфликт и **не выбирает автоматически** локальную, облачную или последнюю по времени запись. Уполномоченный сотрудник видит расхождение, выбирает или объединяет допустимое состояние и публикует согласованную новую редакцию.

Пока конфликт не разрешён, **для локальных заказов действует последняя реально применённая Local POS Server редакция**. Конфликт не блокирует обычные заказы по доступному действующему меню. Owner Dashboard обязан показывать отсутствие подтверждённого локального применения конкурирующей облачной версии.

Если изменения не конфликтуют, их совместное применение допускается только после проверки целостности и порядка редакций; алгоритм автоматически совместимых слияний определяется в SYNC-001, не считается здесь уже согласованным.

## 11.3. Бизнес-правила версий и конфликтов

**BR-MENU-058.** Каждая публикация или изменение доступности имеет идентифицируемую редакцию/версию в пределах филиала и фиксирует источник изменения.

**BR-MENU-059.** Проверенная редакция каталога применяется к локальному действующему меню целиком; частичное применение одной редакции запрещено.

**BR-MENU-060.** При ошибке проверки или сохранения новая редакция не становится действующей даже частично.

**BR-MENU-061.** Редакция, предложенная Owner Dashboard, не считается действующей для филиала до применения Local POS Server.

**BR-MENU-062.** Локальная публикация на POS допускается без интернета и действует сразу после успешного сохранения.

**BR-MENU-063.** Если одна сущность была изменена локально и в облаке конкурирующим образом, автоматическая перезапись любой стороны запрещена; необходимо разрешение конфликта уполномоченным сотрудником.

**BR-MENU-064.** При конфликте локальное обслуживание продолжается по последней принятой локальной редакции, а конфликтующая облачная редакция не подменяет её молча.

**BR-MENU-065.** Уполномоченному сотруднику должны быть доступны сравнимые сведения о конфликтующих изменениях и возможность зафиксировать согласованное решение; исходные варианты и авторы не стираются из истории.

**BR-MENU-066.** Применённая версия и факт её принятия филиалом передаются в облако асинхронно; Owner Dashboard показывает статус ожидания, конфликта либо подтверждённого применения, не выдавая неопределённое состояние за успех.

**BR-MENU-067.** Ни один клиент, кеш браузера или облачная редакция не имеет права напрямую заменить серверную действующую цену при принятии пакета.

**BR-MENU-068.** Повтор одной команды публикации с тем же идентификатором не создаёт повторную независимую редакцию; повтор с изменённым содержимым должен распознаваться как конфликт.

# 12. Снимки цен в заказах и изменения меню

## 12.1. Момент фиксации

При отправке пакета Local POS Server повторно проверяет товар и его пригодность для продажи, цену блюда/размера, модификаторы, их допустимость, количество и общую сумму. После принятия формируется исторический снимок позиции. Допустимое последующее изменение названия, категории, фотографии, перевода, цены или стоп-листа не корректирует прошлые принятые пакеты.

## 12.2. Бизнес-правила истории позиций

**BR-MENU-069.** Для принятого Order Item сохраняются фактическое название/идентификатор товара, размер, конфигурация модификаторов, их цены, количество, общая сумма, связанный пакет, версия меню и серверное время принятия.

**BR-MENU-070.** Отмена или корректировка принятой позиции использует исходный исторический снимок и отдельную корректирующую операцию.

**BR-MENU-071.** Устаревшие цены телефона не становятся источником истины даже тогда, когда черновик восстановлен из IndexedDB после потери Wi-Fi.

**BR-MENU-072.** При успешном принятии пакета клиент получает подтверждённые сервером цены и состав; если они отличаются от требующих подтверждения условий клиента, команда отклоняется до подтверждения новых условий.

**BR-MENU-073.** Архивирование, переименование, смена перевода, категории или доступности не меняют суммы уже оплаченных или принятых исторических заказов.

# 13. Дополнительные сборы и скидки — окончательно согласованная формула

## 13.1. Закреплённая модель для MVP

**Только TABLE:** если в ресторане активированы несколько дополнительных сборов, каждый рассчитывается **независимо** от **одной базы после фиксированной скидки**, без начисления процента на предыдущий сбор. Каждое процентное начисление отдельно округляется до одного тыйына методом `ROUND_HALF_UP`.

Для COUNTER ни один дополнительный процентный сбор не начисляется.

Порядок:

1. Сервер суммирует стоимость действующих подтверждённых позиций по историческим ценам (с учётом корректировок) — `S`.
2. Применяет одну согласованную фиксированную денежную скидку `D`, где `0 ≤ D ≤ S`. После отмены позиций скидка при необходимости автоматически уменьшается до `S` с сохранением истории.
3. Определяет единую базу `B = S − D`.
4. Для каждого сохранённого активного сбора TABLE независимо вычисляет `Fi = ROUND_HALF_UP(B × Pi / 100)` до одного тыйына.
5. Получает итог TABLE `T = B + ΣFi`; итог COUNTER `T = B`.

Ставки `Pi` представляют процентные настройки ресторана; технологию точной денежной арифметики определяет DB-SCHEMA-001, не допускается двоичная ошибка расчёта. Отрицательные значения итогов запрещены.

## 13.2. Фиксация набора сборов на первом пакете

Для TABLE при принятии первого Order Batch сервер фиксирует перечень применимых активных сборов, их названия и проценты **для всего данного посещения/заказа**. Если владелец позже добавил, отключил либо поменял сборы в настройках, это не меняет согласованный набор этого уже начатого заказа. При дальнейших дозаказах, отменах или изменении скидки рассчитываются **новые суммы сборов от обновлённой базы** с прежними сохранёнными ставками.

Если стол открыт, но первый пакет ещё не принят, набор фиксируется при принятии первого пакета, а не в момент визуального открытия стола.

## 13.3. Пример

Товары `2 000,00 сом`; фиксированная скидка `200,00 сом`; база `1 800,00 сом`.

- «Обслуживание», 5%: `90,00 сом`.
- «Электроэнергия», 1%: `18,00 сом`.
- Итог TABLE: **1 908,00 сом**.
- Итог COUNTER при тех же товарах и скидке: **1 800,00 сом**, сборы отсутствуют.

## 13.4. Бизнес-правила финансовых вычислений

**BR-MENU-074.** В MVP скидка остаётся фиксированной денежной суммой на весь заказ; процентные скидки и скидки непосредственно на отдельные позиции не вводятся.

**BR-MENU-075.** Для TABLE процентные сборы рассчитываются от единой базы подтверждённых действующих позиций **после** применения фиксированной скидки.

**BR-MENU-076.** Каждый активный сбор рассчитывается независимо от той же базы; на результаты других сборов процент не начисляется.

**BR-MENU-077.** Каждая сумма процентного сбора округляется отдельно до одного тыйына по `ROUND_HALF_UP`; итоговый счёт до целого сома не округляется.

**BR-MENU-078.** На COUNTER никакие дополнительные процентные сборы не начисляются, независимо от настройки ресторана.

**BR-MENU-079.** Все дополнительные сборы отключены по умолчанию и отображаются отдельными именованными строками лишь при применимости.

**BR-MENU-080.** Для TABLE набор применимых именных сборов и их проценты фиксируется при принятии первого пакета и сохраняется для всего посещения; изменения глобальной настройки не переписывают этот набор.

**BR-MENU-081.** При дозаказе, отмене или изменении фиксированной скидки до оплаты суммы сборов рассчитываются повторно по сохранённым ставкам и актуальной базе.

**BR-MENU-082.** После полной оплаты согласованные скидка, ставки и суммы сборов неизменны в обычном режиме.

**BR-MENU-083.** При уменьшении подтверждённой стоимости из-за отмены скидка не может превысить новую стоимость: сервер корректирует её по ранее утверждённым правилам отмен с записью в аудит.

**BR-MENU-084.** Все вычисления выполняет Local POS Server с точностью до одного тыйына, одинаково для POS Desktop и Waiter Client.

# 14. Кухонная печать и её связь с меню

## 14.1. Печать по настройке блюда

У каждого блюда/товара имеется настройка «Готовится на кухне», определяющая, требуется ли при принятии пакета печать **KITCHEN**. Эта настройка управляет кухонной печатью и не отслеживает приготовление или готовность блюда. Пример: приготовляемый плов печатается, упакованная вода может отпускаться без кухонного задания.

- Если в пакете есть печатаемые и непечатаемые товары, кухонное задание содержит только подлежащие кухонной печати позиции.
- Если ни один товар пакета не требует кухонной печати, сервер сохраняет принятый пакет **без кухонного Print Job**.
- Если была отменена/исправлена позиция, исходно не направленная на кухню, кухонный чек отмены для неё не создаётся. Если исходная позиция была направлена, применяются правила отдельного кухонного уведомления CORE-001 «Отмены и корректировки».
- Настройка печати, применённая к принятому пакету, сохраняется в истории; её последующее изменение не удаляет уже сформированные кухонные задания.
- В MVP существуют только `KITCHEN` и `CUSTOMER`; «Отмена» — назначение сообщения типа `KITCHEN`, а не третий тип чека.

Для выбранного блюда ресторан может указать один существующий товар меню как предлагаемый контейнер для COUNTER. При добавлении блюда кассиру предлагается контейнер, по умолчанию один на порцию; количество можно изменить или отказаться. Контейнер добавляется только после подтверждения отдельной позицией по собственной цене. Если контейнер недоступен, блюдо можно добавить без него. При последующем изменении количества блюда система может предложить изменить количество контейнеров, но не меняет его незаметно. Сервер проверяет доступность, цену и применимые ограничения; кухонная печать определяется настройкой самого контейнера. Подробные правила — CORE-001 «Заказы Counter», §12.

**Уточнение 24.10.2026:** товар упаковки имеет явный признак `isPackaging` («Это упаковка / контейнер»), по умолчанию выключенный. У обычного блюда переключатель «Предлагать контейнер на вынос» задаёт необязательную ссылку `containerId`; отдельный дублирующий флаг предложения не хранится. В выборе доступны только действующие товары упаковки. Упаковка не может иметь свою ссылку на контейнер; ссылки на себя, обычный товар и архивную упаковку для действующего блюда отклоняются сервером. Архивирование или снятие признака упаковки требует сначала исправить действующие привязки. Сохранение настроек проходит обычный черновик и публикацию каталога.

## 14.2. Бизнес-правила печати

**BR-MENU-085.** Для каждого товара можно настроить необходимость печати на кухне.

**BR-MENU-086.** После принятия пакета кухонное задание создаётся, если пакет содержит хотя бы одну позицию с признаком кухонной печати.

**BR-MENU-087.** Кухонный документ не должен включать непечатаемые позиции смешанного пакета, но финансовый заказ включает весь подтверждённый пакет.

**BR-MENU-088.** Если пакет целиком состоит из товаров без кухонной печати, отсутствие задания KITCHEN не является ошибкой принятия заказа.

**BR-MENU-089.** Признак кухонной печати исходной позиции сохраняется в её историческом контексте и используется для корректного решения о кухонных уведомлениях при последующей отмене.

**BR-MENU-090.** Кухонная отмена не создаётся для позиции, которая не была направлена кухне; отмена позиции при этом остаётся в финансовой и операционной истории.

**BR-MENU-091.** Для позиций, направленных кухне, корректировки оформляются согласно согласованным правилам независимого уведомления, порядка печати и неизвестного результата физической печати.

**BR-MENU-092.** Неуспешная кухонная печать не отменяет принятое сохранение пакета или его цены.

**BR-MENU-093.** Номер Order Batch не печатается на бумажном кухонном документе; внутренняя связь пакета и задания печати сохраняется.

# 15. Основные сценарии использования (Use Cases)

## UC-MENU-001 — Создание категории и блюда

**Предусловия:** выбран филиал; владелец либо разрешённый менеджер авторизован.

1. Сотрудник открывает редактор меню в POS Desktop либо Owner Dashboard.
2. Создаёт одноуровневую категорию или выбирает существующую.
3. Указывает основное название блюда, его цену либо цены размеров, необязательные описание/фото, опции и настройку кухонной печати.
4. Добавляет при желании переводы и дополнительные языки.
5. Система проверяет заполнение обязательных данных, цены, структуру категорий и допустимость вариантов.
6. Сотрудник публикует изменение; если это POS — Local POS Server применяет целостную редакцию локально, если облако — редакция ожидает локального применения.
7. История фиксирует автора, редакцию, время и результат.

**Альтернативы:** не заполнена цена, нарушен выбор модификаторов, найден конфликт редакций — публикация отвергается без частичного применения.

## UC-MENU-002 — Размер и платный модификатор

**Предусловия:** в меню есть «Капучино» с размерами 250 мл = 180 сом, 400 мл = 230 сом; есть овсяное молоко +40 сом.

1. Официант выбирает «Капучино», размер 400 мл, опцию «Овсяное молоко».
2. Клиент показывает предполагаемую стоимость 270 сом.
3. При отправке сервер проверяет активную цену размера, группу, доступность и стоимость опции.
4. Сервер подтверждает **270 сом**, фиксирует цены, выбор и версию меню в Order Item.
5. Последующее изменение размера/цены модификатора в меню не влияет на эту принятую позицию.

**Альтернатива:** если стоимость или доступность изменились в Draft, сервер требует актуального выбора/подтверждения.

## UC-MENU-003 — Переключение гостевого языка

1. Гость открывает клиентское QR/NFC-меню в предусмотренном релизе модуля.
2. Выбирает английский или дополнительный активированный рестораном язык.
3. Система показывает доступные переводы; отсутствующие названия/описания берёт на основном языке.
4. Выбор языка не влияет на цену и ID блюд.

**Примечание:** сценарий задаёт требования к данным и поведению клиентского меню, но не утверждает включение расширенного QR/NFC-функционала в критический объём POS MVP.

## UC-MENU-004 — Включение блюда в стоп-лист

1. Уполномоченный кассир выбирает товар.
2. Подтверждает «Нет в наличии».
3. Local POS Server сохраняет изменение и распространяет актуальное состояние клиентам.
4. Блюдо остаётся видимым, но недоступно для нового подтверждённого пакета.
5. Уже принятые позиции сохраняются неизменными.

**Альтернатива:** официант пытался отправить старый Draft; сервер отклоняет недоступную позицию и возвращает актуальную информацию.

## UC-MENU-005 — Отключение отдельного модификатора

1. Заканчивается овсяное молоко.
2. Уполномоченный сотрудник делает соответствующий вариант недоступным.
3. Основное блюдо остаётся продаваемым с другими разрешёнными вариантами.
4. Попытка отправить пакет с недоступной опцией отклоняется, даже если старый телефон показывал её доступной.

## UC-MENU-006 — Локальное изменение цены при открытой смене

1. Менеджер с правом редактирования меняет цену блюда в POS Desktop и публикует редакцию.
2. Local POS Server проверяет и применяет её целиком; новая цена действует сразу.
3. Ранее принятый «Плов ×1» остаётся по прежней цене.
4. Новый пакет в том же посещении использует актуальную цену.
5. Официант с устаревшим черновиком получает конфликт и подтверждает новые условия перед принятием.
6. Новая локальная редакция синхронизируется с облаком позднее.

## UC-MENU-007 — Облачная публикация при отсутствии интернета

1. Владелец изменяет меню через Owner Dashboard.
2. Изменение получает редакцию и ожидает доставки в филиал.
3. При отсутствии интернета филиал продолжает использовать последнюю локально применённую редакцию.
4. После восстановления связи Local POS Server получает и проверяет новое предложение.
5. При отсутствии конфликта сервер применяет полную редакцию и подтверждает факт применения облаку.

**Альтернатива:** обнаружены конкурирующие изменения того же товара — применяется UC-MENU-008, облачное предложение не подменяет локальное меню молча.

## UC-MENU-008 — Конфликт между POS и Owner Dashboard

1. Пока филиал офлайн, менеджер меняет цену блюда локально и применяет редакцию.
2. Владелец независимо изменяет то же блюдо в Owner Dashboard.
3. При синхронизации сервер выявляет несовместимые изменения одной сущности.
4. Действующая локальная цена продолжает применяться; конфликт отображается как неразрешённый.
5. Уполномоченный редактор сравнивает версии и выбирает согласованное значение.
6. Создаётся и публикуется новая проверенная редакция; исходные версии и авторы остаются в истории.

## UC-MENU-009 — Удаление товара из продаж

1. Уполномоченный редактор архивирует блюдо.
2. После применения редакции оно больше недоступно для новых заказов.
3. Исторические принятые позиции, чеки, отмены и аналитика сохраняют первоначальные сведения.

## UC-MENU-010 — Фиксация сборов первого TABLE-пакета

1. В ресторане активированы «Обслуживание 5%» и «Электроэнергия 1%».
2. Официант открывает стол и принимает первый пакет; сервер фиксирует оба применимых сбора для посещения.
3. Владелец меняет глобальную ставку обслуживания на 6%.
4. Уже открытый заказ продолжает рассчитываться по 5% и 1% на актуальную сумму после скидки.
5. Новый заказ TABLE, чей первый пакет принят после применения настройки, получает актуальные ставки.
6. COUNTER не получает никаких дополнительных сборов.

## UC-MENU-011 — Смешанный пакет с выборочной кухонной печатью

1. Официант принимает пакет: плов и бутылка воды.
2. У плова включена кухонная печать, у воды — выключена.
3. Сервер сохраняет обе позиции в едином Order Batch и счёте.
4. Кухонное задание содержит только плов.
5. Отмена воды не создаёт кухонный чек отмены; финансовая корректировка сохраняется.

**Альтернатива:** пакет целиком непечатаемый — заказ принят без задания KITCHEN.

## UC-MENU-012 — Перерасчёт сборов после отмены

1. В TABLE принято блюд на 2 000 сом; зафиксированы сборы 5% и 1%.
2. Применена фиксированная скидка 200 сом.
3. Сервер рассчитывает базу 1 800 сом, сборы 90 и 18 сом, итог 1 908 сом.
4. Уполномоченный сотрудник отменяет ещё действующую позицию по правилам CORE-001 «Отмены и корректировки».
5. Сервер по историческим ценам оставшихся позиций повторно рассчитывает допустимую скидку и оба сбора **по прежним зафиксированным ставкам**, сохраняет финансовую историю корректировки.
6. Операция оплаты по ранее показанной устаревшей сумме отклоняется до нового подтверждения.

# 17. Конкурентные операции, целостность и идемпотентность

## 17.1. Публикация и заказ одновременно

Публикация новой версии и принятие пакета должны получить однозначный порядок фиксации на сервере: если пакет принят до активации версии, он сохраняет прежние цены; если после — применяются новые условия с проверкой подтверждения сотрудником. Нельзя принять один пакет с произвольной смесью разных невалидированных половин редакций.

## 17.2. Два редактора

При одновременных изменениях локального каталога проверяется ожидаемая версия. Если один редактор опубликовал изменения первым, другой обязан получить конфликт/актуальную редакцию и подтвердить повторное действие. Со стороны облака конфликт также не разрешается автоматически при одновременной локальной правке той же сущности.

## 17.3. Идемпотентность

Повтор команды публикации, переключения стоп-листа или принятия пакета с тем же ID не должен порождать второй эффект. Если ответ потерян, клиент сначала проверяет результат исходной команды.

**BR-MENU-097.** Новая публикация и операции с заказами не могут наблюдать частично применённую редакцию каталога.

**BR-MENU-098.** Проверка действующей цены, доступности, вариантов и принятие Order Batch согласованы в одной серверной операции.

**BR-MENU-099.** Одновременная правка одной сущности двумя редакторами защищена проверкой актуальности редакции и не должна незаметно стирать изменения первого.

**BR-MENU-100.** Повтор принятия одного пакета с тем же `command_id` не создаёт новый пакет, вторую сумму или дополнительное обычное кухонное задание.

**BR-MENU-101.** Повтор операции стоп-листа или публикации с тем же идентификатором и содержимым не создаёт второго независимого бизнес-результата.

**BR-MENU-102.** Если запрос с тем же идентификатором имеет иное содержимое, сервер отклоняет его как конфликт.

**BR-MENU-103.** При успешном применении редакции/стоп-листа фиксируется событие для локальных клиентов и асинхронной синхронизации, не требуя облачного подтверждения для локального успеха.

# 18. Работа без интернета и восстановление после сбоя

- Действующие каталог, цены, доступность, размеры, модификаторы и локально доступные переводы находятся на Local POS Server; на каждом переходе интерфейса к облаку обращаться не требуется.
- POS и официанты работают с локальным сервером по служебной сети; при отключении внешнего интернета обычный заказ продолжает принимать Local POS Server.
- На POS могут вноситься и применяться локальные изменения меню уполномоченным редактором, даже если облако недоступно.
- Облачные правки ждут доставки; при восстановлении применяется политика проверки версии и конфликта.
- При сбое сервера новая операция не подтверждается, клиенты используют авторитетные данные после восстановления.
- Черновики в IndexedDB не объявляются подтверждёнными заказами при потере Wi-Fi; автоматическая отправка неподтверждённых новых черновиков после восстановления не выполняется.
- Локально применённая редакция и история операций должны восстанавливаться после перезапуска Windows/службы на основании надёжно сохранённого состояния.

**BR-MENU-104.** Основные ресторанные операции не зависят от доступности Supabase или Owner Dashboard.

**BR-MENU-105.** После восстановления связи сервер и клиенты сверяют актуальную действующую редакцию; несогласованные/устаревшие черновики повторно проверяются до принятия.

**BR-MENU-106.** Сбой во время публикации не должен приводить к действующему каталогу с частично изменёнными ценами, категориями или вариантами.

**BR-MENU-107.** Неотправленные изменения и события синхронизации сохраняются до подтверждённой обработки с защитой от повторного применения.

# 19. Аудит и историческая отчётность

## 19.1. Что фиксируется

Для изменений меню, цен, доступности, языков и сборов необходимо иметь историю, позволяющую определить:

- филиал, объект, тип изменения и источник (POS или Owner Dashboard);
- фактического авторизованного сотрудника, устройство/канал и серверное время;
- предыдущее и новое значение (например цену 180 → 200 сом, включён/выключен, перевод обновлён);
- исходную и новую редакцию, результат применения, отклонения или конфликта;
- сотрудника и результат ручного разрешения конфликта;
- факт и время применения филиалом и последующей синхронизации;
- версию и цены, реально применённые при принятии конкретной позиции заказа;
- при изменении сборов — исторические ставки/названия и привязку к действующим TABLE-заказам.

Нельзя удалять исторические изменения так, чтобы было невозможно понять первоначальный состав заказа и расчёт. Финансовые операции не подменяются административными исправлениями каталога.

**BR-MENU-108.** Успешные публикации, изменения цен, стоп-листа, архивирование, изменение набора активных языков и переводов, а также разрешения конфликтов фиксируют автора, время, объект и изменение. Личный выбор языка гостем не является изменением каталога.

**BR-MENU-109.** Неуспешные административные действия, отказы в доступе и ошибки публикации фиксируются в доступном аудите без раскрытия паролей и токенов.

**BR-MENU-110.** История каталога и принятых позиций позволяет восстановить фактическую стоимость на момент принятия пакета, даже если блюдо архивировано или переименовано.

**BR-MENU-111.** Облачная аналитика и Owner Dashboard должны отличать последнюю предлагаемую редакцию от фактически принятой редакции филиала.

# 20. Критерии приёмки MVP

## 20.1. Каталог и языки

**MENU-AT-001.** Можно создать одноуровневую категорию и товар в ней; создать подкатегорию нельзя.

**MENU-AT-002.** У одного товара не бывает двух одновременно действующих категорий.

**MENU-AT-003.** Создание блюда требует названия на основном языке и корректной заданной цены/цен вариантов.

**MENU-AT-004.** Описание и фото можно не заполнять.

**MENU-AT-005.** RU, KY, EN доступны как языки гостевого меню; можно добавить другой язык.

**MENU-AT-006.** Отсутствие перевода категории, товара, размера или модификатора показывает значение на основном языке, без изменения цены или ID.

**MENU-AT-007.** В интерфейсах POS/Waiter доступны русский и кыргызский языки системных элементов.

**MENU-AT-008.** Изменение перевода не меняет исторически принятую позицию.

## 20.2. Размеры и модификаторы

**MENU-AT-009.** Товар имеет размеры с отдельными конечными базовыми ценами, выбирается один размер.

**MENU-AT-010.** Платный модификатор увеличивает расчётную цену на свою подтверждённую сумму.

**MENU-AT-011.** Бесплатный модификатор сохраняется в позиции, не увеличивая цену.

**MENU-AT-012.** Нарушение обязательного минимума либо максимума группы не позволяет принять позицию.

**MENU-AT-013.** Нельзя указать одну и ту же опцию дважды внутри одной позиции.

**MENU-AT-014.** Одинаковая опция может иметь разную допустимую цену для разных блюд.

**MENU-AT-015.** Разные размеры/модификаторы/комментарии одного блюда сохраняются без смешения конфигураций.

**MENU-AT-016.** Изменение цены модификатора не пересчитывает ранее принятые позиции.

## 20.3. Доступность и цены

**MENU-AT-017.** Стоп-лист показывает блюдо как недоступное, новое подтверждённое добавление запрещено.

**MENU-AT-018.** Кассир/менеджер/владелец с соответствующим разрешением могут менять стоп-лист без интернета.

**MENU-AT-018A.** Официант видит недоступные товары, но не может изменить стоп-лист.

**MENU-AT-019.** Отдельная опция может быть недоступна, но остальные допустимые комбинации блюда продолжают работать.

**MENU-AT-020.** Устаревший Draft с недоступной позицией не принимается.

**MENU-AT-021.** Ручная доступность не меняет ранее принятые пакеты.

**MENU-AT-022.** Архивирование товара исключает новые продажи и сохраняет всю историческую информацию.

**MENU-AT-023.** Установленная цена 0 сом допускается; отсутствующая цена вызывает ошибку, отрицательная — запрещена.

**MENU-AT-024.** Кассир или официант не может вручную подменить цену принятой позиции.

**MENU-AT-025.** У TABLE и COUNTER одна базовая цена, но дополнительные процентные сборы не применяются к COUNTER.

**MENU-AT-026.** Изменение цены филиала A не изменяет цену филиала B.

**MENU-AT-027.** Новая локально опубликованная цена действует сразу, включая открытую смену; ранее принятый Order Item сохраняет прежнюю цену.

**MENU-AT-028.** При изменении цены устаревшего Draft требуется явное подтверждение актуальных условий.

## 20.4. Публикация и конфликты

**MENU-AT-029.** Меню можно редактировать через Owner Dashboard и через POS с проверкой разрешений.

**MENU-AT-030.** Только владелец или уполномоченный менеджер может публиковать изменение каталога/цены.

**MENU-AT-031.** Отказ публикации оставляет целиком прежнюю активную редакцию.

**MENU-AT-032.** Публикация с разными обновлёнными позициями не делает действующей частичную редакцию.

**MENU-AT-033.** Если облачное изменение не дошло до филиала, действующим остаётся локальное меню, а в кабинете видно ожидание.

**MENU-AT-034.** Конфликт цены одной позиции, изменённой в POS и Owner Dashboard, не приводит к автоматической перезаписи; сотрудник разрешает конфликт с сохранением истории.

**MENU-AT-035.** При конфликте обычные локальные заказы продолжаются по фактически действующей локальной редакции.

**MENU-AT-036.** Повтор одного и того же идентификатора публикации или команды стоп-листа не создаёт второго эффекта.

## 20.5. Сборы и кухня

**MENU-AT-037.** При первом принятом TABLE-пакете фиксируются применимые ставки; дальнейшее изменение настройки не меняет их в существующем заказе.

**MENU-AT-038.** Сборы рассчитываются от цены действующих позиций после фиксированной скидки.

**MENU-AT-039.** Несколько сборов рассчитываются независимо от одной базы; отсутствует начисление «процента на процент».

**MENU-AT-040.** Каждый процентный сбор отдельно округляется по `ROUND_HALF_UP` до тыйына.

**MENU-AT-041.** На COUNTER не начисляются дополнительные сборы.

**MENU-AT-042.** Перерасчёт после отмены сохраняет исторические ставки и обновляет суммы применимых сборов.

**MENU-AT-043.** Если пакет содержит плов с кухонной печатью и воду без неё, кухня получает только плов, а сумма заказа включает оба товара.

**MENU-AT-044.** Пакет из непечатаемых товаров сохраняется без KITCHEN Print Job.

**MENU-AT-045.** Отмена ранее непечатаемой позиции не создаёт кухонного чека отмены; финансовое событие остаётся.

**MENU-AT-046.** Неуспешная физическая печать не отменяет сохранённый принятый пакет.

## 20.6. Восстановление и аудит

**MENU-AT-047.** При потере интернета локальное меню, стоп-лист, принятие заказов и расчёты продолжают работать.

**MENU-AT-048.** При перезапуске сервера применённый каталог и история сохраняются.

**MENU-AT-049.** Успешные и отклонённые существенные административные изменения доступны для аудита с фактическим автором и временем.

**MENU-AT-050.** При потере ответа о публикации повтор исходной команды не создаёт вторую редакцию.

**MENU-AT-051.** При конкурентном принятии пакета и обновлении цены сервер не допускает смешения версий и неверного подтверждения суммы.

**MENU-AT-052.** Владелец видит, применена ли предложенная облачная редакция в конкретном филиале.

# 21. Границы MVP

## 21.1. Входит

- одноуровневые категории, базовые карточки блюд и товаров;
- основной язык и необязательные переводы RU/KY/EN и добавляемых рестораном языков;
- русский/кыргызский интерфейс POS/Waiter;
- платные/бесплатные модификаторы, группы min/max, размеры с собственными базовыми ценами;
- отдельная доступность блюд и модификаторов, ручной стоп-лист;
- архивация с сохранением истории;
- одна базовая цена для TABLE и COUNTER внутри филиала;
- отдельные каталоги и цены филиалов;
- нулевая заданная цена и запрет произвольной цены на этапе продажи;
- локальное редактирование и редактирование через Owner Dashboard;
- публикация целостных редакций и явное разрешение конфликтов;
- исторические снимки цен и требований печати;
- фиксация именных сборов TABLE при первом пакете, последовательность скидки и сборов, независимое начисление и `ROUND_HALF_UP` до тыйына;
- поэлементная настройка необходимости кухонной печати;
- идемпотентность, офлайн-работа и аудит.

## 21.2. Не входит

- иерархия категорий и блюда одновременно в нескольких категориях;
- обязательное заполнение всех языковых переводов;
- полная локализация POS/Waiter на произвольные туристические языки;
- автоматический перевод контента;
- рецептуры, калорийность, себестоимость, складские остатки, автоматический стоп-лист;
- автоматическое расписание доступности;
- многократное добавление одной опции в одной позиции;
- произвольная цена блюда при расчёте;
- скидка на отдельную позицию, процентная скидка;
- сложные централизованные мастер-меню между филиалами и автоматическое изменение цен всей сети;
- сложное безусловное автоматическое слияние конфликтующих редакций;
- автоматическая банковская/фискальная интеграция;
- гарантированное включение всех расширенных функций QR/NFC-меню в критический POS MVP (объём определяется архитектурой и отдельным ТЗ).
