# SYNC-MENU-001 — поэтапная синхронизация меню и истории с Cloud

Дата: 24.10.2026. Статус: реализация выполнена; Cloud SQL и Edge Function развёрнуты. После установки ключа пользователем удалённая сквозная проверка прошла, синхронизация включена в исходной конфигурации. Фактические контракты, проверки и ограничения: [API-MENU-SYNC-012](API-MENU-SYNC-012.md).

Раздел 2 ниже сохраняет исходный аудит до реализации; актуальный статус приведён в API-MENU-SYNC-012.

## 1. Цель

Начать синхронизацию Bashkar с меню: хранить опубликованные каталоги и историю в Cloud, доставлять новые редакции в филиал при запуске и периодически, сохраняя Local-First работу и существующие правила заказов.

Облако становится центральным хранилищем согласованной истории и желаемой конфигурации филиала. Local POS Server остаётся единственным источником фактически действующего меню для кассы и официантов, проверяет и применяет редакции, рассчитывает заказы. Отсутствие Cloud не блокирует локальные операции.

Основной принцип: **«сохранено в Cloud», «назначено филиалу» и «применено Local POS Server» — разные подтверждаемые состояния**.

## 2. Что установлено по текущему коду

- `MenuService` хранит черновики в `menu_drafts`, неизменные опубликованные документы в `menu_revisions`, текущую локальную редакцию в `menu_current`.
- Публикация атомарно записывает редакцию, указатель, аудит и событие `menu.published` в локальный `outbox`. Событие содержит номер редакции, а не весь документ; документ доступен из неизменной истории.
- Обработчика доставки этих событий в Cloud пока нет. Наличие outbox не является доказательством отправки.
- Каталог уже содержит MATRIX-цены, переводы сочетаний, фиксированные SET-компоненты, упаковку, архив и локализации. Все эти поля должны передаваться без упрощения.
- Оперативный стоп-лист хранится отдельно в `menu_availability`; процентные сборы — отдельная настройка.
- В проверенных cloud-миграциях есть организации, филиалы, регистрации Local Server и аудит активации; таблиц истории меню и протокола menu-sync ещё нет. Рабочая удалённая БД этим исследованием не опрашивалась.
- Существуют подписанная регистрация устройства и защищённый ключ Local Server. Cloud-регистрация хранит hash публичного ключа, а не полноценную серверную sync-сессию. Транспорт/авторизация синхронизации требуют реализации.
- По реестру допускается один активный Local Server на филиал. Поддержка нескольких кассовых приложений через этот сервер сохраняется; несколько независимых серверов одного филиала в первый этап не входят.
- CORE-001 допускает локальные и облачные правки, запрещает тихую перезапись конфликтов и требует подтверждения фактического применения филиалом.

## 3. Этапы и границы

### Этап 1А — облачная история, отправка и диагностика

Обязательный первый поставляемый результат:

1. Cloud хранит полные неизменные опубликованные редакции филиала.
2. При включении синхронизации передаётся уже существующая локальная история, затем новые публикации.
3. Отправка переживает отсутствие интернета, потерю ответа и перезапуск; повтор не создаёт дублей.
4. В POS видны состояние, очередь, ошибка и последнее подтверждённое сохранение в Cloud.
5. В Cloud доступны история и подтверждённое состояние филиала через защищённый API; в существующем web-приложении добавляется минимальный экран просмотра, если оно входит в поставку. Полный облачный редактор не является условием завершения 1А.
6. Worker уже проверяет облачный manifest при старте и по интервалу. До включения этапа 1Б скачанный каталог хранится как ожидающий применения; интерфейс явно говорит об этом.

**1А — архивирование и проверка обновлений, но ещё не завершённая двусторонняя синхронизация.**

### Этап 1Б — доставка и безопасное применение

Следующая небольшая поставка в рамках этого ТЗ:

- Загрузка полной желаемой редакции из Cloud, проверка, локальное атомарное применение, подтверждение в Cloud.
- Безопасное автоприменение при выполнении условий раздела 8; иначе понятная очередь/конфликт и ручное действие.
- Первичное восстановление каталога пустого активированного филиала после явного выбора облачного источника.
- Сравнение конфликта и создание согласованной новой редакции.

Только после приёмки 1Б допустимо сообщать, что актуальное меню действительно автоматически поступает с Cloud и применяется в филиале.

### За пределами 1А/1Б

Заказы, оплаты, возвраты, смены, столы, сотрудники, склад, рецептуры, фото/файлы, процентные сборы, оперативный стоп-лист, межфилиальное мастер-меню, полный Owner web-редактор и синхронизация незавершённых черновиков. Их возможное развитие описано отдельно ниже. Текущие операции продолжают работать локально.

## 4. Идентификаторы и модель версий

Не считать локальный номер `#12` универсальным cloud-номером. После восстановления или смены регистрации одинаковые локальные номера могут обозначать разные документы.

Каждая передаваемая редакция содержит:

- `versionId` — стабильный UUID версии, закреплённый локально до первой отправки;
- `organizationId`, `branchId`, `registrationId`, `instanceId` — доверенный контекст источника;
- `origin`: LOCAL_POS / CLOUD_OWNER / CLOUD_RESTORE;
- `originLocalRevision`, если версия опубликована на Local Server;
- `parentVersionId` — база этой ветки изменений;
- `catalogSchemaVersion` — версия формата каталога;
- `contentHash` — SHA-256 нормализованного канонического документа;
- полный каталог;
- первоначальный автор и его тип/идентификатор, локальное время публикации, cloud-время приёма;
- `operationId` — идентификатор доставки/команды; отдельно от идентичности документа.

Правила:

1. На Cloud версия неизменна. Исправление/восстановление создаёт новую версию.
2. Числовой cloud sequence назначается транзакционно для навигации по истории; он не заменяет UUID/родителя. Конфликтные версии также сохраняются, поэтому нельзя предполагать, что следующая действующая версия имеет sequence + 1.
3. Локальный номер редакции остаётся локальным счётчиком. Для скачанной версии создаётся новая локальная редакция и сохраняется отображение на cloud versionId.
4. Не полагаться на время устройства для порядка/выбора победителя. Cloud receivedAt не является основанием перезаписать чужие изменения.
5. Одинаковый operationId и hash возвращают исходный результат. Тот же ID с другим содержимым отклоняется.
6. Повтор известной версии не создаёт новую локальную/облачную редакцию. Одного совпадения hash у независимых веток недостаточно для потери информации об авторах/родителях.

## 5. Предлагаемое хранение

Названия сущностей ниже проектные, не утверждение об уже созданных таблицах.

### Cloud

- `menu_cloud_versions`: branch-scoped неизменные документы и происхождение, UUID/sequence/hash/schema/parent.
- `menu_cloud_heads`: согласованный head и желаемая версия филиала, CAS-поколение указателя.
- `menu_sync_commands`: идемпотентные результаты операций, включая конфликт; надёжное выяснение результата после потерянного ответа.
- `menu_device_acknowledgements`: фактически применённые versionId/hash/локальная редакция/время и регистрация сервера.
- `menu_sync_conflicts`: общий предок, обе ветки, причина, статус, решение и автор; исходные документы остаются в истории.
- Защищённый аудит: приём, назначение, применение/отказ, восстановление и разрешение конфликта.
- Challenge/replay-защита устройств с ограниченным временем жизни.

Cloud-указатель не должен объявляться локально применённым только по факту своего изменения. ACK привязан к активной регистрации; старое подтверждение retired-сервера не означает успешное применение новым сервером.

### Local SQLite

- Durable состояние синхронизации филиала: последняя общая cloud-версия, последняя загруженная/применённая, подтверждённая доставка, cursor начальной истории.
- Привязка local revision ↔ versionId/parent/hash/origin/registration.
- Скачанные ожидающие редакции, конфликты и недоставленные ACK.
- Состояние попыток доставки с retryAt и последней безопасной ошибкой, без ключей/паролей.
- Метаданные состояния черновиков/редактирования для определения, можно ли применить входящую редакцию.

Переиспользовать существующий outbox как источник локальных публикаций, а не заводить параллельную публикацию каталога. Подтверждать доставку только конкретных menu-событий; не помечать отправленными заказы/смены и другие события. Отдельно учитывать «документ архивирован в Cloud» и «ветка принята в cloud head».

### Автор входящей версии — обязательная доработка

В текущей SQLite опубликованная редакция ссылается на локального сотрудника через created_by, история использует JOIN employees. Облачный автор не обязан иметь локальный employee ID. Нужна согласованная миграция происхождения/типов автора и чтения истории; нельзя подставлять случайного владельца или создавать фиктивного сотрудника для обхода FK. Техническое применение worker и первоначальный человек-автор фиксируются раздельно. Старые авторы/исторические документы сохраняются.

## 6. Отправка из филиала

### Локальная публикация

1. Действующая команда проверяет права и каталог.
2. Одна SQLite-транзакция сохраняет локальную редакцию/указатель/аудит/outbox и метаданные стабильной sync-идентичности.
3. POS сообщает: «Опубликовано локально. Ожидает отправки в Cloud».
4. Worker получает неизменный документ, отправляет полный snapshot с родителем и ожидаемым cloud head.
5. Cloud проверяет устройство, филиал, схему, hash, родителя и идемпотентность. Валидная версия архивируется; продвижение head выполняется через CAS.
6. После ответа/проверки receipt локально сохраняется подтверждённый результат.

Публикация не ждёт внешней сети. Ни клиент, ни worker не дописывают опубликованный каталог по частям.

### Уже существующая история

При первом включении зафиксировать границу backfill H. Передать локальные версии 1…H в порядке происхождения, сохранив первоначальные номера/авторов; новые публикации продолжают добавляться в очередь после H. У backfill есть устойчивый cursor. Перезапуск не начинает независимую историю заново и не создаёт дублей.

Сначала проверить Cloud head и происхождение. Если Cloud пуст — допустима начальная цепочка. Если Cloud уже содержит другое меню — нельзя автоматически объявить локальную историю новой основной веткой. Она сохраняется как отдельная ветка/конфликт для согласования.

## 7. Проверка обновлений при запуске и по интервалу

Рекомендуемые настройки первого этапа, подлежащие согласованию:

| Событие | Действие |
|---|---|
| Local Server перешёл в READY и проверена реальная активация | Запустить фоновый sync-cycle сразу, не задерживая готовность кассы |
| Обычная работа | Проверка manifest каждые 30 секунд, jitter ±10% |
| После локальной публикации | Сразу разбудить очередь отправки |
| Открытие меню в Desktop | Показать текущий локальный статус; попросить worker проверить Cloud, если последняя попытка была более 10 секунд назад |
| «Синхронизировать сейчас» | Внеочередная проверка с rate limit, без обхода конфликтов/валидаторов |
| Восстановление сети / пробуждение сервера | Один внеочередной цикл, без параллельных дублей |
| Ошибка сети/5xx | Backoff 15 → 30 → 60 → 120 → 300 секунд с jitter |
| 429 | Учитывать Retry-After; не спамить запросами |
| Истёкшая короткая device-сессия | Один раз обновить её через новое доказательство устройства и повторить исходную идемпотентную операцию |
| Повторный 401/403, отозванная регистрация | Остановить автоматические cloud-операции до восстановления доверия; сохранить локальное обслуживание по действующим правилам |

- Таймаут отдельного запроса: предложение 10 секунд. Объём документа ограничивается на обеих сторонах и согласуется с фактическим Local API, без молчаливого повышения лимита.
- Scheduler работает в Local POS Server, а не в каждом renderer/телефоне. Закрытие Desktop не останавливает синхронизацию работающего сервера.
- Один цикл/отправка в полёте на филиал; очередь обрабатывается порциями, сохраняя возможность проверить manifest при большом backfill.
- Сначала получать лёгкий manifest: head/version/hash/schema/CAS generation. Полный документ загружать только при изменении или отсутствии локальной копии.
- Если версия не изменилась, не создавать новую редакцию и не перерисовывать экран меню.
- Фоновый polling не продлевает пользовательскую авторизацию и не считается человеческой активностью.
- UI отдельно показывает последнюю попытку, последнее успешное соединение и последнее подтверждение версии: отсутствие изменений не является ошибкой.

## 8. Загрузка и применение на Local Server

### Последовательность

1. Проверить подписанный cloud manifest/envelope, филиал, активную регистрацию, protocol/schema и hash.
2. Сохранить скачанный документ как PENDING, без изменения active menu.
3. Валидировать весь каталог тем же контрактом, включая ID/архив, MATRIX, SET, переводы, упаковку и денежные лимиты.
4. Проверить родство с общей версией и отсутствие несогласованной локальной ветки.
5. Если разрешено, применить одной SQLite-транзакцией: новая неизменная локальная редакция, указатель, mapping, аудит, durable ACK.
6. После commit отправить ACK с versionId/hash/локальным номером. Если сеть пропала — повторять только ACK, не создавать редакцию ещё раз.
7. Cloud показывает применение только после проверенного ACK. При сбое SQLite остаётся прежняя активная редакция.

Применение использует общий проверенный механизм публикации/валидации и серверный технический субъект с ограниченным назначением. Не имитировать вход сотрудника и не хранить его пароль для фоновой работы.

### Условия автоприменения этапа 1Б

Все условия обязательны:

- Филиал активирован, registration/instance совпадают с ожидаемыми.
- Документ совместим и полностью валиден.
- Родитель входящей версии совпадает с согласованной базой; локальное активное состояние не ушло в независимую ветку.
- Нет локальных опубликованных, но ещё не согласованных изменений или нерешённого конфликта.
- Нет активного редактирования меню или незавершённого сохранённого черновика, который будет сделан устаревшим без решения сотрудника.
- Не исполняется другая публикация/применение; перед commit условия CAS перепроверяются в транзакции.

Открытая смена сама по себе не запрещает применение меню. Принятые позиции заказа и чеки не пересчитываются. Неотправленный заказ, чьи условия изменились, проходит существующее повторное подтверждение.

### Несохранённые формы и черновики

Local Server не видит ввод в renderer автоматически. Для безопасной автоматизации нужна короткая server-side lease редактирования (предложение: heartbeat 20 секунд, TTL 60 секунд) и явные статусы сохранённых черновиков. Это техническая защита, а не новое право редактирования.

- Существующие сохранённые черновики не считать завершёнными только потому, что их baseRevision старее текущей. При миграции неопределённые состояния требуют консервативного определения/действия пользователя.
- При lease или незавершённом черновике скачать новую версию, но отложить применение: «В Cloud есть обновление. Завершите или сохраните работу и выберите действие».
- После разрыва связи/истечения lease старая форма может оставаться открытой: она не стирается. При восстановлении показывается смена базы, сохранение старой формы не должно молча перезаписать новую редакцию.
- Автоматическое применение не вызывает безусловный render(), который теряет введённые поля/прокрутку. UI принимает уведомление о новой версии и сохраняет текущую форму до решения.
- Ручная кнопка применения с menu.edit также проходит проверки; незавершённая работа сохраняется отдельным черновиком/веткой либо явно отменяется пользователем.

### Защита от эха

Версия, пришедшая из Cloud, не отправляется обратно как новая независимая локальная публикация. Сохраняются origin/versionId и mapping; в Cloud отправляется ACK. Известная своя публикация, увиденная при polling, подтверждается по mapping, без отката локального head на более старую уже отправленную версию.

## 9. Конфликты

Первый этап использует консервативное сравнение веток целого каталога. Автоматическое слияние даже разных блюд пока не включать: SET/категории/ID могут создавать перекрёстные зависимости.

При изменении обеих сторон относительно общей базы:

- Обе валидные версии сохраняются в истории.
- Желаемый cloud head не перезаписывается по last-write-wins; локальное меню не заменяется.
- Заказы продолжают обслуживаться по последней реально применённой локальной редакции.
- POS показывает общий предок, локальную/облачную ветки, авторов/источники, отличающиеся товары/цены/состав сетов и архив.
- Сотрудник с разрешённым menu.edit может подготовить согласованную редакцию: взять локальную, облачную или вручную объединить. Любой выбор создаёт новую валидную версию с зафиксированным решением и CAS-проверкой обеих текущих веток. При новом изменении конфликт пересчитывается.
- Потерянный ответ разрешается запросом receipt исходной операции, а не новым operationId и повторной публикацией.

Важно для Cloud-транзакций: если при несовпадении head версия должна сохраниться как конфликтная, обработчик обязан зафиксировать документ и конфликтный результат. Исключение SQL, откатывающее всю транзакцию вместе с документом, этому требованию не соответствует.

## 10. Стоп-лист, цены и другие локальные состояния

- В 1А/1Б переносится структурный каталог и его версии. `menu_availability` остаётся отдельной локальной операционной истиной.
- Загрузка/восстановление каталога не очищает стоп-лист и не делает известные позиции/сочетания доступными автоматически. Стабильные ID сохраняют свои локальные overrides; отсутствующие ID не распространяют статус на новую чужую сущность.
- Cloud-редактирование доступности существующих сущностей не вводить под видом menu.edit. Для него нужен отдельный протокол menu.stoplist.manage с версиями, согласованный будущим этапом. При подготовке восстанавливаемой редакции нельзя незаметно вернуть исторические значения доступности вместо текущих операционных ограничений.
- Cloud до внедрения stoplist-sync явно показывает: «Оперативная доступность филиала не синхронизируется». Нельзя выдавать available из snapshot за подтверждённое наличие сейчас.
- Скидки заказов, сборы TABLE, оплаты и цены принятых позиций не меняются из-за menu-sync.
- Редакция, где компонент сета архивирован/удалён без исправления зависимого активного сета, не применяется.

## 11. Первичное подключение, восстановление и удаление

| Local | Cloud | Поведение |
|---|---|---|
| Есть опубликованное меню | Пусто | Отправить историю, согласовать цепочку и active mapping |
| Нет опубликованного меню | Есть версии | Показать филиал/источник/версию; после явного подтверждения загрузить проверенную версию |
| Обе стороны совпадают по подтверждённому mapping/hash | Есть версии | Продолжить обмен без дублей |
| Обе стороны различаются и общего mapping нет | Есть версии | Первичное согласование; никакой автоматической перезаписи |
| Новая регистрация/замена устройства | Есть история старой | Проверить полномочия и перенос происхождения; старую очередь не считать автоматически доверенной |

- Пустое/неполученное Cloud-меню, 404 или ошибка сети не означают команду удалить локальный каталог.
- Архив товара — явное изменение в новой редакции. Старые опубликованные ID и ссылки истории сохраняются по существующим правилам.
- Восстановление версии: копирование состава старой версии в **новую** редакцию, повторная валидация и проверка актуальных ID/доступности. Не менять старый документ и не откатывать счётчик назад.
- Облачное меню не является полной резервной копией филиала: заказы, оплаты, ключи и сотрудники этим этапом не восстанавливаются.

## 12. Доверие и разграничение доступа

- Все фоновые соединения делает Local Server по HTTPS к разрешённому Cloud origin.
- Использовать существующую идентичность устройства и ACTIVE registration, не передавать cloud-пароль владельца в worker.
- Предлагается challenge-response с подписанными method/operation/bodyHash/branch/registration/instance и одноразовым server nonce. Cloud проверяет hash предъявленного public key по регистрации и подпись; ограничивает TTL, повторы, частоту и размер. Для долгой работы допустима короткая device-сессия, полученная после proof, со scoped claims и отзывом регистрации.
- Повтор доставки по operationId идемпотентен; повтор авторизационного challenge недопустим. Для проверки receipt получать свежий challenge.
- Изменение подписи, branchId, registrationId или тела запроса отвергается. Клиентский JSON не является источником прав/владельца.
- RLS: владелец читает только свои организации/филиалы; запись осуществляется через проверенный server/Edge-контракт. Service role и приватный cloud signing key никогда не попадают в Desktop, renderer, public config или установщик.
- Для входящих manifest/version-envelope предлагается отдельная подпись menu authority и keyId; публичные ключи доверия поставляются безопасно. Не переиспользовать приватный ключ активации автоматически без отдельного решения о ротации и разделении назначения.
- Учёт локального автора сохраняет employeeId/name на момент публикации, cloud-автор берётся из подтверждённой личности; worker не подменяет его собой. Аудит не хранит пароли/токены/приватные ключи.
- Retired/чужое устройство не может читать/писать меню филиала. Отзыв cloud-доступа не превращается в скрытую удалённую команду удалить локальные данные; локальные ограничения задаются существующими правилами авторизации/активации.

## 13. Предлагаемые контракты и UX

Это логические операции для проектирования API, **не существующие endpoint-адреса**:

1. Device challenge / session proof.
2. `pushRevision` — документ, origin/parent/operation/hash и ожидаемый head; результат STORED_ACCEPTED / STORED_CONFLICT / REJECTED.
3. `getManifest` — желаемая версия, поколение head, совместимость и подтверждение применения.
4. `getRevision` / `listRevisions` — защищённые документы и история с пагинацией.
5. `getOperationReceipt` — достоверный результат прежнего запроса.
6. `ackApplied` — версия/hash/локальная редакция/регистрация, идемпотентно.
7. `resolveConflict` / `restoreAsNewRevision` — новые согласованные редакции, проверка прав и CAS.

Перед реализацией выбрать конкретные Edge/RPC/Local API маршруты с учётом существующих контрактов, не создавать прямой доступ renderer к Supabase/SQLite.

На экране меню:

- «Локальная редакция #…», cloud version и реальный статус каждой стороны.
- «Синхронизировано», «Ожидает отправки: N», «В Cloud новая версия», «Применение отложено: редактирование», «Конфликт», «Cloud недоступен», «Ошибка версии», «Синхронизация выключена».
- Последнее соединение и последнее подтверждение сохранения/применения.
- «Синхронизировать сейчас» не публикует рабочую форму и не отбрасывает её.
- История различает версии только в Cloud, только локально и подтверждённое сопоставление.
- Меню без menu.edit остаётся читаемым, диагностика без чувствительных деталей; конфликт/ручное применение/публикация доступны только уполномоченному сотруднику.

## 14. Изолированный clean-preview

`desktop:clean-preview` и подписанные QA-fixture филиалы по умолчанию имеют **CLOUD_SYNC_DISABLED**. Они не используют production registry/ключи и не отправляют стартовое тестовое меню в рабочую Supabase.

Для end-to-end испытаний создаётся отдельный staging-проект/филиал с явной конфигурацией, реальной проверкой регистрации в этом окружении и одноразовыми данными. Нельзя включать сетевой обход доверия для того, чтобы пример меню случайно загрузился в рабочий филиал.

## 15. Обязательная приёмка

1. Отправка текущего меню и всей существующей истории, включая переводы, MATRIX, сеты и упаковку; совпадение полных hash на обеих сторонах.
2. Новая локальная публикация без интернета действует на кассе, остаётся в durable очереди и доставляется после восстановления.
3. Повтор push/ACK, потерянный ответ, перезапуск до/после commit не создают дублей и не теряют результат.
4. Скачивание при старте и polling через заданный интервал; неизменный manifest не скачивает полный документ и не создаёт редакцию.
5. Повреждённый/чужой/неподписанный/несовместимый документ отклоняется, active menu неизменно.
6. Атомарный apply: fault injection на документе/указателе/mapping/аудите/ACK полностью откатывает изменение.
7. Конкурирующие публикации POS/Cloud дают сохранённые ветки и конфликт, без last-write-wins; повтор конфликта возвращает прежний receipt.
8. Открытые формы и незавершённые черновики переживают polling/смену версии, старый base не публикуется поверх нового.
9. Открытая смена и принятые заказы сохраняют исторические цены/составы; новый заказ получает применённую редакцию с существующим подтверждением.
10. Стоп-лист не очищается при скачивании/восстановлении; сеты не продаются при недоступных компонентах.
11. Предотвращение эха своей версии и повторного применения; backfill большой истории не голодает polling.
12. Облако различает upload/desired/apply ACK и не показывает «на кассе применено» до ACK, в том числе после замены регистрации.
13. RLS/IDOR: другой владелец, филиал, retired-устройство, подмена тела/challenge и попытка браузера использовать серверные полномочия отвергаются.
14. Пропажа сети/429/5xx/backoff, завершение Desktop, рестарт сервера, истечение сессии и смена часов не создают бурю запросов или скрытый logout-продлитель.
15. Bootstrap: local-only, cloud-only, совпадение, расхождение, новая регистрация; пустой Cloud не удаляет локальное меню.
16. clean-preview не обращается к рабочему Cloud; staging-тест проходит на реальных Edge/RPC/БД, а не только mock.
17. Проверены локальная миграция и облачная миграция/политики. Развёртывание и remote state подтверждены отдельно от unit/integration тестов. Windows/служба/реальная сеть проверяются отдельным протоколом.

## 16. Предложения для следующих этапов

1. Полный Owner Dashboard редактор с тем же валидатором, просмотром различий, CAS и подтверждённым статусом филиала.
2. Синхронизация стоп-листа отдельным потоком с menu.stoplist.manage, собственными версиями и запретом тихого снятия локального ограничения.
3. Облачные черновики/восстановление несохранённой работы — отдельная модель принадлежности и конфликтов, без автоматической публикации.
4. Планируемая публикация по времени/подтверждение менеджером. Для работающего филиала отдельно решить часовой пояс и поведение при отсутствии интернета.
5. Метрики задержки доставки/применения, размер очереди и оповещение владельца о длительном расхождении. Это не гарантия применения во время офлайна.
6. Затем передавать отчётные события смен/заказов/оплат в Cloud с их собственной идемпотентностью и финансовыми ограничениями. Не переносить на деньги упрощённую логику меню.
7. Фото/файлы — отдельное хранилище с контрольными суммами и офлайн-кешем, не base64 в каждой редакции.
8. Межфилиальный шаблон каталога — отдельная сущность с явным назначением филиалам; не общий branchId и не автоматическая замена локальных цен.
9. Резервное копирование/восстановление всей установки — отдельная задача с проверкой ключей, исторических заказов и рабочего сервера.

## 17. Миграции, выпуск и решения для подтверждения

- Добавлять Cloud миграции/политики/Edge-функции и Local миграции по существующей процедуре. Не менять опубликованные миграции и не обходить защиту обновления при открытой смене.
- Не обновлять MANGO/рабочую базу автоматически. Первая поставка — только staging и остановленная изолированная копия с проверенным восстановлением.
- Совместимые Local Server/Desktop/Waiter должны быть выпущены согласованно; неизвестная версия каталога остаётся ожидающей/ошибочной, но не подменяет рабочую.

Предлагается подтвердить:

1. Поставки 1А (архив + очередь + polling) и 1Б (apply + ACK + конфликты), без объявления 1А полной синхронизацией.
2. Polling 30 секунд, фоновый неблокирующий старт, backoff до 5 минут.
3. Автоприменение только при безопасных условиях; при редактировании/черновике/расхождении — ожидание или ручное согласование.
4. Сначала только опубликованный каталог и история; стоп-лист/черновики/сборы/прочие данные — отдельные последующие потоки.
5. Доверие зарегистрованного Local Server и отдельное staging-развёртывание; clean-preview всегда без рабочего Cloud sync.
6. Без автоматического слияния конфликтов и без тихого выбора «последний победил».

Источники проекта: CORE-001 «Меню и ценообразование», AUTH-001, BACKEND-001, POS-001 TECH; текущие menu/catalog/pricing/activation/device/server модули, migrations/002-operations, существующие Supabase activation registry и register-server. Положения о scheduler, API, таблицах и криптографическом протоколе выше — предлагаемая новая реализация, не отчёт о существующей синхронизации.
