# POS-ORDER-FIRST-CART-008 — табы черновика и раскрытие пакета

Дата: 26.10.2026. Статус: согласовано пользователем и реализовано. Дополнение к [POS-007](POS-ORDER-FIRST-CART-007-IMPLEMENTATION.md). Область — FAST_FIRST («Заказы сначала»). Финальное уточнение пользователя: пакет только отправляется; оплата остаётся общей для заказа, шторка раскрывается на доступную высоту корзины, без анимации.

## Реализованное поведение

### Новый черновик

Жёлтая «+ Новый заказ» в активных сразу открывает локальный черновик, без модального выбора типа и без создания пустого серверного заказа/номера. Под заголовком «Новый заказ» расположены табы «Зал» и «На вынос» с иконками. Пустой новый черновик по умолчанию — Зал, если доступен; сохранённый непустой черновик восстанавливает свой тип.

Переключение без подтверждения сохраняет позиции/варианты/количество/комментарии и назначения зала, пересчитывает сумму сервером. В COUNTER назначения скрываются и сохраняются для обратного переключения. При переходе блокируются конкурирующие действия, старый расчёт сбрасывается; оплата не использует сумму предыдущего типа.

После подтверждённого первого пакета табы исчезают. Тип существующего заказа не изменяется. Неизвестный результат блокирует табы и новые операции до восстановления исходной команды. Личные дозаказы выбранных активных заказов сохраняются в прежних защищённых контекстах.

### Верх принятого заказа

Для TABLE вертикально показываются:

```text
Заказ №003
Стол: С10 ›
Открыл: Админ
Ответственный: Айбек ›
```

Стол и ответственный — текстовые действия в стиле скидки, без крупных залитых карточек, с областью нажатия не менее44px. Открывают прежние серверные сценарии выбора/переноса стола с зонами и назначения официанта. Создатель — обычный текст, без обработчика клика. Без права изменения назначения выводятся обычными строками. Для TABLE без стола: «Стол: не назначен ›». COUNTER показывает тип «На вынос» и реального автора первого пакета; назначений посещения нет.

### Новый пакет

При наличии новых строк шторка занимает всю область между верхом корзины и закреплённым нижним блоком. История в этот момент скрыта; компактное переключение «Принятые пакеты» / «Вернуться к новому пакету» даёт прочитать её без удаления/отправки черновика. Каталог остаётся слева.

В шторке — только редактируемые позиции и кнопка «Отправить пакет». Скидка, сумма нового пакета, общий итог и кнопки оплаты остаются в нижнем блоке корзины. Оплачивается весь заказ существующим atomic checkout; отдельной оплаты пакета нет. После подтверждённой отправки шторка скрывается и история получает пакет. После очистки новых строк также показывается история. Ошибки/неизвестный результат сохраняют состав.

Анимация и переходы раскрытия отсутствуют. Удалён внешний отступ, унаследованный от общей секции, чтобы шторка действительно занимала всю доступную высоту. Длинные списки прокручиваются внутри, отправка и общий расчёт остаются доступны.

## Пустое посещение после прерванного первого приёма

Существующий TABLE first-send мог уже открыть реальное посещение, но ещё не принять пакет. Для смены такого черновика на COUNTER используется native-действие `cashReleaseEmpty` поверх существующего HTTP `/tables/close-empty`:

1. Перечитывается посещение и отсутствие заказа, сохраняется личный draft.
2. Main process проверяет принадлежность workspace сотруднику и контексту, права целевого COUNTER. В одном защищённом локальном commit сохраняет копию draft в новый scope, прежнее состояние этого scope для отката, pending commandId и заморозку исходного draft.
3. Существующая серверная команда проверяет право `table.close_empty`, объектный доступ, ревизию и пустоту посещения. Если другой клиент уже принял пакет, закрытия не происходит.
4. Подтверждённая квитанция атомарно снимает старое назначение workspace и очищает только перенесённый исходный draft; копия COUNTER остаётся. При окончательном отказе локальное состояние target scope восстанавливается, source размораживается.
5. Потерянный/невалидный ответ сохраняет freeze и pending. После перезагрузки доступен повтор того же commandId; до него новая оплата/отправка/смена типа заблокированы.

`localScopeId` существует только в native bridge, в HTTP body не передаётся. Новой бизнес-команды или отдельной серверной оплаты не введено. Серверная `closeEmpty` теперь возвращает минимальную исходную квитанцию собственной завершённой команды после потери объектного доступа. Новая чужая команда всё так же отклоняется; payload fingerprint и действующее право проверяются. Детали закрытого чужого посещения не раскрываются.

Схема остаётся15, новой миграции нет. Для этого восстановления используются согласованные новые исходники Desktop и Local POS Server.
