## 3. Авторизация и доступ

Новые ключи включать в явную матрицу, не в общий административный фильтр Owner. Существующие grants, role ceilings, audience, branch scope и отзыв проверяются на сервере при каждом действии и replay.

| Право | Default | Допустимый grant / область |
|---|---|---|
| payment.refund | Cashier | Owner/Manager grant; Waiter запрещено;24h плюс нужный исторический scope |
| payment.refund.history | Owner | Manager grant; Cashier/Waiter запрещено; минимальный адресный поиск старого Payment |
| payment.incident.resolve | Owner | Manager grant; Cashier/Waiter запрещено |
| financial.case.view | Owner | Manager grant; разрешает детали филиальных случаев; для остальных сохраняется текущая объектная политика |
| financial.case.record | Owner/Manager/Cashier | Запись известного recovery blocker без создания денег/продажи; Waiter запрещено |
| shift.report.view | Cashier, Owner | Manager grant; Waiter запрещено; только текущая сводка и последний закрытый отчёт в пределах24h |
| shift.report.history | Owner | Manager grant; Cashier/Waiter запрещено; архив сводных отчётов филиала |

`payment.refund.history` не даёт выполнить Refund без `payment.refund`. Owner/Manager могут найти старый Payment, но кнопка действия недоступна без права возврата. Просмотр отчёта не открывает произвольные старые Order/Item. Право close само по себе не даёт исторический архив; открытие/закрытие сохраняют существующие defaults (Cashier), Owner/Manager — только с явным grant. Close возвращает собственный минимальный receipt даже без права чтения сумм; UI предварительно предупреждает, что отчёт сможет открыть сотрудник с правом просмотра.

24h проверять от immutable settled_at исходной продажи, по серверному времени; не от Refund, даты поиска или открытия новой смены. Для Cashier необходимы `sales.view_24h` и `payment.refund`; право не открывает чужой TABLE в обход действующей terminal-read политики A. Owner/Manager с historical scope используют отдельный финансовый DTO, а не расширяют TableService. Lookup принимает точный UUID Payment/Settlement/Order либо точный номер COUNTER вместе с идентификатором исходной смены; не поиск всех клиентов по свободному тексту. Возвращает только нужные для проверки снимок заказа, Payment, его действительность/возврат и исходную смену. Невалидный/чужой ID не раскрывает факт существования. Нужные actor names берутся из исторического снимка.

Сводный отчёт может включать суммы всей смены длительностью более24h по отдельному праву report.view: это осознанное разрешение агрегатов, не обход запрета подробностей старых продаж. Из такого отчёта Cashier не проваливается в недоступный старый Order. Переходы из incident/report имеют самостоятельную проверку, отсутствие доступа не скрывает от close сам факт blocker: показываются тип/количество и «Обратитесь к уполномоченному сотруднику», без состава/банковских данных.

Повторный личный логин/постоянный пароль для close проверяется AuthService.prove вне writer, с текущим actor.id. Внутри writer повторяются статус/роль/право/credential_version. PIN-сессия допускается, но не заменяет пароль. Пароль не сохраняется в pending, commands, audit/outbox, URL или renderer storage; при retry вводится заново. Истечение сессии требует входа тем же исполнителем для восстановления исходной команды; не подменять actor в старом pending.

## 4. Refund отдельного Payment

### 4.1. Prepare и регистрация

1. Из доступной продажи или исторического lookup выбрать конкретный Payment. Показать TABLE/COUNTER, исходный расчёт/смену, метод, полную сумму, автора/время, остальные компоненты mixed и их статусы.
2. Сервер проверяет sealed PAID Settlement, положительную сумму, область доступа и отсутствие Refund. ZERO, отменённый заказ и незарегистрированные внешние деньги не имеют допустимого Payment для возврата.
3. Prepare возвращает неизменяемую сумму/метод, текущую OPEN-смену и confirmationHash. Сумму и метод пользователь не редактирует. Причина — NFC,1–300 Unicode code points после trim, без управляющих символов; правила согласованы с A.
4. Сотрудник выполняет возврат денег наличными либо в банковском приложении/терминале, затем отмечает «Деньги фактически возвращены». POS регистрирует заявление сотрудника, не ответ банка. Нет «возврат банком подтверждён», автоматического ожидания банковского callback или списания денег через API.
5. Native сохраняет commandId и frozen business payload до HTTP. Commit принимает paymentId, currentShiftId, reason, confirmedExternalReturn=true, confirmationHash. actor/branch/amount/method берутся сервером. В writer заново проверяются право, окно/исторический scope, действительность Payment, текущая смена и отсутствие другого Refund.
6. Refund, audit, outbox, result фиксируются вместе. Только после commit UI пишет «Возврат зарегистрирован». Потеря ответа → проверка/повтор той же команды; повторная фактическая выдача денег запрещена.

Refund не открывает заказ/посещение, не меняет исходный PAID, seal, сумму заказа, CUSTOMER или видимость COUNTER. В read DTO добавляется отдельный производный признак возвратов: NONE / SOME_PAYMENTS / ALL_PAYMENTS. SOME_PAYMENTS означает полный возврат одной составляющей mixed, а не частичный Refund и не PARTIALLY_PAID.

UNIQUE(branch_id,payment_id) в Refund защищает от разных commandId/процессов; source Payment и Refund сопоставляются составным FK/trigger по branch, Settlement, Order, исходной смене, методу и полной сумме. Нельзя Refund после будущего Reversal; пока Reversal отсутствует, проверяется действительный первичный sealed Payment. Сумма позднего Refund принадлежит текущей смене регистрации, original_shift_id остаётся ссылкой.

### 4.2. Граница внешнего действия

Локальный сервер не способен атомарно связать SQLite с выдачей наличных/банком. Два сотрудника могут физически вернуть деньги до того, как UNIQUE остановит вторую регистрацию. UI показывает предупреждение о единственном исполнителе; кнопка блокируется на время запроса. Проверка сохранённого результата обязательна при любой неизвестности. Межтерминальной гарантии единственной внешней выдачи в B нет; её потребовала бы отдельная процедура резервирования/владения операцией.

Если деньги уже возвращены, а close другого терминала победил раньше регистрации Refund, старая команда получает SHIFT_CHANGED/SHIFT_NOT_OPEN; нельзя автоматически записать её в следующую смену. Создать связанный денежный case при действующей смене, предъявить исходный Payment и доказательство; затем уполномоченный сотрудник решает дальнейшую регистрацию. Не выдавать такую ситуацию за совершённый Refund без локального commit. Неизвестный исход, дубли внешней выдачи и перевод другим методом не исправляются произвольным новым Payment.

## 5. Денежные инциденты и blockers

### 5.1. Модель

Существующие payment_incidents и их state=OPEN не переписывать. Ввести append-only `payment_incident_resolutions`: одна запись на incident, outcome, linkedSettlementId либо externalReturns[], reason/evidenceNote, currentShiftId, actorId/name, createdAt, commandId. Эффективное состояние OPEN выводится отсутствием resolution; RESOLVED — её наличием. Новый API фильтрует эффективное состояние, старые ID/содержимое сохранены. Свободный произвольный UPDATE state или DELETE запрещены.

Инцидент — факт известного расхождения, не денежная проводка. Известные поступления, сопоставления и внешнее урегулирование показывать отдельным разделом отчёта, без добавления в Payment/Refund. Для случаев с неполными исходными сведениями сохранять UNKNOWN и блокировку; не подставлять нули вместо неизвестных сумм.

Допустимые исходы:

| Outcome | Условия | Финансовый эффект |
|---|---|---|
| MATCHED_SETTLEMENT | Найден единственный действительный sealed Settlement того же заказа; проверен source command; документировано соответствие каждого известного поступления методу и сумме, а также получение остатка | Новых денег/Settlement нет, ссылка на существующий |
| EXTERNAL_RETURN | Документирован полный возврат именно незачтённых внешних поступлений по каждому методу; сохранены сумма/время/примечание и заявление исполнителя | Нет фиктивного Refund; заказ остаётся в действительном состоянии и отдельно оплачивается/отменяется |

Для draft incident MATCHED_SETTLEMENT допустим только с проверяемой серверной цепочкой исходный frozen command/draft → принятый COUNTER → Settlement. Произвольного выбора похожей продажи по сумме недостаточно. Если цепочки нет, case остаётся OPEN. При несовпадении/переплате/повторном внешнем поступлении/уже возвращённом Payment одного совпадения общего итога недостаточно; спорный случай не разрешается автоматически. Один Settlement не используется для списания нескольких независимых внешних поступлений: сервер исключает повторное зачтение одной идентифицированной receipt-связи; если идентичность подтвердить нельзя, resolve запрещён. Дубликат incident не удаляется и не объявляется EXTERNAL_RETURN: требуется подтверждённая связь с тем же источником и теми же уже документированными поступлениями, иначе остаётся спорным.

Для EXTERNAL_RETURN нужно подтвердить, что средства не были зачтены в POS. Проверяется source command и текущее состояние заказа; при существующем соответствующем Payment используется Refund-процедура, а не этот исход. Разрешение после обычного полного расчёта возможно отдельной командой; наличие Settlement само по себе incident не закрывает. Evidence — ограниченный текст до1000 code points и безопасные внутренние ссылки; без вложений/банковских секретов/номера карты/PIN/CVV. Инициатор и разрешающий сохраняются отдельно. Это сверка уже существующего факта либо внешнего возврата, не финансовый MANUAL_RECOVERY.

### 5.2. Recovery и поздние случаи

Ввести отдельный immutable `financial_cases` с типом RECOVERY_REVIEW/EXTERNAL_REFUND_DISPUTE, текущей blockingShiftId, исходной shift/order/payment/sourceCommand ссылкой при наличии, причиной, известными суммами либо UNKNOWN, actor/time. Поля ссылок проверяются по branch; клиент не назначает CLOSED-смену как текущую. Это позволяет реально зарегистрировать известную проблему, для которой в A нет формы. Открытые payment_incidents входят в общий blockers query непосредственно, без копирования каждого в financial_cases.

Финансовый MANUAL_RECOVERY и разрешение спорного EXTERNAL_REFUND_DISPUTE новыми проводками в B не реализуются: форма честно сообщает, что дальнейшая финансовая процедура D09/R01 не согласована. Нет общего endpoint «разрешить recovery» и возможности убрать blocker отметкой. Если известен такой неразрешённый случай, нормальное close недоступно до отдельного согласованного решения/реализации. Это ограничение пилота, а не причина подставить «0 инцидентов». Два подтверждающих D09 не заменяются одним Owner.

Поздно обнаруженный случай хранит originalShiftId закрытого периода и blockingShiftId текущего; исходный отчёт не меняется. Отсутствие OPEN не должно мешать сообщить о расхождении: для новых financial_cases предусмотреть branch-level hold без blockingShiftId, который блокирует ближайшую OPEN до урегулирования; открытие смены допускается с явным предупреждением, новые обычные действия — по текущим правам. Исходные payment_incidents A по-прежнему создаются в OPEN. Не переносить автоматически старые финансовые обязательства при close.

### 5.3. Настоящая проверка close

Blockers вычисляются сервером по полному branch-scope SQL, не из первых100 видимых пользователю строк:

- Любое OPEN table_session, включая пустое посещение без Batch. Ссылка на стол/посещение в рамках прав.
- Любой подтверждённый OPEN COUNTER/UNPAID, включая нулевой итог с непройденным ZERO-завершением. Локальный непринятый draft не блокирует серверную смену.
- Все эффективные OPEN payment_incidents и неразрешённые financial_cases филиала, включая branch-level hold и поздний case текущего периода. Несогласованная legacy-связь не игнорируется, а диагностируется.
- Нарушенная согласованность финансового графа/невозможность устойчивой записи — безопасный отказ с диагностикой, а не «успешно закрыто».

Print PENDING/UNKNOWN/failure, отсутствие интернета/Telegram, видимый COMPLETED COUNTER не blockers. Локальный pending на данном Desktop показывается предупреждением и сначала проверяется исходная команда; это не глобальный серверный список: чужой native pending сервер не видит. In-flight серверные мутации упорядочены BEGIN IMMEDIATE: нет отдельно висящего наполовину записанного Payment. Для внешних неизвестных фактов нужен case, а не предположение о состоянии клиентских окон.

## 6. D08 — словарь и примеры отчёта (предложение R-B4)

### 6.1. Правила отбора

У каждого показателя стабильный metric key, версия определения, единица count/tyiyn, источник, формула, TABLE/COUNTER applicability. При реализации описать это в machine-readable `report-metrics.ts` и в API-документе. Формулы ниже — контракт, не произвольные подписи UI.

Отбор по shift_id факта, а не по календарным суткам/локальному времени. Settlement и Payment принадлежат исходной смене расчёта; Refund — смене его регистрации. Refund прошлого периода получает TABLE/COUNTER исходного заказа, а не тип текущего рабочего экрана. В одном срезе БД формируются preview/итог; конечный snapshot сериализуется канонически с schemaVersion=1/metricsVersion=1 и SHA256. Исправления исходных позиций учитываются по историческим ценам, не по текущему меню.

| Metric key / подпись | Формула и смысл |
|---|---|
| completed_count / Завершённые заказы | Число sealed PAID + ZERO_SETTLED; каждый Settlement один раз, mixed не два заказа |
| paid_count / Положительные расчёты | Число PAID; последующий Refund не уменьшает число исторических продаж |
| zero_count / Нулевые расчёты | Число ZERO_SETTLED с действующими позициями; сумма к оплате0, Payment отсутствует |
| finalized_subtotal / Позиции завершённых заказов до скидки | Σ snapshot.subtotal завершённых PAID/ZERO, после отмен/замен, по оставшимся порциям |
| finalized_discount / Скидки завершённых заказов | Σ snapshot.discount PAID/ZERO; не сумма всех промежуточных назначений скидки |
| finalized_fees / Сборы | Σ snapshot.fees[].amount; отдельно по стабильному fee ID и историческому названию/ставке; COUNTER0 |
| completed_amount / Сумма завершённых заказов | finalized_subtotal − finalized_discount + finalized_fees; равна Σ Settlement.amount |
| payments_registered / Зарегистрированные оплаты | Σ Payment.amount; по каждому из3 методов, типу заказа и общая. Без incident, Refund и ZERO |
| refunds_registered / Зарегистрированные возвраты | Σ Refund.amount текущей смены; раздельно из текущей/прошлых исходных смен, по методу/типу; число Refund отдельно |
| registrations_difference / Разница оплат и возвратов | payments_registered − refunds_registered, допускает отрицательное; по методу и типу. Не чистая выручка/прибыль/остаток кассы |
| cancelled_orders_count / Полностью отменённые заказы | COUNT distinct Order со статусом CANCELLED и этой shift_id; не входят в completed_count |
| accepted_items_amount / Принятые позиции | Σ исходных Item.unitPrice×quantity всех подтверждённых Batch этой смены, включая заменяющие; до скидки/сборов; не денежная выручка |
| removed_items_amount / Отменённые позиции до скидки | Σ correction_lines.quantity×исторический unitPrice для отмен/замен/CANCEL_ORDER; CHANGE_COMMENT исключён; одну порцию нельзя списать дважды |
| replacement_removed_amount / В том числе заменено | Подмножество removed_items_amount только REPLACE_ITEM; не прибавлять повторно к отменам |
| batches_count / Принятые пакеты | COUNT Batch, включая заменяющие; replay не увеличивает |
| visits_opened/closed/empty / Посещения | COUNT сохранённых TABLE sessions этой смены; EMPTY — close_reason=EMPTY; дополнительно PAID/ZERO_TOTAL/CANCELLED counts |
| known_cases / Сверка известных случаев | Количество зарегистрированных/разрешённых случаев и подтверждённые суммы незачтённых поступлений/внешних возвратов; отдельное информационное приложение, не Payments/Refund |

Общие суммы и TABLE/COUNTER считаются из одной выборки. При успешном close нет незавершённых подтверждённых заказов; тогда accepted_items_amount − removed_items_amount = finalized_subtotal. Это контроль состава, не формула выручки. В preview при OPEN отдельно показаны subtotal/discount/fees/total действующих незавершённых заказов, не смешанные с completed_amount. Для полностью отменённых заказов финальные скидка/сборы равны0 в итогах завершённых; их изменения видны в истории событий, не суммируются как предоставленная скидка. Цена0 и скидка100% различаются subtotal/discount, хотя оба дают ZERO.

Сервисные сборы рассчитываются существующим pricing: база subtotal−discount; каждый сбор отдельно HALF_UP по basis points, без начисления сбора на другой сбор. Отчёт суммирует сохранённые округлённые суммы заказов; не пересчитывает процент с общего subtotal. Все агрегаты вычисляются BigInt/SQLite integer с проверкой: individual MAX_MONEY нельзя ошибочно применять как предел всей смены. DTO денежных агрегатов — десятичные строки целых тыйынов, включая отрицательную разницу; renderer не складывает их через float. Число записей ограничивается безопасным integer; overflow даёт отказ, не округлённый успех.

### 6.2. Обязательный финансовый вектор

Ниже суммы **в сомах для чтения**, в тестах целые тыйыны.

| Событие смены S | Тип | Subtotal | Скидка | Сбор | Расчёт/оплаты |
|---|---|---:|---:|---:|---|
| Заказ A: принято1200, отменено200; расчёт | TABLE | 1000 | 100 | 90 (10% от900) | PAID990: CASH400 + CARD590 |
| Заказ B | COUNTER | 500 | 0 | 0 | PAID500: QR500 |
| Заказ C, скидка100% | COUNTER | 200 | 200 | 0 | ZERO0, Payment нет |
| Заказ D, полная отмена принятого300 | COUNTER | 0 | 0 | 0 | CANCELLED, Payment нет |
| Полностью возвращён Payment CASH заказа A | TABLE | — | — | — | Refund400 в S |
| Возвращён QR Payment прошлой смены S−1 | COUNTER | — | — | — | Refund700 в S, старый отчёт неизменен |

Ожидается: completed_count3 = paid2 + zero1; cancelled_orders1. accepted_items_amount2200, removed_items_amount500; finalized_subtotal1700; discount300; fees90; completed_amount1490. Payment1490 = CASH400 + CARD590 + QR500. Refund1100 = текущая400 + прошлая700. Разница регистраций390 = CASH0 + CARD590 + QR(−200). TABLE: completed990, payments990, refunds400, difference590. COUNTER: completed500, payments500, refunds700, difference−200. MixedA — одна продажа и два Payment, возвращён только CASH, поэтому SOME_PAYMENTS; исходная сумма заказа990 не переписана.

Дополнительные векторы: только late Refund700 → completed0/payments0/refunds700/difference−700; пустая смена → финансовые0 без выдуманного cash balance; цена0 и100% скидка; несколько сборов/округление на границе тыйына; замена блюда100 на150 → accepted250, removed100, finalized150; изменение комментария → removed0; последовательные скидки100→50 дают final50, не150. Сумма всей смены больше лимита одного заказа; разделение одинаковых fee ID с изменявшимся историческим названием/ставкой без потери детализации. Информационные поступления incident не добавляются повторно к последующему сопоставленному Settlement.

### 6.3. Состав неизменяемого документа

Restaurant/branch display snapshot, shift ID, openedAt/closedAt, открывший/закрывший actor ID+name, часовой пояс Asia/Bishkek, продолжительность с признаком аномалии часов при отрицательной разности; версия приложения/схемы/формул, report ID/hash. Итоги и TABLE/COUNTER, методы, текущие/прошлые Refund; контрольные количества, ссылки на неизменяемые факты и отдельное приложение разрешённых incidents. Хеш — проверка содержимого, не электронная подпись. Закрытие фиксирует snapshot; GET читает его, не пересчитывает по текущим именам/меню или поздним возвратам. Открытый preview помечен «Предварительный, смена открыта» и не хранится как финальный отчёт.

## 7. D05 — отдельное предложение по Reversal

Рекомендуемый объём B: **недоступен**, с понятной причиной в интерфейсе при наличии права; нет фиктивного успешного API. Ошибочный метод не исправляется Refund+новой продажей, потому что Refund означает фактический возврат денег. Это ограничение явно остаётся в PROGRESS и пилотных воротах.

Для дальнейшего отдельного согласования предлагается узкая процедура исправления только распределения методов при неизменной сумме/составе завершённого заказа:

- Единица операции — весь действительный Settlement, включая обе mixed-составляющие. Атомарно создаются immutable reversal всех его Payment и один связанный replacement full-settlement той же суммы; Order/первичная история/посещение не открываются. Это потребует отдельного adjustment ledger и проверки действительного leaf цепочки, а не обхода seal схемы7.
- Owner default / Manager grant, Cashier недоступно по предлагаемому ceiling; причина обязательна. Нельзя исправить Settlement с любым Refund/неразрешённым денежным case. Предложение не меняет уже согласованное право и неизменность первичного факта.
- Если исходная смена OPEN, операция относится к ней. После CLOSED — только текущая OPEN с исторической ссылкой и отдельными отрицательными/положительными регистрационными корректировками методов; исходный отчёт неизменен, completed_amount не начисляется второй раз. Эти дельты показываются отдельными метриками, не как банковские поступление/возврат.
- Повторное исправление может касаться только текущего действительного replacement leaf, CAS по revision и UNIQUE successor предотвращают две ветки. Исходные/погашенные Payment запрещены для Refund; вернуть можно только действительные компоненты leaf. Полный audit chain не удаляется.
- Пример1500 CASH→CARD: исходная продажа1500 остаётся; корректировки CASH−1500/CARD+1500, общий денежный итог исправления0. Mixed CASH800+QR1200→CARD2000 изменяет все компоненты единым фактом, не оставляет действительным QR1200.
- Ошибочно объявленная оплата, когда денег вообще не было, изменение суммы/состава, повторное обслуживание гостя и спорная внешняя выдача в это узкое предложение не входят. Их нельзя провести через фиктивный replacement0/ZERO или открыть старый стол. Требуется отдельное решение финансовой процедуры.

Подтверждение R-B6 означает **отложить реализацию**, не принять перечисленные будущие проводки. Если нужен Reversal в B, сначала отдельно утверждаются этот сценарий, ограничения и дополнение словаря D08; затем пересматриваются DB/API/UI и векторы.

## 8. Закрытие смены: атомарный контракт

### 8.1. Подготовка

`GET close-context` возвращает текущую смену/ревизию, blockers counts, безопасные ссылки и доступный preview. `POST close/prepare` формирует fingerprint фактов, определяющих итоги, blockers и состояние смены. Include Payment/Refund/Settlement/Batch/Correction/Session/case-resolution frontier, версии формул; не использовать только shift.revision, потому что операции A сейчас её не увеличивают. Можно считать канонический hash фактического набора в одной согласованной read transaction. Новый факт между prepare/commit делает confirmation stale. Hide завершённой карточки и изменения print/delivery attempt не меняют финансовое подтверждение.

### 8.2. Commit

Ввод личного логина/пароля → prove вне writer → CommandBus BEGIN IMMEDIATE. Authorize проверяет текущие credentials/право, затем journal replay. Для **новой** команды проверяются expectedShiftId/revision/hash, все blockers и согласованность; считаются финансовые итоги из того же среза. В одной транзакции сохраняются shift_closure, immutable shift_report, status=CLOSED/revision+1, audit, durable outbox event с report ID/hash и commands.result. closedAt и actor snapshot едины. Сбой любой записи откатывает всё; никакой сети/печати/парольного хеширования внутри writer.

Повтор исходной команды после успешного close должен вернуть тот же receipt, даже когда уже открыта следующая смена. Поэтому проверка «та же OPEN»/stale/blockers находится после journal lookup, не в authorize. Право/actor/credential-version всё равно проверяются на replay. Иные close commandId для CLOSED не создают новый отчёт и не закрывают новую смену: SHIFT_ALREADY_CLOSED/SHIFT_CHANGED. Клиентский payload всегда содержит конкретный shiftId.

### 8.3. Конкуренция

Если Batch/checkout/Refund/incident выигрывает writer первым, close видит новые факты и требует новый prepare; при активном заказе/case показывает blocker. Если close выигрывает, новая финансовая команда старой смены получает SHIFT_NOT_OPEN/SHIFT_CHANGED, не переезжает в новую. Все мутации, способные создать blocker или изменить отчёт, проверяют OPEN внутри общей транзакции; дополнительно SQL guard не позволяет вставить Payment/Refund/Batch/новый Order к CLOSED или менять её исторические totals. Branch-level case, записанный после close, не правит отчёт; блокирует следующую смену.

Нет CLOSE_PENDING как долговременного состояния, переоткрытия, массового удаления черновиков, закрытия заказов «заодно» или переноса активных обязательств. Непринятый локальный draft остаётся сохранённым; перед работой в следующей смене требует нового server context/цен и подтверждения. Фото/скриншот/печать отчёта не являются подтверждением close; подтверждение — сохранённый receipt/report ID.

## 9. SQLite и миграция008

Миграция новая, исходники/checksums001–007 не меняются. Сохраняются первичные ID, command receipts, actor references, snapshots, print jobs/dependencies, PIN binding. FK включены; подготовленная миграция проходит fresh и заполненные schema7/предыдущие fixtures. Не менять CHECK state='OPEN' существующих incidents ради удобства; эффективный status через связанные факты.

Предлагаемые таблицы:

| Таблица | Минимальные факты / ограничения |
|---|---|
| refunds | id,branch_id,payment_id,settlement_id,order_id,original_shift_id,shift_id,method,amount>0,reason,external_return_confirmed=1,actor_id/name,created_at,command_id; UNIQUE payment и command; FK/trigger полной суммы/метода/branch; immutable |
| payment_incident_resolutions | id,branch_id,incident_id UNIQUE,outcome,current_shift_id,linked_settlement_id nullable,details,actor_id/name,time,command_id UNIQUE; outcome-specific CHECK/FK/guards; immutable |

При реализации уточнить порядок взаимных closure/report FK (например, deferred FK либо однонаправленная связь и UNIQUE), проверить обязательность обоих фактов до COMMIT. Защитить CLOSED от изменения/удаления и повторного закрытия; существующий shifts не расширять nullable полями, допускающими ложный неполный CLOSED. Старые синтетические/неизвестные CLOSED без нового отчёта не дополнять выдуманными totals: явно legacy/no-report. В fixtures миграции это ожидаемое состояние; для реальной установки требуется отдельный preflight.

Индексы: refunds(branch,shift,method), originalPayment UNIQUE, resolutions(branch,incident), cases(branch,blocking_shift), reports(branch,closedAt/shift), пагинация Payment/incident по стабильным ключам. Неограниченные списки в renderer не загружаются; полный blockers COUNT на сервере не зависит от page limit.

Обновление реальной установки остаётся D11/D13: startup не мигрирует, явная миграция запрещена при OPEN. Старый source без close и с OPEN не обновлять обходом SQL/удалением БД. B сначала проверяется на изолированных базах. Production переход/backup/restore согласуются отдельно; этот документ не разрешает трогать .local/MANGO/Windows-установку.

Ошибка не возвращает недоступный состав заказа. Payload успешного own replay минимален; details идут через отдельный read с текущими правами.

## 11. Интерфейс Desktop RU/KY

### 11.1. Продажа и возврат

В деталях продажи отдельный блок «Оплаты»: строка на каждый Payment, метод/сумма/состояние, действие «Вернуть платёж полностью» по allowedActions. Mixed не получает общей кнопки частичного возврата/возврата всего расчёта. После одного Refund другая составляющая остаётся доступной. Показать историю Refund с причиной/автором/сменой; исходные сумма продажи/чек остаются первичными.

Диалог: шапка TABLE/COUNTER и исходная дата → неизменяемые метод/полная сумма → причина → предупреждение о ручном возврате → checkbox фактического выполнения → footer «Отмена» / «Зарегистрировать возврат … сом». Footer отдельный от прокручиваемого тела, кнопки не перекрывают поля. Для карты/QR прямой текст «Выполните возврат во внешнем приложении. POS только сохраняет запись». Неполная причина/checkbox/нет смены отключают submit, сервер повторяет проверку. Success «Возврат зарегистрирован», UNKNOWN «Результат регистрации неизвестен — проверьте исходную команду; повторно деньги не выдавайте».

Исторический lookup — отдельное действие для уполномоченных на экране финансов, с вводом точной ссылки/исходной смены. Не добавлять Cashier произвольный календарь всех продаж. Если продажа вышла из24h во время диалога, не подменять права: предложить обратиться к уполномоченному сотруднику; уже записанный own receipt восстанавливается без выдачи состава.

### 11.2. Инциденты

На экране смены карточка «Денежные случаи» с числом OPEN и непогашенными recovery holds. Обычный сотрудник видит доступные ему случаи и общее число blockers без секретных деталей. Уполномоченный — фильтры OPEN/RESOLVED и полные карточки; экран не ограничивается первой сотней. «Сообщить о расхождении» доступно и без OPEN для branch-level случая.

Карточка: исходный Order/draft/command и период, известные receipts или «сумма неизвестна», кто/когда сообщил, причина, исход/доказательство при разрешении. Действие «Сверить» только по resolve right: выбрать MATCHED_SETTLEMENT либо EXTERNAL_RETURN, заполнить проверяемые ссылки/полную сверку, посмотреть before/after и подтвердить. Для RecoveryReview/спорного внешнего Refund показывать конкретное ограничение D09/R01; общей кнопки «закрыть проблему» нет. Наличие подходящего обычного Settlement не запускает resolve автоматически.

### 11.3. Смена, закрытие и отчёт

Экран смены: открывший/дата/время → текущая предварительная сводка по правам → «Что мешает закрытию» → кнопка «Проверить и закрыть». Списки активных столов/COUNTER и cases с переходами по правам. Закрывать пустое посещение или отменять заказ можно только отдельным штатным действием. Печать/интернет отражаются информационно и не окрашиваются как financial blocker.

Close-диалог: шапка конкретной смены; предварительные суммы/методы/возвраты текущих и прошлых продаж при report.view; blockers; личный логин и пароль; footer «Назад» / «Закрыть смену». Без ввода физического наличного остатка. До HTTP сохранить безопасный pending без пароля. При stale показать новые цифры/причину и запросить новое явное подтверждение, не повторять автоматически старое намерение на новых условиях. Во время submit disable, при неизвестном исходе — восстановление того же commandId.

После commit показать CLOSED с актором/временем и кнопкой локального отчёта по правам. Отчёт: метаданные → завершённые заказы и TABLE/COUNTER → зарегистрированные оплаты по методам → возвраты (текущие/прошлые) → разница регистраций → отмены/скидки/сборы/ZERO → сверка известных случаев. Явные «Внутренний отчёт», «Банк не подтверждён автоматически», статус доставки «Не подключена» при отсутствии worker. Не создавать фиктивный статус «Доставлен». Экспорт/PDF/реальная печать/Telegram не входят автоматически в B.

Формы доступны клавиатурой, видимый focus, Escape/backdrop закрывают только до отправки без потери уже сохранённого pending; Enter в textarea/пароле не вызывает необратимое действие неожиданно. Смена языка не очищает введённую причину и frozen команду. Проверить1024×768 и1366×768, масштабирование/длинные RU/KY, прокрутку и отдельный footer. Native main держит token, хранит encrypted draft/pending, добавляет whitelist новых действий; renderer не получает произвольный fetch/API path.

## 12. Порядок реализации и приёмка

После подтверждения выполнить крупный согласованный блок:008 и constraints → Refund/cases → report dictionary/preview → close → Desktop/RU/KY/pending → автоматические/доступные Electron проверки → актуальные PROGRESS/README/API-SHIFT-FINANCE-008. Сначала определить финансовые DTO/векторы, затем одновременно проверять server и UI, не просить Windows-тест после каждого небольшого изменения.

Обязательные автоматические сценарии:

1. Refund single/mixed: точная полная сумма, каждый Payment отдельно, нетZERO/частичного/чужого/повторного, неизменность оригинала; reason/метод/внешнее подтверждение; поздний Refund текущей смены.
2. Same-ID replay после restart и после открытия следующей смены; разные commandId и два реальных SQLite процесса дают один Refund/close/report. Текущий revoke/роль/24h проверяются и на replay; пароль close не попадает в persisted DTO.
3. Failure injection Refund/report/closure/audit/outbox/commands-result и физической невозможности записи: полный rollback, исходная OPEN и отсутствие полурезультата. Print/доставка не входят в transaction.
4. Close↔checkout/Batch/table.open/Refund/incident/resolve и два close. Старый closeId не закрывает следующую смену, stale финансовое подтверждение не принимается. Для разрешённого close нет ни одного активного посещения/неоплаченного COUNTER/известного неразрешённого case.
5. Более100 blockers, недоступные пользователю cases, пустой TABLE, zero-but-OPEN COUNTER, masked completed card старше24h. Print PENDING/failure, отсутствие интернета и VISIBLE оплаченная карточка не блокируют close.
6. Incident: исходные OPEN неизменны, правильные effective состояния; неподтверждённый/неверный/mismatched/cross-branch Settlement не разрешает; draft ancestry и receipt reuse; деньги без Payment не создают фиктивный Refund; no-op resolve запрещён. Поздний/branch-level hold сохраняется после restart и препятствует следующему close.
7. Словарь §6: точные целые суммы/строковые aggregates, отрицательная разница, mixed один заказ, поздний Refund не меняет bytes/hash оригинального report, cancellation/replacement/comment/скидки/fees/zero/пустая смена/большие totals.
8. Migration fresh и заполненные7→8, все поддержанные старые пути, FK/integrity, неизменность001–007/истории/receipts/PIN; отказ при OPEN и legacy CLOSED без выдуманного отчёта. Старые тесты CommandBus/Table/Order/Auth/Finance сохраняются и дополняются предметно.

Electron на disposable данных: Refund смешанного Payment; старый доступ/revoke; incident MATCHED/EXTERNAL_RETURN/hold; blockers→штатное завершение→close; личный пароль при PIN-входе; потеря ответа и restart Desktop/server→исходный retry; offline чтение final report; следующий shift; RU/KY и размеры. Скриншоты отчёта, Refund и close-диалога визуально проверить. Тесты не выполняют настоящий банковский возврат.

Раздельно фиксировать static/tests, Electron/macOS, Windows/SCM/DPAPI/4ГБ, реальный банк/принтер/облако, restore/power-loss. Последние не объявлять PASS по fixture. Ручная Windows/оборудование приёмка — единым циклом после крупного блока. До production остаются D05 при необходимости Reversal, D09/R01 спорные восстановительные операции, D11/D13 переход/backup/restore, C печать/Waiter и согласованный пилотный состав/ККМ D16.

## 13. Критерий завершения локального B

Полный обычный Refund, доказуемое разрешение предусмотренных денежных incidents, реальные blockers, атомарный close и сохранённый report по утверждённому D08 доступны через защищённый API и Desktop RU/KY; потерянный ответ не создаёт дубль; поздний Refund не правит прошлый отчёт; текущие проверки и приёмочные векторы пройдены. Reversal и финансовый MANUAL_RECOVERY явно недоступны в согласованной границе. Наличие открытого hold честно блокирует close, а не маскируется под завершённую D09-процедуру. Существующие установки не обновлены без отдельного согласованного безопасного перехода.
