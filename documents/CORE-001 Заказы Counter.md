# 1. Назначение, цель и границы

## 1.1. Назначение

Раздел определяет поведение **заказов на вынос (`COUNTER`)**, оформляемых через Bashkar POS Desktop, без открытия физического стола и сущности Table Session. Цель — минимальное число действий при продаже кофе, еды навынос, готовых товаров и других позиций; при этом сохраняются принятые пакеты, финансовый аудит, печать, история и работа без интернета.

## 1.2. Границы документа

**Включено:** создание и нумерация COUNTER; необязательное имя гостя; черновик; подтверждение одного/нескольких пакетов; быстрый и отложенный расчёт; нулевой расчёт; завершение; список завершённых заказов для удобства выдачи; ручное скрытие карточки; стоп-лист и контейнеры как товары; обозначение «НА ВЫНОС» на кухонном чеке; отмена, ошибки, права, смены, отчёты, аудит, конкуренция и восстановление.

**Не входит:** управление готовностью кухни, подтверждение физической выдачи, KDS, интеграция банков, онлайн-доставка, склад, фискализация, перенос COUNTER в TABLE, автоматическая отмена оставленных заказов, частичные оплаты/возвраты и реализация физических таблиц либо эндпоинтов.

## 1.3. Два и только два типа обслуживания

В MVP разрешены только:

- **`TABLE` / «В зале»** — работа в контексте реального стола и его Table Session.
- **`COUNTER` / «На вынос»** — отдельный заказ без Table Session.

Не создаётся промежуточный вариант «COUNTER в зале». У COUNTER нет `table_id`, не существует привязки к занятому столу и не применяются дополнительные процентные сборы для обслуживания в зале. Изменение `order_type` после создания запрещено; ошибку исправляют допустимой отменой и новым заказом.

## 1.4. Принципы Local-First

Все подтверждённые команды проверяет **Local POS Server**; локальная SQLite является операционным источником истины филиала. Синхронизация с Supabase, Owner Dashboard и Telegram не входит в критический путь. Интернет не требуется для создания, печати, оплаты, отмены, скрытия карточки или завершения кассовой смены. При отказе Local POS Server интерфейс не должен представлять незафиксированное действие как успешное.

# 2. Словарь и бизнес-сущности

| Сущность / понятие | Значение | Важные ограничения |
|---|---|---|
| `Order` (`COUNTER`) | Основной заказ на вынос | Один заказ может содержать несколько пакетов; не имеет Table Session |
| `Order Batch` | Подтверждённый пакет новых позиций | Неизменяемая история; отправитель фиксируется |
| `Order Item` | Принятая позиция с количеством, вариантами, комментариями и ценой | Снимок цены и настроек при принятии |
| `Counter Draft` | Неподтверждённая корзина | Не является серверным заказом или продажей; не блокирует смену |
| `Counter Number` | Короткий последовательный номер для человека | Уникален только **в пределах филиала и смены**, не заменяет постоянный ID |
| `Guest Label` | Необязательное имя или краткая пометка для выдачи | Не является основанием для идентификации/авторизации гостя |
| `Settlement` | Одно логическое завершение расчёта | При платном расчёте связывает Payment; при нулевом — без Payment |
| `Payment` | Зарегистрированная денежная составляющая расчёта | В MVP нет частичных оплат |
| `Zero Settlement` | Завершение счёта на ноль при действующих позициях | Финансовый результат `ZERO_SETTLED`, без фиктивного Payment |
| `Order Correction` | Корректировка принятого пакета | Не стирает исходные позиции и историю кухни |
| `Package Item` | Обычный товар каталога, используемый как контейнер | Может иметь цену 0 или положительную; оформляется отдельной позицией |
| `Packaging Suggestion` | Предложение добавить контейнер при выборе определённого блюда | Не добавляет товар без подтверждения человека |
| `Print Job` | Постоянное задание типа `KITCHEN` или `CUSTOMER` | Ошибка печати не удаляет заказ и не отменяет оплату |
| `Counter Worklist Entry` | Карточка завершённого заказа в рабочем списке | Видимость независима от финансового и операционного статуса |
| `Cash Shift` | Активная кассовая смена филиала | В MVP одновременно одна открытая смена |

Логические ссылки: **Branch → Cash Shift → COUNTER Order → Order Batches → Order Items**; для расчёта — **Order → Settlement → Payment(s)** либо **Order → Zero Settlement без Payment**; для печати и синхронизации сохраняются связанные задания и события. Структура — концептуальная, не схема SQL.

# 3. Состояния и инварианты

## 3.1. Операционное состояние COUNTER

| Состояние | Значение | Обычные изменения заказа |
|---|---|---|
| `ACTIVE` | Существует хотя бы один успешно подтверждённый пакет; заказ ещё не завершён | Разрешены при соблюдении прав и открытой смены |
| `COMPLETED` | Полный платный или нулевой расчёт успешно завершён | Новые пакеты и обычные отмены запрещены |
| `CANCELLED` | Подтверждённый заказ полностью отменён до расчёта с допустимым правом | Новые пакеты и обычная оплата запрещены |

**Черновик (`DRAFT`) не является серверным состоянием Order.** До подтверждения первой непустой корзины Order отсутствует; закрытие редактора или отказ от черновика не требует операции полной отмены заказа.

## 3.2. Финансовое состояние

| Финансовый результат | Условие | Денежные записи |
|---|---|---|
| `UNPAID` | Активный подтверждённый заказ ожидает полного расчёта | Действительного полного Settlement нет |
| `PAID` | Сохранён действительный полный расчёт на сумму больше нуля | Settlement + один или несколько Payment |
| `ZERO_SETTLED` | Стоимость действующего заказа после допустимой скидки равна нулю и расчёт завершён | Сохраняется логический нулевой расчёт **без Payment** |
| `CANCELLED` (бизнес-результат) | Все действующие позиции правомерно отменены до расчёта | Нет фиктивного Settlement/Payment; отмена не считается продажей |

`CANCELLED` как результат отмены и `ZERO_SETTLED` как нулевая продажа **не эквивалентны**. После позднего Refund/Reversal история не переписывается бесследно: отображаются корректирующие финансовые события; обычного автоматического повторного открытия COUNTER нет.

## 3.3. Независимая видимость в рабочем списке

Для завершённого COUNTER имеется признак видимости: `VISIBLE` (по умолчанию) или `HIDDEN` (после нажатия ×). Это **не** признак физической выдачи гостю. Скрытие не меняет `COMPLETED`, `PAID`, `ZERO_SETTLED`, состав заказа, печать, отчёты и историю. Статус видимости общий для филиала, а не для одного браузера; он должен сохраняться при перезапуске.

## 3.4. Таблица разрешённых переходов

| Из | Действие | В | Условие |
|---|---|---|---|
| Нет серверного заказа | Принять первый пакет, отложить оплату | `ACTIVE / UNPAID` | Смена открыта, пакет действителен |
| Нет серверного заказа | Быстро оформить и полностью оплатить | `COMPLETED / PAID` | Одна успешная атомарная операция |
| Нет серверного заказа | Быстро оформить с нулевым расчётом | `COMPLETED / ZERO_SETTLED` | Подтверждённые действующие позиции, итог 0 |
| `ACTIVE / UNPAID` | Дозаказ или допустимая частичная отмена позиции | `ACTIVE / UNPAID` | Актуальные цена и сумма, права |
| `ACTIVE / UNPAID` | Полный платный расчёт | `COMPLETED / PAID` | Итог больше нуля, проверенная оплата |
| `ACTIVE / UNPAID` | Нулевой расчёт | `COMPLETED / ZERO_SETTLED` | Итог 0 при действующих позициях |
| `ACTIVE / UNPAID` | Полная отмена всех позиций | `CANCELLED` | Специальное право полной отмены, причина |
| `COMPLETED / …` | Скрыть карточку | Статус не меняется | Только `VISIBLE → HIDDEN` |

Запрещены: `COMPLETED → ACTIVE`, `CANCELLED → ACTIVE`, повторное обычное завершение того же заказа, приём пакета после завершения и скрытие карточки как эквивалент отмены/возврата.

# 4. Базовые бизнес-правила и типы обслуживания

**BR-CTR-001.** В MVP существует ровно два типа заказов: TABLE («В зале») и COUNTER («На вынос»).

**BR-CTR-002.** COUNTER не создаёт Table Session, не занимает физический стол и не имеет права освобождать стол в результате своей оплаты или отмены.

**BR-CTR-003.** Для COUNTER требуется активная кассовая смена на момент регистрации заказа, нового пакета, обычной корректировки и расчёта.

**BR-CTR-004.** COUNTER использует меню филиала, снимки цен, платные/бесплатные модификаторы и историю исходных пакетов по общим правилам CORE-001.

**BR-CTR-005.** Базовые цены TABLE и COUNTER одинаковы в рамках филиала; **дополнительные процентные сборы к COUNTER не применяются** при любых настройках ресторана.

**BR-CTR-006.** Фиксированная скидка на весь заказ допускается при разрешении сотрудника, но не может приводить к отрицательной сумме.

**BR-CTR-007.** Подтверждённый COUNTER определяется локальной серверной записью; UI не вправе самостоятельно устанавливать статус, цену или факт успешной оплаты.

**BR-CTR-008.** После завершения либо полной отмены COUNTER не может принимать новые Order Batch, независимо от видимости карточки в рабочем списке.

| Создать/подтвердить COUNTER | При наличии права | При наличии права | При наличии права | Не входит в обычный сценарий MVP |

| Завершить нулевой расчёт | При соответствующем праве расчёта | При соответствующем праве | При соответствующем праве | Нет обычного права COUNTER |
| Отменить часть принятого заказа | При праве отмены | При праве отмены | При праве отмены | Только по отдельно согласованной модели; в обычном COUNTER-UX не требуется |
| Полностью отменить принятый заказ | Кассир с соответствующим правом | Менеджер с соответствующим правом | По явно предоставленному праву | Нет обычного права |

Роли служат ориентиром UX; фактические разрешения проверяет Local POS Server. Утверждённый Q01=B не расширяет COUNTER на официантов. Предусмотренный ранее механизм STRICT/SHARED относится к TABLE и не управляет доступом к COUNTER. Один сотрудник может подтвердить заказ, другой — принять оплату, если оба обладают правами. В истории всегда сохраняется фактический исполнитель каждого действия.

## 5.2. Бизнес-правила полномочий

**BR-CTR-009.** Создавать COUNTER в обычном MVP могут Cashier, Manager и Owner при соответствующем серверном разрешении.

**BR-CTR-010.** Проводить расчёт COUNTER могут Cashier, Manager и Owner с правом регистрации оплат, независимо от сотрудника создания.

**BR-CTR-011.** Право отменять отдельные позиции не позволяет обойти отдельное право полной отмены последовательным либо групповым удалением всех действующих позиций.

**BR-CTR-012.** Запрос должен связываться с фактически авторизованным сотрудником; переданный клиентом `employee_id` не является доказательством личности.

**BR-CTR-013.** При отзыве разрешения новая операция должна отклоняться сервером без изменения заказа.

**BR-CTR-014.** Детальный каталог permission-key и локальная идентификация определяются в AUTH-001, а не в этом разделе.

# 6. Черновик, создание и нумерация

## 6.1. Корзина до подтверждения

Сотрудник выбирает товары, размеры, модификаторы и комментарии. Отображение предложения контейнера происходит на этапе добавления подходящего блюда в корзину. Пока подтверждённого пакета нет, корзина остаётся черновиком. Она не печатается, не учитывается в продажах и не блокирует закрытие смены. Успешное подтверждение первой непустой корзины создаёт `COUNTER Order` и `Order Batch` одновременно.

## 6.2. Номер для персонала

При создании сервер выдаёт человекочитаемый **порядковый номер внутри конкретной смены филиала** (`001`, `002`, `003`, ...). Нумерация начинается заново для каждой смены; длина представления может расширяться без ограничения количества заказов. В UI, печати и поиске при необходимости указывается контекст смены, чтобы `№014` из вчерашней смены не путали с `№014` из сегодняшней. UUID остаётся постоянным идентификатором заказа.

## 6.3. Имя гостя

Поле «Имя / пометка» необязательно; его отсутствие не препятствует подтверждению или оплате. Поле предназначено для удобства выдачи и не требует телефона, паспорта или регистрации гостя. Для печати имени на кухонном документе оно может включаться как дополнительная информативная строка, если записано; правки имени после завершения не должны менять финансовую историю.

## 6.4. Бизнес-правила создания

**BR-CTR-015.** Нажатие «Новый заказ» само по себе не создаёт постоянный Order.

**BR-CTR-016.** Пустой черновик запрещено подтверждать как первый пакет; без принятых позиций не создаётся заказ и не выдаётся порядковый номер.

**BR-CTR-017.** Первая успешная отправка непустого пакета атомарно создаёт COUNTER Order и Order Batch.

**BR-CTR-018.** Порядковый номер выдаёт сервер при успешном создании; он уникален в рамках `branch + shift` и не подменяет уникальный ID сущности.

**BR-CTR-019.** Повтор первого подтверждения с тем же `command_id` возвращает прежний результат, не создавая новый Order, Batch или номер.

**BR-CTR-020.** Имя гостя/короткая пометка необязательны, не являются персональным аккаунтом и не влияют на сумму или права доступа.

**BR-CTR-021.** Несколько незавершённых COUNTER-заказов одного филиала могут существовать одновременно.

**BR-CTR-022.** Несколько сотрудников могут последовательно работать с одним доступным заказом; сохраняются фактические создатель и отправители пакетов.

# 7. Подтверждение пакетов, дозаказы и отложенные заказы

После подтверждения первого пакета сотрудник может отложить неоплаченный COUNTER, открыть другой заказ и вернуться позднее. Возможны несколько Order Batch внутри одного Counter Order, но **только до успешного полного/нулевого расчёта**. Принятые пакеты остаются в истории при корректировках. Изменения доступности товаров/цен проверяются перед каждой следующей отправкой; устаревшее меню требует явного подтверждения новых цен, исходные исторические снимки не изменяются.

**BR-CTR-023.** У ACTIVE COUNTER допускается более одного Order Batch.

**BR-CTR-024.** Новый пакет содержит только новые подтверждаемые позиции и не воспроизводит позиции ранее принятого пакета как дозаказ.

**BR-CTR-025.** Отложенный заказ остаётся `ACTIVE / UNPAID` и при дальнейшей работе извлекается из локального сервера.

**BR-CTR-026.** Отложенный заказ не считается завершённым и блокирует обычное закрытие смены.

**BR-CTR-027.** Сервер обязан проверить текущую цену, допустимые варианты, стоп-лист, смену, права, состояние Order и идемпотентность до принятия пакета.

**BR-CTR-028.** При изменившейся цене черновика новая сумма показывается сотруднику для повторного подтверждения; скрытая подмена цены запрещена.

**BR-CTR-029.** После перехода заказа в `COMPLETED` или `CANCELLED` новые пакеты недопустимы.

**BR-CTR-030.** Повторно принятый с тем же `command_id` пакет не создаёт второе кухонное задание.

# 8. Два сценария расчёта

## 8.1. Быстрый сценарий (основной UX)

1. Сотрудник открывает «Заказ на вынос»; серверный Order пока не создаётся.
2. Выбирает товары, размеры, модификаторы, комментарии, подтверждает или отклоняет предложенные контейнеры.
3. Выбирает способ оплаты; при необходимости использует утверждённый сценарий смешанного расчёта.
4. Получает/проверяет средства (для CASH, CARD_MANUAL, QR_TRANSFER_MANUAL проверка факта денег лежит на сотруднике).
5. Нажимает **«Оформить и оплатить»**.
6. Local POS Server перепроверяет меню, права, смену, цену, состав, уникальность команды и факт отсутствия прежнего расчёта.
7. В **одной атомарной локальной операции** создаются Order, первый Batch и Items, Settlement и Payment(s) при сумме больше нуля, итог `COMPLETED / PAID`, необходимые KITCHEN/CUSTOMER Print Jobs, аудит и события синхронизации.
8. Только после фиксации результат считается успешным; заказ появляется в списке завершённых для выдачи. Печать выполняется асинхронно.

Если какая-либо бизнес-проверка не пройдена до фиксации, никакая часть этой быстрой операции не должна превращаться в подтверждённую продажу. В частности, не допускается зарегистрировать денежный Payment без связанного подтверждённого заказа. Сотрудник после возврата актуальной суммы подтверждает её заново.

## 8.2. Сценарий «сначала заказ, потом оплата»

1. Сотрудник формирует корзину и нажимает «Подтвердить заказ».
2. Сервер создаёт `ACTIVE / UNPAID`, первый пакет, необходимые кухонные задания.
3. Гость может ожидать, сотрудник может отложить заказ; дозаказ до оплаты возможен.
4. Когда гость платит, сотрудник открывает существующий COUNTER, видит актуальный состав и стоимость.
5. Выбирает метод, проверяет получение средств и завершает **полную** оплату.
6. Сервер атомарно сохраняет Settlement/Payment(s), `COMPLETED / PAID`, CUSTOMER Print Job, аудит/синхронизацию. Повторное подтверждение не создаёт второй Payment.
7. Заказ остаётся в видимом списке завершённых до ручного скрытия.

## 8.3. Методы и смешанная оплата

Поддерживаются `CASH`, `CARD_MANUAL` и `QR_TRANSFER_MANUAL`. Обычная оплата — на всю серверную стоимость без ввода суммы. Смешанный расчёт — одно логическое завершение с несколькими составляющими, сохраняемыми атомарно по общим правилам CORE-001 «Оплаты и расчёты». Частичные оплаты до окончательного расчёта не разрешены. Ни один платёж не является автоматически подтверждённым банком: банковская операция проверяется сотрудником во внешнем интерфейсе.

## 8.4. Правила расчёта

**BR-CTR-031.** COUNTER поддерживает два UX: быстрый «Оформить и оплатить» и раздельный «Подтвердить заказ → Завершить оплату».

**BR-CTR-032.** Быстрая операция при положительной стоимости должна атомарно фиксировать первый Order Batch, полный Settlement, Payment(s), итог заказа, печать и синхронизационные события.

**BR-CTR-033.** Клиент не должен показывать успешную оплату до подтверждения зафиксированной серверной операции.

**BR-CTR-034.** При обычном расчёте сумму определяет сервер, сотрудник не вводит её вручную.

**BR-CTR-035.** Для COUNTER разрешены CASH, CARD_MANUAL, QR_TRANSFER_MANUAL и согласованная смешанная оплата; внешняя банковская интеграция не требуется.

**BR-CTR-036.** Нельзя повторно завершить уже оплаченный COUNTER обычной командой независимо от используемого `command_id`.

**BR-CTR-037.** Кнопка оплаты недоступна для `CANCELLED` и `COMPLETED`; серверное отклонение обязательно даже при устаревшем UI.

**BR-CTR-038.** Если между показом стоимости и оплатой изменился состав, скидка или применимая цена, оплата по прежней сумме отклоняется с показом нового расчёта.

**BR-CTR-039.** Успешный расчёт не требует подтверждения физической выдачи блюда и не зависит от успешной печати CUSTOMER.

# 9. Нулевой расчёт (ZERO_SETTLED)

Нулевая сумма возможна из-за нулевых цен действующих товаров либо разрешённой фиксированной скидки на весь заказ. Если все позиции были отменены, применяется **полная отмена** `CANCELLED`, а не нулевой расчёт.

Сервер создаёт логическую запись завершения расчёта на `0 сом`, **не создавая ни одного Payment**; заказ переходит в `COMPLETED / ZERO_SETTLED`. Для него формируется внутренний `CUSTOMER` Print Job с перечнем товаров, ценами, скидкой, итогом `0 сом` и обозначением отсутствия полученной оплаты (не указывать метод CASH и фиктивное «получено 0»). При быстром сценарии все связанные данные, включая этот Print Job, сохраняются атомарно. Клиентский чек не объявляется автоматически фискальным документом.

**BR-CTR-040.** `ZERO_SETTLED` применяется только к заказу с сохраняющимися действующими товарами при итоговой сумме ровно ноль.

**BR-CTR-041.** Нулевой расчёт и завершение заказа сохраняются согласованно; `Payment(amount=0)` создавать нельзя.

**BR-CTR-042.** Для нулевого расчёта автоматически создаётся CUSTOMER Print Job с итогом 0 и без ложного указания полученного платежа.

**BR-CTR-043.** `ZERO_SETTLED` учитывается в числе завершённых продаж/заказов, но **не увеличивает суммы денежных поступлений**.

**BR-CTR-044.** Полностью отменённый заказ не может перейти в `ZERO_SETTLED`; применяются основание и правила `CANCELLED`.

**BR-CTR-045.** Как и для обычной оплаты, после `ZERO_SETTLED` запрещены дозаказ и обычная коррекция принятого пакета.

# 10. Завершённые заказы и рабочий список выдачи

## 10.1. Концепция

COUNTER считается `COMPLETED` **сразу после полного/нулевого расчёта**, даже если напиток или блюдо готовятся и гость ещё не получил их физически. В MVP нет отдельной сущности подтверждения выдачи и статусов `READY/DELIVERED`. **Сверка 24.10.2026:** код соответствует этому правилу; обсуждаемая отметка «Выдан» пока предложение, не реализованная команда. «Скрыть» не следует переименовывать в «Выдан» без отдельной модели и истории. При этом для удобства кассира завершённый заказ **остаётся карточкой в рабочем списке**.

Каждая карточка должна позволять посмотреть номер заказа, имя/пометку (если есть), список позиций с количествами и комментариями/модификаторами, сумму и тип/результат расчёта. Сотрудник может вручную нажать «×» / «Скрыть». Это скрывает карточку из общего рабочего списка филиала и переживает перезапуск сервера/клиента. Заказ остаётся в истории, поиске и отчётах. При необходимости по истории его можно просматривать независимо от скрытия.

Рабочий список является **операционной памяткой**, а не гарантированным списком реально невыданных блюд. Скрытие не доказывает выдачу гостю. Оплаченные, но видимые карточки **не блокируют закрытие смены**; старые карточки не должны автоматически превращаться в задолженность при открытии новой смены.

## 10.2. Бизнес-правила видимости

**BR-CTR-046.** После `PAID` или `ZERO_SETTLED` завершённый COUNTER появляется в рабочем списке как `VISIBLE`.

**BR-CTR-047.** На карточке должны быть доступны фактические состав заказа, номер, необязательная пометка гостя, финансовый результат и актуальная информация о корректирующих финансовых событиях, если они имеются.

**BR-CTR-048.** Нажатие «×» меняет только видимость `VISIBLE → HIDDEN` и не удаляет заказ, не является возвратом денег, отменой продажи или подтверждением физической выдачи.

**BR-CTR-049.** Видимость общая для авторизованных POS-сотрудников филиала и сохраняется локально после перезапуска.

**BR-CTR-050.** Скрытый завершённый COUNTER остаётся доступным в истории и в установленной отчётности.

**BR-CTR-051.** Видимая карточка завершённого COUNTER не препятствует закрытию смены, даже если сотрудник ещё не нажал «×».

**BR-CTR-052.** Изменение видимости при повторном запросе с тем же `command_id` не создаёт дублирующихся действий и не меняет финансовую историю.

**BR-CTR-053.** Автоматические статусы «Готов» или «Выдан» и автоматическое скрытие по таймеру не входят в MVP.

# 11. Кухонная и клиентская печать

## 11.1. Только два типа документов

Поддерживаются **KITCHEN** (включая подтип сообщения «ОТМЕНА/КОРРЕКТИРОВКА» в рамках существующего типа) и **CUSTOMER**. Третьего типа печатного чека для COUNTER не вводится. В исходной записи заказа сохраняется связь с Batch, но номер пакета на бумажном чеке не отображается.

## 11.2. KITCHEN: крупный заголовок «НА ВЫНОС»

Для COUNTER в верхней части кухонного чека крупно выводится:

> **НА ВЫНОС**  
> Заказ №014

Для TABLE в соответствующем кухонном документе вместо этой надписи крупно указывается **СТОЛ №7**. Номер COUNTER обязателен и однозначен в контексте смены филиала. Далее: дата/время, фактический отправитель пакета, позиции, количества, выбранные размеры/модификаторы и комментарии. Корректирующий кухонный чек имеет явную метку «ОТМЕНА» или «ИЗМЕНЕНИЕ» **и сохраняет «НА ВЫНОС»** для идентификации заказа. Задание `KITCHEN` создаётся только при наличии позиций, требующих направления на кухню, по настройке товара.

Если в пакете есть только товары без кухонной печати, пакет подтверждается без KITCHEN Job. Кухонная печать — асинхронная очередь: принятый заказ не отменяется из-за отсутствия бумаги, принтера или неоднозначного результата печати. Неизвестный результат нельзя повторять бесконтрольно из-за риска дубля заказа на кухне.

## 11.3. CUSTOMER

В CUSTOMER используется стандартный согласованный формат заказа и расчёта: позиции, модификаторы, скидка, итог и фактические способы платежа (или нулевой результат). **Крупная надпись «НА ВЫНОС» в CUSTOMER не требуется** (C02=B). Клиентская печать создаётся только после успешной платной/нулевой финализации; ошибки печати не откатывают её. Неподтверждённый предчек отсутствует.

## 11.4. Бизнес-правила печати

**BR-CTR-054.** Для каждого KITCHEN COUNTER верхний заголовок «НА ВЫНОС» должен быть крупным и отчётливо отличаться от списка блюд.

**BR-CTR-055.** Для TABLE кухонный документ идентифицируется номером стола вместо заголовка «НА ВЫНОС».

**BR-CTR-056.** Номер Order Batch не выводится на бумажном кухонном чеке, но его связь с заданием печати остаётся в истории.

**BR-CTR-057.** Если в подтверждаемом пакете нет товаров с признаком необходимости кухонной печати, KITCHEN Print Job не создаётся, и это не считается ошибкой.

**BR-CTR-058.** Если есть печатаемые и непечатаемые позиции, кухня получает только печатаемые; все позиции учитываются в составе заказа и расчёте.

**BR-CTR-059.** В CUSTOMER не требуется крупная надпись «НА ВЫНОС»; вид и финансовое содержание соответствуют общим правилам клиентского чека.

**BR-CTR-060.** Ошибка печати не удаляет Order/Batch/Payment и не меняет операционный статус успешно завершённого COUNTER.

**BR-CTR-061.** Перепечатка выполняется как повторная обработка ранее сохранённого бизнес-результата, а не новая продажа.

**BR-CTR-062.** При отмене/замене направлявшейся на кухню позиции сообщение корректировки сохраняется отдельным заданием типа KITCHEN с соответствующей меткой и «НА ВЫНОС».

# 12. Предложение контейнера при добавлении блюда

## 12.1. Модель

Для **выбранных рестораном блюд** меню настраивается связь с предложением контейнера (упаковки). При оформлении `COUNTER` и выборе такого блюда система **сразу предлагает добавить контейнер в корзину**; отсутствие выбора не препятствует добавлению самого блюда. Контейнер — обычный товар меню: имеет ID, название, цену (включая 0), доступность и исторический снимок. Он добавляется **отдельным Order Item**, а не скрытой наценкой, дополнительным сбором или изменением цены блюда.

**Уточнение 24.10.2026:** у товара-контейнера включается «Это упаковка / контейнер», у блюда — «Предлагать контейнер на вынос» с выбором одного действующего товара упаковки. Контейнер не предлагает другой контейнер. Цена упаковки может задаваться матрицей сочетаний; при наличии вариантов сотрудник выбирает доступное сочетание с полной конечной ценой. При изменении количества блюда связанная строка упаковки изменяется только после подтверждения, без дублирования. При удалении блюда из локального черновика предлагается удалить связанную упаковку либо оставить её самостоятельной строкой. Для принятого пакета действуют общие правила корректировок и неизменности истории.

По умолчанию предложенное количество равно количеству выбранных порций блюда, но сотрудник **может изменить количество или отказаться от добавления**. Товар, добавленный через предложение, должен быть ясно обозначен в корзине и входить в серверный итог после подтверждения. Если контейнер временно недоступен, система не должна молча добавлять его; сотруднику показывается причина недоступности, а блюдо может оформляться по применимым правилам. Для `TABLE` автоматическое предложение контейнера не показывается.

Пример (условные цены): `Плов ×2` по 300 сом = 600 сом; предложение `Контейнер ×2` по 15 сом = 30 сом; итог товаров COUNTER 630 сом до возможной фиксированной скидки. **Дополнительный процентный сбор за упаковку не применяется**; стоимость самой упаковки является ценой обычного товара.

## 12.2. Бизнес-правила упаковки

**BR-CTR-063.** Ресторан может настроить для конкретного блюда предложение контейнера, используя существующий товар локального меню.

**BR-CTR-064.** Предложение показывается при добавлении соответствующего блюда в COUNTER-корзину; для TABLE такое автоматическое предложение отсутствует.

**BR-CTR-065.** Контейнер добавляется только после явного подтверждения сотрудником, а не автоматически.

**BR-CTR-066.** Предлагаемое по умолчанию количество контейнеров равно количеству порций соответствующего блюда; сотрудник может изменить его или полностью отказаться.

**BR-CTR-067.** Контейнер — самостоятельная позиция заказа с собственной действительной ценой, количеством и историей; его цена не скрывается в стоимости блюда и не записывается как дополнительный процентный сбор.

**BR-CTR-068.** Контейнер может стоить 0 сом или положительную сумму; отрицательная цена недопустима.

**BR-CTR-069.** Перед подтверждением пакета контейнер проверяется на актуальность, доступность, цену и право использования по общим правилам меню.

**BR-CTR-070.** Если предлагаемого контейнера нет в наличии или он архивирован, сервер не принимает недоступную позицию; отсутствие контейнера само по себе не запрещает заказ блюда.

**BR-CTR-071.** При отсутствии настроенного предложения упаковки блюдо добавляется стандартно без дополнительных всплывающих запросов.

**BR-CTR-072.** Если на этапе черновика изменено количество блюда, интерфейс предлагает привести выбранное количество контейнеров в соответствие, но не делает скрытого платного изменения уже подтверждённых позиций.

**BR-CTR-073.** После подтверждения пакета коррекция позиции контейнера подчиняется общим правилам отмены и аудита; никакая коррекция не стирает исходный пакет.

**BR-CTR-074.** Необходимость кухонной печати контейнера определяется настройкой самого товара, а не фактом его использования как упаковки.

# 13. Отмены, исправления и ошибочный тип заказа

COUNTER наследует CORE-001 «Отмены и корректировки»: свободное редактирование **черновика**, отдельные операции коррекции **подтверждённых** позиций, обязательная причина при отмене, сохранение исходной истории, отдельные кухонные уведомления для направлявшихся на кухню позиций, идемпотентность, проверка прав. Полная отмена заказа до расчёта выполняется только уполномоченным сотрудником; результат `CANCELLED`. Фиктивный Payment не создаётся. Если сотрудник выбрал «На вынос» вместо «В зале», заказ нельзя механически перенести на стол — разрешено только допустимое аннулирование и новый заказ с корректным типом.

**BR-CTR-075.** Отмены подтверждённых позиций COUNTER требуют сохранения причин, количества, сотрудников и исходных снимков, по общим правилам коррекции.

**BR-CTR-076.** При корректировке не меняются бесследно уже принятые Order Batch и исходные Print Jobs.

**BR-CTR-077.** Если отменяется последнее действующее количество всех позиций, применяется право **полной отмены всего заказа**, в том числе при последовательных отменах.

**BR-CTR-078.** Полная допустимая отмена до расчёта переводит заказ в `CANCELLED`, не создавая Settlement и Payment и исключая заказ из незавершённых обязательств смены.

**BR-CTR-079.** Нельзя использовать нулевой расчёт вместо полной отмены заказа, у которого больше нет действующих позиций.

**BR-CTR-080.** После успешной оплаты или `ZERO_SETTLED` обычные отмены/правки запрещены; возвраты и исправления оплаты — отдельные финансовые операции по CORE-001 «Оплаты».

**BR-CTR-081.** COUNTER нельзя превращать в TABLE или наоборот в рамках существующего заказа; для ошибочного типа используется допустимая отмена и новый заказ.

**BR-CTR-082.** Брошенный подтверждённый COUNTER не отменяется автоматически по времени; требуется ручная полная отмена с причиной и необходимым правом.

# 14. Работа со сменами и финансовая отчётность

В филиале одна активная кассовая смена. Для закрытия Local POS Server проверяет отсутствие `ACTIVE` COUNTER и активных TABLE-посещений, а также прочих незавершённых финансовых операций. Завершённые `COMPLETED / PAID`, `COMPLETED / ZERO_SETTLED` и полностью отменённые `CANCELLED` COUNTER не блокируют закрытие. **Видимость карточки рабочего списка не имеет отношения к условиям закрытия**. В отчёт включаются общие итоги и отдельная аналитика по TABLE и COUNTER с разделением методов оплаты, скидок, отмен и нулевых расчётов. История смены и денежных операций не должна изменяться задним числом вследствие позднего возврата.

**BR-CTR-083.** Подтверждённый `ACTIVE / UNPAID` COUNTER блокирует обычное закрытие кассовой смены.

**BR-CTR-084.** Не подтверждённый черновик COUNTER не блокирует закрытие смены.

**BR-CTR-085.** `COMPLETED / PAID`, `COMPLETED / ZERO_SETTLED` и `CANCELLED` COUNTER не блокируют закрытие смены независимо от видимости карточек.

**BR-CTR-086.** Проверка незавершённых COUNTER и переход смены в CLOSED согласованы транзакционно; новый пакет или заказ не могут появиться в уже закрытой смене.

**BR-CTR-087.** Отчёт смены содержит общие итоги и отдельные показатели TABLE/COUNTER, в том числе количество завершённых заказов, отмен и соответствующие суммы.

**BR-CTR-088.** Смешанный расчёт COUNTER учитывается как одна продажа с отдельными суммами по каждому реально зарегистрированному методу.

**BR-CTR-089.** Завершённый нулевой COUNTER включается в число завершённых продаж, но не прибавляет денег ни к одному платёжному методу.

**BR-CTR-090.** Сохранённая поздняя операция Refund или Payment Reversal корректирует отчёт текущей допустимой смены по общим правилам оплат, не переписывая бесследно закрытый отчёт исходной смены.

**BR-CTR-091.** Отсутствие интернета, отложенная отправка отчёта в Telegram или ошибки KITCHEN/CUSTOMER печати сами по себе не препятствуют закрытию смены при выполнении бизнес-проверок.

# 15. Идемпотентность, конкурентность и атомарность

## 15.1. Повтор одной команды

Каждая изменяющая команда имеет устойчивый `command_id`, идентификатор исходного объекта (когда он существует) и идентификатор актуальной версии состояния, необходимый для обнаружения конфликта. Повторная отправка той же команды возвращает ранее сохранённый результат; повтор с другим `command_id` не означает право дублировать платёж уже завершённого заказа. Клиент после потери ответа **сначала выясняет исходный результат**, а не создаёт новый заказ/платёж с новым идентификатором.

## 15.2. Порядок конкурентных операций

- **Одновременное создание:** две копии одной команды создания дают один Order и один номер; разные команды могут создать разные COUNTER при наличии прав.
- **Два дозаказа:** каждый уникальный подтверждённый пакет может быть принят в активный Order в согласованном порядке; позиции каждого сохраняются один раз.
- **Оплата против дозаказа:** если первым принят пакет, оплата обязана учитывать изменившуюся сумму и при устаревшем подтверждении отклоняется; если первой успешно прошла оплата, дозаказ отклоняется.
- **Оплата против отмены:** при успешной оплате первой обычная отмена отклоняется; если отмена первая, сервер требует обновлённый расчёт и подтверждение.
- **Оплата против оплаты:** только один действительный полный Settlement; проигравший запрос получает фактическое состояние заказа.
- **Скрыть против расчёта:** скрытие доступно только после `COMPLETED`; оно никогда не превращается в способ провести финансовую операцию.
- **Закрытие смены против создания COUNTER:** если первым создан `ACTIVE / UNPAID` заказ, закрытие смены отклоняется; если первой завершена атомарная быстрая продажа, она не блокирует закрытие при выполнении остальных проверок. Если смена закрыта первой, заказ не создаётся.

## 15.3. Атомарность

Критически связанные изменения фиксируются как единый логический результат локальной транзакции: создание заказа/пакета, регистрация оплаты/нулевого расчёта, необходимое задание печати, аудит и исходящее событие синхронизации. Само **физическое исполнение печати** асинхронно и не входит в транзакцию. Изменение видимости — отдельная лёгкая операция, не способная менять финансовый результат.

## 15.4. Бизнес-правила целостности

**BR-CTR-092.** Повтор одной команды с тем же `command_id` не создаёт дубли заказа, пакета, Settlement, Payment, Print Job или изменения видимости.

**BR-CTR-093.** При утрате ответа клиент обязан проверить результат исходной команды, прежде чем разрешать новый независимый расчёт.

**BR-CTR-094.** Для одного COUNTER существует не более одного действительного полного/нулевого расчёта в обычном жизненном цикле.

**BR-CTR-095.** Оплата и дозаказ, оплата и отмена, открытие/закрытие смены и создание заказа должны разрешаться по серверному согласованному порядку.

**BR-CTR-096.** Обновление заказа по устаревшей версии состояния отклоняется с возвратом актуальных данных для повторного подтверждения.

**BR-CTR-097.** При неуспешной атомарной транзакции операция не считается зафиксированной частично.

**BR-CTR-098.** Успешно сохранённая операция не откатывается из-за сбоя физической печати или отсутствия интернета.

**BR-CTR-099.** Полный заказ/расчёт всегда хранит ссылку на филиал, смену и фактического сотрудника или сотрудников соответствующих действий.

# 16. Работа без интернета, сбои и восстановление

## 16.1. Нет интернета / Supabase

Локальные операции продолжаются; события остаются в исходящей очереди и передаются при восстановлении. Owner Dashboard может показывать задержку актуальности. Это не меняет локальное состояние заказа.

## 16.2. Потеря ответа/закрытие POS Desktop

Повторное открытие POS считывает реальные данные с Local POS Server. Неопределённая по клиентскому восприятию оплата не объявляется неуспешной и не повторяется как новая, пока сервер не подтвердил исход. Рабочий список `VISIBLE/HIDDEN` восстанавливается из локального состояния.

## 16.3. Windows / локальный сервер

После запуска службы сервер восстанавливает активную смену, COUNTER, пакеты, финансовые результаты, задания печати, видимость карточек и очередь синхронизации из сохранённых локальных данных. При недоступном Local POS Server операции принятия и оплаты недоступны — **не создаём самостоятельного офлайн-источника подтверждённых COUNTER в интерфейсе**.

## 16.4. Отказ принтера

Сервер сохраняет заказ/расчёт и постоянное задание печати, фиксирует ошибку либо неопределённость и предоставляет управляемую повторную обработку. Ошибка печати никогда не превращает завершённый платный заказ в неоплаченный. Сохраняются последовательность исходного кухонного задания и последующих корректировок и риск неизвестного физического результата.

**BR-CTR-100.** COUNTER работает без внешнего интернета при доступности Local POS Server и локальной БД.

**BR-CTR-101.** Отказ локального сервера не разрешает POS самостоятельно подтверждать новое оформление или оплату.

**BR-CTR-102.** После перезапуска из SQLite восстанавливаются активные/завершённые COUNTER, номера, история, состояние видимости и задания печати.

**BR-CTR-103.** После восстановления интернета синхронизация не должна создавать повторные продажи и платежи.

**BR-CTR-104.** Состояние принтера `UNKNOWN` не является доказательством успешной или неуспешной физической печати; автоматическая слепая перепечатка не допускается.

# 17. Аудит и неизменность истории

Для операций COUNTER фиксируются не менее: стабильный ID заказа, филиал, ID смены, короткий номер, события создания и подтверждения пакетов, сотрудники/устройства и время, исходные Order Items со снимками названий, цен, размеров, модификаторов, комментариев, ссылки на предложения контейнеров и фактически добавленные контейнеры, изменения скидки, коррекции/причины, итоговый расчёт и его методы, нулевые расчёты, статусы, Print Jobs и их результаты, события изменения видимости, события синхронизации. Нельзя удалять исходные Payment или ранее принятый Batch под видом исправления.

**BR-CTR-105.** История заказа содержит его исходные пакеты, корректирующие операции, суммы и фактических исполнителей.

**BR-CTR-106.** Скрытие карточки фиксирует факт действия, исполнителя и время, но не создаёт кассовую операцию.

**BR-CTR-107.** Исторические цены, составы и методы расчёта не меняются задним числом при изменении меню, стоп-листа или настроек упаковки.

**BR-CTR-108.** Отчёт по исходной закрытой смене не должен бесследно изменяться из-за последующего Refund/Reversal.

**BR-CTR-109.** Секреты, пароли и учётные данные платёжных сервисов в журнале операций не сохраняются.

| Попытка оплаты отменённого заказа | Отказать |
| Попытка дозаказа в COMPLETED | Отказать |

| Ошибочный выбор COUNTER вместо TABLE | Не менять тип Order; правомерная отмена и новый заказ |
| Непечатаемый пакет | Принять без KITCHEN Print Job |
| Недоступный кухонный принтер | Сохранить заказ и задание; отразить ошибку/UNKNOWN |
| Недоступный клиентский принтер | Не откатывать завершённый платёж или нулевой расчёт |
| Скрыли карточку × | Убрать только из рабочего списка филиала; оставить историю, суммы и статус |
| Поздний возврат оплаченного заказа | Не менять исходную историю; действовать по отдельной финансовой процедуре |
| Попытка закрыть смену с ACTIVE COUNTER | Отказать и перечислить препятствующие заказы |
| Попытка закрыть смену с видимыми COMPLETED | Разрешить при отсутствии других препятствий |
| Интернет пропал | Продолжать локальные операции, события синхронизации сохранить |
| Local POS Server недоступен | Не подтверждать операции из одного только клиентского интерфейса |

# 19. Основные сценарии (Use Cases)

## UC-CTR-001 — Быстрый заказ с полной оплатой

**Дано:** смена OPEN, кассир авторизован, каталог доступен. **Когда:** сотрудник выбирает капучино, проверяет цену и получение наличных, нажимает «Оформить и оплатить». **Тогда:** одна атомарная серверная операция создаёт COUNTER с номером смены, Batch/Items, Settlement, Payment CASH, нужные KITCHEN и CUSTOMER Jobs; результат `COMPLETED / PAID`; карточка `VISIBLE`.

## UC-CTR-002 — Подтверждение с оплатой позже

**Дано:** смена OPEN. **Когда:** сотрудник подтверждает пакет и откладывает заказ. **Тогда:** Order `ACTIVE / UNPAID`, кухонное задание при наличии печатаемых позиций, закрытие смены блокируется. Позже кассир оплачивает: `COMPLETED / PAID`, CUSTOMER Job, карточка `VISIBLE`.

## UC-CTR-003 — Дозаказ до оплаты

**Дано:** COUNTER ACTIVE, первый пакет уже принят. **Когда:** клиент добавляет круассан. **Тогда:** создаётся новый Batch, актуальная сумма пересчитывается; первый Batch повторно не печатается. Если оплата уже зафиксирована, дозаказ отклоняется.

## UC-CTR-004 — Необязательное имя гостя

**Когда:** сотрудник указывает «Айбек». **Тогда:** пометка отображается в карточке завершённого заказа, помогает выдаче, но не меняет финансовый расчёт и не является персональной авторизацией.

## UC-CTR-005 — Предложение упаковки

**Дано:** ресторан настроил для плова предложение обычного товара «Контейнер 15 сом». **Когда:** кассир добавляет плов ×2 в COUNTER-корзину. **Тогда:** система предлагает контейнер ×2; кассир выбирает ×1; в корзине возникают отдельные позиции «Плов ×2» и «Контейнер ×1». Итог рассчитывает сервер; без подтверждения контейнер не добавляется.

## UC-CTR-006 — Контейнер недоступен

**Дано:** настроенный контейнер внесён в стоп-лист. **Когда:** сотрудник добавляет подходящее блюдо. **Тогда:** предложение контейнера не создаёт недоступную позицию; интерфейс объясняет причину, блюдо можно оформить без контейнера по обычным правилам.

## UC-CTR-007 — Крупная пометка KITCHEN

**Когда:** успешно принят COUNTER Batch с кухонными позициями. **Тогда:** KITCHEN Print Job формирует заголовок «НА ВЫНОС» и номер заказа. Для аналогичного TABLE — крупный «СТОЛ №…». В CUSTOMER такая крупная пометка не обязательна.

## UC-CTR-008 — Пакет без кухонной печати

**Когда:** оплачена готовая бутылка воды с выключенной кухонной печатью. **Тогда:** COUNTER и CUSTOMER Job есть, а KITCHEN Job не создаётся. Суммы и история при этом полные.

## UC-CTR-009 — Нулевой расчёт

**Дано:** в заказе действуют позиции, разрешённая скидка приводит к итогу 0. **Когда:** сотрудник завершает нулевой расчёт. **Тогда:** `COMPLETED / ZERO_SETTLED`, нулевой логический Settlement без Payment, CUSTOMER Job с итогом 0, карточка видима и смена может быть закрыта.

## UC-CTR-010 — Скрытие карточки после расчёта

**Дано:** заказ №014 `COMPLETED / PAID`, карточка VISIBLE. **Когда:** уполномоченный сотрудник нажимает ×. **Тогда:** она становится HIDDEN у всех POS-клиентов филиала, остаётся в истории; ни Payment, ни отчёт, ни принтерные задания не меняются. После перезапуска карточка не возвращается автоматически.

## UC-CTR-011 — Полная отмена брошенного заказа

**Дано:** COUNTER ACTIVE/UNPAID с принятыми пакетами; гость отказался. **Когда:** кассир с правом полной отмены указывает причину и подтверждает. **Тогда:** сохраняется отдельная корректирующая операция, отправляются допустимые кухонные уведомления, заказ `CANCELLED` и больше не блокирует закрытие смены. Payment не создаётся.

## UC-CTR-012 — Смена не закрывается из-за отложенного заказа

**Дано:** есть ACTIVE/UNPAID COUNTER №008; все TABLE закрыты. **Когда:** кассир закрывает смену. **Тогда:** сервер отклоняет команду с указанием №008; не меняет Shift OPEN и не формирует ложный итоговый отчёт.

## UC-CTR-013 — Смена закрывается с видимыми завершёнными карточками

**Дано:** нет ACTIVE заказов, но остаются видимые COMPLETED COUNTER. **Когда:** кассир закрывает смену. **Тогда:** при остальных выполненных условиях смена закрывается; видимость не блокирует её.

## UC-CTR-014 — Потеря ответа при быстром расчёте

**Когда:** сервер зафиксировал быстрый расчёт, но POS не получил ответ. **Тогда:** повтор исходного `command_id` находит тот же Order/Settlement; новый Order/Payment/Print Job не создаётся, UI получает фактический результат.

## UC-CTR-015 — Конкурентная оплата и дозаказ

**Дано:** один сотрудник подтверждает новый Batch, второй нажимает оплату со старой суммой. **Тогда:** либо сначала принимается Batch, тогда оплату нужно повторно подтвердить с новой суммой; либо первым фиксируется полный расчёт, тогда Batch отклоняется.

## UC-CTR-016 — Кухонная ошибка после принятия

**Дано:** успешная оплата и сохранённый KITCHEN Job, принтер недоступен. **Тогда:** заказ остаётся COMPLETED/PAID, карточка доступна, задание с ошибкой сохраняется, персонал видит проблему и может управляемо перепечатать документ.

# 20. Критерии приёмки MVP

## 20.1. Типы и создание

**CTR-AT-001.** В выборе типов заказа доступны только TABLE («В зале») и COUNTER («На вынос»).

**CTR-AT-002.** COUNTER не создаёт Table Session и не занимает физический стол.

**CTR-AT-003.** Открытие пустой COUNTER-корзины не создаёт Order или порядковый номер.

**CTR-AT-004.** Первый подтверждённый пакет создаёт один Order и Batch.

**CTR-AT-005.** Повтор команды создания не создаёт нового номера, Batch или Order.

**CTR-AT-006.** Номера COUNTER возрастают в пределах смены, при новой смене последовательность начинается заново без коллизии постоянных ID.

**CTR-AT-007.** Заказ можно создать без имени гостя; при указанном имени оно видно в рабочей карточке.

**CTR-AT-008.** Допускается несколько активных COUNTER-заказов одновременно.

## 20.2. Пакеты и оплата

**CTR-AT-009.** Подтверждённый заказ можно отложить без оплаты и открыть повторно.

**CTR-AT-010.** До расчёта можно принять второй пакет; после COMPLETED новый Batch отклоняется.

**CTR-AT-011.** Быстрая оплата одной командой создаёт связанный Order, Batch, полный Settlement, Payment(s) и задания печати без частичного результата.

**CTR-AT-012.** Раздельный сценарий сначала создаёт ACTIVE, затем переводит в COMPLETED при полном расчёте.

**CTR-AT-013.** Обычная оплата CASH/CARD_MANUAL/QR_TRANSFER_MANUAL выполняется на полную серверную сумму без произвольного ввода суммы.

**CTR-AT-014.** Смешанная оплата сохраняет несколько Payment одного Settlement и распределяет суммы по методам.

**CTR-AT-015.** На COUNTER не начисляются дополнительные процентные сборы.

**CTR-AT-016.** Устаревшая сумма перед расчётом приводит к отказу и показу актуальной суммы.

**CTR-AT-017.** Повтор одной команды оплаты не создаёт вторую оплату и клиентское задание печати.

## 20.3. Нулевая сумма и отмены

**CTR-AT-018.** Заказ с действующими позициями и итогом 0 завершается как ZERO_SETTLED без Payment.

**CTR-AT-019.** После ZERO_SETTLED создаётся CUSTOMER Job с итогом 0 и без фиктивного метода оплаты.

**CTR-AT-020.** Полностью отменённый заказ получает CANCELLED, не считается нулевой продажей и не создаёт Payment.

**CTR-AT-021.** Без права полной отмены нельзя удалить последние действующие позиции последовательными или массовыми исправлениями.

**CTR-AT-022.** После PAID или ZERO_SETTLED обычные отмены позиций отклоняются.

**CTR-AT-023.** Ошибочно выбранный COUNTER нельзя конвертировать в TABLE внутри того же Order.

## 20.4. Кухня и контейнеры

**CTR-AT-024.** KITCHEN для COUNTER содержит крупное «НА ВЫНОС» и номер заказа; KITCHEN для TABLE — крупный номер стола.

**CTR-AT-025.** Номер пакета на бумажном KITCHEN не отображается.

**CTR-AT-026.** CUSTOMER не требует крупного заголовка «НА ВЫНОС».

**CTR-AT-027.** Непечатаемый пакет подтверждается без KITCHEN Job.

**CTR-AT-028.** При смешанном пакете кухне отправляются только позиции с признаком kitchen-print.

**CTR-AT-029.** При выборе блюда с настроенным предложением контейнера UI спрашивает подтверждение контейнера, не добавляет его самостоятельно.

**CTR-AT-030.** По умолчанию предлагается контейнер на порцию, но сотрудник может изменить количество либо отказаться.

**CTR-AT-031.** Принятый контейнер — самостоятельный Order Item с ценой и историей.

**CTR-AT-032.** Недоступный контейнер не включается в заказ, но сам доступный товар можно оформить.

**CTR-AT-033.** Для TABLE автоматическое предложение контейнера не появляется.

**CTR-AT-034.** Ошибка KITCHEN/CUSTOMER печати не отменяет успешно завершённый заказ и не удаляет Print Job.

## 20.5. Рабочий список

**CTR-AT-035.** После оплаты/нулевого расчёта карточка заказа остаётся в рабочем списке филиала с составом и суммой.

**CTR-AT-036.** Нажатие × скрывает карточку у клиентов филиала, но не удаляет заказ из истории.

**CTR-AT-037.** Скрытие сохраняется после перезапуска.

**CTR-AT-038.** Оплаченная видимая карточка не блокирует закрытие смены.

**CTR-AT-039.** В MVP нет обязательного статуса приготовления или подтверждения фактической выдачи.

## 20.6. Смены, надежность, аудит

**CTR-AT-040.** ACTIVE COUNTER блокирует закрытие смены; пустой черновик — нет.

**CTR-AT-041.** COMPLETED PAID, ZERO_SETTLED и CANCELLED не блокируют закрытие.

**CTR-AT-042.** При попытке закрыть смену с ACTIVE сервер указывает препятствующие COUNTER-номера.

**CTR-AT-043.** Отчёт показывает общие итоги и отдельные TABLE/COUNTER показатели, не приписывает нулевому расчёту денежные поступления.

**CTR-AT-044.** Все основные операции выполняются без интернета при работающем локальном сервере.

**CTR-AT-045.** После перезапуска данные заказа, смены, печати и видимости восстанавливаются.

**CTR-AT-046.** После потери ответа повтор того же `command_id` не создаёт дубль.

**CTR-AT-047.** Конкурентные дозаказ/оплата/отмена не приводят к оплаченной устаревшей сумме или новым пакетам после завершения.

**CTR-AT-048.** В истории остаются Order, Batch, принятые позиции, контейнеры, отправители, корректировки, операции расчёта, Print Jobs и действия скрытия.

# 21. Границы MVP и отложенные возможности

## 21.1. Включено в MVP

- Два типа: TABLE/COUNTER; COUNTER строго «На вынос».
- Создание при первом успешном подтверждении пакета.
- Номера заказов, последовательные в рамках смены.
- Необязательное имя/пометка гостя.
- Несколько одновременно активных и отложенных COUNTER.
- Несколько пакетов до оплаты.
- Быстрая и раздельная модели полной оплаты.
- Финансовый результат ZERO_SETTLED без Payment, автоматический CUSTOMER на ноль.
- Отмена с существующими причинами, правами и историей.
- Видимый список завершённых заказов с ручным скрытием ×, общим для филиала и переживающим перезапуск.
- Крупное «НА ВЫНОС» в KITCHEN; крупный номер стола для TABLE; два типа чеков.
- Настраиваемое предложение контейнера к выбранным блюдам COUNTER; подтверждение человеком, изменение количества, цена из меню.
- Выборочная KITCHEN печать по настройкам товаров.
- Отдельная аналитика TABLE/COUNTER и контроль закрытия смены.
- Local-First, аудит, синхронизация, идемпотентность и конкурентная безопасность.

## 21.2. Не входит в MVP

- Отдельный тип «COUNTER в зале»; отдельные режимы самовывоза/доставки.
- Конвертация TABLE↔COUNTER внутри принятого заказа.
- Фиксация готовности кухни и подтверждение физической выдачи.
- KDS, экран очереди для посетителей, SMS/push о готовности.
- Автоматическое скрытие завершённых карточек по таймеру.
- Автоматическое начисление контейнера без согласия сотрудника.
- Фиктивные нулевые платежи, частичные платежи, частичные возвраты отдельного Payment.
- Склад упаковки, автоматическое списание количества контейнеров со склада.
- Банковская, курьерская, онлайн-доставочная и фискальная интеграция.

## 21.3. Архитектурный резерв

В будущем возможно независимо добавить учёт физической выдачи, самостоятельные интерфейсы кухни, экран готовности, несколько POS-касс, дополнительные источники заказов, сложные политики упаковки и конвертацию типов через контролируемые бизнес-операции. Эти возможности **не утверждены** для MVP.

# 23. Контроль противоречий и оставшиеся уточнения

## 23.1. Проверенные согласованные различия

1. **Q12=A и C05=B не противоречат друг другу.** Завершение заказа — финансово-операционный факт; видимость в рабочем списке — независимое состояние, не факт выдачи.
2. **C01=A устраняет третий вид заказа.** COUNTER всегда «На вынос», TABLE всегда «В зале». Предложения предыдущего вопроса C01=B или C не действуют.
3. **C02=B не вводит третий тип печати.** Крупный заголовок только в KITCHEN; CUSTOMER по общим правилам.
4. **C03=A / C04=B** не создают скрытую доплату. Контейнер — отдельная подтверждаемая товарная позиция с изменяемым количеством.
5. **Q02=B / Q07=C совместимы.** При быстрой продаже Order создаётся в момент первого подтверждения пакета **внутри той же атомарной операции**, которой производится полный расчёт.
6. **Q09=A / Q10=A** устраняют прежний пробел о нулевой сумме без платёжной записи; необходимы точечные поправки финансового раздела.
7. **Q16=A и C05=B** означают: видимые завершённые карточки не являются незавершёнными обязательствами и не могут блокировать Shift CLOSE.

## 23.2. Не блокирует текущее бизнес-ТЗ; решить в специальных документах

- **PRINT-OPEN-01:** типографика крупной надписи, ширина бумаги, язык названий/корректировок на KITCHEN/CUSTOMER и физическая маршрутизация принтеров.

# 25. Итоговые принципы

1. COUNTER — исключительно «На вынос»; система имеет ровно два типа TABLE и COUNTER.
2. COUNTER не создаёт и не занимает Table Session.
3. Первый успешно принятый пакет создаёт COUNTER Order; пустой черновик Order не создаёт.
4. Номер заказа последователен в пределах одной смены; устойчивый ID остаётся глобально уникальным.
5. Разрешены быстрый полный расчёт и предварительное подтверждение с отложенной оплатой.
6. Оплата подтверждённого заказа завершается в одной согласованной операции; частичных оплат нет.
7. Нулевая сумма при действующих товарах завершается как ZERO_SETTLED без Payment и с CUSTOMER-чеком на 0 сом.
8. Завершённый оплаченный COUNTER видим в рабочем списке до ручного ×; × скрывает только карточку, а не продажу.
9. В MVP не фиксируются готовность кухни и факт передачи товара гостю.
10. Кухонный чек COUNTER содержит крупное «НА ВЫНОС»; для TABLE — крупный номер стола; на CUSTOMER крупная маркировка не требуется.
11. Для выбранных блюд COUNTER предлагается контейнер из меню: сотрудник решает, добавлять ли его, и может изменить количество.
12. Отмены и замены выполняются по существующим правилам с аудитом и без уничтожения исходного пакета.
13. Незавершённый COUNTER блокирует закрытие смены; завершённый видимый — нет.
14. Все операции остаются работоспособными без интернета при доступности локального сервера.
15. Отчёты отдельно показывают TABLE и COUNTER, сохраняя корректные методы оплат и историю смен.
