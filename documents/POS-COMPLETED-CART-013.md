# POS-013 — завершённый заказ в корзине

Реализовано 27.10.2026 для FAST_FIRST («Заказы сначала»).

## Интерфейс

- Нажатие на карточку «Последние продажи» показывает завершённый заказ в правой колонке. Выбранная карточка выделена контуром; активный заказ/черновик перестаёт выглядеть выбранным.
- Состав и суммы берутся из серверного снимка расчёта: блюда, варианты/модификаторы/компоненты, комментарии, количество, цена, скидка, сборы, итог, платежи. Показаны номер/статус, время завершения по Бишкеку, тип обслуживания, стол/официант для TABLE, автор открытия (если сохранён) и сотрудник завершения.
- Просмотр только для чтения: нет действий над строками, назначениями или оплатой; добавление из каталога заблокировано. Сохранён просмотр принятых пакетов/отметок выдачи.
- Рабочий workspace не переключается на завершённый заказ. «Вернуться к текущему заказу» восстанавливает его, «Новый заказ» создаёт новый черновик, сохраняя прежний. Переход к активному заказу/черновику закрывает просмотр завершённого.
- Жёлтая кнопка «Оформить возврат» открывает диалог с обязательной причиной и подтверждением фактического возврата денег. POS регистрирует возврат; банковские операции остаются внешними.
- После полного возврата статус «Возвращён», повторное действие заблокировано. При ранее возвращённом отдельном платеже показываются статус частичного возврата и остаток; возвращается только остаток. ZERO не создаёт фиктивный возврат. Требуется `payment.refund`; доступ к продаже ограничен действующим 24-часовым контрактом.

## Сервер и восстановление

Существующие endpoints возврата одного платежа сохранены. Добавлены:

- `POST /api/v1/sales/:id/refunds/prepare`: `{reason}` → `orderId`, `settlementId`, `currentShiftId`, нормализованная причина, оставшиеся платежи, сумма и `confirmationHash`.
- `POST /api/v1/sales/:id/refunds/commit`: `{commandId, reason, currentShiftId, confirmedExternalReturn, confirmationHash}` → минимальная квитанция `{commandId, orderId, refundIds, result: ORDER_REFUND_REGISTERED}`.

Проверяются текущие права/область доступа, завершённый расчёт, открытая смена, причина, фактический возврат и актуальность подтверждения. Команда `order.refund` выполняет обычные дочерние `payment.refund` с индивидуальными UUID, квитанциями, audit/outbox и существующим ограничением одного возврата на платёж. Все записи и квитанции входят в одну writer-транзакцию CommandBus. Ошибка любого платежа откатывает весь новый возврат. Снимок расчёта и исходное финансовое состояние не переписываются; UI-статус возврата выводится из записей refunds.

Native `orderRefundCommit` сохраняет команду в защищённом pending до получения проверенной квитанции. После неизвестного результата UI предлагает проверку исходного действия, без новой регистрации. Повтор после перезапуска возвращает ту же квитанцию; отзыв права блокирует даже повтор. Схема 17 и миграции остаются прежними.
