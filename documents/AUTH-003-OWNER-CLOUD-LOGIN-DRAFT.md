# AUTH-003 — единый облачный вход владельца и экран входа кассира

Статус: **ТЗ подтверждено пользователем 23.10.2026; реализация для новых установок в исходном коде**. Уточнение пользователя: кнопка «Кабинет владельца» открывает кабинет внутри Desktop. Переход действующих установок остаётся отдельной процедурой раздела 6.

## 1. Цель и границы

Убрать второй пользовательский шаг создания Owner при первой активации. Владелец использует свой существующий облачный email и пароль при активации и при каждом новом входе. Для входа Owner нужен работающий интернет и успешная проверка Cloud Auth. Кассир продолжает входить личным четырёхзначным PIN либо локальным логином и паролем, без внешнего интернета. Waiter Web и предметные правила CORE-001 не меняются.

В ежедневном стартовом экране оставить две вторичные кнопки: **«Войти по логину и паролю»** и **«Кабинет владельца»**. Убрать **«Локальный Owner / Manager»**. Обе кнопки ведут к одной визуальной форме, но с разным назначением: общая — локальный вход CASHIER/MANAGER, кабинет — только облачный Owner. Режим и проверку выбирает сервер по маршруту/сессии, а не по введённому email или заявленной клиентом роли. На форме владельца явно сообщить, что нужен интернет.

**Уточнено пользователем:** «Кабинет владельца» в этой задаче — административные разделы текущего Desktop, открываемые Owner только после онлайн-проверки. Отдельный облачный Owner Dashboard остаётся будущим самостоятельным этапом. Это временно меняет ранее утверждённый AUTH-002 R-01 об отдельном сайте, поэтому переход и отключение локального Owner должны пройти по правилам R-07, без потери административного доступа.

## 2. Фактическое состояние и затронутые решения

- Сейчас `/activation/start` проверяет облачный email/пароль и возвращает доступные филиалы; `/activation/complete` отдельно требует `login`, `name`, `password` локального Owner. Создание локальной записи и привязка филиала уже атомарны, повтор активации не сбрасывает Owner.
- Локальный `/auth/login` проверяет `employees.password_hash`, включая Owner. Кнопка «Кабинет владельца» сейчас показывает сообщение о недоступности, а не открывает кабинет.
- `employees.password_hash` обязателен по схеме; email не подходит под текущий формат локального `login`. Значит, только удалением поля из формы задачу безопасно не решить.
- AUTH-001 требовал отдельный локальный пароль; AUTH-002 уже утвердил целевую онлайн-модель Owner, но R-07 разрешает выключить локальный Owner лишь после работающей замены. Этот проект уточняет переход. ARCH/CORE Local-First для кассира, официанта, заказов, смены, оплаты и печати сохраняется.
- Существующий Platform Admin создаёт облачного Owner. Полноценный отдельный Owner Dashboard пока отсутствует; его нельзя обозначить как готовый редирект.

## 3. Пользовательские сценарии

### 3.1. Первая активация новой установки

1. На отдельном экране активации Owner вводит облачные email и пароль; Local POS Server проверяет их через Cloud Auth по HTTPS, получает подтверждённый `ownerCloudId` и доступные организации/филиалы.
2. Owner выбирает филиал и подтверждает привязку устройства. Экран **не** спрашивает локальные имя, логин, пароль или повтор пароля.
3. Local POS Server использует прежний идемпотентный протокол резервации/подписанной квитанции. После подтверждения облака атомарно создаёт технического локального актора OWNER, привязанного к `ownerCloudId` и филиалу. Для отображения использует подтверждённый облачный email и, если доступно, имя; облачный пароль не становится локальным паролем и не сохраняется в SQLite.
4. Успех показывается только после локального commit и проверки привязки. При потере ответа повтор исходной активации возвращает прежний результат, не создаёт второго Owner и не занимает другой филиал.
5. После активации открывается форма онлайн-входа Owner либо стартовый PIN-экран — выбор фиксируется при реализации UI; скрытого автоматического входа из токена активации нет.

### 3.2. Повседневный вход

- Старт: экран PIN кассира с цифровой клавиатурой, физической клавиатурой, четырьмя маскированными ячейками и доступной ошибкой. PIN, пароли и токены не выводятся в DOM после проверки, логах или URL.
- «Войти по логину и паролю»: локальные реквизиты сотрудника. CASHIER и MANAGER допускаются согласно действующим audience/правам. Удалённая почта Owner этим маршрутом не принимается.
- «Кабинет владельца»: та же стилистика формы, но подпись «Вход владельца», поле **«Облачный email»**, поле **«Пароль»**, индикатор необходимости интернета. Local POS Server проверяет Cloud Auth и текущую принадлежность Owner к привязанной организации/филиалу; сверяет неизменяемый `ownerCloudId`, а не одно совпадение email. После успеха открывает административные разделы Owner в Desktop, без перехода на отдельный сайт. Чужой Owner и утрата прав — отказ без локальной сессии.
- При отсутствии интернета/Cloud Auth: для нового входа и изменяющих действий Owner нужен интернет. После успешной онлайн-проверки чтение уже доступных локальных данных может продолжаться в пределах 30 секунд; следующая проверка блокирует доступ до восстановления связи. Локальный пароль и PIN не служат обходом. Кассир и официант продолжают локальную работу.
- «Сменить пользователя» отзывает текущую сессию и возвращает стартовый экран; смена, столы и принятые заказы не закрываются. После рестарта сервера Owner проходит облачную проверку заново.

## 4. Контракты и безопасность

1. У Local POS Server отдельный маршрут входа Owner, например `POST /api/v1/auth/owner-cloud` с `{email,password}`. Он доступен только через существующий native loopback transport. Ответ содержит только локальную сессию с отдельными `audience/method` и безопасными сведениями актора; облачный токен/пароль не возвращаются renderer и не пишутся в защищённый Desktop-файл. Старый `/auth/login` серверно запрещает Owner.
2. На сервере нужна отдельная привязка локального `employee_id` к `ownerCloudId` и подтверждённому email. Локальный `login` может остаться внутренним стабильным ключом; email — идентификатор для облачного входа и показа. Нельзя менять существующие checksum миграций; новую модель вводить следующей миграцией. Из-за `password_hash NOT NULL` допустим случайный недоступный парольный verifier, но серверный запрет локального Owner-входа и смены/сброса его пароля обязателен. Предпочтительно явно пометить `CLOUD_OWNER` в отдельной credential/binding записи.
3. После проверки Cloud Auth и филиальной принадлежности сервер выдаёт локальную Owner-сессию только для этого филиала. Локальная сессия и права проверяются на каждом запросе. **Уточнение пользователя 23.10.2026 для скорости переходов:** успешная облачная проверка повторно используется до 30 секунд для чтения и `auth/activity`; изменяющие команды требуют свежей облачной проверки. По истечении 30 секунд чтение также требует онлайн-проверки. Отзыв облачного доступа может отразиться в чтении с задержкой до 30 секунд, в изменениях — при следующей команде. Проверка выполняется на серверной границе до предметной команды. Повтор после неизвестного результата использует прежний command ID и текущую авторизацию.
4. Облачный пароль передаётся только через native IPC → Local POS Server → HTTPS Cloud Auth, остаётся в памяти на время запроса и очищается из полей UI. Не хранить его хеш как локальный пароль; не писать в SQLite, command journal, audit, outbox, логи, telemetry и Desktop protected state. Успешная проверка фиксирует безопасные `ownerCloudId`, `branchId`, время и audit-событие без секрета.
5. Сессии CASHIER/MANAGER/WAITER и их права остаются независимы от Owner. Клиент не может выбрать роль, audience, филиал или employee ID в теле запроса для повышения прав. Учитывать rate limit, отмену/таймаут, повторный ответ и отключение сети во время уже начатой операции.
6. При смене облачного пароля следующий вход использует новый пароль автоматически; локального «сброса пароля Owner» больше нет. Изменение подтверждённого email не создаёт нового Owner, если `ownerCloudId` тот же. Смена самого облачного владельца организации — отдельная контролируемая процедура, не часть этого ТЗ.

## 5. Дизайн и доступность

- Взять из приложенного референса светлую мятную палитру, логотип слева сверху, язык справа, одну центральную белую карточку, четыре крупные ячейки PIN и клавиатуру 3×4. Убрать кнопку «Локальный Owner / Manager»; две оставшиеся кнопки разместить симметрично и достаточно крупно для сенсорного экрана.
- Парольная форма и онлайн-форма владельца используют тот же визуальный язык, но разные заголовки и пояснения. Кнопка возврата на PIN-экран видима. Не раскрывать технические ID, activation flow ID, email в ошибках и секреты.
- Проверить 1366×768 и минимальный размер Electron 800×600, RU/KY, клавиатурную навигацию, видимый focus, доступные подписи, масштабирование Windows и отсутствие обрезания кнопок. Декоративные формы не должны мешать вводу; стили держать в отдельных scoped CSS-файлах действующей безбандлерной архитектуры.
- Состояния: загрузка, неверные реквизиты, лимит попыток, нет интернета, Cloud Auth недоступен, потеря разрешения на филиал, локальный сервер недоступен, неопределённый результат активации, восстановление связи. До подтверждения сервера успех не показывать.

## 6. Переход и приёмка

- **Новые установки:** новая схема и новый сценарий активации; один облачный Owner и одна техническая локальная запись без второго пользовательского пароля.
- **Уже активированные установки:** не удалять локального Owner и его пароль автоматически. Сначала отдельный backup/preflight, закрытая смена, остановленный сервер, проверка `ownerCloudId`, успешный онлайн-вход, миграция, отзыв прежних Owner-сессий и проверка административных действий. При ошибке переход не должен оставлять филиал без администратора. MANGO со схемой 3 и открытой сменой не мигрировать в рамках этой задачи.
- Серверные тесты: один Owner после активации/повтора/потери ответа/рестарта; чужой и неподтверждённый Owner; изменение email/пароля; отсутствие и восстановление интернета; отзыв доступа; local Owner login/password-change/reset denial; role/audience isolation; неизменность cashier/waiter offline; текущий command replay, права и audit.
- Electron QA: новый мастер без второго Owner-пароля; кнопки PIN/пароль/кабинет; правильные назначения форм; успешный и неуспешный Owner-вход; реальные экраны Owner после входа; RU/KY; размеры 1366×768 и 800×600. Отдельно проверить Windows/сенсор/сетевой отказ; macOS fixture не считать Windows-приёмкой.

## 7. Решения, которые нужно подтвердить вместе с ТЗ

1. **Кабинет Owner: решено пользователем.** Открывается внутри Desktop после облачного входа; отдельный сайт в этот объём не входит. Изменение относительно AUTH-002 R-01 явно фиксируется при утверждении всего ТЗ.
2. После первой активации показывать Owner-форму сразу или возвращаться на общий PIN-экран. Предложение: Owner-форму сразу, без автоматического входа.
3. Под «использовать пароль удалённого аккаунта» понимается **проверять его в Cloud Auth при каждом входе**, без локальной копии/хеша. Это устраняет двойной аккаунт и соответствует требованию обязательного интернета.

После утверждения этих решений можно менять код, API и миграции; до утверждения не менять действующие профили/регистрации/схемы.
