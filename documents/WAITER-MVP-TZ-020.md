# ТЗ: сотрудники, подключение и рабочий экран официанта

Дата: 27.10.2026. Статус: **согласованное ТЗ; реализация по этапам**. Приоритеты и фактический срез — [WAITER-MVP-ROADMAP-019](WAITER-MVP-ROADMAP-019.md). Реализованные технические возможности описаны в [WAITER-SCREEN-017](WAITER-SCREEN-017.md) и [WAITER-HTTP-MVP-018](WAITER-HTTP-MVP-018.md). Этот документ описывает целевой пользовательский путь; слово «должен» не означает, что пункт уже реализован.

## 1. Цель и границы

Уполномоченный сотрудник филиала создаёт кассира или официанта с автоматически выданным личным PIN, затем показывает официанту QR. Официант подключает телефон к служебному Wi-Fi, открывает общий URL филиала, входит по PIN, работает со столами и отправляет заказы. На MVP URL имеет вид `http://<частный-IP>:<порт>/waiter/`; адрес берётся из фактической конфигурации, порт по умолчанию 3002. Никаких установок сертификата на телефон в HTTP-срезе. HTTPS позднее меняет транспорт и origin, сохраняя бизнес-команды.

В этом ТЗ нет нового приложения из магазина, входа по QR без PIN, общего PIN на смену, облачного доступа через интернет, автоматической готовности/выдачи блюда и новой модели платежей. Текущие роли, права, смена, TABLE/STRICT/SHARED, CommandBus, история и печать остаются авторитетными.

## 2. Desktop: создание сотрудника

- Форма «Создать сотрудника»: имя, роль и логин; для WAITER текст объясняет, что вход на телефоне выполняется личным PIN. Логин остаётся обязательным полем существующего API; интерфейс может предложить значение, но перед созданием показывает его и даёт изменить. Не вводить пароль/PIN вручную от имени менеджера.
- При создании CASHIER или WAITER сервер автоматически создаёт уникальный четырёхзначный PIN, включая возможный ведущий ноль. Сохранение сотрудника и PIN — **одна атомарная серверная команда**. При недоступных PIN-ключах, исчерпании кодов, отсутствии прав или ошибке записи сотрудник не появляется. MANAGER создаётся без PIN по действующей политике ролей.
- После успеха показать одноразовую карточку «Сотрудник создан» с личным PIN; для WAITER — действие «Перейти к подключению». PIN не печатать автоматически и не добавлять в QR. При потерянном ответе сначала проверить результат по существующему сотруднику/commandId, не повторять создание с новым ID; повтор исходной команды не должен выдавать PIN второй раз. Если одноразовый код утерян, уполномоченный сотрудник делает отдельный reset PIN.
- Для создания CASHIER/WAITER сервер проверяет оба права: `employee.create` и `employee.pin.issue`. Разрешение создавать MANAGER не даёт права обходить PIN-политику для CASHIER/WAITER. Действие и результат отражаются в аудите без открытого PIN.
- В списке явно видны роль, статус доступа и «PIN не выдан / выдан». Приостановление, архив, изменение роли и сброс PIN отражаются в подключении и отзывают прежний доступ по действующему контракту.
- Разделить ежедневный сценарий сотрудников от расширенных прав/делегирования: общие действия видны сразу, административные настройки раскрываются отдельно. Не скрывать у существующего Owner/Manager возможности управления правами.
- Существующий временный пароль может оставаться для парольного сценария кассира, но не подменяет автоматически выданный PIN. Для официанта он не нужен для входа на телефоне; точное представление временного пароля в новой карточке решить при реализации, не записывая ни один секрет в журнал команд.

## 3. Desktop: отдельная страница «Подключение официантов»

- Отдельный пункт навигации, доступный по `network.waiter.manage`. Сверху: состояние HTTP listener, адрес, порт, доступность, кнопки «Показать QR», «Скопировать ссылку», «Обновить состояние». QR кодирует только URL текущего филиала; возле QR короткая инструкция подключения к служебному Wi-Fi и входа по личному PIN.
- Ниже: WAITER своего филиала с состояниями «Готов к входу / PIN отсутствует у старой записи / доступ приостановлен»; кнопка «Выдать PIN» нужна только старым записям без PIN, «Сбросить PIN» — действующим с кодом. Они показываются только при соответствующих `employee.pin.issue/reset`. Одноразовый результат отображается отдельной карточкой и не попадает в QR, URL, лог или снимок диагностики. Повторный просмотр PIN подчиняется уже действующему `employee.pin.view` и его ограничению по роли; право управления сетью само по себе его не даёт.
- Пустое состояние: «Сначала создайте официанта» с переходом в создание. Ошибка listener: конкретная причина и действие по настройке без ложного QR «готово». Изменение IP/порта: предупреждение, что адрес и браузерное хранилище изменятся; перед переключением проверить незавершённые черновики/pending на телефонах.
- Страница не обещает, что телефон доступен, только потому что процесс слушает порт. Фактическая проверка: открыть URL и выполнить PIN-вход на телефоне в той же сети. Функция определения устройства/подтверждения подключения сервером пока не входит в MVP.

## 4. Телефон: вход и сеанс

- Маскированный четырёхзначный PIN, включая ведущие нули; понятные ошибки и задержка после неверных попыток. Роль WAITER и права проверяет сервер. На HTTP активная вкладка после обновления восстанавливает действующий вход и зашифрованный черновик по позднему правилу [WAITER-HTTP-MVP-018](WAITER-HTTP-MVP-018.md); выход, отзыв/истечение и 60 секунд в фоне снова требуют PIN.
- Показывать понятные состояния: сервер недоступен, смена закрыта, права изменились, сессия завершилась, запись черновика не удалась. Не называть сохранение в браузере «отправлено».

## 5. Телефон: столы и открытие

- Стартовый экран после входа: «Мои / Все», зоны и доступный поиск по номеру/названию стола; карточка показывает стол, зону, статус и ответственного в пределах разрешённых данных. Сортировка: мои занятые, остальные доступные, далее прочие; не менять смысл «Все» на «все подробности».
- Свободный стол: отдельное понятное действие «Открыть стол», затем переход к посещению только после ответа сервера. При конфликте другого сотрудника обновить карточку и объяснить результат, не повторять открытие новой командой без проверки.
- Занятый стол: показывать разрешённый состав и действия. В STRICT чужой стол показывает статус занятости без состава, суммы, комментариев и черновиков; объяснение доступа вместо пустой страницы. В SHARED показывать детали по текущим правам без автоматической смены ответственного.
- Сохранить последний выбранный фильтр и зону на устройстве как удобство; это не источник права. Обновление списка не должно стирать локальный черновик.

## 6. Телефон: меню, партия, отправка

- В посещении видны стол/зона, ответственный, принятые партии и отдельный блок новой партии. Меню: категории, поиск RU/KY, стоп-лист, варианты/MATRIX/SET, количество и комментарий. Выбранный состав редактируется локально; видимая метка «Не отправлен» и состояние сохранения.
- Перед отправкой сервер заново проверяет меню, цены, сборы, смену, стол и права. Экран подтверждения показывает состав, скидку/сборы при наличии, итог и ясную кнопку «Отправить заказ». Изменения цены/недоступность требуют нового выбора или явного подтверждения; не отправлять устаревшую партию молча.
- После принятия показать номер/время/автора партии и отдельный статус передачи кухне. `SENT` означает принятие задания спулером согласно текущему print-контракту, не приготовление и не получение бумаги. Дозаказ создаёт новую партию к тому же посещению.
- При потере ответа показать «Результат неизвестен»: сначала проверить исходную команду/receipt, затем предлагать повтор той же команды. Не создавать второй заказ от повторного нажатия. Смена сотрудника и обновление страницы не открывают чужой черновик.

## 7. Дополнительные функции и права

История партий и коррекция доступны в пределах текущих grants и CAS; полная отмена, запрещённая официанту, передаётся кассиру. Скидка, ответственный/перенос, закрытие пустого посещения и TABLE-расчёт отображаются только когда сервер даёт право и объект допускает операцию. Расчёт не входит в основную кнопку отправки заказа; подтверждение фактического получения денег остаётся отдельным шагом. Нет доступа к COUNTER, возвратам, отчётам смены и настройкам персонала из телефона.

## 8. Приёмка

1. Desktop: создание CASHIER/WAITER сразу выдаёт личный PIN; MANAGER создаётся без PIN. Затем отдельная страница подключения показывает общий QR без секрета. Сбой подготовки/сохранения PIN не создаёт сотрудника; replay не выдаёт другой код; отсутствие любого из двух прав запрещает создание CASHIER/WAITER и в UI, и на сервере.
2. Телефон: Android Chrome и iPhone Safari на служебном Wi-Fi, маленький экран и landscape; скан QR, PIN, обновление страницы, выход, 60 секунд в фоне, отзыв PIN/сотрудника.
3. Столы: свободный/мой/чужой STRICT/SHARED, конфликт открытия, закрытая смена, пропадание сети, поиск и зоны; отсутствие чужого состава даже при прямом URL/API.
4. Заказ: варианты, стоп-лист, локальный черновик, обновление, принятая партия, дозаказ, изменившаяся цена, неизвестный ответ и исходный receipt без дубля. Реальный принтер проверяется отдельно от статуса сервера.
5. Результаты фиксируются раздельно: unit/API, browser QA, реальные телефоны и сеть филиала. Тестовая одноразовая БД не считается пилотным рестораном.

## 9. Принятые решения и оставшееся уточнение

- «Сотрудники» отвечают за создание с автоматическим PIN и статус; «Подключение официантов» — за QR, сеть и сброс/восстановление PIN. QR один общий для филиала.
- Временный пароль из существующего контракта показывается в раскрываемой части одноразовой карточки создания; PIN показан сразу и является способом входа официанта на телефоне.
- Первый UX-срез: столы → открытие → меню/новая партия → подтверждение. Следующие правки карточки посещения проверять на физическом телефоне перед выпуском пилота.
