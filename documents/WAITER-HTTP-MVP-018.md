# Waiter Web: локальный HTTP для MVP

Дата: 27.10.2026. Пользователь выбрал временное подключение официантов по HTTP в локальной сети, чтобы открывать экран по QR без установки сертификата. Это позднее решение для MVP относительно HTTPS-контракта [API-WAITER-009](API-WAITER-009.md). HTTPS остаётся доступным при выключенном HTTP-режиме.

## Включение

На подготовленном и активированном профиле откройте Desktop → «Подключение официантов», выберите локальный IP компьютера и порт (по умолчанию `3002`), нажмите «Включить HTTP и показать QR». Настройка сохраняется в `waiter-http.json` внутри каталога данных филиала и восстанавливается при следующем запуске. При отсутствии рабочего локального IP подключите компьютер к Wi-Fi ресторана и обновите страницу. QR и ссылка показываются только когда веб-сервер действительно слушает выбранный адрес.

Альтернативно при запуске отдельного профиля можно задать `BASHKAR_WAITER_HTTP_IP` равным фактическому частному IPv4 интерфейса компьютера и, при необходимости, `BASHKAR_WAITER_HTTP_PORT`. Переменные запуска имеют приоритет над сохранённым адресом. Пример:

```sh
pnpm run build
BASHKAR_WAITER_HTTP_IP=192.168.1.50 BASHKAR_WAITER_HTTP_PORT=3002 node infrastructure/local/run-desktop.cjs start prepared-profile
```

`192.168.1.50` и `prepared-profile` — **заполнители**, не адрес и профиль текущей установки. Не запускать этот пример на MANGO и не мигрировать рабочую БД ради просмотра экрана. Сервер привязывает web listener только к указанному частному IPv4, не к `0.0.0.0`; native API остаётся на loopback. Некорректный HTTP IP/порт оставляет native POS работающим и отражается как `WEB_HTTP_CONFIG_INVALID`. Порт и доступ по служебному Wi-Fi/Firewall настраиваются на месте. Не публиковать порт в WAN.

Для быстрого просмотра на телефоне без активации рабочего профиля есть одноразовый стенд:

```sh
BASHKAR_HTTP_QA_IP=<LAN_IP_КОМПЬЮТЕРА> pnpm run preview:waiter-http
```

Команда выведет фактический URL, тестовый PIN и путь к QR PNG. Телефон должен быть в той же локальной сети. Заказы будут только в тестовой базе; после `Ctrl+C` сервер остановится и база удалится. Это предпросмотр, не подключение официанта к реальному филиалу.

Раздел Desktop «Официанты» показывает текущий `http://IP:PORT/waiter/` и QR-код, когда HTTP-режим включён. Телефон подключается к той же локальной сети и входит личным PIN официанта. Если адрес или порт меняется, браузерные черновики старого origin не переносятся автоматически.

## Поведение и ограничения

- HTTP-режим включается явным действием на странице подключения или переменными запуска. При отсутствии обоих действует прежняя HTTPS-конфигурация из БД и прежний `__Host-bashkar-waiter` Secure cookie.
- HTTP использует отдельный `bashkar-waiter-http` HttpOnly/SameSite=Strict cookie без `Secure`, поскольку браузер не отправит Secure cookie по HTTP. Exact Host/Origin, Fetch Metadata, JSON, CSRF, memory unlock, роль WAITER, PIN limiter, права TABLE, CommandBus и own receipt остаются серверными проверками.
- По просьбе пользователя **обновление активной HTTP-вкладки не требует повторного PIN**: вкладка временно держит CSRF, unlock ticket и ключ черновика в `sessionStorage`, после reload проверяет текущую сессию/сотрудника/устройство/права на сервере и снова открывает encrypted draft. Выход, отзыв/истечение серверной сессии и пребывание в фоне 60 секунд очищают эти данные и требуют PIN. В HTTPS-режиме прежнее правило PIN после reload сохраняется. `sessionStorage` расширяет время хранения секретов в браузере по сравнению с исходным memory-only контрактом; доступ скрипта и HTTP-подмена остаются риском этого MVP.
- На HTTP частного IP браузер может не выдавать SubtleCrypto и `crypto.randomUUID`. Клиент использует `node-forge` AES-GCM/SHA-256 для прежнего формата ciphertext IndexedDB и `crypto.getRandomValues` для UUID/IV. Для восстановления после reload нужен сохранённый в активной вкладке ключ черновика и действующая серверная сессия; если их уже нет, нужен новый PIN-вход. Это **шифрование хранения на устройстве**, не защита трафика HTTP.
- На HTTP частного IP service worker/offline app shell недоступен. Уже загруженная страница может редактировать локальный черновик в пределах действующего server context; после reload для восстановления входа нужен сервер. Pending сохраняется до отправки и проверяется исходной командой. На реальных Android/iPhone это ещё нужно подтвердить.
- PIN, cookie, CSRF, unlock ticket, draft key, состав заказа и финансовые команды идут по сети **без транспортного шифрования**. Участник сети, способный перехватить или подменить трафик, может получить доступ шире одного заказа. В интерфейсе настройки HTTP это указано явно. Локальный Wi-Fi/ограничение порта уменьшают круг доступа, но не шифруют данные.

## Проверка

`pnpm run check`; `pnpm test`; `pnpm run test:waiter-http`; прежний `pnpm run test:service-clients-desktop`. HTTP browser QA использует временную БД/профиль. На loopback он принудительно отключает SubtleCrypto/randomUUID/service worker; дополнительно пройден на текущем частном IP компьютера, где браузер сам сообщил `isSecureContext=false`. Проверены вход, зашифрованный черновик, reload без PIN в активной вкладке, PIN после 60-секундной блокировки/выхода, отправка пакета и Desktop QR. Это не физическая приёмка телефона или сети ресторана.
