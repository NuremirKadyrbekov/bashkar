# 1. Общая информация

## 1.1. Назначение проекта

Bashkar.kg — программная система автоматизации ресторанов, кафе и других заведений общественного питания.

Основой системы является десктопное POS-приложение, работающее на Windows и обеспечивающее управление заказами, столами, кассовыми сменами, оплатами и кухонной печатью.

Система также предусматривает:

- веб-интерфейс официанта для работы со смартфона;
- локальный сервер ресторанных операций;
- автономную работу без интернета;
- облачную синхронизацию;
- веб-кабинет владельца;
- цифровое QR/NFC-меню;
- возможность подключения дополнительных модулей.

## 1.2. Основная техническая цель

Разработать быстрый, надёжный и расширяемый ресторанный POS, основные функции которого не зависят от постоянного интернет-соединения.

При отсутствии интернета ресторан должен сохранять возможность:

- открывать кассовую смену;
- принимать заказы;
- обслуживать столы;
- отправлять заказы на кухонный принтер;
- регистрировать оплаты;
- закрывать счета;
- сохранять данные;
- продолжать работу официантов в локальной сети.

После восстановления интернета накопленные изменения должны синхронизироваться с облачной инфраструктурой.

## 1.3. Приоритеты разработки

1. Скорость и надёжность POS.
2. Работа без интернета.
3. Быстрый и удобный экран официанта.
4. Надёжная отправка заказов на кухню.
5. Сохранность заказов и финансовой истории.
6. Работа с кассовыми сменами.
7. Облачная синхронизация.
8. Аналитика владельца.
9. QR/NFC-меню.
10. Дополнительные интеграции.

## 1.4. Архитектурный принцип

Основной архитектурный подход — **Local-First Architecture**.

Local POS Server является основным источником операционных данных конкретного филиала.

Supabase используется для облачного хранения синхронизированных данных, централизованного управления, аналитики и онлайн-функций.

Основные ресторанные операции не должны зависеть от доступности Supabase.

# 2. Архитектура системы

## 2.1. Общая модель

Система состоит из двух основных уровней:

**Локальная инфраструктура ресторана**

- Bashkar POS Desktop;
- Local POS Server;
- SQLite;
- Waiter Web Client;
- WebSocket Gateway;
- Kitchen Print Service;
- Sync Worker.

**Облачная инфраструктура Bashkar.kg**

- Supabase PostgreSQL;
- Cloud Backend;
- Owner Dashboard;
- централизованная авторизация владельцев;
- управление конфигурацией;
- аналитика;
- QR/NFC-меню.

## 2.2. Схема взаимодействия

Локальный уровень:

**POS Desktop ↔ Local POS Server ↔ SQLite**

**Waiter Web Client ↔ Local POS Server**

**Local POS Server → Print Service → Kitchen Printer**

Облачный уровень:

**Local POS Server ↔ Sync Backend ↔ Supabase**

**Owner Dashboard ↔ Cloud Backend ↔ Supabase**

Телефон официанта и POS Desktop должны работать с одним локальным сервером.

Прямое взаимодействие между интерфейсом официанта и интерфейсом кассира не требуется.

## 2.3. Основные архитектурные правила

**ARCH-001:** Все критические операции проходят через Local POS Server.

**ARCH-002:** Сохранение заказа не требует обращения к облаку.

**ARCH-003:** POS Desktop и экран официанта используют общую серверную бизнес-логику.

**ARCH-004:** Local POS Server проверяет права, цены, суммы и состояние бизнес-объектов.

**ARCH-005:** SQLite является основным операционным хранилищем филиала.

**ARCH-006:** Облачная синхронизация выполняется асинхронно.

**ARCH-007:** При недоступности интернета локальные операции продолжаются.

**ARCH-008:** При отказе локального сервера работа сетевых клиентов может приостанавливаться до восстановления.

# 4. Bashkar POS Desktop и Local POS Server

## 4.1. Принцип размещения

В MVP следующие компоненты устанавливаются **на один физический Windows-компьютер**:

- POS Desktop;
- Local POS Server;
- SQLite Database;
- Kitchen Print Service;
- Sync Worker;
- локальные ресурсы Waiter Web Client.

Использование отдельного выделенного серверного компьютера в MVP не предусматривается.

## 4.2. Разделение процессов

POS Desktop и Local POS Server должны работать как отдельные процессы.

**POS Desktop** отвечает за:

- графический интерфейс кассира;
- отображение заказов;
- управление столами;
- работу со сменами;
- интерфейс регистрации оплат;
- отображение ошибок;
- выполнение действий через локальный API.

**Local POS Server** отвечает за:

- основную бизнес-логику;
- авторизацию сотрудников;
- роли и права;
- управление заказами;
- состояние столов;
- кассовые смены;
- расчёт сумм;
- регистрацию оплат;
- кухонную печать;
- локальные события;
- хранение данных;
- синхронизацию.

## 4.3. Механизм запуска

Local POS Server устанавливается как отдельная **Windows Service**.

Сценарий запуска:

1. Пользователь включает Windows-компьютер.
2. Windows автоматически запускает Local POS Server.
3. Сервер инициализирует SQLite, API и необходимые службы.
4. Кассир открывает Bashkar POS Desktop.
5. POS Desktop подключается к Local POS Server.
6. Официанты получают возможность подключаться к серверу через локальную сеть.

При запуске POS Desktop должен проверять состояние сервера и отображать понятную ошибку, если сервер недоступен.

## 4.4. Независимость сервера от интерфейса

Закрытие окна POS Desktop не должно останавливать Local POS Server.

Если кассир случайно закрыл интерфейс, сервер продолжает:

- хранить данные;
- принимать разрешённые запросы официантов;
- обслуживать WebSocket-соединения;
- выполнять фоновые задачи;
- обрабатывать очередь печати;
- синхронизировать данные при наличии интернета.

При повторном запуске POS Desktop подключается к существующему серверу и загружает актуальное состояние.

## 4.5. Ограничения MVP

В MVP предусматривается:

- один основной Local POS Server на филиал;
- одно рабочее место кассира;
- один авторитетный экземпляр операционной БД.

Подключение нескольких независимых кассовых рабочих мест не является требованием MVP.

Архитектура API должна позволять добавить дополнительные POS-клиенты в дальнейшем.

# 5. Архитектура Local POS Server

## 5.1. Стиль архитектуры

Для локального backend используется **Modular Monolith**.

Основные функциональные модули работают в рамках одного серверного приложения, но имеют разделённую ответственность.

Микросервисная архитектура для локального MVP не требуется.

## 5.2. Предварительная структура модулей

| Модуль | Ответственность |
|---|---|
| Auth | Авторизация и сессии |
| Employees | Сотрудники |
| Permissions | Роли и права |
| Shifts | Кассовые смены |
| Tables | Столы и посещения |
| Menu | Каталог и цены |
| Orders | Заказы и позиции |
| Order Batches | Отправки заказов |
| Payments | Учёт оплат |
| Printing | Кухонная печать |
| Realtime | WebSocket-события |
| Sync | Облачная синхронизация |
| Audit | Журнал действий |
| Backup | Резервные копии |
| System | Состояние и диагностика |

## 5.3. Разделение бизнес-логики

Основные бизнес-правила выполняются на сервере.

Например, сервер определяет:

- разрешено ли сотруднику открыть стол;
- открыта ли кассовая смена;
- можно ли отправить заказ;
- актуальна ли цена товара;
- сколько должен заплатить гость;
- можно ли отменить позицию;
- можно ли закрыть посещение стола.

Клиентские интерфейсы не должны самостоятельно принимать окончательные решения по этим операциям.

## 5.4. Архитектурные требования

**ARCH-SRV-001:** Сервер должен быть независимым от интерфейса POS Desktop.

**ARCH-SRV-002:** Все изменения операционных данных выполняются через серверные команды.

**ARCH-SRV-003:** Сервер обязан проверять полномочия сотрудника.

**ARCH-SRV-004:** Сервер самостоятельно рассчитывает финансовые суммы.

**ARCH-SRV-005:** Сервер должен поддерживать одновременную работу нескольких официантов.

**ARCH-SRV-006:** Ошибка одного запроса не должна приводить к повреждению остальных данных.

**ARCH-SRV-007:** Фоновая синхронизация не должна блокировать создание заказов.

**ARCH-SRV-008:** При перезапуске сервер восстанавливает состояние из локальной БД.

# 6. Экран официанта

## 6.1. Технология MVP

Для MVP используется локальный веб-сайт, который раздаётся Local POS Server.

Официант открывает сайт через браузер смартфона.

Установка отдельного мобильного приложения не требуется.

## 6.2. Поддерживаемые устройства

Целевые платформы:

- Android;
- iPhone.

Интерфейс должен быть адаптирован для смартфонов.

Работа проверяется на актуальных поддерживаемых браузерах выбранных тестовых устройств.

## 6.3. Принцип работы

Официант подключается к Wi-Fi ресторана и открывает локальный веб-сайт.

После авторизации может:

- просматривать разрешённые столы;
- открывать стол;
- просматривать меню;
- собирать черновик заказа;
- подтверждать заказ у гостей;
- отправлять пакет заказа;
- выполнять дозаказ;
- просматривать отправленные пакеты.

Все операции, требующие изменения серверных данных, выполняются через Local POS Server.

## 6.4. Ограничения

В MVP не входят:

- нативное приложение Android;
- нативное приложение iOS;
- push-уведомления;
- гарантированные фоновые уведомления при заблокированном телефоне.

В следующих версиях допускается создание мобильного приложения с использованием существующего Local API.

## 6.5. Локальное хранение черновиков

Для черновиков официанта используется IndexedDB браузера.

Черновик привязывается к:

- сотруднику;
- устройству;
- филиалу;
- посещению стола.

Черновик не является подтверждённым заказом.

При перезагрузке страницы приложение пытается восстановить сохранённый черновик.

После успешной отправки на сервер черновик помечается завершённым.

При удалении данных браузера черновик может быть потерян, поэтому IndexedDB не считается гарантированным постоянным хранилищем.

## 6.6. Работа при потере Wi-Fi

Если телефон потерял соединение:

- приложение показывает статус отсутствия связи;
- не подтверждённый сервером заказ не отображается как успешно отправленный;
- черновик сохраняется, насколько это позволяет браузер;
- после восстановления связи приложение выясняет состояние предыдущих команд;
- повторная отправка использует прежний идентификатор команды.

Автоматическая отправка новых неподтверждённых черновиков после восстановления Wi-Fi не предусматривается.

# 7. Локальная сеть и HTTPS

## 7.1. Организация сети

В каждом ресторане предусматривается локальная сеть.

Основные устройства:

- POS-компьютер;
- Wi-Fi роутер;
- смартфоны официантов;
- кухонный принтер.

POS-компьютер рекомендуется подключать к роутеру через Ethernet.

Официанты подключаются через служебную Wi-Fi-сеть.

## 7.2. Работа без интернета

Локальная сеть должна сохранять работоспособность при отключении внешнего интернета.

Отключение интернета не должно останавливать:

- локальный API;
- работу с заказами;
- работу столов;
- WebSocket;
- локальную авторизацию;
- кухонную печать.

## 7.3. Адрес подключения

Для промышленной версии предлагается использование локального HTTPS-адреса с доменом, принадлежащим Bashkar.kg.

Пример:

`https://r001.pos.bashkar.kg`

Локальный DNS направляет этот адрес на внутренний IP POS-компьютера.

Пример:

`r001.pos.bashkar.kg → 192.168.1.10`

Этот домен является примером предлагаемой схемы, а не уже работающим адресом.

## 7.4. Безопасное соединение

Предпочтительная схема:

- HTTPS для локального веб-клиента;
- HTTPS API;
- WSS для событий в реальном времени;
- один origin для веб-сайта, API и WebSocket.

TLS-сертификаты могут выдаваться посредством DNS-01.

Выпуск и обновление сертификатов должны управляться безопасно. Секреты DNS-провайдера не должны распространяться по ресторанным компьютерам без необходимости.

## 7.5. Обязательная техническая проверка

До окончательного утверждения реализации проверить:

1. Локальный DNS без интернета.
2. HTTPS на Android и iPhone.
3. Доступ после отключения внешнего интернета.
4. Доступ после перезапуска роутера.
5. Срок действия и обновление TLS-сертификатов.
6. Поведение смартфонов с Private DNS, VPN и мобильной передачей данных.
7. Подключение после изменения IP POS-компьютера.

Если предложенная схема окажется слишком сложной для типового ресторанного оборудования, необходимо выбрать проверенную альтернативу, сохраняющую безопасный локальный доступ.

## 7.6. Подключение официанта

POS Desktop должен иметь возможность показывать QR-код подключения.

Официант сканирует код, открывает сайт и проходит авторизацию.

Сам QR-код подключения не должен предоставлять административные права.

# 8. Архитектура данных

## 8.1. Основной принцип

Каждый филиал имеет собственную локальную операционную БД.

Для MVP используется SQLite.

Единая облачная PostgreSQL через Supabase содержит синхронизированные данные организаций и филиалов.

## 8.2. Локальное хранилище

SQLite хранит:

- сотрудников и необходимые локальные учётные данные;
- роли и разрешения;
- кассовые смены;
- столы;
- посещения столов;
- меню и версии цен;
- заказы;
- пакеты заказов;
- позиции заказов;
- платежи;
- задания печати;
- события синхронизации;
- историю действий.

## 8.3. Конфигурация SQLite

Для MVP предварительно выбираются:

- WAL Journal Mode;
- `synchronous=FULL`;
- атомарные транзакции;
- ограничения целостности;
- контролируемые миграции;
- регулярная проверка состояния БД.

Основную SQLite необходимо хранить на локальном диске POS-компьютера.

Не предусматривается совместное открытие файла активной SQLite несколькими компьютерами по сетевой файловой системе.

## 8.4. Предварительные сущности

| Таблица | Назначение |
|---|---|
| organizations | Организации |
| branches | Филиалы |
| employees | Сотрудники |
| roles | Роли |
| permissions | Разрешения |
| devices | Устройства |
| shifts | Кассовые смены |
| tables | Столы |
| table_sessions | Посещения столов |
| menu_categories | Категории меню |
| menu_items | Товары |
| menu_versions | Версии меню |
| orders | Заказы |
| order_batches | Пакеты отправки |
| order_items | Позиции заказов |
| payments | Платежи |
| print_jobs | Задания печати |
| sync_outbox | Исходящая очередь |
| sync_inbox | Входящие изменения |
| audit_logs | Журнал действий |

Окончательная структура БД определяется в DB-SCHEMA-001.

## 8.5. Идентификаторы

Основные сущности должны иметь глобально уникальные идентификаторы.

Предварительно выбирается UUID.

Для работников ресторана дополнительно могут использоваться удобные номера заказов.

## 8.6. Финансовые значения

Денежные суммы должны храниться без ошибок двоичной арифметики с плавающей точкой.

Для MVP предлагается хранение денежных значений целыми числами минимальных денежных единиц.

Правила округления, скидок и сервисных сборов определяются в CORE-001.

---

# 9. Столы, посещения и пакеты заказов

## 9.1. Основные понятия

В системе разделяются три сущности:

**Стол (`table`)**

Физический стол ресторана.

**Посещение (`table_session`)**

Конкретное обслуживание гостей за столом.

**Пакет заказа (`order_batch`)**

Группа позиций, которую сотрудник одним действием подтверждает; предназначенные для кухни позиции направляются на печать.

## 9.2. Открытие стола

Сценарий:

1. Гости занимают стол.
2. Официант открывает стол с телефона.
3. Клиент отправляет команду Local POS Server.
4. Сервер проверяет смену, стол и права сотрудника.
5. Сервер создаёт активное посещение.
6. Стол получает статус «Занят».
7. Подключённые клиенты получают обновление.

Открытие стола выполняется на сервере.

Одновременное создание двух активных посещений одного стола должно предотвращаться ограничениями данных и серверной логикой.

## 9.3. Создание черновика

Официант выбирает блюда.

До подтверждения гостями позиции находятся в черновике.

Черновик сам по себе:

- не направляется на кухню;
- не считается принятым сервером заказом;
- не входит в подтверждённый счёт;
- может изменяться официантом.

## 9.4. Отправка пакета

После подтверждения гостями официант нажимает «Отправить заказ».

Local POS Server:

1. Проверяет авторизацию.
2. Проверяет кассовую смену.
3. Проверяет посещение стола.
4. Проверяет товары.
5. Проверяет цены и модификаторы.
6. Проверяет уникальность команды.
7. Рассчитывает сумму.
8. Сохраняет пакет и позиции.
9. Создаёт задание кухонной печати, если пакет содержит позиции, предназначенные для кухни.
10. Записывает событие синхронизации.
11. Подтверждает приём клиенту.

Сохранение полного пакета, необходимых заданий печати и события синхронизации должно выполняться атомарно. Если ни одна позиция не предназначена для кухни, пакет сохраняется без кухонного задания.

## 9.5. Дозаказы

В пределах одного посещения стола может существовать несколько пакетов.

Например:

- пакет №1 — напитки;
- пакет №2 — основные блюда;
- пакет №3 — десерты.

Предназначенные для кухни позиции каждого пакета отправляются отдельно; остальные позиции сохраняются в заказе без кухонной печати.

Дозаказ не должен приводить к повторной печати ранее отправленных пакетов.

## 9.6. Формирование счёта

Счёт объединяет подтверждённые позиции активного посещения с учётом корректировок, отмен, скидок и других утверждённых правил.

Неподтверждённые черновики не должны изменять итоговую сумму счёта.

## 9.7. Конкурентная работа

Сервер должен корректно обрабатывать действия нескольких сотрудников.

При изменении одного стола разными устройствами используются транзакции и проверка актуального состояния.

Для конфликтующих изменений сервер возвращает ошибку и необходимые актуальные данные.

---

# 10. Кухонная печать

## 10.1. Принцип работы

В MVP заказы отправляются на обычные термопринтеры чеков.

KDS (Kitchen Display System) не входит в MVP.

## 10.2. Предварительные требования к принтерам

Основной целевой тип:

- термопринтер чеков;
- бумага 80 мм;
- поддержка ESC/POS или совместимого драйвера;
- подключение Ethernet или USB.

Модели с шириной 58 мм и дополнительные способы подключения могут поддерживаться позднее.

Конкретные производители и модели утверждаются после испытаний.

## 10.3. Print Service

Отдельный компонент обеспечивает:

- создание задания;
- выбор принтера;
- формирование кухонного чека;
- передачу на печать;
- обработку ошибок;
- повторную отправку;
- ручную перепечатку;
- журналирование.

## 10.4. Надёжность

Заказ сохраняется до фактической обработки печати.

При недоступности принтера принятый заказ не удаляется.

Состояние задания должно быть доступно на POS.

Необходимо различать:

- ожидание печати;
- передачу драйверу;
- успешное подтверждение доступного этапа отправки;
- ошибку;
- неопределённый результат.

Успешный ответ драйвера не всегда доказывает физическую печать чека.

При неопределённом результате автоматическое повторение должно учитывать риск дублирования.

## 10.5. Корректировки

При отмене уже отправленного на кухню блюда исходная отправка сохраняется в истории.

Корректировка создаётся как отдельная операция.

---

# 11. Кассовые смены

## 11.1. Общий принцип

Для полноценной работы с заказами должна быть открыта кассовая смена.

Сервер проверяет наличие активной смены при выполнении соответствующих операций.

## 11.2. Открытие смены

Открытие выполняется авторизованным кассиром, менеджером или владельцем в пределах предоставленных прав.

Фиксируются:

- филиал;
- сотрудник;
- устройство;
- время.

В MVP ввод и учёт начального остатка наличных не требуются.

## 11.3. Работа во время смены

Во время активной смены разрешаются соответствующие роли операции:

- создание заказов;
- дозаказы;
- управление посещениями столов;
- регистрация оплат;
- отмены и корректировки.

## 11.4. Закрытие смены

При закрытии должны проверяться:

- незакрытые счета;
- неоплаченные посещения;
- зарегистрированные платежи;
- возвраты.

В MVP система не выполняет физическую сверку наличных, не фиксирует фактически пересчитанную сумму и не рассчитывает кассовое расхождение. Эти возможности остаются для последующих версий.

Обычное закрытие смены при наличии незавершённых операций блокируется согласно правилам CORE-001.

Перенос обязательств между сменами может быть предусмотрен как отдельная разрешённая менеджеру операция.

---

# 12. Архитектура учёта оплат

## 12.1. Назначение

В MVP Bashkar POS обеспечивает **внутреннюю регистрацию оплат**.

Система не гарантирует фактическое поступление денег на банковский счёт и не подтверждает банковские транзакции.

## 12.2. Методы

Предварительно поддерживаются:

- наличные;
- банковская карта — ручная регистрация;
- другой вручную выбранный метод оплаты.

## 12.3. Возможности

Архитектура предусматривает:

- полную оплату;
- частичную оплату — для последующих версий; в MVP не поддерживается;
- смешанную оплату;
- регистрацию возврата;
- историю изменений;
- расчёт задолженности.

Полноценный UX разделения счёта между гостями может быть реализован позднее.

## 12.4. Требования

**ARCH-PAY-001:** Каждая зарегистрированная оплата является отдельной записью.

**ARCH-PAY-002:** Операции не удаляются бесследно.

**ARCH-PAY-003:** Возврат регистрируется отдельной корректирующей операцией.

**ARCH-PAY-004:** Право выполнять возвраты ограничивается ролями.

**ARCH-PAY-005:** Сервер самостоятельно рассчитывает остаток к оплате.

**ARCH-PAY-006:** Повторный запрос с тем же идентификатором не создаёт повторную оплату.

**ARCH-PAY-007:** Интерфейс должен различать внутренне зарегистрированную и подтверждённую внешней платёжной системой оплату. В MVP внешнего подтверждения нет.

## 12.5. Фискализация

Кухонный чек и внутренний счёт Bashkar POS не являются автоматически фискальными документами.

Интеграции с ККМ и банковскими терминалами не входят в архитектурный объём MVP.

До коммерческого использования необходимо отдельно определить применимые требования законодательства Кыргызстана, допустимый способ формирования фискальных документов и порядок совместной работы с ККМ.

---

# 13. Меню, цены и версии

## 13.1. Кеширование

Меню должно храниться локально.

При каждом переключении экранов POS не должен повторно загружать меню из Supabase.

Для оперативной работы допускается дополнительный кеш в памяти Local POS Server и клиентов.

Источником актуальной действующей версии для локальных операций остаётся Local POS Server.

## 13.2. Снимок цены

При сохранении позиции заказа необходимо фиксировать:

- ID товара;
- название;
- количество;
- цену;
- модификаторы;
- скидки;
- действовавшую версию меню;
- рассчитанную сумму.

Изменение меню в дальнейшем не должно изменять историческую стоимость сохранённой позиции.

## 13.3. Устаревшее меню на телефоне

Официант может открыть меню до изменения цены.

При отправке сервер проверяет актуальность данных.

Если цена изменилась, сервер возвращает информацию о конфликте и требует подтверждения новых условий.

Тихое изменение итоговой суммы без уведомления сотрудника не допускается.

## 13.4. Изменения из облака

Изменения конфигурации из веб-кабинета получают отдельную версию.

Local POS Server применяет новые версии после проверки.

Облако должно отображать фактический статус применения изменений в ресторане.

## 13.5. Дополнительные локальные изменения

Возможность редактирования меню менеджером непосредственно на POS допускается архитектурой.

Политика конфликта локальных и облачных редакций должна быть определена отдельно до реализации функции.

---

# 14. Синхронизация с Supabase

## 14.1. Цель

Синхронизация переносит операционные данные в облако и доставляет разрешённые изменения конфигурации обратно в ресторан.

Синхронизация не является обязательным этапом подтверждения локального заказа.

## 14.2. Transactional Outbox

При создании или изменении операционных данных сервер записывает бизнес-операцию и исходящее событие в одной транзакции SQLite.

Sync Worker отправляет ожидающие события в Cloud Backend.

## 14.3. Гарантии обмена

- Неотправленные события сохраняются локально.
- Повторная отправка не создаёт повторный бизнес-результат.
- Каждое событие имеет уникальный ID.
- Cloud Backend проверяет уникальность событий.
- Для изменений одной сущности контролируется последовательность.
- После подтверждения событие отмечается синхронизированным.
- Ошибки не должны блокировать локальную кассовую работу.

## 14.4. Входящие изменения

Для получения облачных команд и конфигурации используется отдельный механизм Inbox.

Изменения должны проверяться, применяться транзакционно и подтверждаться облаку.

## 14.5. Политика конфликтов

Для MVP:

- локальный сервер является главным для заказов, оплат и смен своего филиала;
- облако не должно перезаписывать локальную финансовую историю устаревшими данными;
- конфигурация передаётся версиями;
- сложные конфликты разрешаются предусмотренными доменными правилами, а не простым выбором самой поздней временной метки.

## 14.6. Состояние синхронизации

POS должен отображать:

- доступность интернета;
- состояние Cloud Backend;
- время последней синхронизации;
- количество ожидающих событий;
- ошибки синхронизации.

Веб-кабинет владельца должен показывать актуальность своих данных.

# 15. События в реальном времени

## 15.1. Технология

Используется WebSocket.

WebSocket применяется для отправки подключённым клиентам уведомлений об изменении состояния.

## 15.2. Основные события

| Событие | Назначение |
|---|---|
| `shift.updated` | Изменение смены |
| `table.updated` | Изменение стола |
| `order.created` | Новый заказ |
| `order.updated` | Изменение заказа |
| `order_batch.created` | Новый пакет |
| `payment.created` | Регистрация оплаты |
| `print_job.updated` | Изменение печати |
| `menu.updated` | Обновление меню |

## 15.3. Восстановление состояния

WebSocket не считается гарантированным постоянным хранилищем событий.

После потери соединения клиент должен:

1. Повторно подключиться.
2. Получить актуальное состояние с сервера.
3. Проверить незавершённые операции.
4. Продолжить работу.

# 16. Пользователи, авторизация и безопасность

## 16.1. Общий принцип

Предусматривается два контекста пользователей:

**Облачный**

Владельцы и уполномоченные сотрудники, работающие с веб-кабинетом.

**Локальный**

Сотрудники ресторана, работающие через POS или Waiter Client.

## 16.2. Локальная авторизация

Локальная авторизация не должна требовать интернет-соединения для заранее зарегистрированных сотрудников.

Local POS Server самостоятельно проверяет локальные сессии и разрешения.

ID сотрудника, полученный от клиента, не является доказательством его личности.

## 16.3. Предварительные роли

- Owner;
- Manager;
- Cashier;
- Waiter.

Окончательная модель ролей и разрешений определяется в AUTH-001.

## 16.4. Отзыв прав

Менеджер с соответствующими разрешениями должен иметь возможность заблокировать сотрудника локально.

Локальная блокировка применяется к новым операциям сразу.

Облачная блокировка доставляется на локальный сервер при синхронизации.

До получения команды сервер не может гарантировать применение нового облачного ограничения.

## 16.5. Безопасность API

Необходимо предусмотреть:

- защищённые соединения;
- управление сессиями;
- проверку прав;
- ограничение доступа к локальному API;
- проверку входных данных;
- регистрацию устройств;
- контроль административных операций;
- журналирование критических действий.

## 16.6. Защита секретов

Административные ключи Supabase не должны включаться в распространяемое клиентское приложение.

Для обмена с облаком используются ограниченные полномочиями учётные данные зарегистрированного устройства.

Локальные секреты должны храниться с использованием подходящих механизмов защиты Windows и ограниченных прав системной службы.

---

# 17. Резервное копирование

## 17.1. Цель

Снизить риск потери операционных данных при:

- сбое Windows;
- повреждении файлов;
- отказе накопителя;
- неудачном обновлении;
- случайных действиях;
- других авариях.

## 17.2. Предварительный график

- Автоматический снимок БД каждые 30 минут.
- Дополнительная копия после закрытия смены.
- Ежедневное сохранение резервной копии.
- Копия перед обновлением программы.
- Выгрузка зашифрованной резервной копии во внешнее хранилище при наличии подключения.

## 17.3. Срок хранения

Предварительная политика:

- 48 последних получасовых копий;
- ежедневные копии за 30 дней;
- хотя бы одна актуальная копия вне основного диска POS.

Окончательные сроки хранения и ограничения по объёму определяются после нагрузочного тестирования.

## 17.4. Механизм

Для активной SQLite используется безопасный механизм резервирования, например SQLite Online Backup API.

Неконтролируемое файловое копирование работающей БД не допускается.

## 17.5. Восстановление

Система должна иметь документированную процедуру восстановления.

Необходимо тестировать восстановление на отдельном компьютере.

При полном уничтожении локального компьютера возможна потеря операций, не попавших во внешнюю резервную копию или облако. Архитектура MVP не гарантирует нулевую потерю данных при физическом отказе основного диска.

# 18. Установка и лицензирование

## 18.1. Единый установщик

Для Windows предусматривается единый установщик Bashkar POS.

Он должен устанавливать:

- POS Desktop;
- Local POS Server;
- Windows Service;
- SQLite и необходимые каталоги;
- веб-ресурсы официанта;
- сервис печати;
- механизмы синхронизации и резервирования.

## 18.2. Первичная настройка

После установки выполняются:

1. Проверка системы.
2. Настройка локального сервера.
3. Регистрация устройства и филиала.
4. Первичная активация при наличии интернета.
5. Загрузка начальной конфигурации.
6. Настройка локальной сети.
7. Настройка принтера.
8. Проверка сохранения данных.
9. Проверка подключения официанта.

## 18.3. Лицензирование

Первичная активация может требовать интернет-соединения.

Обычная работа ресторана после активации не должна зависеть от постоянной связи с сервером лицензирования.

В MVP временная недоступность проверки лицензии не должна приводить к блокировке принятия заказов посреди активной смены.

## 18.4. Обновления

Обновления должны поддерживать:

- фоновую загрузку;
- проверку целостности и подписи;
- проверку совместимости;
- резервное копирование;
- контролируемую установку;
- миграции БД;
- восстановление после неудачного обновления.

Установка обновления во время активной смены не должна выполняться автоматически.

---

# 19. Нефункциональные требования

## 19.1. Производительность

Система должна быть оптимизирована для существующих ресторанных POS-компьютеров.

Меню должно храниться локально и не загружаться из облака при каждой навигации.

Фоновая синхронизация и резервирование не должны существенно мешать работе кассы.

## 19.2. Масштаб MVP

Предварительная целевая нагрузка:

- 1 локальный сервер;
- 1 основная касса;
- до 10 одновременно работающих официантов;
- до 50 столов;
- один или несколько кухонных принтеров.

## 19.3. Целевые показатели

При исправном оборудовании и локальной сети:

- P95 подтверждения обычного заказа сервером — не более 1 секунды;
- P95 доставки события подключённым клиентам — не более 1 секунды;
- интерфейс POS остаётся отзывчивым при фоновой синхронизации;
- работа без интернета поддерживается в течение полной смены;
- не допускаются дубли заказов при повторной передаче одной команды.

Показатели должны быть проверены нагрузочными тестами. Время физической кухонной печати не входит во время серверного подтверждения заказа.

## 19.4. Диагностика

Должны быть доступны:

- статус Local POS Server;
- статус локальной БД;
- состояние сети;
- состояние принтеров;
- состояние синхронизации;
- ошибки;
- журналы технических операций.

Логи не должны раскрывать пароли, токены и иные секретные данные.

# 22. Что не входит в MVP

В первоначальную версию не входят:

- нативное мобильное приложение официанта;
- push-уведомления;
- полноценный KDS;
- несколько независимых касс на один филиал;
- резервный локальный сервер с автоматическим переключением;
- автоматические банковские платежи;
- интеграция со всеми моделями ККМ;
- сложная CRM;
- складской учёт;
- программы лояльности;
- онлайн-доставка;
- автоматические заказы гостей через QR;
- сложные интеграции со сторонними POS.

Архитектура должна позволять добавлять эти возможности в следующих версиях.

QR/NFC-меню является запланированным дополнительным модулем, но его расширенные интерактивные функции не входят в критический контур MVP.

# 23. Основные технические риски

## RISK-01. Отказ POS-компьютера

Локальный сервер является единой точкой отказа.

Меры: резервные копии, проверка восстановления, рекомендации по UPS и качественному SSD.

## RISK-02. Нестабильная Wi-Fi-сеть

При потере соединения телефоны официантов не смогут обмениваться данными с сервером.

Меры: служебная Wi-Fi-сеть, проводное подключение сервера, повторное подключение и идемпотентные команды.

## RISK-03. Дублирование заказов

Повторная отправка после потери ответа может создавать дубли.

Меры: уникальные идентификаторы команд и сохранение результатов их обработки.

## RISK-04. Ошибки кухонной печати

Заказ может быть сохранён, но не доставлен кухне физически.

Меры: постоянная очередь печати, видимые ошибки и управляемая перепечатка.

## RISK-05. Конфликты синхронизации

Разные источники могут иметь несовпадающие данные.

Меры: разделение ответственности, версии сущностей, idempotent processing и журнал событий.

## RISK-06. Windows 10 без обновлений безопасности

Часть оборудования клиентов может использовать устаревшие редакции Windows.

Меры: контроль конфигурации, ограничение сетевого доступа, тестирование и рекомендации по обновлениям безопасности.

## RISK-07. HTTPS в локальной сети

Некоторые роутеры и настройки смартфонов могут мешать доступу по локальному домену.

Меры: обязательный технический прототип и утверждённая схема развёртывания.

## RISK-08. Слабое POS-оборудование

Electron и дополнительные процессы могут потреблять слишком много ресурсов.

Меры: раннее тестирование 4 ГБ RAM, оптимизация и возможность пересмотра оболочки Desktop.

---

# 24. Решения, требующие окончательной проверки

Следующие решения предварительно приняты, но требуют технического подтверждения:

1. Совместимость выбранного Desktop-стека с реальными Windows 10 POS.
2. Достаточность 4 ГБ оперативной памяти.
3. HTTPS + локальный DNS на типовых роутерах.
4. Поддержка конкретных моделей термопринтеров.
5. Надёжность печати кыргызских и русских символов.
6. Реальное время восстановления после отказа оборудования.
7. Эксплуатационные ограничения Windows 10 без актуальных обновлений.
8. Требования Кыргызстана к использованию ПО совместно с ККМ и другими обязательными средствами фискализации.

Эти вопросы не изменяют фундаментальный выбор Local-First, но должны быть разрешены до промышленного запуска.

# 26. Итоговое архитектурное решение

**Bashkar.kg представляет собой Local-First ресторанную платформу.**

В MVP система разворачивается на одном Windows-компьютере.

POS Desktop является интерфейсом кассира.

Local POS Server работает как отдельная Windows Service и содержит основную бизнес-логику.

SQLite является локальным источником операционных данных.

Официанты используют веб-интерфейс, раздаваемый Local POS Server через локальную сеть.

Заказы сохраняются на локальном сервере и автоматически формируют необходимые задания кухонной печати для предназначенных для кухни позиций.

Операционная работа ресторана не зависит от постоянного подключения к интернету.

Supabase используется как облачная платформа синхронизации, аналитики и централизованного управления.

Архитектура проектируется с возможностью последующего добавления мобильных приложений, KDS, QR/NFC-сервисов, дополнительных касс и интеграций.
