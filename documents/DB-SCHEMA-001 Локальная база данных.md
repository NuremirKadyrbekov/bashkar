# BASHKAR.KG — DB-SCHEMA-001
# Локальная база данных Local POS Server

**Версия:** 0.1  
**Дата:** 21 октября 2026 года  
**Статус:** проект для технического и продуктового согласования; не является готовой миграцией  
**Область:** локальная операционная SQLite одного филиала MVP.

## 1. Назначение и границы

Документ переводит согласованные бизнес-инварианты в проект хранения, ограничений, транзакций и проверок. Он предназначен для разработки вместе с ARCH-001, AUTH-001, тематическими разделами CORE-001, BACKEND-001 v0.1 и POS-001 TECH v0.1. Схема не заменяет API, PRINT-001, SYNC-001, BACKUP-001 и финансовую процедуру исправлений.

**Метки:** `[ИСТОЧНИК]` — согласованное требование источника; `[ПРОЕКТ]` — предлагаемая техническая реализация; `[ОТКРЫТО]` — неутверждённое решение или то, что требует проверки. Имена таблиц/полей, типы и структуры ниже — проект, а не утверждённый публичный контракт. Никакие предложенные реализации не отменяют открытые D02–D04, D06–D07, D10, D12–D15 и D18 BACKEND-001.

При расхождении ранних и позднее согласованных бизнес-решений использовать конкретное позднее решение; не выбирать по одному номеру версии. Противоречие, не разрешённое источниками, выносится на согласование. В частности, старый список открытых вопросов CORE «Оплаты» не отменяет позднее согласованные фиксированную скидку, запрет сборов COUNTER и `ZERO_SETTLED`.

## 2. Принципы хранения

1. `[ИСТОЧНИК]` Один авторитетный Local POS Server и один локальный операционный файл SQLite на филиал; клиенты и другие компьютеры не открывают его напрямую. Облако не участвует в критическом пути локальных операций.
2. `[ИСТОЧНИК]` Успех команды возвращается после commit; бизнес-изменения, обязательные задания печати, аудит, outbox и результат команды сохраняются согласованно. Печать, сеть и ручное получение денег вне транзакции.
3. `[ПРОЕКТ]` SQLite с `foreign_keys=ON` для **каждого соединения**, WAL и `synchronous=FULL`; результат настройки проверяется на целевом Windows-оборудовании. `CHECK` и `NOT NULL` используются совместно: SQLite допускает `NULL` в выражении `CHECK`.
4. `[ПРОЕКТ]` Идентификаторы — непрозрачные устойчивые TEXT ID; сервер создаёт идентификаторы сущностей, клиент — `command_id` до отправки. Человекочитаемый номер COUNTER не является первичным ключом. Формат ID, область уникальности и срок журнала D03 ещё не утверждены.
5. `[ПРОЕКТ]` Деньги KGS — `INTEGER` в тыйынах без float; количества порций — положительные целые числа, если источники для конкретного товара не разрешают иное. Ограничивать диапазоны и проверять переполнение при умножении и суммировании. Цены и суммы неотрицательны, положительный Payment/Refund строго больше нуля.
6. `[ПРОЕКТ]` Моменты времени — UTC epoch milliseconds в `INTEGER`; отображаемая временная зона филиала хранится отдельно. Сервер присваивает время регистрации; время бумажной операции хранится отдельно и не выдаётся за серверное. Часы не используются вместо ревизии или порядка транзакций.
7. `[ПРОЕКТ]` Изменяемые агрегаты имеют `revision INTEGER NOT NULL`, увеличиваемую при изменении. Устаревшая команда отклоняется, а не перезаписывает чужую работу. Исторические данные не удаляются каскадом.
8. `[ИСТОЧНИК]` Пароли и токены не записываются в открытом виде; секреты, пароль, полный платёжный ввод и токены исключаются из audit, outbox, технических логов и ответов. Шифрование/хранение ключей и ограничения доступа к файлам определяются SEC/BACKUP.

## 3. Карта связей

```text
branch ── employees, permissions, shifts, tables, menu revisions
shift ── table sessions ── [0..1] TABLE order ── batches ── items
shift ── COUNTER orders ── batches ── items
order ── corrections / discount history / fee snapshots ── settlement ── payments ── refunds
commands ── results + audit + outbox + print jobs ── print attempts
shift ── immutable report; incidents ── manual recovery ── evidence / approval
```

Открытое посещение может не иметь заказа до первого принятого непустого пакета. COUNTER не имеет посещения или стола. Не все стрелки означают физический FK: конкретные составные ссылки, направление и области целостности определяются миграциями и проверяются тестами. Для связей одной базы не допускать перекрёстный `branch_id` — составными FK/UNIQUE или эквивалентной проверяемой схемой и серверной проверкой в транзакции.

## 4. Справочник проектных сущностей

Общие поля сущностей по необходимости: `id`, `branch_id`, `created_at_ms`, `created_by_employee_id`, `revision`. `created_by` берётся из серверной сессии, а не из доверенного клиентского поля. Все ссылки на сотрудников и исторические объекты сохраняются при их архивировании.

### 4.2. Смены и столы

| Таблица `[ПРОЕКТ]` | Ключевые поля и назначение |

| `restaurant_tables` | `id`, `branch_id`, отображаемый номер/имя, доступность/архив, ревизия. Статус занятости выводится из активного посещения, не является независимым источником истины. |
| `table_sessions` | `id`, `branch_id`, `shift_id`, `table_id`, состояние, `opened_by_employee_id`, `responsible_waiter_id`, открытие/закрытие и причина закрытия. В MVP передача ответственности не реализуется. |
| `shift_reports` | Один исходный итог на закрытую смену: `shift_id`, версия формата, момент создания, неизменяемый snapshot и контрольная сумма по выбранному каноническому представлению. Состав и точные финансовые формулы — D08. |

Не более одной `OPEN` смены на филиал и одной активной сессии на стол, в том числе при гонке. Закрытая смена не переоткрывается; активные посещения, неоплаченные COUNTER и определённые источниками денежные/бумажные инциденты блокируют обычное закрытие. Видимость завершённого COUNTER и ошибка печати сами по себе не блокируют. Отчёт, состояние смены и события доставки фиксируются атомарно.

Реализация revision-specific строк либо неизменяемого полного документа редакции — `[ОТКРЫТО]` для DB/SYNC; в любом варианте сервер атомарно выбирает одну целостную активную редакцию и сохраняет исторические снимки заказа. FK на текущий каталог не заменяет снимок имени и цены. Признак «Готовится на кухне» означает необходимость KITCHEN-печати, не статус готовности.

| `order_discount_events` | Изменения одной фиксированной скидки, автор/время/причина изменения, включая автоматическое уменьшение после отмены. |
| `order_corrections`, `order_correction_lines` | Тип операции, причина, автор, время, исходные item ID, положительные количества, ссылки на созданные позиции и связанные печатные задания. Групповая операция принимается целиком или не принимается. |
| `counter_visibility_events` | События показа/скрытия завершённой карточки; текущее состояние может храниться в заказе с ревизией. Не подтверждает физическую выдачу. |

Количество, оставшееся действующим после всех корректировок, не может стать отрицательным; проверка производится внутри транзакции с защитой от гонок. Разделение комментария на часть порций и замена сохраняют связь со старой позицией и исторический состав. Для последней действующей порции требуется право полной отмены. Корректировка не переписывает принятую исходную запись; после расчёта обычные корректировки запрещены.

### 4.5. Расчёт, оплаты и возвраты

| Таблица `[ПРОЕКТ]` | Ключевые поля и назначение |
|---|---|
| `settlements` | `id`, `order_id`, `shift_id`, тип результата `PAID/ZERO_SETTLED`, итог в тыйынах, снимки суммы позиций/скидки/сборов, автор/время, связь с командой. Не более одного действительного полного результата на заказ; модель исправлений — открытый D05. |
| `payments` | `id`, `settlement_id`, `shift_id`, метод `CASH/CARD_MANUAL/QR_TRANSFER_MANUAL`, положительная сумма, автор/время. Ручная регистрация банковского метода не доказывает банковскую операцию. |
| `payment_refunds` | `id`, исходный `payment_id`, текущая `shift_id`, полная сумма этого Payment, причина, автор/время. Повторный полный Refund запрещён; отдельный частичный Refund Payment не входит в MVP. |
| `financial_corrections` | `[ОТКРЫТО]` Отдельная связанная история Reversal без изменения исходного Payment. Право и обязательная причина согласованы, но модель замены Settlement, ограничения и отражение в отчёте не утверждены; не выпускать произвольное изменение метода до отдельного решения. |

Для `PAID` сумма Payment равна полному актуальному итогу, каждый Payment положительный; MVP допускает один или два метода. Для `ZERO_SETTLED` итог ровно 0, действующие позиции существуют и Payment отсутствуют. `CANCELLED` не равен нулевому расчёту. Проверки сумм нескольких строк и наличия действующих позиций нельзя обеспечить простым `CHECK` строки: обязательны транзакционная серверная проверка, тесты и, где уместно, ограничения БД. Возврат в следующей смене связывается с исходным платежом и текущей сменой; исторический отчёт не переписывается.

Формула: `S = сумма действующих позиций`, `0 ≤ D ≤ S`, `B = S − D`; TABLE: `F_i = ROUND_HALF_UP(B × P_i / 100)` до тыйына **для каждого сбора отдельно**, итог `B + ΣF_i`; COUNTER: `B`. Проектное представление ставки — целый числитель и масштаб/знаменатель с утверждённым допустимым диапазоном; конкретная точность ставок и переполнение при промежуточном умножении требуют проверки. Исходные снимки ставок не меняются при изменении настроек.

### 4.6. Команды, печать, синхронизация и аудит

| Таблица `[ПРОЕКТ]` | Ключевые поля и назначение |
|---|---|
| `command_journal` | Scope, `command_id`, тип, канонический fingerprint запроса, субъект, состояние и сохранённый результат/ссылка; уникальность в выбранном scope. Scope, retention, канонизация и право повторно читать результат — D03. Долговечность финансовой дедупликации обязательна. |
| `print_jobs` | `id`, `branch_id`, тип только `KITCHEN/CUSTOMER`, назначение, snapshot содержимого/ссылки, направление, состояние, связь с источником и при необходимости с исходным job. Создаются при commit бизнес-команды; физическая печать — после. |
| `print_job_items` | Только позиции, относящиеся к соответствующему направлению и допустимые для печати; KITCHEN не включает непечатаемые товары. Замена отдельно проверяет старую и новую позиции. |
| `print_attempts` | `job_id`, последовательность, принтер, исполнитель/worker, время и подтверждённый результат/неопределённость. `UNKNOWN` не запускает безусловный автоматический повтор; `FAILED_SAFE` требует подтверждённых критериев драйвера D06. |
| `outbox_events` | Устойчивый event ID, branch, тип/версия, безопасная полезная нагрузка, агрегат/ревизия, попытки и состояние доставки. Создание атомарно с доменным изменением; повторная доставка требует dedup потребителя. |
| `inbox_events` | Внешний event ID, источник, fingerprint, состояние обработки и результат; повторное получение не должно применять событие дважды. Scope и версия протокола — SYNC/D07/D10. |
| `audit_events` | Актор, филиал, время, действие, объект, результат, command ID и необходимый безопасный контекст; аудит не содержит секретов. Историю корректировок и финансовых первичных записей не удалять ради освобождения места. |

Для кухонных заданий требуется логический порядок исходной печати и корректировок по направлению, но порядок очереди не доказывает фактический порядок бумаги. Состояния попыток, механизм разрешения/перенаправления и подтверждения драйверов согласуются с PRINT-001 и аппаратными тестами.

| `manual_recoveries` | Ссылка на инцидент, исходную и текущую смены, инициатор, фактическое время и время регистрации, статус рассмотрения и связь с разрешённой корректировкой. |
| `recovery_evidence` | Идентификатор нумерованной бумажной записи, безопасные сведения и расположение подтверждающих документов; политика хранения — BACKUP/SEC. Проверять отсутствие дубликата до финансовой регистрации. |
| `recovery_approvals` | Один подтверждающий для финансовой MANUAL_RECOVERY, отличный от инициатора; оба сотрудника уполномочены. Без второго запись остаётся на рассмотрении. |
| `backup_runs` | Идентификатор филиала/экземпляра, времена, версия схемы, расположение без секретов, статус проверки, результат тестового восстановления и версия ПО. Ключи шифрования не помещаются в эти метаданные. |

Финансовая и фискальная процедура аварийной регистрации и формат корректировки не утверждены. Хранение evidence не доказывает получение денег или законность операции. После закрытия исходной смены её отчёт не изменять; зарегистрированная позже операция ссылается на исходную и относится к разрешённому текущему периоду.

## 5. Ограничения и транзакционные инварианты

`[ПРОЕКТ]` Следующие примеры SQLite демонстрируют защиту от гонок **после утверждения физических имён и состояний**; это не исполняемая миграция полного проекта:

```sql
CREATE UNIQUE INDEX one_open_shift_per_branch
  ON shifts(branch_id) WHERE status = 'OPEN';
CREATE UNIQUE INDEX one_active_session_per_table
  ON table_sessions(branch_id, table_id) WHERE status = 'ACTIVE';
CREATE UNIQUE INDEX one_order_per_table_session
  ON orders(table_session_id) WHERE table_session_id IS NOT NULL;
CREATE UNIQUE INDEX one_counter_number_per_shift
  ON orders(branch_id, shift_id, counter_number) WHERE type = 'COUNTER';
CREATE UNIQUE INDEX one_refund_per_payment ON payment_refunds(payment_id);
```

Эти индексы работают только при согласованных `NOT NULL`, типах и жизненном цикле. В частности, для COUNTER необходимы `counter_number IS NOT NULL`, `table_session_id IS NULL`; для TABLE — `table_session_id IS NOT NULL` и отсутствие COUNTER-номера. Порядок создания последнего индекса должен учитывать жизненный цикл Refund; отклонённые попытки хранятся отдельно, а не как завершённые Refund. Не вводить частичный уникальный индекс действительного Settlement до утверждения модели Reversal; но сервер обязан обеспечивать не более одного действительного результата.

Дополнительные обязательные проверки:

- Валидность филиала всех связанных сущностей и владельца данных; FK с `ON DELETE RESTRICT`/эквивалентом для исторических ссылок, без массового каскадного удаления.
- Каждая принятая команда имеет durable результат в той же транзакции, что и её эффекты; повтор с другим fingerprint не выполняется. Scope и retention ещё требуют D03.
- Закрытие смены сериализуется с созданием заказов и денежными командами. Если первой завершилась быстрая продажа, она сама по себе закрытие не блокирует; если первым создан неоплаченный ACTIVE COUNTER — блокирует; если первой закрылась смена — новая продажа в ней не создаётся.
- Закрытие TABLE после полной оплаты/нулевого расчёта либо полной отмены, состояние заказа, финансовый результат, обязательные Print Jobs, audit и outbox согласованы атомарно. Закрытие пустого посещения возможно только при отсутствии принятых пакетов.
- Внутри транзакции повторно проверять доступ, актуальное состояние/версию, цены и итог. Не ожидать сотрудника, принтер или сеть внутри SQLite-транзакции.
- Новая редакция меню и подтверждение пакета получают последовательный порядок; пакет никогда не содержит несогласованную смесь редакций. Для новых позиций проверять наличие цены и доступность, включая отдельно подтверждённый контейнер.
- Финансовая MANUAL_RECOVERY не может перейти в подтверждённое состояние без двух разных уполномоченных сотрудников и необходимого основания. Уникальность evidence и разрешённый финансовый эффект уточняются по D09/D16.

`[ОТКРЫТО]` Физический механизм writer queue, transaction mode, `busy_timeout`, retry, журнал незавершённых команд и точный snapshot isolation — D04. Требуется подтвердить race-тестами, а не считать примеры SQL достаточными.

## 6. Отчёты и аналитические данные

Исходный `shift_reports` формируется при закрытии из локальных подтверждённых операций и сохраняется атомарно с закрытием. После commit snapshot неизменен; исправление ошибки системы требует отдельно контролируемого события/представления, не скрытой перезаписи.

Согласованные D08 принципы: завершённые продажи и зарегистрированные оплаты показываются отдельно; методы Payment, скидки, сборы, отмены и возвраты отображаются раздельно; `ZERO_SETTLED` учитывается в количестве завершённых заказов без поступления; общие показатели и TABLE/COUNTER; поздний возврат относится к смене выполнения со ссылкой на оригинал. Точные определения выручки, чистого итога, Reversal и MANUAL_RECOVERY, особенно для смешанной оплаты, остаются открытыми. Не выдавать предварительную формулу за утверждённую. Owner Dashboard использует тот же согласованный словарь и различает состояние синхронизации.

## 7. Миграции, старт и восстановление

1. `[ПРОЕКТ]` Версионированные SQL-миграции и журнал `schema_migrations(version, checksum, applied_at_ms, application_version)`; таблица версии и миграционный журнал проверяются совместно. Каждая выпущенная миграция неизменяема; изменения — новой версией.
2. До обновления проверять совместимость, место на диске и пригодную предварительную копию; автоматически не устанавливать миграции при открытой смене. Восстановление копии требует контролируемой процедуры, а не автоматической подмены данных.
3. Миграции выполнять транзакционно, где SQLite и конкретный способ позволяют; для остальных заранее определить безопасную процедуру и проверку после прерывания. При частичном или неизвестном состоянии не объявлять READY и блокировать опасные изменения.
4. Отдельно различать первый запуск неактивированного экземпляра и исчезновение БД активированного филиала: в последнем случае не создавать новую пустую рабочую БД автоматически.
5. Копирование живой SQLite/WAL — через проверенный согласованный механизм согласованного snapshot, не произвольное копирование одного `.db` при работающем сервере. Проверять целостность, версию, филиал и тестовое восстановление на отдельной базе. Проверить действие `PRAGMA foreign_key_check` и `integrity_check` на копии; они не доказывают полноту отсутствующих транзакций или соответствие бизнес-правилам.
6. Бинарный rollback допустим только при совместимости с текущей схемой; не откатывать автоматически SQLite к старому backup. RPO/RTO, частоты, ключи и носители остаются открытыми до испытаний.

## 8. Доступ, приватность и жизненный цикл данных

Только Local POS Server получает рабочий доступ к SQLite; Windows ACL и учётная запись службы ограничивают доступ к данным, WAL, копиям и журналам. UI проверок прав недостаточно: сервер проверяет авторизацию и актуальные разрешения при каждой команде. При отзыве права и параллельной операции результат должен соответствовать согласованному порядку фиксации.

Архивирование сотрудника или товара не удаляет исторические ссылки и снимки. Политики хранения финансовых первичных данных, command journal, audit, логов, попыток печати, очередей и резервных копий определяются отдельно по D03/D18 и применимым требованиям; финансовую историю нельзя автоматически удалять ради места. При нехватке диска транзакция не должна сообщать об успехе без подтверждённого commit; нужны диагностика и безопасное восстановление.

## 9. Проверки и критерии приёмки

До выпуска соответствующего модуля на реальном Windows POS выполнить автоматизированные миграционные, интеграционные и конкурентные тесты:

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| DB-AT-01 | Два одновременных открытия смены и одного стола | Одна OPEN смена на филиал и одно ACTIVE посещение на стол. |
| DB-AT-02 | Первая корзина TABLE/COUNTER, в том числе пустая | Пустая не создаёт заказ/пакет; непустая создаёт необходимые записи атомарно. |
| DB-AT-03 | Быстрая продажа против закрытия смены | Результат соответствует порядку commit; нет продажи в уже закрытой смене. |
| DB-AT-04 | Два расчёта, повтор command ID, иной fingerprint | Один действительный расчёт, одинаковый повтор получает исходный результат, конфликтующий ID не меняет данные. Проверить также после restart. |
| DB-AT-05 | Batch/коррекция против расчёта | Сервер либо учитывает раннее изменение и переподтверждает сумму, либо отклоняет позднее изменение; частичный commit невозможен. |
| DB-AT-06 | Смешанная оплата и нулевой расчёт | Payment положительны и равны полному итогу; ZERO_SETTLED с действующими позициями без Payment; CUSTOMER Job создан. |
| DB-AT-07 | Два Refund одного Payment | Только один полный Refund; при позднем возврате исходный отчёт не меняется. |
| DB-AT-08 | Две отмены одной порции и отмена последней порции | Количество не отрицательно; для полной отмены необходимо соответствующее право. |
| DB-AT-09 | Изменение меню во время Batch | Пакет содержит одну целостную редакцию и исторические цены; при конфликте требуется повторное подтверждение. |
| DB-AT-10 | Пакет без кухонных позиций; замена печатаемой на непечатаемую и наоборот | Заказ сохраняет все позиции; создаются только необходимые кухонные задания по соответствующим направлениям. |
| DB-AT-11 | Ошибка печати и UNKNOWN | Финансовый commit не откатывается, UNKNOWN не перепечатывается автоматически. |
| DB-AT-12 | Перезапуск/потеря ответа и отказ диска на границе commit | Нет ложного успеха или частичной бизнес-операции; после restart можно определить исход принятой команды. |
| DB-AT-13 | Чужой филиал, архивный сотрудник, отзыв прав в гонке | Нет обхода scope/прав; исторические ссылки сохраняются, результат соответствует порядку фиксации. |
| DB-AT-14 | Миграция, прерывание, несовместимая БД, отсутствие существовавшей БД | Никакой автоматической пустой подмены; безопасная диагностика и контролируемое восстановление. |
| DB-AT-15 | Копия при работающем WAL и тестовый restore | Согласованная восстановимая копия; фиксируются проверка и версия, исходная рабочая БД не подменяется. |
| DB-AT-16 | Финансовая MANUAL_RECOVERY с одним или тем же сотрудником | До подтверждения другим уполномоченным сотрудником финансовое подтверждение не выполняется. |
| DB-AT-17 | Переполнение денег/количеств и отсутствие цены | Ошибка до commit; нулевая цена и отсутствие цены различаются. |

Эти критерии — требования к будущим проверкам, не свидетельство выполненного тестирования. До согласования D05/D08/D09/D16 тестировать только утверждённые части и не выпускать выдуманные финансовые процедуры.
