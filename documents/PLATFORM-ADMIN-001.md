# PLATFORM-ADMIN-001 — первый админ-сайт BASHKAR

22.10.2026. Пользователь запросил быстрый понятный сайт администратора для создания нового владельца, его организации и первых филиалов. Первый администратор: nuremirdev@gmail.com. Выдача доступа: админ задаёт начальный пароль в форме, без писем. Кабинет владельца отложен; локальный OWNER и R-07 сохраняются.

## UI и границы

Отдельный небольшой сайт: вход администратора; организации/владельцы/филиалы со статусом регистрации; мастер «Владелец → организация → первые филиалы»; добавление филиала существующей организации. Простой RU интерфейс, поиск по загруженным данным, постраничная загрузка, empty/error/loading, подтверждение итогов. Нет биллинга, блокировки POS, переноса действующей регистрации, удаления клиента, Owner Dashboard, продаж или персонала локального ресторана.

Новый Site остаётся private. Sites authentication защищает hosting; дополнительно операции BASHKAR требуют подтверждённую Supabase Auth личность и активное членство в server-only platform_admins. Служебный ключ только в Supabase Edge, в статическом frontend лишь публичная конфигурация. Права из user_metadata/параметров/скрытия UI не принимаются. Регистрации администратора через сайт нет. Первый администратор создаётся отдельной одноразовой loopback-формой для утверждённого email: человек задаёт пароль сам, Auth Admin создаёт подтверждённую запись без письма, затем назначается platform_admins. Скрипт проверяет резервированный UUID и bootstrap-маркер; существующий чужой аккаунт или пароль не перезаписывается. Пароль не вводится в чат.

## Создание

Новый Owner создаётся Auth Admin API с email_confirm=true: выбранная пользователем административная выдача без писем, это не доказательство владения email по почтовой ссылке. UI явно показывает, что администратор проверяет адрес и передаёт пароль владельцу отдельно. Пароль минимум 12 символов, до 256 байт, не простой повтор/очевидный распространённый; ни в audit/result/хранилище браузера, ни в commands. Введённый пароль обнуляется после успеха/выхода. Существующему Auth-пользователю пароль не заменяется; для уже существующей организации есть отдельное добавление филиала.

Auth и Postgres не имеют общей транзакции. Durable provisioning request заранее резервирует UUID пользователя и безопасный payload. Credential proof PBKDF2-SHA256 210000 с солью command UUID хранится только в закрытой таблице запросов, не в аудите/result; одинаковый ID с иными полями/паролем конфликтует. Auth Admin create использует заранее сохранённый ID и app_metadata маркер команды. Потеря ответа восстанавливается GET по этому ID с проверкой email/маркера, без перезаписи пароля и без присвоения чужого пользователя. Затем организация + все филиалы + audit + request result сохраняются одной SQL-транзакцией. Сбой оставляет честный «Настройка не завершена» и исходный запрос для продолжения тем же админом/паролем; не обещается откат Auth API удалением учётной записи. Пароль не сохраняется для автоматического retry.

Пределы: до 20 первых филиалов; одинаковые имена в одном запросе запрещены; до 10 mutating запросов/админ/минуту; тела ≤16 KiB; чтение ограничено 50 организациями за страницу. Branch add использует durable UUID команды и повторяет исходный результат, аудит обязателен. Админ не может сменить ownership/registration через эти RPC. Прежние Owner RLS/активация не расширяются и таблицы действующих данных не перезаписываются.

## Проверка и эксплуатация

PGlite: anon/owner/admin isolation, RPC privileges, конфликт и replay, атомарность audit/org/branches, revoke. Edge harness с Auth fake: повтор после потери ответа на Auth и DB, другой email/маркер/ID, отсутствие служебного ключа в ответах, Origin/size/body limits. Настоящий браузер: вход, мастер, ошибки, продолжение и добавление филиала на disposable backend. Реальные cloud migration/deploy/bootstrap и создание пользователей отмечаются отдельно. Пользовательские MANGO/Windows/локальные DB/keys/OPEN-смены не обновляются.

## Первое подключение администратора

Скрипт `infrastructure/platform-admin/setup-admin.cjs` запускается с абсолютным путём к авторизованному Supabase CLI в первом аргументе. Он выводит одноразовый URL на 127.0.0.1 со случайным портом. Открыть URL на этом компьютере, задать и повторить пароль для nuremirdev@gmail.com. После сообщения «Администратор создан» войти на Site этим email/паролем. Setup завершается спустя минуту; повторный запуск с тем же безопасным `.local/platform-admin-setup/state.json` умеет продолжить незавершённую выдачу с исходным паролем. Service key получает CLI, держит только память процесса; state не содержит паролей/ключей.

В кабинете выбрать «Новый клиент», заполнить владельца и начальный пароль, название организации и первые филиалы. Проверить итог и подтвердить. Владелец затем входит этими данными в экран облачной активации новой локальной установки POS и выбирает свой свободный филиал. Это не команда обновления или сброса существующей установки.
