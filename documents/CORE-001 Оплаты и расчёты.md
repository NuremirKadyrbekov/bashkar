# 1. Назначение документа

## 1.1. Цель

Настоящий раздел определяет бизнес-логику проведения расчётов с гостями ресторанной системы Bashkar.kg.

Главная задача — обеспечить максимально быстрый, простой и надёжный процесс оплаты заказов, сохраняя корректный финансовый учёт.

Приоритеты:

1. Минимальное количество действий кассира.
2. Отсутствие ручного ввода суммы при стандартной оплате.
3. Быстрое завершение полного расчёта.
4. Автоматическая печать клиентского чека после успешной оплаты.
5. Поддержка основных способов оплаты.
6. Корректный учёт смешанных оплат.
7. Защита от дублирования платежей.
8. Сохранение финансовой истории.
9. Работа без интернета.
10. Согласованность со сменами, заказами и посещениями столов.

## 1.2. Основные принципы

Для MVP устанавливаются следующие правила:

- Заказ оплачивается полностью в конце обслуживания.
- Частичные оплаты не поддерживаются.
- Кассир не вводит сумму при обычном расчёте.
- Сумма определяется Local POS Server.
- Кассир выбирает способ оплаты и нажимает «Завершить оплату».
- Смешанная оплата поддерживается отдельным дополнительным действием.
- После успешной регистрации полной оплаты автоматически создаётся задание печати клиентского чека.
- Предварительная печать неоплаченного счёта отсутствует.
- Кухонные задания создаются при принятии пакетов только для позиций, предназначенных для кухни.
- Каждая операция сохраняет фактического сотрудника.
- Финансовые записи не удаляются бесследно.
- Интернет не требуется для выполнения локальных операций.

## 1.3. Разделение ответственности

**CORE-001** определяет правила расчёта.

**AUTH-001** определяет права сотрудников.

**POS-001** определяет пользовательские интерфейсы оплаты.

**WAITER-001** определяет возможности оплаты со смартфона официанта.

**BACKEND-001** определяет серверные команды и проверки.

**DB-SCHEMA-001** определяет структуру хранения финансовых записей.

**SYNC-001** определяет синхронизацию финансовой истории.

Детальное устройство интерфейсов, API и физические схемы хранения не определяются настоящим разделом.

# 2. Основные бизнес-сущности

## 2.1. Order — заказ

Order является объектом, по которому формируется итоговый расчёт.

Заказ объединяет:

- подтверждённые позиции;
- пакеты заказов;
- стоимость товаров;
- скидки;
- сервисные сборы;
- итоговую сумму;
- финансовые операции;
- состояние расчёта.

Для MVP предлагается два типа заказа:

| Тип       | Назначение               |
| --------- | ------------------------ |
| `TABLE`   | Заказ посещения стола    |
| `COUNTER` | Заказ на кассе без стола |

Заказ TABLE сохраняет существующую модель:

**Одно посещение → один основной заказ → несколько пакетов заказа.**

Заказ COUNTER существует независимо от Table Session.

## 2.2. Settlement — завершение расчёта

**Settlement** — логическая операция полного расчёта по заказу.

Она объединяет одну или несколько финансовых записей в одно действие завершения оплаты.

Основные характеристики:

- уникальный ID;
- ID заказа;
- ID кассовой смены;
- сумма полного расчёта;
- сотрудник;
- время;
- уникальный `command_id`;
- способ или способы оплаты;
- связанные записи Payment;
- результат операции.

Для одного заказа допускается одно действительное завершение полного расчёта.

Повторное проведение возможно только через отдельную разрешённую процедуру исправления ошибочного расчёта.

## 2.3. Payment — зарегистрированная оплата

Payment — отдельная финансовая запись, представляющая сумму, зачтённую определённым способом оплаты.

Основные логические данные:

| Поле                        | Назначение               |
| --------------------------- | ------------------------ |
| `id`                        | Уникальный ID            |
| `settlement_id`             | Общее завершение расчёта |
| `order_id`                  | Заказ                    |
| `shift_id`                  | Кассовая смена           |
| `method`                    | Способ оплаты            |
| `amount`                    | Зачтённая сумма          |
| `registered_by_employee_id` | Сотрудник                |
| `registered_at`             | Время регистрации        |

При оплате одним способом Settlement содержит один Payment.

При смешанной оплате Settlement содержит несколько Payment, объединённых одной серверной операцией.

Так сохраняется требование ARCH-PAY-001: каждая зарегистрированная оплата является отдельной записью.

## 2.4. Refund — возврат

Refund — самостоятельная корректирующая финансовая операция, фиксирующая возврат ранее зарегистрированной суммы.

Каждый возврат содержит:

- уникальный идентификатор;
- ссылку на исходный Payment;
- сумму;
- метод;
- кассовую смену возврата;
- сотрудника;
- причину;
- время;
- `command_id`.

## 2.5. Payment Reversal — исправление ошибочной оплаты

Payment Reversal — корректирующая операция для отмены ошибочно зарегистрированного финансового результата.

Refund и Payment Reversal не являются одной и той же операцией.

Refund фиксирует возврат денег.

Payment Reversal исправляет ошибку в учёте.

Исходная финансовая запись сохраняется в обоих случаях.

# 3. Поддерживаемые способы оплаты

## 3.1. Способы MVP

| Код                  | Название         | Подтверждение                                |
| -------------------- | ---------------- | -------------------------------------------- |
| `CASH`               | Наличные         | Сотрудник подтверждает получение             |
| `CARD_MANUAL`        | Банковская карта | Сотрудник проверяет результат внешней оплаты |
| `QR_TRANSFER_MANUAL` | QR-перевод       | Сотрудник проверяет результат перевода       |

Все методы регистрируются вручную.

Система не обращается к банковским API при подтверждении платежа.

## 3.2. Наличные

При оплате наличными:

1. Кассир видит итоговую стоимость заказа.
2. Получает деньги от гостя.
3. Самостоятельно выдаёт сдачу, если необходимо.
4. Выбирает способ «Наличные».
5. Нажимает «Завершить оплату».
6. Сервер регистрирует полную стоимость заказа как оплаченную.
7. Система автоматически создаёт задание клиентского чека.

Дополнительный ввод суммы, переданной гостем, не требуется.

## 3.3. Банковская карта

При оплате картой:

1. Гость использует внешний банковский терминал.
2. Кассир проверяет результат операции.
3. Выбирает «Карта».
4. Нажимает «Завершить оплату».
5. Сервер регистрирует полную стоимость заказа методом `CARD_MANUAL`.
6. Автоматически создаётся задание клиентского чека.

Система не получает подтверждение напрямую из банка.

## 3.4. QR-перевод

При оплате QR:

1. Гость использует банковское приложение.
2. Выполняет перевод по банковскому QR-коду ресторана.
3. Сотрудник проверяет доступное подтверждение платежа.
4. Выбирает «QR-перевод».
5. Нажимает «Завершить оплату».
6. Сервер регистрирует оплату методом `QR_TRANSFER_MANUAL`.
7. Создаётся задание клиентского чека.

Автоматическая банковская интеграция не требуется.

## 3.5. Бизнес-правила

**BR-PAY-001.** Поддерживаются методы CASH, CARD_MANUAL и QR_TRANSFER_MANUAL.

**BR-PAY-002.** Все три метода используются для ручной регистрации полного расчёта.

**BR-PAY-003.** Система не должна автоматически считать банковскую транзакцию подтверждённой.

**BR-PAY-004.** Обычный расчёт не требует ввода суммы оплаты.

**BR-PAY-005.** Сумма определяется сервером из актуального состояния заказа.

**BR-PAY-006.** Сотрудник обязан выбрать метод оплаты перед завершением.

**BR-PAY-007.** Регистрация оплаты означает подтверждение сотрудником факта получения денег, а не автоматическую банковскую проверку.

# 4. Основной сценарий полной оплаты

## 4.1. Принцип

В MVP используется модель:

**Один заказ → одно полное завершение расчёта.**

Частичные оплаты исключены.

В обычном сценарии кассир не вводит финансовую сумму и не разбивает счёт.

## 4.2. UC-PAY-001 — Полная оплата заказа

Предусловия:

- открыта кассовая смена;
- существует подтверждённый заказ;
- заказ ещё не оплачен;
- сотрудник имеет разрешение на приём оплаты;
- Local POS Server доступен.

Последовательность:

1. Гости заканчивают обслуживание.
2. Кассир открывает заказ.
3. Система показывает подтверждённые позиции.
4. Сервер рассчитывает итоговую стоимость.
5. Кассир получает от гостя подтверждение выбранного способа расчёта.
6. Принимает или проверяет оплату.
7. Выбирает соответствующий метод в интерфейсе.
8. Нажимает «Завершить оплату».
9. POS передаёт команду на Local POS Server.
10. Сервер проверяет сотрудника и его разрешения.
11. Проверяет активную кассовую смену.
12. Проверяет актуальное состояние заказа.
13. Проверяет отсутствие ранее проведённого действительного полного расчёта.
14. Проверяет окончательную сумму.
15. Сохраняет Settlement и Payment.
16. Фиксирует полное погашение счёта.
17. Создаёт задание клиентской печати.
18. Создаёт событие синхронизации.
19. Завершает транзакцию.
20. Подтверждает успешную регистрацию оплаты.
21. Print Service начинает обработку клиентского чека.

## 4.3. Бизнес-правила

**BR-PAY-008.** Обычная оплата выполняется на полную актуальную стоимость заказа.

**BR-PAY-009.** В стандартном интерфейсе отсутствует поле ручного ввода суммы платежа.

**BR-PAY-010.** Частичная оплата не поддерживается в MVP.

**BR-PAY-011.** Оплата допускается после формирования подтверждённого заказа.

**BR-PAY-012.** Обычный сценарий оплаты предназначен для окончательного расчёта с гостем.

**BR-PAY-013.** Оплата требует активной кассовой смены.

**BR-PAY-014.** Оплата требует соответствующего разрешения сотрудника.

**BR-PAY-015.** Сервер самостоятельно определяет итоговую сумму.

**BR-PAY-016.** Клиентская сумма не считается источником истины.

**BR-PAY-017.** После успешной полной оплаты финансовое состояние заказа становится PAID.

**BR-PAY-018.** Нельзя повторно провести полный расчёт уже оплаченного заказа обычной командой.

**BR-PAY-019.** Успешный расчёт должен сохраняться в SQLite.

**BR-PAY-020.** Подтверждение оплаты отправляется клиенту только после успешного сохранения сервером.

# 5. Смешанная оплата

## 5.1. Общий принцип

Смешанная оплата сохраняется в MVP.

Она предназначена для случаев, когда гость использует более одного способа оплаты.

При этом интерфейс должен оставаться простым.

Смешанная оплата не должна быть основным визуальным элементом экрана.

## 5.2. Интерфейс

Основной экран содержит:

- Наличные.
- Карта.
- QR-перевод.
- Завершить оплату.

Дополнительно предусматривается визуально второстепенная кнопка:

**«Смешанная оплата».**

Точное расположение определяется в POS-001.

## 5.3. UC-PAY-002 — Смешанная оплата

Пример:

Стоимость заказа: 2 000 сом.

Гость оплачивает:

- 800 сом наличными;
- 1 200 сом QR-переводом.

Кассир:

1. Нажимает «Смешанная оплата».
2. Выбирает два метода.
3. Указывает 800 сом для первого метода.
4. Система автоматически вычисляет 1 200 сом для второго.
5. Кассир проверяет получение обеих составляющих.
6. Нажимает «Завершить оплату».

Local POS Server создаёт:

- один Settlement на 2 000 сом;
- Payment CASH на 800 сом;
- Payment QR_TRANSFER_MANUAL на 1 200 сом.

Все записи сохраняются одной транзакцией.

Заказ считается оплаченным только после успешного завершения всей операции.

## 5.4. Правила смешанной оплаты

**BR-PAY-021.** Смешанная оплата доступна через дополнительное действие.

**BR-PAY-022.** Смешанная оплата выполняется в рамках одного логического завершения расчёта.

**BR-PAY-023.** Для двух методов сотрудник указывает сумму только первого метода.

**BR-PAY-024.** Сумму второго метода определяет сервер.

**BR-PAY-025.** Каждая составляющая должна иметь положительную сумму.

**BR-PAY-026.** Сумма составляющих должна точно соответствовать итоговой стоимости заказа.

**BR-PAY-027.** Каждая составляющая сохраняется с собственным методом оплаты.

**BR-PAY-028.** Все составляющие одной смешанной оплаты должны фиксироваться атомарно.

**BR-PAY-029.** Смешанный расчёт учитывается как один завершённый заказ в статистике продаж.

**BR-PAY-030.** Финансовые отчёты должны распределять суммы по фактически указанным методам.

**BR-PAY-031.** Нельзя записывать весь смешанный расчёт как один метод, если сотрудник указал раздельные составляющие.

## 5.5. Ограничения MVP

Для минимизации сложности интерфейса предлагается поддержать смешанный расчёт двумя методами одновременно.

Архитектура должна допускать большее количество составляющих в последующих версиях.

Поддержка трёх методов одновременно в интерфейсе MVP требует отдельного утверждения.

# 6. Финансовое состояние заказа

## 6.1. Состояния

Для нового стандартного сценария предлагаются:

| Состояние | Значение                            |
| --------- | ----------------------------------- |
| `UNPAID`  | Подтверждённый заказ ещё не оплачен |
| `PAID`    | Полная стоимость заказа погашена    |
| `ZERO_SETTLED` | Нулевой расчёт с действующими позициями завершён без Payment |

Состояние `PARTIALLY_PAID` в обычном жизненном цикле MVP не используется.

Если система расширится до частичных оплат, соответствующее состояние может быть добавлено позже.

## 6.2. Расчёт

Для обычного заказа:

**Остаток к оплате = Итоговая стоимость − зачтённая сумма расчёта.**

До завершения оплаты остаток равен полной итоговой стоимости.

После успешного полного расчёта остаток равен нулю.

Отдельные возвраты и корректировки, оформленные позднее, учитываются в финансовой истории, не переписывая исходное состояние закрытого посещения.

## 6.3. Бизнес-правила

**BR-PAY-032.** Финансовое состояние определяется серверными данными.

**BR-PAY-033.** Клиент не может самостоятельно устанавливать статус PAID.

**BR-PAY-034.** До полного расчёта обычный заказ имеет состояние UNPAID.

**BR-PAY-035.** Успешное завершение полного расчёта с оплатой фиксирует состояние PAID; нулевой расчёт с действующими позициями фиксируется отдельно согласно §6.4.

**BR-PAY-036.** Изменение финансового состояния должно быть согласовано с сохранением платежей.

**BR-PAY-037.** Историческое состояние заказа на момент закрытия должно сохраняться.

## 6.4. Завершение нулевого расчёта

Если после серверного расчёта итог заказа равен нулю и в нём остаются действующие позиции, сотрудник с разрешением на завершение расчёта может завершить нулевой расчёт. Это не отмена заказа и не получение денег. Сервер фиксирует отдельный результат `ZERO_SETTLED`, состав заказа и применённую скидку без создания фиктивного Payment или регистрации поступления денег.

Для TABLE и COUNTER сервер атомарно фиксирует результат, историю, событие синхронизации и постоянное задание печати клиентского чека с нулевым итогом. Для TABLE в той же транзакции сервер закрывает посещение с причиной `ZERO_TOTAL` и освобождает стол. Фактическая печать выполняется асинхронно; её ошибка не отменяет завершение. Для COUNTER завершение нулевого расчёта не создаёт Table Session; подробные состояния COUNTER определяются отдельно.

Сервер проверяет актуальный состав и нулевой итог, права и активную смену. Повтор команды с тем же `command_id` возвращает сохранённый результат без повторного завершения или нового обычного задания печати. Если сумма изменилась, команда отклоняется и сотруднику показываются актуальные условия.

# 7. Связь оплаты с посещением стола

## 7.1. Основной принцип

Для заказов TABLE используются уже существующие сущности:

- Table;
- Table Session;
- Order;
- Order Batch;
- Order Item.

Оплата связывается с Order.

Посещение сохраняет отдельное состояние ACTIVE или CLOSED.

## 7.2. Предварительный процесс

1. Официант открывает посещение.
2. Создаёт первый пакет.
3. Добавляет необходимые дозаказы.
4. Гости завершают заказ.
5. Кассир выполняет полный расчёт.
6. Финансовое состояние становится PAID.
7. Посещение завершается в соответствии с правилами закрытия посещений.
8. Стол освобождается.

## 7.3. Оплата и автоматическое закрытие посещения

### 7.3.1. Основной принцип

В Bashkar POS **успешная полная оплата заказа автоматически завершает посещение и освобождает стол**.

**Уточнение сверки 24.10.2026:** это действующее правило расчёта и занятости стола, а не подтверждение физической подачи. Отдельных команд «Готово/Подано/Выдано» нет. Предложение отделить выполнение от оплаты ещё не утверждено; вопросы и последствия для смены — DOCS-AUDIT-001 §4.

Официанту или другому уполномоченному сотруднику не требуется отдельно закрывать стол после оплаты.

Вся операция выполняется через Local POS Server.

**Одно действие «Завершить оплату» должно:**

1. Зарегистрировать полную оплату заказа.
2. Подтвердить финансовое состояние `PAID`.
3. Закрыть посещение со статусом `CLOSED`.
4. Зафиксировать причину закрытия `PAID`.
5. Освободить стол, переведя его в состояние `FREE`.
6. Создать задание автоматической печати клиентского чека.
7. Сохранить финансовую историю и событие синхронизации.

Все изменения должны выполняться атомарно в одной транзакции SQLite.

### 7.3.2. UC-PAY-003 — Оплата и закрытие стола официантом

**Предусловия:**

- Кассовая смена открыта.
- Посещение стола имеет статус `ACTIVE`.
- Заказ существует и ещё не оплачен.
- Официант авторизован и имеет право регистрации оплаты.
- Официант имеет доступ к соответствующему посещению согласно режиму STRICT или SHARED.
- Отсутствуют незавершённые операции, препятствующие определению окончательной суммы заказа.

**Основной сценарий:**

1. Гости заканчивают приём пищи и просят счёт.
2. Официант открывает веб-интерфейс Bashkar.
3. Выбирает соответствующий занятый стол.
4. Система отображает все принятые пакеты и окончательную стоимость заказа.
5. Официант уточняет у гостей способ оплаты.
6. Получает наличные либо проверяет оплату картой или QR-переводом.
7. Выбирает соответствующий способ оплаты.
8. Нажимает **«Завершить оплату»**.
9. Local POS Server проверяет полномочия официанта, активную смену, состояние посещения и актуальную сумму заказа.
10. Сервер регистрирует полную оплату.
11. Устанавливает финансовое состояние заказа `PAID`.
12. Автоматически закрывает посещение, присваивая ему статус `CLOSED` и причину `PAID`.
13. Стол становится свободным (`FREE`).
14. Сервер сохраняет задание печати клиентского чека и событие синхронизации.
15. После успешного сохранения операции возвращает подтверждение.
16. Kitchen Print Service / Print Service начинает обработку клиентского чека через назначенный принтер.
17. POS Desktop и подключённые интерфейсы официантов получают уведомление об освобождении стола.

**Результат:** заказ полностью оплачен, посещение завершено, стол свободен и доступен для новых гостей.

### 7.3.3. Бизнес-правила

**BR-PAY-CLOSE-001.** Успешная полная оплата заказа TABLE автоматически закрывает связанное посещение.

**BR-PAY-CLOSE-002.** После успешной оплаты дополнительное ручное действие «Закрыть стол» не требуется.

**BR-PAY-CLOSE-003.** Регистрация оплаты и закрытие посещения должны выполняться одной атомарной серверной транзакцией.

**BR-PAY-CLOSE-004.** Стол освобождается только после успешного сохранения полного расчёта и закрытия посещения.

**BR-PAY-CLOSE-005.** При ошибке до фиксации транзакции оплата не должна считаться успешной, посещение остаётся активным, а стол — занятым.

**BR-PAY-CLOSE-006.** После успешного закрытия посещения запрещается отправка новых пакетов и дозаказов в него.

**BR-PAY-CLOSE-007.** Повторное нажатие «Завершить оплату» с тем же `command_id` не должно создавать дополнительную оплату, повторно закрывать посещение или создавать новое обычное задание печати.

**BR-PAY-CLOSE-008.** Если одновременно выполняются дозаказ и завершение оплаты, Local POS Server должен обеспечить согласованное выполнение операций: принятый до закрытия пакет учитывается в окончательном счёте, а пакет, поступивший после закрытия, отклоняется.

**BR-PAY-CLOSE-009.** Если итоговая сумма заказа изменилась до подтверждения расчёта, сервер отклоняет оплату по устаревшим условиям и возвращает актуальную сумму для повторного подтверждения сотрудником.

**BR-PAY-CLOSE-010.** После успешной оплаты автоматически создаётся постоянное задание клиентской печати. Отказ принтера не должен отменять оплату, повторно открывать посещение или занимать освобождённый стол.

**BR-PAY-CLOSE-011.** Закрытое посещение сохраняется в истории со всеми заказами, пакетами, платежами, сотрудниками и временем операций.

**BR-PAY-CLOSE-012.** При потере ответа от сервера клиент проверяет результат исходной команды по `command_id`, не создавая повторный расчёт с новым идентификатором.

**BR-PAY-CLOSE-013.** В режиме STRICT оплату может завершить ответственный официант либо другой сотрудник с необходимыми специальными разрешениями. В режиме SHARED — любой официант, имеющий право регистрации оплат и доступ к данному посещению.

### 7.3.4. Критерии приёмки

**PAY-CLOSE-AT-001:** После нажатия «Завершить оплату» успешно оплаченный заказ получает статус `PAID`.

**PAY-CLOSE-AT-002:** Посещение автоматически получает статус `CLOSED` с причиной `PAID`.

**PAY-CLOSE-AT-003:** Стол автоматически становится `FREE`.

**PAY-CLOSE-AT-004:** Официанту не требуется отдельно закрывать стол.

**PAY-CLOSE-AT-005:** После успешной оплаты автоматически создаётся задание печати клиентского чека.

**PAY-CLOSE-AT-006:** При ошибке сохранения оплата и закрытие посещения не выполняются частично.

**PAY-CLOSE-AT-007:** Повтор команды не создаёт дублированных платежей или чеков.

**PAY-CLOSE-AT-008:** После закрытия посещения нельзя добавить новый пакет заказа.

**PAY-CLOSE-AT-009:** Все подключённые клиенты получают актуальное состояние освободившегося стола.

**PAY-CLOSE-AT-010:** Весь процесс регистрации оплаты и освобождения стола работает без подключения к интернету.

## 7.4. Необходимое согласование

Полная оплата и закрытие посещения выполняются одним серверным действием при соблюдении обязательных проверок. Это утверждённое правило заменяет отдельное закрытие посещения после оплаты.

После успешной полной оплаты посещение не остаётся `ACTIVE`; новые пакеты и дозаказы в него не принимаются.

# 8. Заказы на кассе без стола

## 8.1. Назначение

В MVP Bashkar POS поддерживает заказы без открытия физического стола.

Примеры:

- еда навынос;
- кофе с собой;
- покупка готового товара;
- заказ непосредственно на кассе.

## 8.2. Тип COUNTER

Предлагается использовать:

`order_type = COUNTER`

Заказ COUNTER:

- не создаёт Table Session;
- не занимает физический стол;
- связывается с активной кассовой сменой;
- имеет сотрудника, оформившего заказ;
- содержит подтверждённые позиции;
- использует общую систему платежей;
- может создавать кухонные задания;
- включается в отчёты смены.

## 8.3. UC-COUNTER-001 — Заказ на кассе

1. Кассир выбирает «Новый заказ».
2. Добавляет товары.
3. Подтверждает состав заказа.
4. Local POS Server создаёт заказ COUNTER и первый пакет.
5. Сервер создаёт необходимое задание кухонной печати.
6. Гость получает или ожидает заказ.
7. Кассир выбирает способ оплаты.
8. Нажимает «Завершить оплату».
9. Сервер атомарно сохраняет полный расчёт, завершает заказ COUNTER и создаёт задание печати клиентского чека.
10. Физическая печать выполняется асинхронно; выдача гостю и скрытие карточки не являются условиями завершения заказа.

## 8.4. Бизнес-правила

**BR-COUNTER-001.** Создание заказа COUNTER не требует физического стола.

**BR-COUNTER-002.** Заказ COUNTER требует активной кассовой смены.

**BR-COUNTER-003.** Сотрудник и время создания заказа фиксируются сервером.

**BR-COUNTER-004.** Все позиции рассчитываются по серверным ценам.

**BR-COUNTER-005.** Пакеты заказа COUNTER используют ту же логику принятия и защиты от дублей, что обычные пакеты.

**BR-COUNTER-006.** На кухонном чеке для COUNTER используется номер заказа и крупное обозначение «НА ВЫНОС» вместо номера стола.

**BR-COUNTER-007.** Стандартная оплата COUNTER выполняется на полную сумму.

**BR-COUNTER-008.** Смешанная оплата COUNTER допускается.

**BR-COUNTER-009.** Завершённый заказ COUNTER сохраняется в истории.

**BR-COUNTER-010.** Новые пакеты не принимаются к уже закрытому заказу COUNTER.

**BR-COUNTER-011.** Незавершённый заказ COUNTER препятствует обычному закрытию кассовой смены.

# 9. Печать чеков

## 9.1. Основной принцип

В Bashkar POS MVP поддерживаются только два вида чеков:

1. Кухонный чек.
2. Клиентский чек.

Предчек и другие виды обычных чеков не реализуются.

Отчёты смен, доступные в POS и Owner Dashboard, не образуют третий тип печатного чека.

## 9.2. Кухонный чек — KITCHEN

Кухонный чек предназначен для передачи подтверждённых блюд и пожеланий гостей на кухню.

Кухонное задание автоматически создаётся после успешного принятия пакета, если он содержит позиции, предназначенные для кухни. Полный пакет сохраняется в заказе; непечатаемые позиции не включаются в кухонный чек.

Содержание кухонного чека

Кухонный чек должен содержать:

Номер стола или номер заказа COUNTER.

Дату и время отправки заказа.

Имя или идентификатор сотрудника, отправившего заказ.

Названия заказанных блюд.

Количество каждой позиции.

Модификаторы блюд, если они имеются.

Индивидуальные комментарии к позициям.

Номер пакета заказа на кухонном чеке не отображается.

При этом каждый кухонный чек по-прежнему связан с конкретным Order Batch внутри системы. Эта связь необходима для истории, аудита, контроля печати и предотвращения дублирования.

Бизнес-правила

BR-KITCHEN-PRINT-001. Кухонный чек создаётся автоматически после успешного принятия пакета с предназначенными для кухни позициями; если таких позиций нет, кухонное задание не создаётся.

BR-KITCHEN-PRINT-002. На кухонном чеке не отображается номер пакета.

BR-KITCHEN-PRINT-003. При дозаказе печатаются только предназначенные для кухни новые позиции соответствующего пакета.

BR-KITCHEN-PRINT-004. Индивидуальные комментарии должны печататься непосредственно под соответствующими блюдами.

BR-KITCHEN-PRINT-005. Отказ кухонного принтера не должен удалять или отменять принятый заказ.

BR-KITCHEN-PRINT-006. Внутренняя связь задания печати с пакетом заказа должна сохраняться независимо от содержимого напечатанного чека.
## 9.3. Клиентский чек — CUSTOMER

Клиентский чек предназначен для предоставления гостю информации об успешно зарегистрированном расчёте.

Печатается автоматически после успешного полного расчёта.

Клиентский чек содержит:

- название ресторана;
- дату и время;
- номер заказа;
- номер стола, если применимо;
- наименования товаров;
- количество;
- цены;
- скидку, если применялась;
- сервисный сбор, если применялся;
- итоговую стоимость;
- способ оплаты;
- распределение сумм, если оплата смешанная.

Это внутренний нефискальный чек, если отдельная законно допустимая система фискализации не сформировала соответствующий фискальный документ.

## 9.4. Автоматическая печать после оплаты

**UC-RECEIPT-001 — Автоматическая печать клиентского чека**

1. Сотрудник нажимает «Завершить оплату».
2. Сервер проверяет команду.
3. Рассчитывает окончательную сумму.
4. Сохраняет Settlement.
5. Сохраняет Payment или несколько Payment.
6. Фиксирует состояние PAID.
7. Создаёт Print Job типа CUSTOMER.
8. Создаёт событие синхронизации.
9. Подтверждает успешное сохранение операции.
10. Print Service начинает печать.

Дополнительного нажатия «Распечатать» не требуется.

## 9.5. Атомарность

Сохранение полного расчёта, связанных платежей, итогового финансового состояния, задания клиентской печати и события синхронизации должно выполняться согласованно в рамках одной локальной транзакции.

При ошибке до фиксации транзакции операция не считается завершённой.

После успешного сохранения финансовых данных ошибка физической печати не отменяет оплату.

## 9.6. Сбой принтера

Если клиентский принтер недоступен:

- зарегистрированная оплата сохраняется;
- заказ остаётся оплаченным;
- задание печати сохраняется;
- POS отображает ошибку;
- доступна контролируемая повторная печать.

Перепечатка не создаёт второй Payment или Settlement.

Если результат физической печати неизвестен, нельзя бесконтрольно повторять задание.

## 9.7. Бизнес-правила

**BR-RECEIPT-001.** В MVP существуют только типы KITCHEN и CUSTOMER.

**BR-RECEIPT-002.** Кухонный чек создаётся после успешного принятия пакета заказа.

**BR-RECEIPT-003.** Клиентский чек создаётся только после успешного полного расчёта.

**BR-RECEIPT-004.** Предчек не поддерживается.

**BR-RECEIPT-005.** Клиентский чек автоматически поступает в очередь печати.

**BR-RECEIPT-006.** Дополнительная кнопка подтверждения обычной печати не требуется.

**BR-RECEIPT-007.** Клиентский чек содержит фактический итог зарегистрированного расчёта.

**BR-RECEIPT-008.** При смешанной оплате чек содержит разбивку по использованным методам.

**BR-RECEIPT-009.** Задание клиентской печати сохраняется атомарно с оплатой.

**BR-RECEIPT-010.** Ошибка принтера не отменяет успешно зарегистрированный платёж.

**BR-RECEIPT-011.** Повторная печать не создаёт новый платёж.

**BR-RECEIPT-012.** Повтор одной команды оплаты не создаёт повторное обычное задание печати.

**BR-RECEIPT-013.** Успешный ответ драйвера не обязательно доказывает физическую печать.

**BR-RECEIPT-014.** Для неопределённого результата печати требуется контролируемая повторная обработка.

**BR-RECEIPT-015.** Печать клиентских чеков должна работать без доступа к облачной инфраструктуре.

# 10. Скидки на заказ

## 10.1. Назначение

В MVP предусматривается ручная скидка на весь заказ.

Скидки на отдельные позиции не входят в первоначальный объём.

## 10.2. Основная модель

Скидка применяется к общему заказу до окончательного расчёта.

Сервер должен учитывать её при вычислении итоговой суммы.

Исторические снимки исходных цен блюд не изменяются.

## 10.3. Бизнес-правила

**BR-DISCOUNT-001.** В MVP скидка применяется к общему заказу.

**BR-DISCOUNT-002.** Применение скидки требует соответствующего разрешения.

**BR-DISCOUNT-003.** Скидку рассчитывает Local POS Server.

**BR-DISCOUNT-004.** Скидка не может привести к отрицательной стоимости заказа.

**BR-DISCOUNT-005.** Историческая цена отдельной позиции не должна изменяться из-за скидки.

**BR-DISCOUNT-006.** Применение скидки фиксирует сотрудника, время и результат.

**BR-DISCOUNT-007.** После завершения полного расчёта обычное редактирование скидки запрещено.

## 10.4. Ручная скидка на заказ

10.4.1. Основной принцип

В MVP Bashkar POS поддерживает ручную скидку в виде фиксированной денежной суммы на весь заказ.

Процентные скидки в первоначальную версию не входят.

Скидка уменьшает общую стоимость заказа и учитывается при окончательном расчёте.

10.4.2. Права сотрудников

Применять скидку могут:

Кассир (Cashier).

Официант (Waiter).

Эти роли по умолчанию имеют право устанавливать скидку на доступные им заказы.

Local POS Server проверяет авторизацию и допустимость операции.

Для официантов сохраняются правила доступа STRICT и SHARED. Право предоставления скидки не позволяет изменять чужие недоступные посещения.

10.4.3. Применение скидки

Пример:

Стоимость заказа: 2 000 сом.

Скидка: 200 сом.

Стоимость после скидки: 1 800 сом.

Кассир или официант вводит размер скидки в сомах.

Local POS Server проверяет сумму и пересчитывает итог заказа.

Скидка не должна превышать стоимость заказа или приводить к отрицательному результату.

10.4.4. Изменение скидки

Применённую скидку разрешается изменять до успешной регистрации оплаты.

Сотрудник может:

Установить скидку.

Изменить её сумму.

Уменьшить скидку.

Полностью убрать скидку.

При каждом изменении сервер пересчитывает итоговую стоимость.

После успешного полного расчёта изменение скидки обычной операцией запрещено.

Бизнес-правила

BR-DISCOUNT-008. В MVP поддерживается фиксированная скидка в сомах и тыйынах.

BR-DISCOUNT-009. Скидка применяется к общей стоимости заказа, а не непосредственно изменяет сохранённые цены позиций.

BR-DISCOUNT-010. Кассир и официант имеют право устанавливать скидку на доступные им заказы.

BR-DISCOUNT-011. Размер скидки не может превышать допустимую стоимость заказа.

BR-DISCOUNT-012. До успешной оплаты сотрудник может изменить или удалить ранее применённую скидку.

BR-DISCOUNT-013. После успешной оплаты обычное изменение скидки запрещено.

BR-DISCOUNT-014. Каждое изменение скидки фиксирует сотрудника, время, прежнее и новое значение.

BR-DISCOUNT-015. Окончательную стоимость заказа после скидки рассчитывает Local POS Server.

# 11. Сервисный сбор

## 11.1. Назначение

Bashkar POS поддерживает настраиваемый процент обслуживания.

Процент задаётся в конфигурации ресторана.

## 11.2. Расчёт

Сервисный сбор должен учитываться в общей стоимости заказа.

Система сохраняет фактически применённую ставку.

Изменение настройки ресторана не должно автоматически изменять исторические оплаченные заказы.

## 11.3. Настраиваемые дополнительные сборы

11.3.1. Основной принцип

По умолчанию в Bashkar POS никакие дополнительные сборы не начисляются.

Владелец ресторана может самостоятельно включать и настраивать дополнительные процентные сборы в настройках ресторана.

Система не должна автоматически добавлять плату за обслуживание или другие начисления, если владелец их не настроил и не активировал.

11.3.2. Настройка дополнительных сборов

Владелец может создавать дополнительные сборы, указывая:

Название сбора.

Процент начисления.

Состояние: активен или отключён.

Примеры:

Название

Процент

За обслуживание

5%

За электроэнергию

1%

Другой сбор

2%

Названия являются пользовательскими и определяются владельцем ресторана.

Приведённые значения используются только как примеры.

11.3.3. Несколько сборов

В одном ресторане может быть настроено несколько дополнительных сборов.

Например:

Стоимость блюд: 2 000 сом.

Настроены:

Обслуживание — 5%.

Электроэнергия — 1%.

При простом независимом начислении процентов от одной базы:

Обслуживание: 100 сом.

Электроэнергия: 20 сом.

Итого: 2 120 сом.

Если для заказа не зафиксирован ни один активный сбор, итоговая сумма определяется без дополнительных начислений.

Для TABLE сервер суммирует действующие позиции по историческим ценам (`S`), применяет фиксированную скидку `D` в пределах `0 ≤ D ≤ S` и получает базу `B = S − D`. Каждый применимый сбор независимо рассчитывается от этой базы: `Fi = ROUND_HALF_UP(B × Pi / 100)` до одного тыйына. Итог TABLE — `B + ΣFi`, итог COUNTER — `B`, без дополнительных сборов. После отмены при необходимости скидка уменьшается до новой стоимости позиций с записью прежнего и нового значений в историю.

Набор активных сборов, их названия и ставки фиксируются для TABLE при принятии первого пакета, а не при открытии стола. При последующих дозаказах, отменах и изменении скидки суммы пересчитываются по сохранённым ставкам и актуальной базе; изменение настроек ресторана не меняет набор уже начатого заказа. Подробные согласованные правила приведены в CORE-001 «Меню и ценообразование», BR-MENU-074–084.

11.3.4. Отображение в счёте

Каждый активный сбор должен отображаться отдельной строкой с понятным названием и суммой.

Скрытое начисление сборов запрещается.

Итоговая сумма с учётом дополнительных начислений рассчитывается Local POS Server.

Бизнес-правила

BR-SERVICE-007. По умолчанию дополнительные сборы отключены.

BR-SERVICE-008. Создавать, изменять, включать и отключать дополнительные сборы может владелец ресторана или другой сотрудник с отдельно предоставленным административным разрешением.

BR-SERVICE-009. Каждый сбор содержит собственное название и процент.

BR-SERVICE-010. Ресторан может иметь несколько активных дополнительных сборов.

BR-SERVICE-011. Каждый активный сбор рассчитывается и отображается отдельно.

BR-SERVICE-012. Сборы, не входящие в зафиксированный для заказа набор, не влияют на его итог. Последующее отключение сбора в настройках не удаляет его из набора ранее начатого TABLE-заказа.

BR-SERVICE-013. Local POS Server самостоятельно рассчитывает суммы дополнительных сборов.

BR-SERVICE-014. В финансовой истории заказа сохраняются фактически применённые названия, проценты и суммы сборов.

BR-SERVICE-015. Изменение настроек сборов не должно изменять исторические оплаченные заказы.

BR-SERVICE-016. На клиентском чеке каждый применённый дополнительный сбор отображается отдельной строкой.

## 11.4. Бизнес-правила

**BR-SERVICE-001.** Сервисный сбор определяется процентом.

**BR-SERVICE-002.** Сервисный сбор рассчитывается сервером.

**BR-SERVICE-003.** Сервисный сбор отображается отдельной составляющей счёта.

**BR-SERVICE-004.** Применённый процент должен сохраняться в финансовых данных заказа.

**BR-SERVICE-005.** Успешная оплата фиксирует окончательные значения скидок и сервиса.

**BR-SERVICE-006.** После завершения расчёта обычное изменение сервисного сбора запрещено.

## 11.5. Дополнительные сборы для заказов COUNTER

Основной принцип

Для заказов типа COUNTER дополнительные сборы не начисляются.

Это правило действует независимо от настроек сборов для обслуживания гостей за столами.

Примеры заказов COUNTER:

Кофе с собой.

Еда навынос.

Покупка готового товара на кассе.

Для таких заказов система рассчитывает стоимость подтверждённых товаров с учётом применимой скидки, но без дополнительных процентных сборов.

Бизнес-правила

BR-SERVICE-017. Дополнительные сборы применяются только к заказам типа TABLE.

BR-SERVICE-018. Заказы COUNTER освобождаются от дополнительных сборов.

BR-SERVICE-019. Настройки дополнительных сборов ресторана не должны влиять на стоимость заказов COUNTER.

BR-SERVICE-020. В клиентском чеке заказа COUNTER не должны отображаться неприменимые дополнительные сборы.

BR-SERVICE-021. Итоговая стоимость COUNTER рассчитывается сервером на основании стоимости товаров и применённой скидки без дополнительных сборов.

# 12. Финансовая точность

## 12.1. Валюта

Для MVP используется кыргызский сом.

Система поддерживает суммы в сомах и тыйынах.

1 сом = 100 тыйынов.

## 12.2. Хранение

Рекомендуется хранить суммы целыми числами минимальных денежных единиц.

Например:

150 сом 50 тыйынов = 15 050 тыйынов.

Это исключает ошибки двоичной арифметики с плавающей точкой при денежных расчётах.

## 12.3. Бизнес-правила

**BR-CALC-001.** Денежные значения поддерживают точность до одного тыйына.

**BR-CALC-002.** Автоматическое округление счёта до целого сома не применяется.

**BR-CALC-003.** Финансовые вычисления выполняет сервер.

**BR-CALC-004.** Повторный расчёт одинаковых данных должен давать одинаковый результат.

**BR-CALC-005.** Сумма смешанного расчёта должна точно совпадать с итоговой стоимостью.

**BR-CALC-006.** Правила округления процентных начислений должны быть едиными для всех клиентов.

Каждый применимый процентный сбор отдельно округляется методом ROUND_HALF_UP до одного тыйына согласно §11.3 и BR-MENU-077. Процентные скидки в MVP не применяются.

# 13. Возвраты платежей

## 13.1. Основное правило

В MVP поддерживается полный возврат отдельного зарегистрированного платежа.

Частичные возвраты отдельного Payment не поддерживаются.

## 13.2. Права

Согласно согласованному решению, любой авторизованный кассир может выполнять допустимые возвраты.

Дополнительное подтверждение менеджера в обычном сценарии возврата не требуется.

Операция фиксирует фактического кассира.

## 13.3. UC-REFUND-001 — Полный возврат

1. Кассир открывает финансовую историю.
2. Выбирает платёж.
3. Инициирует возврат.
4. Указывает причину.
5. Проверяет и подтверждает фактическое выполнение возврата денег.
6. Local POS Server проверяет полномочия.
7. Проверяет исходную оплату.
8. Проверяет отсутствие предшествующего полного возврата или отмены.
9. Создаёт Refund.
10. Сохраняет операцию в SQLite.
11. Создаёт событие синхронизации.
12. Подтверждает регистрацию возврата.

Если исходный метод предполагает банковский возврат, фактическое перечисление денег выполняется вне Bashkar POS.

## 13.4. Смешанные оплаты и возвраты

При смешанном расчёте каждый Payment сохраняется отдельно.

Правило полного возврата применяется к конкретному Payment.

Например, в расчёте:

- CASH — 800 сом;
- QR — 1 200 сом.

Полный возврат Payment CASH составляет 800 сом.

Частичный возврат 300 сом из Payment CASH недоступен.

Возврат обеих составляющих возможен отдельными связанными операциями. Единое действие возврата всего Settlement может быть добавлено позже.

## 13.5. Бизнес-правила

**BR-REFUND-001.** Возврат связан с существующим Payment.

**BR-REFUND-002.** Сумма возврата равна полной действительной сумме выбранного Payment.

**BR-REFUND-003.** Частичный возврат отдельного Payment запрещён.

**BR-REFUND-004.** Нельзя повторно возвратить уже полностью возвращённый Payment.

**BR-REFUND-005.** Refund регистрируется отдельной финансовой записью.

**BR-REFUND-006.** Исходный Payment сохраняется.

**BR-REFUND-007.** Причина возврата обязательна.

**BR-REFUND-008.** Возврат требует активной кассовой смены.

**BR-REFUND-009.** Операция фиксирует фактического сотрудника.

**BR-REFUND-010.** Повтор команды с тем же `command_id` не создаёт повторный возврат.

**BR-REFUND-011.** Внутренняя регистрация Refund не является автоматическим подтверждением банковского возврата.

# 14. Возврат после закрытия смены

## 14.1. Принцип

Закрытие исходной смены не препятствует выполнению разрешённого возврата.

Возврат регистрируется в новой активной смене.

## 14.2. Пример

Смена №101:

- заказ полностью оплачен;
- Payment составляет 1 000 сом;
- посещение закрыто;
- смена завершена.

На следующий день открывается смена №102.

Гость обращается за возвратом.

Кассир оформляет Refund на 1 000 сом.

Новая запись содержит:

- ID смены №102;
- ссылку на исходный Payment из №101;
- причину возврата;
- ID кассира.

Первоначальный отчёт смены №101 сохраняет историю зарегистрированной тогда оплаты.

Возврат отображается отдельно в смене №102.

## 14.3. Бизнес-правила

**BR-REFUND-012.** Возврат после закрытия исходной смены разрешён.

**BR-REFUND-013.** Возврат выполняется только при наличии текущей активной смены.

**BR-REFUND-014.** Исходная смена не открывается повторно.

**BR-REFUND-015.** Старый отчёт не должен бесследно перезаписываться.

**BR-REFUND-016.** Refund сохраняет связь с исходным платежом.

**BR-REFUND-017.** Историческое посещение не открывается автоматически после возврата.

**BR-REFUND-018.** Отчёты должны отдельно учитывать зарегистрированные оплаты и последующие возвраты.

Важно: возврат денег не должен автоматически означать отмену блюд. Эти действия относятся к разным бизнес-процессам.

# 15. Исправление ошибочной регистрации

## 15.1. Назначение

Если сотрудник зарегистрировал неправильный метод оплаты или ошибочно указал полученную оплату, система должна позволять исправить учёт без удаления исходной записи.

## 15.2. Пример

Счёт составляет 1 500 сом.

Кассир ошибочно выбрал CASH, хотя гость оплатил банковской картой.

Правильное исправление:

1. Сотрудник выбирает ошибочный расчёт.
2. Указывает причину.
3. Сервер создаёт корректирующую операцию.
4. Исходные записи сохраняются.
5. Исправленный способ оплаты отражается новой финансовой записью.

При исправлении завершённого расчёта сервер должен контролировать весь Settlement, а не изменять отдельные составляющие бесконтрольно.

## 15.3. Бизнес-правила

**BR-REVERSAL-001.** Исходные финансовые записи не удаляются.

**BR-REVERSAL-002.** Исправление осуществляется отдельной корректирующей операцией.

**BR-REVERSAL-003.** Указывается обязательная причина.

**BR-REVERSAL-004.** Фиксируется сотрудник и время.

**BR-REVERSAL-005.** Повторное исправление одного и того же действительного результата не должно создавать дубли.

**BR-REVERSAL-006.** История должна показывать исходный результат и внесённое исправление.

**BR-REVERSAL-007.** Исправление после закрытия смены не изменяет бесследно её первоначальный отчёт.

Правила проведения замещающего полного расчёта по уже закрытому заказу и необходимое разрешение сотрудника требуется детализировать до реализации.

# 16. Связь с кассовыми сменами

## 16.1. Основной принцип

Каждая регистрация оплаты, возврат и корректировка связываются с кассовой сменой фактического выполнения.

## 16.2. Влияние новых заказов COUNTER

Обычное закрытие смены требует:

- отсутствия активных посещений;
- отсутствия незавершённых заказов COUNTER;
- отсутствия незавершённых критических финансовых операций.

## 16.3. Состав финансовой отчётности

Отчёт смены должен учитывать отдельно:

- количество оплаченных заказов;
- зарегистрированные оплаты CASH;
- зарегистрированные оплаты CARD_MANUAL;
- зарегистрированные оплаты QR_TRANSFER_MANUAL;
- итог зарегистрированных оплат;
- возвраты;
- корректировки, влияющие на показатели.

Смешанная оплата считается одним оплаченным заказом, но её финансовые составляющие отражаются в соответствующих методах.

Сумма зарегистрированных оплат не должна автоматически обозначаться как фактические деньги в кассе или подтверждённое поступление на банковский счёт.

## 16.4. Бизнес-правила

**BR-PAY-SHIFT-001.** Регистрация нового полного расчёта требует открытой смены.

**BR-PAY-SHIFT-002.** Каждая операция фиксирует ID смены.

**BR-PAY-SHIFT-003.** Незавершённый COUNTER-заказ блокирует обычное закрытие смены.

**BR-PAY-SHIFT-004.** Финансовые операции, принятые до закрытия смены, учитываются в её отчёте.

**BR-PAY-SHIFT-005.** Закрытая смена не принимает новые обычные платежи задним числом.

**BR-PAY-SHIFT-006.** Возвраты после закрытия исходной смены фиксируются в текущей смене.

**BR-PAY-SHIFT-007.** Отсутствие начального остатка наличных не препятствует регистрации платежей.

**BR-PAY-SHIFT-008.** Отчёт не должен показывать рассчитанное кассовое расхождение, если физическая сверка кассы не выполнялась.

# 17. Права сотрудников

## 17.1. Регистрация оплаты

Разрешить регистрацию оплаты:

- кассиру;
- менеджеру;
- официанту с соответствующим разрешением.

Официант без необходимого разрешения не может проводить расчёт.

## 17.2. Доступ к заказам

Для заказов TABLE продолжают действовать режимы доступа STRICT и SHARED.

Право регистрации оплаты не должно автоматически предоставлять право просмотра всех чужих заказов.

Для заказов COUNTER доступ определяется отдельными разрешениями на кассовые операции.

## 17.3. Возвраты

В MVP любой авторизованный кассир может выполнить допустимый возврат.

Права менеджера и владельца определяются отдельно в AUTH-001.

## 17.4. Бизнес-правила

**BR-PAY-AUTH-001.** Сервер проверяет разрешение на проведение оплаты.

**BR-PAY-AUTH-002.** Сотрудник без разрешения получает отказ.

**BR-PAY-AUTH-003.** Официант может оплатить доступный ему заказ при наличии соответствующего права.

**BR-PAY-AUTH-004.** Возврат доступен авторизованному кассиру.

**BR-PAY-AUTH-005.** ID сотрудника определяется из авторизованной сессии.

**BR-PAY-AUTH-006.** Клиент не может самостоятельно назначить другого сотрудника исполнителем.

**BR-PAY-AUTH-007.** Исправления финансовых записей должны иметь отдельные правила полномочий.

# 18. Защита от повторных и конкурентных операций

## 18.1. Идемпотентность

Каждое завершение оплаты должно содержать уникальный `command_id`.

Повтор одной команды не должен создавать дополнительный расчёт.

## 18.2. Потеря ответа

Если сервер сохранил оплату, но клиент не получил подтверждение из-за потери связи, операция может иметь неопределённый результат для клиента.

После восстановления связи клиент должен запросить результат исходной команды.

Нельзя автоматически создавать новую команду с другим идентификатором.

## 18.3. Одновременное завершение оплаты

Пример:

Кассир и уполномоченный официант одновременно пытаются оплатить один заказ.

Сервер должен гарантировать, что только один действительный Settlement будет создан.

Второму сотруднику возвращается актуальный статус заказа.

## 18.4. Оплата одновременно с дозаказом

Возможны два порядка:

**Сначала принят дозаказ.**

Оплата должна учитывать обновлённую стоимость.

**Сначала завершён расчёт.**

Новый пакет не должен бесконтрольно изменять сумму уже проведённого полного расчёта.

Для этого требуется согласованная серверная проверка состояния заказа и его версии.

После полной оплаты TABLE посещение закрывается автоматически, и новые пакеты в него не принимаются согласно BR-PAY-CLOSE-006.

## 18.5. Бизнес-правила

**BR-CONCURRENT-PAY-001.** Проверка заказа и сохранение полного расчёта выполняются атомарно.

**BR-CONCURRENT-PAY-002.** Нельзя зарегистрировать два действительных полных расчёта одного заказа обычными командами.

**BR-CONCURRENT-PAY-003.** Повтор одного `command_id` возвращает ранее сохранённый результат.

**BR-CONCURRENT-PAY-004.** Повтор идентификатора команды с другим содержимым вызывает конфликт.

**BR-CONCURRENT-PAY-005.** Если сумма изменилась до подтверждения оплаты, сервер возвращает актуальное значение и требует нового подтверждения.

**BR-CONCURRENT-PAY-006.** Клиент не должен молча оплачивать изменившийся счёт.

**BR-CONCURRENT-PAY-007.** Смешанная оплата сохраняется целиком либо не сохраняется вовсе.

**BR-CONCURRENT-PAY-008.** Ошибка одного платежного запроса не должна повреждать ранее сохранённые финансовые записи.

# 19. Работа без интернета

## 19.1. Основной принцип

Bashkar POS должен продолжать работать при отсутствии внешнего интернета.

Локальные операции выполняются через Local POS Server и SQLite.

## 19.2. При отсутствии интернета доступны

- завершение расчёта наличными;
- ручная регистрация внешней оплаты картой;
- ручная регистрация QR-перевода при подтверждённом сотрудником результате внешней операции;
- смешанный расчёт;
- вычисление итоговой стоимости;
- сохранение финансовой истории;
- оформление разрешённых возвратов;
- создание заданий клиентской печати;
- локальная печать чеков.

Само выполнение банковской или QR-транзакции зависит от внешней платёжной инфраструктуры, а не от автономности Bashkar POS.

## 19.3. После восстановления интернета

Sync Worker передаёт накопленные события в облако.

Повторная передача не должна создавать вторые финансовые операции.

## 19.4. Бизнес-правила

**BR-PAY-OFFLINE-001.** Сохранение расчёта не требует подключения к Supabase.

**BR-PAY-OFFLINE-002.** Операции сохраняются в SQLite.

**BR-PAY-OFFLINE-003.** Клиент не показывает успешную оплату до подтверждения сервера.

**BR-PAY-OFFLINE-004.** Неизвестный результат должен проверяться по исходному `command_id`.

**BR-PAY-OFFLINE-005.** Ошибки синхронизации не блокируют локальные расчёты.

**BR-PAY-OFFLINE-006.** Клиентская печать не зависит от доступности облачной инфраструктуры.

# 20. Ошибки и нестандартные ситуации

| Ситуация                                | Ожидаемое поведение                               |
| --------------------------------------- | ------------------------------------------------- |
| Нет активной смены                      | Завершение оплаты запрещено                       |
| Нет прав у сотрудника                   | Сервер отклоняет операцию                         |
| Заказ уже оплачен                       | Повторный обычный расчёт запрещён                 |
| Изменилась сумма заказа                 | Требуется подтверждение нового итога              |
| Ошибка SQLite                           | Оплата не подтверждается                          |
| Потеря Wi-Fi при отправке               | Результат UNKNOWN до проверки                     |
| Повтор того же запроса                  | Возвращается прежний результат                    |
| Отказ клиентского принтера              | Оплата сохраняется, ошибка видна                  |
| Нет интернета                           | Локальные операции продолжаются                   |
| Одновременные оплаты                    | Только один действительный результат              |
| Неверное распределение смешанной оплаты | Сервер отклоняет расчёт                           |
| Возврат уже возвращённого платежа       | Операция запрещена                                |
| Закрыта исходная смена                  | Возврат возможен в текущей смене                  |
| Незавершённый COUNTER-заказ             | Закрытие смены блокируется                        |
| Повреждение или недоступность SQLite    | Финансовая команда не подтверждается как успешная |

# 21. Критерии приёмки

## 21.1. Основной расчёт

**PAY-AT-001:** Кассир может оплатить заказ наличными.

**PAY-AT-002:** Кассир может вручную зарегистрировать оплату картой.

**PAY-AT-003:** Кассир может вручную зарегистрировать QR-перевод.

**PAY-AT-004:** При обычной оплате кассир не вводит сумму.

**PAY-AT-005:** Итог рассчитывает Local POS Server.

**PAY-AT-006:** Стандартный расчёт выполняется на полную сумму заказа.

**PAY-AT-007:** Частичная оплата не доступна в MVP.

**PAY-AT-008:** После успешного расчёта финансовое состояние становится PAID.

## 21.2. Смешанная оплата

**PAY-AT-009:** Смешанная оплата доступна через дополнительную кнопку.

**PAY-AT-010:** Сумма второго метода рассчитывается автоматически.

**PAY-AT-011:** Сумма составляющих точно соответствует итогу заказа.

**PAY-AT-012:** Смешанная оплата сохраняется атомарно.

**PAY-AT-013:** Смешанный расчёт учитывается как один оплаченный заказ.

**PAY-AT-014:** Отчёт корректно распределяет сумму между методами.

## 21.3. Клиентская печать

**PAY-AT-015:** До успешной полной оплаты клиентский чек не создаётся.

**PAY-AT-016:** После успешной оплаты автоматически создаётся задание печати клиентского чека.

**PAY-AT-017:** Кассир не нажимает отдельную кнопку печати в обычном процессе.

**PAY-AT-018:** Клиентский чек содержит правильную итоговую стоимость.

**PAY-AT-019:** Клиентский чек отображает использованные методы оплаты.

**PAY-AT-020:** Ошибка печати не отменяет сохранённую оплату.

**PAY-AT-021:** Повторная печать не создаёт нового платежа.

**PAY-AT-022:** Предчек отсутствует.

## 21.4. Заказы COUNTER

**PAY-AT-023:** Заказ COUNTER создаётся без стола.

**PAY-AT-024:** Заказ COUNTER не создаёт Table Session.

**PAY-AT-025:** При создании подтверждённого пакета COUNTER формируется необходимое кухонное задание.

**PAY-AT-026:** Заказ COUNTER можно полностью оплатить стандартным методом.

**PAY-AT-027:** Заказ COUNTER можно оплатить смешанным методом.

**PAY-AT-028:** Незавершённый COUNTER-заказ блокирует обычное закрытие смены.

## 21.5. Возвраты и исправления

**PAY-AT-029:** Авторизованный кассир может оформить полный возврат отдельного платежа.

**PAY-AT-030:** Частичный возврат отдельного платежа запрещён.

**PAY-AT-031:** Нельзя дважды возвратить один платёж.

**PAY-AT-032:** Исходная запись сохраняется.

**PAY-AT-033:** Возврат из завершённой смены регистрируется в текущей смене.

**PAY-AT-034:** Ошибочная регистрация исправляется отдельной записью.

## 21.6. Надёжность

**PAY-AT-035:** Оплата сохраняется без интернета.

**PAY-AT-036:** Повтор команды не создаёт дубль.

**PAY-AT-037:** Два сотрудника не могут создать два действительных полных расчёта одного заказа.

**PAY-AT-038:** При изменении итоговой стоимости требуется подтверждение новой суммы.

**PAY-AT-039:** Перезапуск POS Desktop не уничтожает платежи.

**PAY-AT-040:** После перезапуска Local POS Server финансовая история восстанавливается.

**PAY-AT-041:** После восстановления интернета события синхронизируются без повторного создания операций.

## 21.7. Финансовая точность

**PAY-AT-042:** Поддерживаются сомы и тыйыны.

**PAY-AT-043:** Нет обязательного округления итогового счёта до целого сома.

**PAY-AT-044:** Сервер обеспечивает детерминированный расчёт суммы.

**PAY-AT-045:** Итоги кассовой смены используют фактические зарегистрированные методы оплаты.

# 22. Границы MVP

## 22.1. Входит в MVP

- Полная оплата в конце обслуживания.
- Наличные.
- Карта с ручной регистрацией.
- QR-перевод с ручной регистрацией.
- Завершение оплаты без ввода суммы.
- Смешанная оплата как дополнительный сценарий.
- Одна логическая операция полного расчёта.
- Сохранение отдельных составляющих смешанной оплаты.
- Расчёт стоимости сервером.
- Ручная скидка на заказ.
- Настраиваемый процент обслуживания.
- Поддержка сомов и тыйынов.
- Кухонные чеки.
- Автоматическая печать клиентских чеков.
- Возврат полной суммы отдельного платежа.
- Исправление ошибочных финансовых записей.
- Возврат после закрытия исходной смены.
- Заказы COUNTER.
- Работа без интернета.
- История финансовых операций.
- Защита от повторных запросов.
- Синхронизация с Supabase.

## 22.2. Не входит в MVP

- Частичная оплата общего счёта.
- Основной интерфейс разделения счета между гостями.
- Предчеки.
- Ручной ввод суммы обычной оплаты.
- Автоматический расчёт сдачи.
- Автоматические банковские платежи.
- Проверка переводов через банковский API.
- Автоматические банковские возвраты.
- Частичный возврат отдельного платежа.
- Депозиты и авансы.
- Расширенные схемы кредитования гостей.
- Физическая сверка кассы.
- Учёт начальных наличных.
- Автоматическая фискализация средствами Bashkar POS.

## 22.3. Post-MVP

Архитектурно предусмотреть возможность:

- частичных оплат;
- расширенного разделения счетов;
- банковских интеграций;
- онлайн-платежей;
- автоматических возвратов;
- частичных возвратов;
- депозитов;
- фискальных интеграций;
- расширенных скидок;
- гибких финансовых отчётов.

Эти функции не должны усложнять рабочий интерфейс первой версии.
