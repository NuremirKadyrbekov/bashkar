## Облако

`supabase/migrations/20261021000100_activation_registry.sql`: организации с одним облачным Owner, филиалы, реестр серверов, аудит регистрации. RLS разрешает чтение только владельцу. Anon не читает, authenticated не создаёт/меняет владельцев, филиалы или реестр. Первоначальная организация/филиал создаются административной процедурой, а не самоназначением из Desktop.

`register_branch_server` доступна только service_role. Edge Function сначала проверяет bearer через Auth `/user` и подтверждение email, затем доказательство владения Ed25519 ключом устройства. Owner из JSON не принимается. Сервисный ключ используется только внутри облака/административных инструментов, не в поставке POS.

Регистрация блокирует строки филиала/организации и атомарно фиксирует сервер с обязательным аудитом. UNIQUE запрещает два активных сервера филиала и повторное использование instance/device для другого активного филиала. Повтор с прежним ID/владельцем/филиалом/instance/device/nonce возвращает прежние claims. Чужой payload — конфликт. После истечения 15 минут тот же запрос может получить обновлённую квитанцию без новой регистрации или аудита. Это окно первичного потребления, не срок работы офлайн-филиала. Сетевой ответ теряется безопасно: прежний запрос восстанавливает регистрацию.

Edge подписывает только результат состоявшегося commit. Приватный ключ импортируется до обращения к RPC: отсутствие секрета не резервирует филиал. Нет ручки замены/автоматического освобождения занятого филиала. Rotation/revoke/restore и эксплуатационная процедура физического вывода старого сервера ещё требуют реализации и Windows-приёмки; облачный revoke не обещает остановить офлайн-узел.

Наблюдалось опережение часов облачной БД примерно на 200 мс. После проверки подписи/instance/device/nonce локальный потребитель может асинхронно дождаться `issuedAt` (не более 5 секунд), затем строго проверяет `issuedAt ≤ now < expiresAt` до и внутри транзакции. Это не допуск просроченной/будущей квитанции и не общая политика D12. Заметное расхождение — `ACTIVATION_CLOCK_MISMATCH`, без автоматической коррекции часов.

## Локальный сервер и Desktop

Локальная схема **3**, отдельная миграция `003-activation-pending`: неизменяемый запрос регистрации сохраняется в SQLite с FULL commit до сети. Токены облака и пароли там не сохраняются. Миграции 1/2 не переписаны; существующая схема 2 требует явного `migrate-db` при остановленном сервере и без OPEN-смены.

`main.ts` использует публичные URL/publishable key/authority, встроенные в `cloud-config.ts`. Authority нельзя заменить HTTP-запросом/квитанцией. Копия открытой конфигурации находится в `config/`; приватный ключ только в игнорируемом `.env.cloud-signing.local` (0600) и разрешённых Supabase Secrets. Этот файл нужно сохранить как секрет и не добавлять в поставку/репозиторий. `prepare-signing-key.cjs` не перезаписывает существующий ключ.

Облачный пароль отправляется через локальный native API и HTTPS в Auth, не сохраняется. Access token остаётся только в памяти локального сервера максимум на десятиминутный flow. Renderer получает только узкий flow ID и список доступных филиалов. После перезапуска нужен повторный облачный вход; registration ID/nonce сохраняются. При неопределённом ответе повторяется прежняя регистрация; выбор другого филиала блокируется. После local commit повтор не сбрасывает пароль Owner.

Локальная привязка/Owner/audit/outbox коммитятся атомарно. READY включается только после проверки подписанной привязки и ключа устройства. При следующем старте проверка квитанции локальная, без облачного lease; обычный вход не обращается в Supabase.

macOS development: отдельный ключ устройства в login Keychain, привязанный к каталогу данных. Windows: CurrentUser DPAPI под SID LocalService `S-1-5-19`, файл шифротекста внутри защищённого каталога службы. Отсутствующий/недоступный ключ активированного сервера не создаётся заново; READY не включается. Копирование/потеря ключей, профиль службы, ACL и DPAPI на настоящей Windows пока НЕ проверены. macOS Keychain не заменяет Windows-испытания.

## Маршруты

- GET `/api/v1/activation/status`: `{configured,activated}`, без токенов/ключей.
- POST `/api/v1/activation/start`: `{email,password}` → `{flowId,branches}`.
- POST `/api/v1/activation/complete`: `{flowId,branchId,login,name,password}`; password — отдельный локальный пароль. Успех `{branchId,alreadyActivated}` после local commit.
- Все маршруты наследуют native loopback Host/Origin/JSON ограничения; браузерный облачный кабинет этим не создаётся.

## Ручная проверка macOS

Один раз, в корне проекта:

```sh
pnpm run desktop:local:init
pnpm run desktop:local
```

Данные сохраняются в `.local/branch`, encrypted Desktop session — `.local/desktop`; оба игнорируются Git. Этот launcher использует порт 3213 (`BASHKAR_LOCAL_PORT`), чтобы не занимать порт существующего сервера 3210. Инициализация только явная, повторный init не стирает данные. Нет автоматического reset/замены БД. UI постоянно помечен тестовым; облачная активация при этом настоящая и занимает выбранный филиал. Использовать «Тестовый филиал», не организацию ресторана.

Ввести email/облачный пароль созданного Owner, выбрать филиал и задать отдельные локальные реквизиты. Затем войти локально. Закрытие Electron оставляет сервер работающим; `desktop:local:window` открывает окно снова. Ctrl+C в терминале останавливает этот локальный сервер. После успешной активации проверить перезапуск и локальный вход с отключённым интернетом. Не активировать тот же филиал на другом компьютере для обхода ошибки: замена узла — отдельная процедура.

### Отдельный стенд MANGO

По запросу пользователя подготовлен отдельный профиль `mango` для организации MANGO и филиала «MANGO — тестовый». Учётная запись Owner предварительно создана и подтверждена в Supabase; её пароль в проекте не сохраняется. Для provisioning используется собственный игнорируемый `.env.cloud-bootstrap.mango.local`, старый `.env.cloud-bootstrap.local` не заменяется.

`pnpm run desktop:mango:init` — только один раз для новой установки. `pnpm run desktop:mango` запускает сервер на порту 3214 и Electron с отметкой MANGO. `pnpm run desktop:mango:window` открывает окно повторно, когда сервер уже работает. Данные — `.local/mango/branch`, protected Desktop session — `.local/mango/desktop`. Профиль по умолчанию продолжает использовать прежние `.local/branch`, `.local/desktop`, порт 3213. Чужие каталоги, регистрации и ключи не сбрасываются.
