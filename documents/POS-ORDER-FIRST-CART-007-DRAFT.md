# POS-ORDER-FIRST-CART-007 — корзина активного заказа и быстрая оплата

Дата: 25.10.2026. Статус: **Согласовано пользователем, реализовано 25.10.2026.**

Контракт поставки: [API-CHECKOUT-015](API-CHECKOUT-015.md). Проверки, файлы и границы: [отчёт реализации](POS-ORDER-FIRST-CART-007-IMPLEMENTATION.md).

Область: самостоятельный вид Кассы **«Заказы сначала»**. Вид «Столы сначала» и его полноэкранная быстрая продажа сохраняют свои сценарии. Общие компоненты адаптировать параметрами контекста, а не менять оба вида незаметно.

Основа: [API-CASH-WORKSPACE-014](API-CASH-WORKSPACE-014.md), [POS-CASH-UX-004](POS-CASH-UX-004-DRAFT.md), [UI-MESSAGES-001](UI-MESSAGES-001.md). Этот этап меняет ранее зафиксированную неизменяемость назначения стола/ответственного и добавляет атомарный checkout с дозаказом; это серверная работа, не только оформление.

## 1. Что есть в коде и чего ещё нет

- Выбор активного TABLE/COUNTER уже открывает его в правой корзине. Есть принятые пакеты, независимые отметки выдачи, отдельный защищённый черновик дозаказа и серверные суммы.
- Верх корзины сейчас содержит «Текущий заказ», большие режимы и локальную кнопку нового заказа; ниже есть назначения, финансовые действия и дополнительные строки сумм.
- `TableService.assign` разрешает только первое назначение стола контексту с `table_id=NULL`. Перенос уже назначенного посещения запрещён сервисом и триггером истории. Ответственный также защищён от изменения.
- `FinanceService.prepareSettlement/settle` оплачивает принятые позиции. COUNTER `CHECKOUT` существует только для нового COUNTER, а не для существующего заказа или TABLE с новым пакетом. Последовательно отправлять пакет и оплату двумя обычными запросами без нового протокола недостаточно: между ними возможен частичный результат.

## 2. Верх корзины

### Выбран активный заказ

- Вместо «Текущий заказ» показать крупно **«Заказ №…»**, используя общий серверный номер смены, без UUID.
- Сразу ниже — две компактные явно интерактивные кнопки с иконками и стрелкой/обозначением изменения:
  - **«Стол С10 ▾»** либо **«Выбрать стол ▾»** для TABLE без стола;
  - **«Ответственный: Алина ▾»** либо корректное состояние без назначенного официанта по серверным правилам.
- Сохранить авторство отдельной небольшой подписью **«Открыл: Марат»**. Автор открытия — исторический факт; его нельзя переписывать при смене ответственного. Кнопка сотрудника меняет именно текущего ответственного, а не создателя заказа/посещения.
- У COUNTER показать читаемую метку **«На вынос»** и автора создания по реальному первому принятому пакету. Кнопки стола/ответственного посещения не показывать; тип принятого заказа здесь не преобразовывается.
- При отсутствии прав показывать фактические данные без ложного интерактивного состояния; доступные действия имеют фокус и область нажатия ≥44×44 px.
- Убрать большие переключатели **«Зал / На вынос»** из корзины. Тип принятого заказа остаётся неизменяемым, но визуально читаемым.

### Новый черновик

- Пока сервер не принял первый пакет, заголовок **«Новый заказ»**, без вымышленного/заранее выданного номера. Номер появляется после серверного приёма, как сейчас.
- Выбранный тип показывать компактной меткой. Для TABLE назначения расположены в верхних кнопках; стол остаётся необязательным. Для COUNTER назначений нет.

## 3. «Новый заказ» в блоке активных

- Удалить кнопку из правой корзины и расположить **«+ Новый заказ ▾»** в правом углу заголовка блока «Активные заказы».
- Сделать заметный мягкий жёлтый фон, тёмную подпись, плюс и достаточный размер для сенсора. На 1366×768 кнопка не вытесняет заголовок и счётчик за границы.
- Нажатие предлагает компактный выбор **«Зал» / «На вынос»**, заменяющий убранные большие режимы корзины. Выбор создаёт только локальный черновик выбранного типа, а не серверный пустой заказ.
- При переходе из существующего заказа его неотправленный пакет сохраняется за своим контекстом. При повторном выборе карточки восстанавливается тот же дозаказ; другой новый заказ его не перезаписывает.

## 4. Изменение стола и ответственного

### Стол

- Верхняя кнопка открывает компактные карточки столов с табами зон, текущим выбором и видимым состоянием доступности.
- Разрешить перенос OPEN посещения на другой **свободный активный** стол того же филиала при открытой соответствующей смене. Нынешний стол доступен как текущий выбор, но повторный выбор не создаёт перенос.
- Назначение/перенос — отдельная серверная команда с commandId, ожидаемой ревизией посещения, проверкой прав и атомарным аудитом. Сохраняются ID заказа/контекста, номер заказа, время открытия, создатель, ответственный, пакеты, скидка и финансовый снимок сборов.
- После подтверждения прежний стол становится FREE, новый — OCCUPIED. Конкурентное занятие цели/изменение ревизии отклоняет перенос целиком; локального «успешного переноса» до ответа нет. Объединение с заказом занятого стола и перенос между филиалами не входят в этап.
- TABLE без стола можно назначить на свободный стол. Снятие уже назначенного стола обратно в «Без стола» не добавлять без отдельного решения.

### Ответственный

- Верхняя кнопка открывает карточки доступных действующих официантов и действие применения выбора.
- На сервере добавить отдельную команду смены ответственного OPEN посещения, с commandId/CAS/проверкой прав. Сохранять прежнего/нового ответственного, выполнившего действие сотрудника и серверное время.
- Не менять `opened_by`, имя автора открытия, авторов старых пакетов и исторические финансовые/печатные снимки. Отсутствие ответственного разрешается только там, где это допускают действующие правила; не обходить обязательное назначение при наличии официантов.
- Предлагаемые отдельные права: `table.move` и `table.responsible.change`, по умолчанию OWNER/MANAGER/CASHIER; WAITER без них. Ролевое право **не заменяет** объектный доступ STRICT/SHARED и не даёт видеть чужой заказ автоматически.
- После смены ответственного сервер пересчитывает доступ. Если сотрудник в STRICT потерял доступ, выбранный заказ убирается из его корзины/списка; новые детали не раскрываются. Его личный неотправленный черновик сохраняется защищённо и не передаётся другому сотруднику автоматически.
- Если есть локальный дозаказ, в диалоге назначения пояснить, что он остаётся личным черновиком. Не отправлять его автоматически ради смены ответственного.

Сохранять назначения отдельными событиями истории. Старые кухонные задания не перепечатывать автоматически; последующие пакеты используют актуальные стол/ответственного. Для этих изменений потребуется новая миграция/расширение серверных правил: старые миграции и закрытые исторические записи не менять.

## 5. Пространство пакетов и нижняя шторка

- Убрать текущий низкий лимит высоты истории. Когда дозаказ пуст, **принятые пакеты занимают всю доступную высоту** между верхом корзины и закреплёнными итогами/оплатой. История имеет свою вертикальную прокрутку.
- Сохранить раскрытие/сворачивание пакетов, номера, время, автора, позиции/варианты/комментарии, отмены и независимые отметки выдачи. «Принят сервером» не означает «распечатан/выдан».
- Пока новый пакет пуст, его большая пустая область/шторка скрыта. Добавление первого блюда открывает **нижнюю шторку «Новый пакет» внутри корзины**, без перехода на страницу и без модального перекрытия каталога.
- В шторке — редактируемые новые строки, количество, варианты, комментарии и удаления по существующим правилам. Неизвестный товар сохраняет прежний режим без кухни/комментария.
- История и шторка делят доступную высоту: в длинном дозаказе прокручиваются строки шторки, а итоги/оплата и действие отправки остаются доступны. На целевых разрешениях история не вытесняется полностью, страница не получает горизонтальный скролл.
- Под строками шторки, **перед скидкой**, расположить основную кнопку **«Отправить пакет»**. Она относится только к текущему новому пакету, а не к принятым позициям.
- После успешной отправки новый пакет появляется в истории, черновик очищается, шторка скрывается. При удалении всех неподтверждённых строк шторка также скрывается. При ошибке/неизвестном результате состав сохраняется.
- Верхние и локальные действия очистки/неизвестного товара сохраняются, но очищают только новый черновик. Принятые пакеты локально не удаляются.

## 6. Отправка пакета без подтверждающего модального окна

- «Отправить пакет» сразу запускает действующий серверный prepare → проверку расчёта → submit, без обычного окна просмотра/подтверждения пакета.
- Сохранить проверку показанного расчёта, версии меню, ревизии заказа/посещения, скидок/сборов и прав. Если условия изменились — обновить отображаемую сумму, показать предупреждение и потребовать **нового явного нажатия**; не отправлять изменённый состав/цену автоматически.
- Во время запроса заблокировать повтор отправки/оплату/переключение контекста; не терять исходный защищённый черновик. Неизвестный результат восстанавливать той же командой, а не новым пакетом.
- Принятый пакет получает очередной номер пакета в том же заказе. Для нового заказа первое отправление создаёт серверный заказ с общим номером смены. Кухонные задания включают только предусмотренные сервером позиции.
- Подтверждение приёма — общий короткий success-toast; добавление товаров остаётся без success-toast.

## 7. Нижний блок сумм

Удалить из корзины:

- нижние дубли кнопок стола и официанта;
- «Действия с заказом» и «К расчёту»;
- строки «Принято сервером» и «Сумма товаров»;
- прежнюю общую нижнюю кнопку «Отправить пакет» — отправка теперь находится в шторке.

Оставить закреплённый нижний блок в таком порядке:

1. **«Скидка ›»** — доступная по правам кнопка с текущим значением, существующий диалог суммы с цифровой клавиатурой.
2. **«Новый пакет — … сом»** — непосредственно над «Итого», с таким же размером/весом текста. Это серверная сумма позиций именно собираемого пакета **до общей скидки и сборов заказа**; при пустом пакете показывать 0 сом.
3. **«Итого — … сом»** — полная предполагаемая сумма всего заказа: действующие принятые позиции плюс новый пакет, минус скидка и с применимыми серверными сборами. Это не сумма только последней отправки.
4. Три кнопки оплаты из §8.

Скидка относится ко всему заказу, не списывается повторно с каждого пакета. Политика существующего снимка сборов TABLE сохраняется при переносе стола. Хотя отдельная строка сборов в упрощённом блоке не нужна, итог не должен их терять; состав расчёта доступен в деталях продажи/расчёта.

## 8. Три быстрых способа оплаты

Вместо прежней нижней кнопки разместить в один ряд равнозначные сенсорные действия:

| Кнопка | Поведение |
|---|---|
| **Наличные** | Без дополнительного стандартного окна оплаты: полный расчёт методом CASH по актуальному серверному итогу |
| **Перевод** | Полный расчёт методом QR_TRANSFER_MANUAL; нажатие сотрудника подтверждает уже полученный внешний перевод |
| **Смешанная** | Компактный диалог/нижняя панель с двумя различными методами, цифровой клавиатурой для первой суммы и автоматически вычисленным остатком; затем одно «Оплатить» |

**Смешанную оплату нельзя корректно провести одним нажатием без ввода долей.** По умолчанию предложить наличные + перевод; выбирать только существующие разрешённые методы системы. Не добавлять отдельную четвёртую кнопку карты в этот интерфейс и не удалять серверную поддержку CARD_MANUAL из других сценариев.

- Оплачивается **весь заказ целиком**, включая ещё не отправленный пакет, если он есть. Нажатие на неизменившийся показанный итог запускает расчёт без дополнительного общего подтверждения для CASH/TRANSFER.
- Если нового пакета нет — рассчитать уже принятый заказ. Если он есть — принять его и рассчитать полный заказ **одной атомарной серверной операцией** (§9). Пустой новый заказ оплатить нельзя.
- «Оплачено» показывать только после подтверждения Local POS Server. Кнопка «Перевод» регистрирует ручное подтверждение поступления, а не выполняет банковский перевод и не доказывает поступление от банка автоматически.
- Смешанная оплата — два разных метода; суммы положительны и в точности дают итог в целых тыйынах. Итог/методы проверяются сервером.
- При нулевом итоге денежные способы не создают фиктивные Payment. Вместо группы денежных кнопок показать **«Завершить без оплаты»** через существующий ZERO_SETTLED.
- После подтверждённого расчёта очистить только соответствующий принятый черновик, обновить активные/последние продажи и открыть новый локальный контекст. TABLE освобождает назначенный стол, как сейчас; COUNTER финансово завершается, а действующая видимость в отдельном рабочем списке до ручного скрытия не означает выдачу.
- Отметки выдачи не блокируют расчёт. Наличие кухонного задания/SENT не подтверждает физическую печать или выдачу.
- При изменившемся итоге/меню/ревизии до commit оплату остановить, показать новый расчёт и потребовать повторного явного действия. При тайм-ауте сохранить исходный payment/checkout commandId и запретить новую оплату до проверки результата. Возврат денег — отдельная существующая процедура, а не локальная отмена отметки «Оплачено».

## 9. Серверная поставка

1. Расширить назначения посещения из §4: права, CAS, события, immutable openedBy и корректный объектный доступ после смены ответственного.
2. Добавить общий prepare/commit checkout для TABLE/COUNTER, нового/существующего заказа и необязательного нового пакета. Переиспользовать существующие priceLine/totals, финансовые проверки, CommandBus, Payment/Settlement и генерацию печати.
3. Одна транзакция подтверждённого checkout при необходимости создаёт контекст/заказ, принимает один пакет, рассчитывает полную сумму, записывает Settlement/Payments, закрывает заказ/посещение и ставит соответствующие кухонные/клиентские задания в очередь. Физическая печать находится вне транзакции.
4. При ошибке откатываются все новые бизнес-факты. При неизвестном ответе повтор с тем же commandId возвращает исходный результат: не добавляет второй пакет/номер/оплату/задание печати.
5. Проверять текущую смену, права приёма пакета и расчёта, право скидки/произвольной цены при необходимости, ревизии заказа/посещения/черновика, подтверждённый ценовой hash и ограничения суммы/методов. Расчёт без нового пакета не требует права создавать новые позиции сверх действующей модели.
6. Сохранить общий номер TABLE/COUNTER на смену. Новый checkout выдаёт номер один раз; checkout существующего заказа не меняет его номер.
7. Расширить native frozen/pending/retry на атомарную checkout-команду. Не подменять её двумя независимыми запросами «отправить → оплатить» с неучтённым промежуточным исходом.
8. Миграции — только следующие номера, с сохранением исторических данных/контрольных сумм прежних миграций и запретом обновления рабочей БД с OPEN сменой.

## 10. Финансовые действия и совместимость

Удаление кнопки «Действия с заказом» не отменяет серверные возможности коррекции/отмены. В раскрытых принятых строках предусмотреть компактное **«⋯»** для разрешённых коррекций; в заголовке списка пакетов — компактное меню с полной отменой по правам. Сохранить существующие подтверждение причины, серверный prepare/commit и кухонные отмены. Это не возвращает большую кнопку в нижний блок.

Сохраняются варианты/размеры, комментарии, неизвестный товар, фильтры каталога, раздельные защищённые дозаказы, WebSocket, offline-работа через Local POS Server и новый стандарт ошибок PIN. Повторная печать не должна автоматически запускаться при восстановлении неизвестного расчёта.

## 11. Приёмка

- Выбор активного заказа меняет заголовок на номер; верхние назначения выглядят как кнопки и реально работают с сервером. «Открыл» остаётся неизменяемым, «Ответственный» меняется с аудитом и соблюдением STRICT/SHARED.
- Перенос на свободный стол освобождает прежний; конкуренция за цель/ревизии, смена ответственного и потеря доступа не дают частичных результатов/утечки деталей. Старые пакеты/квитанции не переписываются.
- Жёлтый новый заказ находится только в Header активных; сохраняет оба новых сценария и не теряет дозаказ выбранного заказа. Больших режимов в корзине нет.
- История занимает доступную высоту при пустом дозаказе; шторка открывается после первого добавления и скрывается после приёма/очистки. Длинные списки прокручиваются внутри; отправка/скидка/итоги/оплата доступны на 1366×768 и 1920×1080.
- Нет удалённых нижних кнопок/дублирующих строк. «Новый пакет» и «Итого» показывают разные правильные серверные суммы при скидках, сборах, вариантах, отменах и неизвестном товаре.
- Отправка пакета проходит без обычного подтверждающего окна, но не принимает автоматически изменившуюся цену.
- CASH/TRANSFER оплачивают полный заказ; MIXED требует корректных долей. Проверены новый TABLE, TABLE без стола, существующий TABLE, новый/существующий COUNTER, с дозаказом и без него, нулевой итог и ограниченные права.
- На каждой стадии ошибки checkout откатывают всё; потерянный ответ/перезапуск/повтор команды не дублируют пакет, номер, Payment или печать. Двойное нажатие/конкурентная отправка и оплата безопасны.
- Проверить регрессии вида «Столы сначала», его полноэкранной продажи, финансовых отмен/возвратов, закрытия смены и PIN. QA — изолированный профиль; аппаратная Windows/бумага/сенсор фиксируются отдельно.
