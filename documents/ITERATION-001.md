# ITERATION-001 — сервер, сотрудники, смены и меню

Дата: 21.10.2026. Основание: детальное ТЗ двух блоков из чата, подтверждение рекомендаций D03/D04 и остальных предложенных рекомендаций. Отдельно подтверждены числовые пределы, UI сотрудников и форма настройки сборов TABLE. Статусы ниже описывают факты реализации, не готовность всего MVP.

## Подтверждённые решения

- D03: UUID v4 команды уникален в пределах филиальной операционной базы, независимо от операции и сотрудника. Fingerprint SHA-256 канонических данных включает API v1, тип, автора и значимые поля. Другой payload/автор с тем же ID — конфликт. Повтор заново проверяет действующую сессию, актуальные права и область. Автоматической очистки журнала нет.
- Ввод повторного пароля не сохраняется. Для смены личного пароля в fingerprint используется медленный Argon2id proof, индивидуально salted UUID команды. Пароли, токены, временные пароли не включаются в audit/outbox/результат команды.
- Временный пароль возвращается только первым успешным ответом создания/сброса. Повтор возвращает `secretAlreadyIssued`; при потере секрета нужен отдельный сброс. После потери ответа на смену личного пароля результат проверяется новым входом: старые сессии отозваны.
- D04: одна операционная connection, короткие синхронные BEGIN IMMEDIATE; очередь бизнес-команд максимум 64. Security-транзакции выполняются на той же connection в одном event loop. Внутри нет hashing/network/printing. SQLite busy timeout — 5000 мс; переполнение/занятость дают ошибку и безопасный повтор, не бесконечное ожидание. SQL UNIQUE и CAS по revision сохраняются.
- D10: Supabase Owner, проверка владения филиалом на cloud backend; атомарный реестр одного активного узла; отдельная пара ключей устройства и подписанная квитанция instance/device/nonce. Owner задаёт отдельный локальный пароль. При замене офлайн-узла выбран управляемый физический вывод старого сервера из работы. Мгновенный удалённый отзыв офлайн-узла не обещается.
- После первого блока пользователь создал облачный проект, подтвердил UI настоящей активации, создал Owner и разрешил установку ключа подписи в Secrets. Облачные миграция/RLS/реестр/function развёрнуты. main подключает публичную authority и защищённый device provider, UI реализован; схема 3 хранит неизменяемый pending request. Rotation/revoke/restore и Windows DPAPI/ACL остаются отдельными непроверенными контурами. Обновление: CLOUD-ACTIVATION-001.md/PROGRESS.md имеют приоритет над прежними ограничениями ниже.
- D02: Desktop native main хранит токен через safeStorage; renderer получает узкий IPC без токена. Открытый/basic_text backend запрещён. Только loopback native HTTP, без cookies/CORS. Origin/Sec-Fetch-Site браузера и чужой Host отклоняются. Waiter/LAN/cookie/CSRF/HTTPS/WSS ждут D01/D02 своего контура.
- D15: `modules/auth/permissions.ts` — registry только текущей итерации. Ролевые запреты приоритетны над grant. OWNER не получает shift.open/close по умолчанию. Manager не меняет себя/Owner; индивидуальное делегирование требует собственного действующего права и Owner-набора. Создание сотрудника использует согласованный шаблон роли; это не расширяет индивидуальные grants самого Manager.
- D13: checksum исходной миграции 1 сохранён. Новая установка получает схему 2. Существующая схема 1 остаётся неизменной до отдельной migrate-db. Ожидающее обновление при OPEN-смене запрещено. Нет downgrade/автоматического restore. Доказанная процедура backup/restore реального филиала остаётся D11/D13.
- Подтверждены: цена и итог 0…999999999 тыйынов (9999999,99 сом); количество 1…9999 целых единиц. Ставка — целые сотые процента 0…10000; сумма ставок ≤10000. BigInt промежуточно, каждый сбор ROUND_HALF_UP отдельно.
- Общее подтверждение рекомендаций не подменяет отсутствующие финансовые процедуры D05/D08/D09, параметры RPO/RTO D11, правовую проверку D16 или hardware-приёмку. Исходные согласованные принципы сохраняются, будущие контуры не реализуются в этой итерации.

## Модули, данные, транзакции

**Storage/migrations.** Явная установка; маркер и проверка связи с БД; WAL/FULL/FK, quick_check/FK check, версии/checksums и write probe. Пропавшая/повреждённая БД не заменяется. Блокировка: отдельная SQLite OS lock + старый sentinel. Проверяется файловая идентичность/link count/sentinel, перед командой и перед записью результата. Это дополнительная проверка, не замена ACL и не защита от администратора, способного менять процесс/диск.

**Command bus.** Business + обязательный audit + локальные события/outbox + result одной транзакцией. Исключение откатывает всё. Успех после commit. FULL/IOERR/CORRUPT/NOTADB/READONLY переводят API в BLOCKED без подмены данных; busy/queue overflow допускают повтор.

**Activation.** Проверяется Ed25519 квитанция, создаются binding + локальный Owner + audit + outbox атомарно. Окно годности квитанции ограничивает первичное потребление, не работу активированного офлайн-филиала. Это проверяющий модуль, не готовая регистрация в реальном облаке. В shipped entrypoint нет тестового флага/ключа, позволяющего включить READY.

**Auth.** Employees/credentials/sessions, login NFKC/lower-case ASCII `[a-z0-9._-]`, 3…64. Логин не переиспользуется после архива. ACTIVE/SUSPENDED/DEACTIVATED, повторный приём с новым ID. Argon2id: 64 MiB, 3 passes, 4 lanes, 32-byte tag, random 16-byte salt; профиль требует замера на 4 ГБ. Минимум 8 символов, без обязательных типов; common-password проверка. Максимум ввода UTF-8 1024 byte — ресурсный предел. Локальный словарь SecLists из 10000 распространённых паролей включён в исходники; происхождение/checksum/license — third-party/SecLists-PROVENANCE.md, обращения к сети при проверке нет.

Лимитер по нормализованной идентичности: с пятой ошибки 1 с, далее экспоненциально до 60 с, окно 15 минут; одновременно ≤4 hashing tasks. Случайный токен 256 bit, в БД только SHA-256 токена. POS idle 3 часа, Waiter policy 3 часа, абсолютные 12 часов; фоновое чтение не продлевает сессию. Logout/status/password revoke не закрывают Shift. Временный пароль однократен, до личного доступ только к необходимой смене пароля. Архив и ролевые границы проверяются сервером, административные изменения атомарны с аудитом.

**Shifts.** Отдельное право + повторный логин/пароль текущего исполнителя; SQL unique OPEN на филиал. Открытие + audit/outbox/result атомарны. Нет автоматического закрытия. Close отвечает SHIFT_CLOSE_DEPENDENCIES_UNAVAILABLE до заказов, расчётов, инцидентов и D08; нет фиктивного отчёта.

**Menu.** Сохраняемый draft и его CAS; неизменяемые полные документы опубликованных редакций; CAS base revision и атомарный active pointer. Один уровень категорий; названия и translations/fallback; цена без размеров либо конечные цены размеров; группы min/max, бесплатные/платные опции на товар; kitchen flag. Category/item ID сохраняются через архив; ID не меняет вид/владельца между редакциями. Стоп-лист item/modifier — отдельная revision, публикацией не сбрасывается. Публикация доступна и во время OPEN. Облачного автообъединения/LWW нет.

**Pricing.** Сервер проверяет актуальную редакцию, состав, availability, принадлежность опций, min/max, размер, целое количество, дубли и лимиты. Подготавливает исторический snapshot; QUOTE_ONLY не создаёт заказ/Payment. Одна фиксированная скидка ≤subtotal. TABLE fees независимо от базы после скидки, COUNTER без fees. Фиксация набора ставок реального TABLE первым Batch — точка расширения следующего блока, не уже готовая продажа.

## Согласованные UI и клиент

Вход/первый пароль/смена пользователя; открытие смены; категории/товары и редакции. Сотрудники отдельно подтверждены: список/архив, имя/логин/роль, временный пароль один раз, подтверждения reset/suspend/deactivate, права и Owner-набор делегирования.

Desktop — Electron 45.0.0, отдельный процесс от Node 24 сервера. ContextIsolation/sandbox, без Node в renderer, CSP без сетевых запросов, запрет навигации/новых окон/permissions. Main вызывает только whitelist loopback routes, сохраняет encrypted token и pending command IDs до отправки, без password payload. После неопределённого ответа для того же действия сохраняется ID. Неразрешённые команды показаны отдельным списком для того же сотрудника; исходный безопасный payload/ID сохраняется зашифрованно. Повтор после перезапуска использует сохранённую команду; для повторной проверки запрашивается пароль, который не сохраняется. Смена пользователя не удаляет чужие pending-команды.

Формы RU/KY; server drafts можно сохранить и открыть; публикация отдельно/целиком; конфликт требует обновления и проверки. При отсутствующем облаке показывается недоступная активация; ввод cloud-пароля и фиктивный успех не предлагаются. Полный UI реальной активации зависит от облачного backend. Пароли не сохраняются, выход не закрывает смену.

## Проверки и ограничения

Автоматические проверки: БД/маркер/locks/crash, явная миграция 1→2, несовместимость, replay/conflict/rollback, отдельные SQLite процессы, shift uniqueness, роли/сессии/first password/revoke, API Host/Origin/foreign fields, меню/min/max/stoplist/immutable revisions, точная арифметика/лимиты. Фактические числа тестов фиксируются в PROGRESS.md после финального прогона.

Desktop macOS: настоящий Electron + HTTP API + safeStorage, одноразовая test authority/device. Вход, first password, сотрудник, смена пользователя, OPEN shift, draft/publication, категория/товар, форма сборов и TABLE/COUNTER quote, RU/KY; потеря ответа и перезапуск с прежним ID, безопасный отказ повреждённого protected storage. Это не облачная активация и не Windows/DPAPI приёмка.

Windows 10/11, 4 ГБ, служба/restart/ACL/DPAPI, power loss, настоящая активация, offline реального филиала, принтеры/телефоны/сеть — НЕ приняты. Общий план: infrastructure/windows-service/ITERATION-001-ACCEPTANCE.md. Полный цикл двух блоков начнётся после D10 и доступности оборудования; фундаментальные проверки можно провести на новой изолированной тестовой установке раньше.
