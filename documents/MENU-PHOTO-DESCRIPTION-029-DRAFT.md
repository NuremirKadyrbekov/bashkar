# MENU-PHOTO-DESCRIPTION-029 — описания в POS и фотографии меню в Cloud/Bunny

**Статус:** реализация продолжается 01.11.2026. Переводы и многострочное описание добавлены в локальный каталог, Desktop-редактор и Cloud-контракт schema 2. Добавлены локальные разрешения на фото, Cloud-таблицы, функция `menu-photo` и загрузка/замена/снятие фото из Desktop. Тесты на изолированной Cloud-БД и Electron прошли. Пользователь сообщил, что применил две миграции, добавил четыре Bunny Secrets и развернул `menu-sync`/`menu-photo` в Supabase. После исправления `BUNNY_STORAGE_ENDPOINT` безопасный GET без авторизации к `menu-photo` подтвердил ожидаемый `CLOUD_LOGIN_REQUIRED`: функция запускается и проверяет доступ. Реальная передача файла в Bunny из Desktop ещё не проверена. Удалённый кабинет Owner и публичное меню ещё не реализованы; Cloud API поддерживает Owner JWT для будущего кабинета.
**Связано:** [PUBLIC-MENU-SITE-028](PUBLIC-MENU-SITE-028-DRAFT.md), [API-MENU-SYNC-012](API-MENU-SYNC-012.md), [MENU-UX-002](MENU-UX-002.md). **Решение 01.11.2026:** фото загружают Desktop Owner/Cashier и удалённый Owner; файлы и привязка живут только в Bunny/Cloud, локальный сервер их не хранит.

## 1. Цель и существующее состояние

В текущем Desktop-редакторе меню улучшить основное описание, добавить переводы описания и управление фотографией для владельца и кассира с правом `menu.edit`. То же управление фото доступно владельцу в удалённом кабинете. Выбранный файл передаётся из интерфейса **в Cloud media API, далее в Bunny Storage**, минуя локальный сервер; связь с `branchId`/`itemId` хранится в Cloud-таблицах. Публичный сайт соединяет подтверждённый каталог филиала с этой связью. Для одного филиала все столы используют один каталог и те же фото/описания. В рабочей кассе локального POS фотографии не нужны.

Сейчас `Item.description` уже существует, редактируется на вкладке «Основное», ограничен сервером 2000 символами и сохраняется в черновике/опубликованной редакции. `Item.name` и названия категорий/вариантов поддерживают `translations`. Поля `descriptionTranslations` нет; в Desktop есть декоративная заглушка фото, но реальных файлов нет. Поэтому **не добавлять второе основное описание**; заменить заглушку на реальное управление фото в редакторе. Фото не включать в локальный JSON каталога.

## 2. Поведение редакторов

- В Desktop на вкладке «Основное» оставить существующее поле «Описание» для основного языка. Сделать его удобным для нескольких строк и показывать число символов/ошибку превышения. Описание необязательное; пустая строка означает отсутствие описания.
- На вкладке «Переводы» для каждого дополнительного языка из `catalog.languages` добавить «Описание» рядом с переводом названия. Переводы описания необязательные. При просмотре на языке без перевода показывать основное описание, без автоматического перевода. Удаление языка из настроек меню удаляет соответствующий перевод описания в редактируемой версии после подтверждения в действующем сценарии смены языков.
- В Desktop-редакторе Owner и Cashier с `menu.edit` могут выбрать, заменить и убрать одну фотографию товара. Показать текущую миниатюру из Bunny CDN, временный предпросмотр выбранного файла, прогресс и статус «Фото опубликовано / ожидает появления товара в Cloud / ошибка». Приложение не копирует файл в папку данных и не отправляет его через Local Server. В рабочей кассе/карточках заказа фото не загружать. При отсутствии сети управление фото недоступно с понятным сообщением; тексты и цены редактируются как раньше.
- В удалённом кабинете Owner выбирает свой филиал и товар по неизменяемому `itemId`, загружает, заменяет или убирает фото через тот же Cloud media API. Оба кабинета видят одну Cloud-привязку и её ревизию; не привязывать по имени. Для нового локального товара разрешён статус ожидающей привязки до подтверждения публикации/синхронизации каталога, без показа фото гостям до этого подтверждения.
- В локальном списке товаров можно показывать короткий фрагмент описания; миниатюра фото нужна только в редакторе, с загрузкой по требованию. Изменение описания следует существующему циклу форма → черновик → публикация с правом `menu.edit`. Фото публикуется отдельной Cloud-ревизией; интерфейс явно показывает это различие.
- RU/KY строки интерфейса, клавиатурный доступ и видимый фокус. На публичном сайте текстовая альтернатива фото — название товара. Фото не передаёт смысл доступности или цены.

## 3. Модель каталога и совместимость

Расширить локальный `Item` только переводами описания:

```ts
description?: string;                       // существующее, основной язык, до 2000 символов
descriptionTranslations?: Record<string,string>; // только языки catalog.languages, до 2000 на язык
```

Чистый `validateCatalog` проверяет типы, разрешённые языки, длину и контрольные символы переводов описания. Пустые переводы нормализуются как отсутствующие. Старые каталоги без нового поля читаются без миграции каждого JSON-документа; существующее `description` и цены остаются прежними. `photoAssetId`, Bunny URL и метаданные фото в локальный каталог/SQLite/outbox не добавлять: фото не влияет на расчёт цены, заказ, состав сета, печать кухни или исторические снимки строк заказа.

Cloud menu-sync ранее валидировал строгую схему каталога и `schema=1`. Для `descriptionTranslations` и многострочных описаний введён catalog schema v2 в локальном валидаторе и подготовлен общий Cloud-валидатор/Edge-контракт. Старые schema 1 документы и старые редакции читаются без переводов описания. Новый schema 2 документ не отправлять неподдерживающему клиенту как schema 1 и не терять поле при Cloud round-trip, разрешении конфликта или восстановлении старой версии. Фото и их ревизии ведутся отдельно в Cloud и не меняют локальную схему меню.

## 4. Cloud-таблицы и Bunny Storage

### Где задавать Bunny-параметры

После создания Storage Zone и подключённой Pull Zone открыть **Supabase Dashboard → проект Bashkar (`veghvtxwhtvocpuvmrlr`) → Edge Functions → Secrets**. Там задать следующие имена для Cloud media API:

| Secret | Значение |
|---|---|
| `BUNNY_STORAGE_ZONE` | Название Storage Zone. |
| `BUNNY_STORAGE_ENDPOINT` | HTTPS endpoint основного региона Storage Zone, без имени зоны и пути. |
| `BUNNY_STORAGE_ACCESS_KEY` | Пароль **этой Storage Zone** для HTTP Storage API, не ключ аккаунта Bunny. |
| `BUNNY_PULL_ZONE_URL` | HTTPS origin подключённой Pull Zone, без пути. |

Для локальной разработки те же переменные помещаются в игнорируемый Git файл `supabase/functions/.env`; в Desktop, `config/cloud.public.json`, локальный сервер и репозиторий пароль Storage Zone не записывается. Наличие секретов само по себе не включает загрузку: сначала нужны Cloud media API и его развёртывание.

**Состояние реализации:** текущая Cloud-функция принимает JPEG/PNG/WebP до 10 МБ, сверяет сигнатуру файла, пишет исходный файл в Bunny и фиксирует связь в Cloud с CAS-ревизией; при отказе записи Cloud пытается удалить новый объект из Bunny. Обработка ориентации, декодирование изображения, проверка размеров, создание WebP/миниатюры, ожидание ещё не синхронизированного товара `PENDING_BIND` и подтверждение доступности CDN пока не реализованы. До выпуска для гостей эти пункты требуют завершения и проверки на реальном Bunny. Удалённому кабинету Owner после выбора его HTTPS-адреса потребуется `BASHKAR_OWNER_ORIGIN` в Edge Function Secrets; без него браузерные запросы с Origin отклоняются.

Cloud хранит `menu_photo_assets` (`assetId`, `branchId`, `itemId`, тип, размер, размеры изображения, SHA-256, Bunny object key, статус, автор/время), историю `menu_item_photo_revisions` (`branchId`, `itemId`, `itemPhotoRevision`, `assetId|null`, автор/время) и общий `menu_photo_manifest` (`branchId`, `revision`). Составные ключи/проверки не допускают привязку фото другого филиала; перед публичной привязкой `itemId` сверяется с подтверждённым Cloud-каталогом этого филиала, поскольку товары меню сейчас хранятся внутри документа каталога. Для ещё не синхронизированного товара допустима только непубличная запись `PENDING_BIND` по подписанному разрешению Desktop. Текущая публичная связь — последняя подтверждённая ревизия для пары `(branchId,itemId)`; любое изменение связи атомарно увеличивает `menu_photo_manifest.revision`. Изменение требует `expectedPhotoRevision` и CAS, чтобы два кабинета не затирали друг друга. Старые ревизии сохраняют прежний ключ до отдельной политики хранения. В SQLite филиала нет таблицы медиа, фото, Bunny URL или очереди их передачи.

Оба кабинета передают выбранный файл **напрямую в доверенный Cloud media API**; локальный сервер не принимает и не проксирует байты. Удалённый Owner проходит Cloud Auth и проверку права на филиал. Desktop Owner/Cashier сначала запрашивает у Local Server короткоживущее подписанное разрешение на фото для конкретных `branchId`, `itemId`, сотрудника и операции: Local Server проверяет действующую сессию и `menu.edit`, подписывает разрешение зарегистрированным ключом устройства, но не получает файл. Cloud media API проверяет подпись/активную регистрацию, срок, nonce и scope разрешения, затем принимает файл. Повтор/переиспользование разрешения для чужого филиала или товара отклоняется. Это лёгкая операция метаданных для локального сервера, без хранения фото. Если безопасное разрешение не может быть выдано, загрузка из Desktop недоступна; ключ Bunny в Desktop не передавать.

В Desktop файл выбирается через системный диалог, а **основной процесс Electron** потоково отправляет выбранный файл в Cloud media API после получения разрешения. Renderer получает только статус/метаданные и при необходимости временный предпросмотр; не вводить общий доступ renderer к файловой системе. Это учитывает текущие `loadFile`, `contextIsolation`, `sandbox` и `webSecurity` Desktop и не требует разрешать небезопасный CORS для `file://`/`null` origin. Удалённый веб-кабинет загружает файл через браузер на Cloud media API с проверенным Cloud Auth и ограниченным CORS для своего HTTPS-origin.

Cloud media API декодирует изображение и загружает подготовленные байты в Bunny Storage Zone по HTTPS. `AccessKey` зоны хранится только в секретах Cloud media API; не выдавать его браузеру, Desktop или публичному сайту. Endpoint задаётся настройкой первичного региона зоны. Предлагаемый неизменяемый ключ объекта: `menu/{branchId}/{assetId}/{sha256}/large.webp` и `thumb.webp`; все сегменты формирует сервер. Повтор с тем же идентификатором/hash не создаёт вторую привязку.

Для чтения подключить к Storage Zone Bunny Pull Zone с HTTPS-адресом. Публичный API меню формирует URL из подтверждённого object key и разрешённого CDN-origin. Сайт не получает ключ записи Bunny. Путь файла неизменяем: новая фотография получает новый ключ, а CDN-кеш старого пути не подменяет её. Уже опубликованное фото может оставаться доступным по известному CDN-URL; для срочного снятия предусмотреть удаление файла/очистку кеша и проверку исторических ссылок.

Предлагаемые ограничения: JPEG, PNG, WebP; до 10 МБ и 4000×4000 пикселей. Cloud media API проверяет содержимое декодированием, исправляет ориентацию, удаляет EXIF, создаёт изображение до 1200 px и миниатюру до 320 px; отклоняет SVG, анимацию и повреждённые/опасные файлы. Лимиты подтвердить по QA. Никаких произвольных внешних URL в привязке.

## 5. Два независимых цикла публикации

1. **Описание и его переводы:** Desktop сохраняет их в локальном черновике через `draftSave`, затем публикует через действующий `publish`. Menu-sync доставляет подтверждённый каталог в Cloud. Это не требует Bunny и работает офлайн.
2. **Фото:** Owner/Cashier в Desktop или Owner в удалённом кабинете выбирает товар, загружает изображение через Cloud media API и подтверждает замену/удаление. Cloud записывает новую `photoRevision` только после успешной загрузки, проверки доступности файла и привязки к подтверждённому товару. Для нового локального товара фото может быть загружено как `PENDING_BIND` и активируется после появления `itemId` в подтверждённом Cloud-каталоге филиала; если товар так и не опубликован, файл не показывается гостям и удаляется по политике очистки. При отсутствии сети или Bunny сохранить новое фото нельзя; локальное меню и его публикация продолжают работать. Незавершённая загрузка не меняет текущую фотографию.
3. Публичная проекция по [PUBLIC-MENU-SITE-028](PUBLIC-MENU-SITE-028-DRAFT.md) соединяет применённую версию каталога с текущими Cloud-привязками фото по `(branchId,itemId)`. Ответ содержит `menuVersionId` и общую `photoRevision` из `menu_photo_manifest`; изменение фото обновляет публичное меню отдельно от локальной ревизии каталога. Все ссылки столов филиала получают одну и ту же пару версий. Если товар архивирован или исчез из применённого каталога, фото не показывается, но историческая привязка не удаляется автоматически.

## 6. Приёмка

- В Desktop изменить основное описание и переводы, сохранить черновик и опубликовать; после перезапуска и Cloud-синхронизации тексты соответствуют выбранной версии. Старые schema 1 товары открываются без потери описания/цены; RU/KY и fallback основного описания работают.
- Owner и Cashier с `menu.edit` загружают/заменяют/убирают фото из Desktop, Owner — из удалённого кабинета; оба видят одну Cloud-привязку. Публичный сайт получает новый `photoRevision`; Local Server выдаёт только подписанное разрешение и не получает/не хранит байты или ключ Bunny. Desktop загружает файл только в Cloud и при необходимости читает миниатюру из CDN в редакторе. Фото другого филиала, неверный/отозванный grant, неизвестного товара без подтверждённого ожидания, битый/слишком большой файл, SVG и чужой object key отвергаются Cloud-сервером.
- При недоступности Bunny/интернета фото остаётся прежним на сайте, возникает понятная ошибка в обоих кабинетах; локальные касса и редактор описаний работают. Потерянный ответ/повтор загрузки не создаёт две публичные ревизии. Проверить неверный регион/AccessKey, недоступный CDN-объект, старый кеш и замену фото. Проверить, что файл не появляется в SQLite, папке данных филиала, локальном outbox, логах или резервной копии POS.
- Два стола одного филиала показывают одинаковые `menuVersionId` и `photoRevision`; другой филиал не получает их фото. Проверки — на изолированном Cloud-филиале; рабочий MANGO этим ТЗ не менять.

## 7. Порядок изолированного развёртывания

1. Проверить наличие четырёх Bunny Secrets по именам, без вывода значений; подтвердить Storage Zone, её основной регион и подключённую Pull Zone.
2. На тестовом Cloud-проекте/филиале применить `20261101000100_menu_description_translations.sql`, затем `20261101000200_menu_photos.sql`. Обновить `menu-sync`, затем развернуть `menu-photo` с `verify_jwt=false` из `supabase/config.toml`; сама функция проверяет Owner JWT или одноразовый подписанный grant устройства.
3. Синхронизировать тестовое опубликованное меню до ACK. Из Desktop Owner и Cashier проверить чтение текущего фото, загрузку, замену, снятие, конфликт ревизий, отозванное устройство, чужой филиал и отсутствие файлов в SQLite/папке POS. Из Cloud Owner API проверить JWT и ограничение филиала.
4. Проверить Bunny GET через Pull Zone и фактический тип изображения. До использования с гостевого сайта завершить декодирование/оптимизацию/миниатюры и обработку повреждённых файлов.

Рабочий MANGO и его открытая смена в этот этап не включены. Пока нет стабильного публичного сайта, QR и публичные URL столов не раздавать.

## 8. Документация Bunny для реализации

- [Bunny Storage HTTP API](https://bunny.net/docs/storage/http) — загрузка бинарного файла по PUT с `AccessKey`, региональный endpoint и проверка SHA-256 через `Checksum`.
- [Bunny Storage Quickstart](https://bunny.net/docs/storage/quickstart) — подключение Storage Zone к Pull Zone и выдача файлов по CDN-адресу.
