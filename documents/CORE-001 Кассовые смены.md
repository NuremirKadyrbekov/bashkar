# 1. Назначение раздела

## 1.1. Цель

Настоящий раздел определяет бизнес-логику кассовых смен ресторанной платформы Bashkar.kg.

Цель — обеспечить контролируемое начало и завершение работы ресторана, регистрацию операций в рамках смены, сохранение финансовой истории и формирование итоговых отчётов.

Все критические операции со сменами выполняет Local POS Server.

POS Desktop предоставляет пользовательский интерфейс, но не является самостоятельным источником состояния смены.

## 1.2. Основные принципы

1. Один филиал в MVP может иметь только одну активную кассовую смену.
2. Открытие и закрытие смены требует авторизации по логину и паролю.
3. Официанты не могут выполнять ресторанные операции без активной смены.
4. Смена не привязана к определённому календарному времени и может продолжаться после полуночи.
5. Закрытие смены запрещено, если хотя бы один стол имеет активное посещение.
6. Закрытие смены выполняется отдельным подтверждённым действием кассира.
7. После закрытия формируется итоговый отчёт.
8. Отчёт сохраняется локально, синхронизируется с облаком и отправляется владельцу через Telegram.
9. Интернет не требуется для открытия, работы и закрытия смены.
10. В MVP не выполняется учёт начального остатка наличных и сверка физической кассы.

## 1.3. Область ответственности

Данный раздел определяет:

- сущность кассовой смены;
- открытие и закрытие;
- состояния и переходы;
- взаимодействие со столами и посещениями;
- связь с пакетами заказов;
- связь с зарегистрированными оплатами;
- формирование отчёта;
- доставку отчётов владельцу;
- работу без интернета;
- исключительные ситуации;
- сохранение истории;
- критерии приёмки.

Конкретные интерфейсы, API, схема БД и механизмы авторизации описываются в соответствующих технических заданиях.

# 2. Бизнес-сущности

## 2.1. Кассовая смена — Cash Shift

**Cash Shift** — период операционной работы филиала, начинающийся подтверждённым открытием смены и завершающийся подтверждённым закрытием.

Одна кассовая смена может включать операции многих сотрудников.

Кассовая смена не является индивидуальным рабочим графиком кассира или официанта.

### Основные логические данные

| Поле | Назначение |
|---|---|
| `id` | Уникальный идентификатор смены |
| `branch_id` | Филиал |
| `status` | Состояние смены |
| `opened_by_employee_id` | Сотрудник, открывший смену |
| `opened_at` | Фактическое время открытия |
| `opening_device_id` | Устройство открытия |
| `closed_by_employee_id` | Сотрудник, закрывший смену |
| `closed_at` | Фактическое время закрытия |
| `closing_device_id` | Устройство закрытия |

Идентификаторы сотрудников определяются сервером на основании проверенных учётных данных.

Для незакрытой смены поля закрытия отсутствуют.

Точная структура хранения будет утверждена в DB-SCHEMA-001.

## 2.2. Отчёт кассовой смены — Shift Report

**Shift Report** — итоговый документ, сформированный системой на основании принятых и сохранённых операций за период смены.

Отчёт связывается с конкретной сменой и содержит её идентификатор.

После формирования итоговая версия отчёта сохраняется в истории.

## 2.3. Задание доставки отчёта — Report Delivery

**Report Delivery** — логическая запись о необходимости доставить отчёт владельцу.

Поддерживаются два канала:

- Owner Dashboard — публикация через облачную синхронизацию;
- Telegram — отправка уведомления и краткого отчёта.

Состояние доставки не определяет состояние кассовой смены.

Ошибка доставки не отменяет закрытие.

## 2.4. Связь сущностей

Концептуальная модель:

**Branch → Cash Shifts → Shift Reports**

Каждая смена связана с операциями, выполненными в её рамках:

- посещениями столов;
- заказами и пакетами;
- зарегистрированными оплатами;
- отменами и корректировками после реализации соответствующих правил;
- сотрудниками, выполнявшими действия.

`table_session.shift_id` сохраняет принадлежность посещения к смене, в которой оно открыто.

В принятой для MVP модели все активные посещения должны быть завершены до закрытия этой смены. Поэтому обычная работа не требует переноса посещений между сменами.

# 3. Жизненный цикл кассовой смены

## 3.1. Состояния

| Состояние | Значение |
|---|---|
| `OPEN` | Смена открыта, разрешены соответствующие ресторанные операции |
| `CLOSED` | Смена завершена, новые операции в рамках неё запрещены |

Отсутствие активной смены не является отдельным состоянием существующей записи.

## 3.2. Переходы

**Нет активной смены → OPEN → CLOSED**

Переход `CLOSED → OPEN` для той же смены запрещён.

После закрытия создаётся новая смена с новым идентификатором.

## 3.3. Бизнес-правила

**BR-SHIFT-001.** Одновременно в филиале допускается не более одной смены со статусом `OPEN`.

**BR-SHIFT-002.** Открытие смены создаёт новую запись с уникальным ID.

**BR-SHIFT-003.** Закрытие смены переводит существующую запись из `OPEN` в `CLOSED`.

**BR-SHIFT-004.** Закрытая смена не может быть повторно открыта обычной пользовательской операцией.

**BR-SHIFT-005.** Система не должна автоматически закрывать смену в полночь, по расписанию или при освобождении последнего стола.

**BR-SHIFT-006.** Фактическое время открытия и закрытия определяется Local POS Server.

**BR-SHIFT-007.** После перезапуска компьютера или сервера состояние смены восстанавливается из SQLite.

# 4. Открытие кассовой смены

## 4.1. Основной сценарий

**UC-SHIFT-001 — Открытие смены**

Предусловия:

- Local POS Server работает;
- существует зарегистрированный филиал;
- сотрудник имеет необходимые разрешения;
- отсутствует активная смена.

Последовательность:

1. Кассир запускает Bashkar POS Desktop.
2. Выбирает действие «Открыть смену».
3. Вводит логин.
4. Вводит пароль.
5. Подтверждает открытие.
6. POS передаёт команду на Local POS Server.
7. Сервер проверяет учётные данные.
8. Сервер проверяет полномочия сотрудника.
9. Сервер проверяет отсутствие активной смены.
10. Сервер создаёт новую смену.
11. Сохраняет ID сотрудника и время открытия.
12. Подтверждает успешное открытие.
13. POS показывает активную смену.
14. Официантам становится доступна работа с заказами.

## 4.2. Данные, вводимые кассиром

Для открытия смены требуются только:

- логин;
- пароль.

Не требуются:

- начальный остаток наличных;
- фактический пересчёт кассы;
- причина открытия;
- ручной ввод даты и времени;
- подтверждение наличия денежных средств.

Филиал, устройство, сотрудник и время определяются автоматически.

## 4.3. Бизнес-правила

**BR-SHIFT-008.** Открывать смену может только сотрудник с соответствующим разрешением.

**BR-SHIFT-009.** Открытие требует успешной проверки логина и пароля.

**BR-SHIFT-010.** Проверка учётных данных должна выполняться локально и не требовать доступа к интернету для заранее зарегистрированного сотрудника.

**BR-SHIFT-011.** Если активная смена существует, создание новой смены запрещается.

**BR-SHIFT-012.** Ошибка авторизации не должна приводить к созданию смены.

**BR-SHIFT-013.** Данные о сотруднике, открывшем смену, сохраняются в истории и не изменяются.

**BR-SHIFT-014.** Открытие смены не требует регистрации начальных наличных.

**BR-SHIFT-015.** Начальный остаток наличных не должен автоматически приниматься равным нулю. В MVP он не учитывается как показатель.

**BR-SHIFT-016.** Повтор одной команды открытия не должен создавать вторую смену.

**BR-SHIFT-017.** При одновременных запросах открытия только один запрос может создать активную смену.

**BR-SHIFT-018.** После успешного открытия сведения об активной смене становятся доступными POS Desktop и авторизованным клиентам официантов.

# 5. Работа сотрудников во время смены

## 5.1. Основной принцип

Активная кассовая смена является обязательным условием выполнения основных ресторанных операций.

В рамках активной смены сотрудник работает с учётом своей роли и индивидуальных разрешений.

## 5.2. Поведение официанта без активной смены

Если активная смена отсутствует:

- официант не может открыть новый стол;
- не может отправить пакет заказа;
- не может оформить дозаказ;
- не может выполнять иные операции, требующие активной смены.

Официант может открыть веб-интерфейс и пройти допустимую локальную авторизацию, но рабочие операции остаются недоступны.

Интерфейс должен сообщать:

**«Кассовая смена не открыта. Дождитесь открытия смены кассиром».**

Это сообщение не означает, что пользователь лишён права на вход в систему.

## 5.3. Действия в активной смене

После открытия смены в пределах соответствующих разрешений доступны:

1. Открытие посещений столов.
2. Создание и отправка пакетов заказов.
3. Оформление дозаказов.
4. Просмотр активных посещений.
5. Регистрация оплат.
6. Закрытие посещений.
7. Разрешённые отмены и корректировки.

Правила STRICT и SHARED продолжают действовать независимо от состояния смены.

## 5.4. Бизнес-правила

**BR-SHIFT-019.** Открытие посещения требует существования смены `OPEN`.

**BR-SHIFT-020.** Создание нового пакета требует существования смены `OPEN`.

**BR-SHIFT-021.** Обычная регистрация оплаты требует активной смены.

**BR-SHIFT-022.** Клиент не может самостоятельно установить состояние смены.

**BR-SHIFT-023.** После закрытия смены сервер отклоняет новые ресторанные операции, которым требуется активная смена.

**BR-SHIFT-024.** Закрытие смены не должно уничтожать черновики официантов, сохранённые в IndexedDB.

**BR-SHIFT-025.** Черновик, относящийся к уже закрытому посещению, не может быть принят сервером.

**BR-SHIFT-026.** Если во время работы закрывается смена, клиенты должны получить уведомление об изменении её состояния.

**BR-SHIFT-027.** При повторном подключении клиент получает актуальное состояние смены непосредственно с сервера.

# 6. Закрытие кассовой смены

## 6.1. Основной принцип

Закрытие смены выполняется кассиром после окончания обслуживания гостей.

**Обязательное условие: количество активных посещений столов равно нулю.**

Недостаточно проверить только визуальные индикаторы столов в POS. Local POS Server обязан использовать фактические данные SQLite.

## 6.2. Основной сценарий

**UC-SHIFT-002 — Успешное закрытие смены**

Предусловия:

- существует активная смена;
- все посещения завершены;
- отсутствуют подтверждённые активные неоплаченные COUNTER; неподтверждённые черновики, завершённые оплаченные или `ZERO_SETTLED` и полностью отменённые COUNTER не блокируют закрытие независимо от видимости карточки;
- отсутствуют незавершённые критические финансовые операции, способные изменить итог смены;
- сотрудник имеет право закрытия смены.

Последовательность:

1. Кассир выбирает «Закрыть смену».
2. Система запрашивает логин и пароль.
3. Кассир вводит свои учётные данные.
4. Сервер проверяет полномочия.
5. Проверяет наличие активной смены.
6. Проверяет количество активных посещений.
6a. Проверяет отсутствие активных неоплаченных COUNTER с учётом согласованного серверного порядка конкурентных операций.
7. Проверяет отсутствие конфликтующих незавершённых операций.
8. Рассчитывает итоговые показатели.
9. Переводит смену в `CLOSED`.
10. Сохраняет сотрудника и время закрытия.
11. Сохраняет итоговый отчёт.
12. Регистрирует необходимость облачной синхронизации и отправки уведомления.
13. Подтверждает успешное закрытие.
14. POS Desktop показывает отчёт завершённой смены.

Изменение состояния смены, сохранение отчёта и необходимых событий доставки должно выполняться согласованно и атомарно.

## 6.3. Закрытие при занятых столах

**UC-SHIFT-003 — Попытка закрыть смену с активными посещениями**

Пример:

- Активная смена открыта.
- Стол №3 занят.
- Стол №7 занят.
- Все остальные столы свободны.

Кассир пытается закрыть смену.

Сервер обнаруживает два активных посещения и отклоняет команду.

POS отображает:

**«Невозможно закрыть смену. Остались активные столы: №3, №7. Завершите все посещения».**

Смена остаётся открытой.

Официанты продолжают обслуживать гостей.

После завершения всех посещений кассир может повторно выполнить операцию закрытия.

## 6.4. Бизнес-правила

**BR-SHIFT-028.** Закрытие требует повторной проверки логина и пароля сотрудника.

**BR-SHIFT-029.** Для закрытия необходимо соответствующее разрешение, проверяемое сервером.

**BR-SHIFT-030.** Нельзя закрыть смену, если существует хотя бы одно посещение со статусом `ACTIVE`.

**BR-SHIFT-031.** Проверка должна включать все активные посещения филиала, в том числе посещения без отправленных пакетов.

**BR-SHIFT-032.** Если обнаружены активные посещения, сервер отклоняет закрытие и возвращает сведения о препятствующих столах.

**BR-SHIFT-033.** После отказа смена остаётся `OPEN`.

**BR-SHIFT-034.** Освобождение последнего стола само по себе не закрывает смену.

**BR-SHIFT-035.** Закрытие происходит только после отдельной подтверждённой команды сотрудника.

**BR-SHIFT-036.** Проверка отсутствия активных посещений и изменение статуса смены выполняются в рамках согласованной транзакционной операции.

**BR-SHIFT-037.** Успешное закрытие фиксирует фактического сотрудника и время завершения.

**BR-SHIFT-038.** Закрытая смена не принимает новые операции оформления заказов.

**BR-SHIFT-039.** Повтор той же команды закрытия не должен изменять отчёт или создавать новую операцию закрытия.

**BR-SHIFT-040.** Если невозможно надёжно сохранить состояние закрытия и отчёт, операция не должна считаться успешно завершённой.

## 6.5. Особенность закрытия

Нулевое количество занятых столов — необходимое, но не единственное техническое условие.

Сервер должен исключать ситуацию, когда одновременно с закрытием принимается операция, способная изменить финансовый итог смены.

При этом не требуется ждать облачной синхронизации или доставки уведомления в Telegram.

# 7. Финансовый учёт кассовой смены

## 7.1. Принятая модель MVP

В Bashkar.kg кассовая смена используется для учёта операций и формирования отчётности.

В MVP система **не выполняет физическую сверку денежного ящика**.

Не предусматриваются обязательные:

- ввод начального остатка наличных;
- ввод конечного остатка наличных;
- пересчёт денежного ящика;
- вычисление ожидаемых наличных с учётом разменного остатка;
- расчёт недостачи или излишка кассы.

## 7.2. Что учитывается

Несмотря на отсутствие сверки кассы, система регистрирует:

- принятые заказы;
- стоимость заказов;
- отдельные оплаты;
- метод каждой оплаты;
- сумму зарегистрированных наличных оплат;
- сумму вручную зарегистрированных оплат банковской картой;
- другие разрешённые методы;
- возвраты и корректировки после согласования их бизнес-правил.

Финансовые операции сохраняются в локальной базе.

## 7.3. Разделение сумм

Система должна различать:

**Сумма заказов** — стоимость подтверждённых заказов с учётом утверждённых корректировок.

**Зарегистрированные оплаты** — суммы, внесённые сотрудниками в учёт POS как произведённые платежи.

**Наличные оплаты** — платежи, зарегистрированные методом `CASH`.

**Банковские карты** — платежи, зарегистрированные соответствующим методом вручную.

Зарегистрированная банковская оплата не является автоматическим подтверждением банковской транзакции.

Система не должна обозначать сумму зарегистрированных наличных оплат как фактически пересчитанный остаток кассы.

## 7.4. Бизнес-правила

**BR-SHIFT-041.** Отсутствие ввода начальных наличных не препятствует открытию смены.

**BR-SHIFT-042.** Закрытие смены не требует ввода фактической суммы наличных.

**BR-SHIFT-043.** Отчёт должен отдельно учитывать зарегистрированные оплаты по поддерживаемым методам.

**BR-SHIFT-044.** Итоговые суммы определяются сервером из сохранённых финансовых операций.

**BR-SHIFT-045.** Система не должна рассчитывать кассовые расхождения на основании отсутствующих данных о физическом остатке денег.

**BR-SHIFT-046.** Финансовая история сохраняется независимо от состояния облачной синхронизации.

## 7.5. Границы раздела

Точные правила частичных оплат, смешанных оплат, возвратов, скидок и округления определяются в следующем разделе CORE-001 — «Оплаты и расчёты».

Этот раздел не заменяет проектирование полноценной бизнес-логики платежей.

# 8. Отчёт по кассовой смене

## 8.1. Основной принцип

После успешного закрытия смены Local POS Server автоматически формирует итоговый отчёт на основании данных SQLite.

Для каждого закрытия создаётся один логический итоговый отчёт.

Отчёт должен сохраняться даже при отсутствии интернета.

## 8.2. Состав отчёта MVP

### Общая информация

- Название ресторана и филиала.
- ID смены.
- Дата открытия.
- Время открытия.
- Время закрытия.
- Продолжительность смены.
- Сотрудник, открывший смену.
- Сотрудник, закрывший смену.

### Операционная информация

- Количество открытых посещений.
- Количество закрытых посещений.
- Количество пустых посещений.
- Количество основных заказов.
- Количество принятых пакетов.
- Сумма подтверждённых заказов с учётом реализованных корректировок.
- Количество заказов и суммы отдельно для TABLE и COUNTER, включая отменённые заказы и нулевые расчёты; видимость завершённой карточки не влияет на итоги.

### Финансовая информация

- Общая сумма зарегистрированных оплат.
- Сумма зарегистрированных наличных оплат.
- Сумма оплат банковскими картами, зарегистрированных вручную.
- Суммы других зарегистрированных методов оплаты.
- Сумма зарегистрированных возвратов, если такая функция реализована.
- Скидки, отмены и нулевые расчёты в общих итогах и отдельно для TABLE и COUNTER; `ZERO_SETTLED` не создаёт денежного поступления.

Возврат, выполненный после закрытия исходной смены, учитывается в смене выполнения возврата; закрытый отчёт исходной смены задним числом не изменяется. Ошибки KITCHEN/CUSTOMER печати, отсутствие интернета или отложенная доставка отчёта сами по себе не блокируют закрытие при выполнении остальных проверок.

Не реализованные финансовые показатели не должны отображаться так, будто система достоверно вычислила их значение.

## 8.3. Пример отчёта

**BASHKAR.KG — ОТЧЁТ КАССОВОЙ СМЕНЫ**

Филиал: Кафе №1  
Дата открытия: 19.10.2026  
Открыта: 09:00  
Закрыта: 23:30  
Кассир открытия: Сотрудник №4  
Кассир закрытия: Сотрудник №4

**Обслуживание:**

- Закрыто посещений: 42
- Пустых посещений: 2
- Заказов: 40
- Отправленных пакетов: 76

**Финансы:**

- Стоимость подтверждённых заказов: 58 450 сом
- Зарегистрированные оплаты: 58 450 сом
- Наличные оплаты: 28 450 сом
- Банковские карты (вручную): 30 000 сом

Статус смены: CLOSED

*Все значения приведены исключительно для иллюстрации формата.*

## 8.4. Историческая неизменность

После закрытия сохранённый отчёт не должен изменяться бесследно.

Если в будущих версиях требуется корректировка операции после закрытия смены, она оформляется отдельным финансовым событием со ссылкой на исходную запись.

Необходимо сохранять исходную историю.

## 8.5. Бизнес-правила

**BR-SHIFT-047.** После успешного закрытия автоматически формируется итоговый отчёт.

**BR-SHIFT-048.** Отчёт формируется на основании серверных данных.

**BR-SHIFT-049.** Отчёт связывается с конкретной сменой.

**BR-SHIFT-050.** Отчёт сохраняется локально до подтверждения успешного закрытия.

**BR-SHIFT-051.** Отчёт должен быть доступен для повторного просмотра.

**BR-SHIFT-052.** Повторное получение отчёта не создаёт новую финансовую историю.

**BR-SHIFT-053.** Исторические итоговые показатели не должны бесследно перезаписываться последующими корректировками.

**BR-SHIFT-054.** Смена, пересекающая полночь, формирует один отчёт за фактический период смены, а не автоматически два отчёта по календарным датам.

# 9. Отправка отчёта владельцу через Telegram

## 9.1. Назначение

После завершения смены владелец ресторана должен получать итоговую информацию через Telegram.

Отправка выполняется автоматически, без отдельного действия кассира.

## 9.2. Предварительные требования

Для доставки необходимы:

- настроенная Telegram-интеграция;
- привязанный получатель;
- разрешение владельца на получение уведомлений;
- интернет-соединение в момент фактической отправки.

Если интеграция не настроена, отчёт всё равно сохраняется, а POS отображает отсутствие настроенного канала доставки.

## 9.3. Основной сценарий

**UC-SHIFT-004 — Автоматическая отправка отчёта**

1. Кассир успешно закрывает смену.
2. Local POS Server сохраняет отчёт.
3. Регистрируется событие завершения смены.
4. При наличии интернета данные передаются в облачную инфраструктуру.
5. Cloud Backend сохраняет отчёт для Owner Dashboard.
6. Система доставки создаёт или обрабатывает задание Telegram-уведомления.
7. Telegram-бот отправляет сообщение настроенному получателю.
8. Результат доставки фиксируется.

Предпочтительная схема: Cloud Backend выполняет отправку Telegram-уведомлений после получения отчёта через синхронизацию.

Это предотвращает необходимость хранить общий административный Telegram-токен внутри POS Desktop.

Конкретная техническая реализация определяется в BACKEND-001 и SYNC-001.

## 9.4. Работа без интернета

Если интернет недоступен:

- закрытие смены выполняется локально;
- отчёт сохраняется;
- событие синхронизации остаётся в очереди;
- доставка Telegram ожидает восстановления подключения;
- после восстановления выполняется повторная обработка ожидающих событий.

Нельзя показывать уведомление как доставленное, если фактическое подтверждение отсутствует.

## 9.5. Надёжность доставки

**BR-SHIFT-055.** Закрытие смены не зависит от доступности Telegram.

**BR-SHIFT-056.** Для каждого закрытого отчёта должно существовать логическое задание отправки в настроенный канал Telegram.

**BR-SHIFT-057.** Повторная синхронизация одного отчёта не должна создавать множество независимых заданий отправки.

**BR-SHIFT-058.** Ошибка доставки должна фиксироваться и не должна приводить к потере отчёта.

**BR-SHIFT-059.** После восстановления связи система должна обрабатывать ожидающие задания.

**BR-SHIFT-060.** Данные доступа Telegram-интеграции не должны находиться в незащищённых клиентских файлах.

**BR-SHIFT-061.** Если результат отправки неизвестен, система должна учитывать риск повторной доставки при повторной попытке.

Гарантировать, что Telegram физически покажет сообщение ровно один раз при любых сетевых сбоях, нельзя. Система должна гарантировать сохранность задания и предотвращать заведомо дублирующиеся отправки.

## 10.1. Основной принцип

**BR-SHIFT-065.** Отсутствие облачного подключения не должно изменять локальный статус смены.

**BR-SHIFT-066.** История должна сохранять фактические данные открытия и закрытия смены.

# 11. Работа без интернета и восстановление

## 11.1. Отключение интернета

Система должна сохранять возможность:

- открыть смену;
- обслуживать столы;
- принимать пакеты заказов;
- регистрировать оплаты;
- закрывать посещения;
- завершать смену;
- формировать локальный отчёт.

Интернет требуется только для функций, которые непосредственно используют внешние сервисы.

## 11.2. Закрытие POS Desktop

Если интерфейс кассира закрыт:

- Local POS Server продолжает работать;
- смена остаётся открытой;
- официанты могут продолжать разрешённые операции;
- сервер продолжает принимать данные;
- состояние восстанавливается при повторном запуске POS Desktop.

## 11.3. Перезапуск Windows

Если Windows перезагружается во время активной смены:

1. Windows запускает Local POS Server.
2. Сервер открывает SQLite.
3. Определяет активную смену.
4. Восстанавливает операционное состояние.
5. POS Desktop после подключения отображает текущую смену.

Новая смена автоматически не создаётся.

## 11.4. Сбой во время закрытия

Возможны два корректных результата:

**Результат A:** транзакция закрытия не зафиксирована — смена остаётся открытой.

**Результат B:** транзакция зафиксирована — смена закрыта, отчёт и события доставки сохранены.

Недопустимо состояние, в котором смена считается закрытой, но обязательный отчёт отсутствует вследствие частично выполненной операции.

## 11.5. Бизнес-правила

**BR-SHIFT-067.** Работа со сменами не требует доступности Supabase.

**BR-SHIFT-068.** Потеря интернета не должна автоматически закрывать смену.

**BR-SHIFT-069.** Закрытие POS Desktop не должно закрывать кассовую смену.

**BR-SHIFT-070.** Перезапуск Local POS Server не должен создавать новую смену взамен существующей.

**BR-SHIFT-071.** Состояние смены определяется сохранёнными локальными данными.

**BR-SHIFT-072.** Сбой операции закрытия не должен приводить к частичному сохранению критически связанных данных.

# 12. Параллельные действия сотрудников

## 12.1. Одновременное открытие смены

Если два сотрудника одновременно пытаются открыть смену:

- сервер должен принять не более одной новой смены;
- второй запрос не должен создать конкурентную смену;
- клиент получает информацию о существующей активной смене.

## 12.2. Закрытие смены одновременно с открытием стола

**UC-SHIFT-005 — Конфликт закрытия и открытия посещения**

Ситуация:

- активных посещений нет;
- кассир закрывает смену;
- официант одновременно пытается открыть стол.

Правильное поведение:

**Если первым зафиксировано открытие посещения:** закрытие смены отклоняется.

**Если первой зафиксирована операция закрытия:** открытие посещения отклоняется.

Нельзя допустить, чтобы после закрытия смены в ней появилось новое активное посещение.

## 12.3. Закрытие смены одновременно с финансовой операцией

Регистрация оплаты и закрытие смены должны проходить через согласованную серверную проверку.

Финансовая операция, принятая до завершения смены, должна войти в соответствующие итоги.

Новая финансовая операция не должна быть зарегистрирована задним числом в уже закрытую смену.

## 12.4. Бизнес-правила

**BR-SHIFT-073.** Открытие и закрытие смены должны быть защищены от конкурентного выполнения.

**BR-SHIFT-074.** Проверка активной смены и создание нового посещения должны быть согласованы транзакционно.

**BR-SHIFT-075.** Закрытие смены должно учитывать все финансовые операции, успешно зафиксированные до него.

**BR-SHIFT-076.** Запрос, полученный после фактического закрытия смены, не может создавать новую операцию внутри закрытого периода.

**BR-SHIFT-077.** После изменения состояния смены сервер рассылает соответствующее событие подключённым клиентам.

# 13. Авторизация и безопасность

## 13.1. Открытие

При открытии смены требуется подтверждение личности сотрудника по логину и паролю.

Сервер определяет сотрудника по проверенным учётным данным.

Клиент не может самостоятельно объявить операцию выполненной от имени другого сотрудника.

## 13.2. Закрытие

Закрытие смены требует новой проверки логина и пароля.

Наличие открытой сессии POS Desktop само по себе не отменяет требование повторной проверки.

Сотрудник, открывший смену, и сотрудник, закрывший её, могут различаться, если оба обладают необходимыми разрешениями.

Окончательные права ролей Cashier, Manager и Owner определяются в AUTH-001.

## 13.3. Аудит

Система должна сохранять:

- успешное открытие;
- успешное закрытие;
- сотрудника и время;
- неуспешные попытки закрытия из-за активных посещений;
- отказы в выполнении административных операций;
- сведения о критических ошибках.

Пароли и другие секретные данные не должны записываться в журнал аудита.

## 13.4. Бизнес-правила

**BR-SHIFT-078.** Открытие и закрытие требуют проверки полномочий на сервере.

**BR-SHIFT-079.** Действия должны фиксироваться за фактически авторизованным сотрудником.

**BR-SHIFT-080.** Операции открытия и закрытия должны сохраняться в истории аудита.

**BR-SHIFT-081.** Система не должна сохранять введённый пароль в данных смены или отчёта.

# 14. Ошибки и исключительные ситуации

| Ситуация | Ожидаемое поведение |
|---|---|
| Неверный логин или пароль | Отказ в операции, состояние смены не меняется |
| Нет права открыть смену | Отказ с сообщением о недостаточных разрешениях |
| Смена уже открыта | Новая смена не создаётся |
| Нет активной смены | Операции официантов запрещены |
| Есть хотя бы один активный стол | Закрытие смены запрещается |
| Потерян интернет | Локальная смена продолжает работу |
| Telegram недоступен | Отчёт сохраняется, доставка ожидает повторной обработки |
| Supabase недоступен | Локальное закрытие выполняется, синхронизация откладывается |
| Перезапущен POS Desktop | Смена сохраняется |
| Перезапущен Windows-компьютер | Состояние восстанавливается из SQLite |
| Повтор открытия с тем же `command_id` | Не создаёт вторую смену |
| Повтор закрытия с тем же `command_id` | Не создаёт новый итоговый отчёт |
| Сбой SQLite при закрытии | Операция не подтверждается как успешная |
| Одновременное закрытие и открытие стола | Применяется согласованный порядок операций |
| Черновик остался после закрытия | Сервер отклоняет отправку в завершённое посещение |

## 14.1. Ошибки кухонной печати

Уже принятые пакеты сохраняются независимо от состояния принтера.

**BR-SHIFT-082.**

Ошибка печати ранее принятого пакета сама по себе не блокирует закрытие смены, если все посещения завершены и отсутствуют другие запрещающие условия.

Незавершённые задания печати сохраняются и остаются доступны для диагностики после закрытия смены.

# 15. Критерии приёмки

## 15.1. Открытие смены

**SHIFT-AT-001:** Кассир с действующими полномочиями открывает смену по логину и паролю.

**SHIFT-AT-002:** Открытие не требует ввода начальных наличных.

**SHIFT-AT-003:** Вторая одновременная активная смена филиала не создаётся.

**SHIFT-AT-004:** Неверные учётные данные не позволяют открыть смену.

**SHIFT-AT-005:** После открытия официанты могут выполнять разрешённые операции.

## 15.2. Работа сотрудников

**SHIFT-AT-006:** Без активной смены официант не может открыть посещение.

## 15.3. Закрытие смены

**SHIFT-AT-009:** Закрытие требует повторной проверки логина и пароля.

**SHIFT-AT-010:** Если занят хотя бы один стол, закрытие запрещено.

**SHIFT-AT-011:** Пустое, но активное посещение также блокирует закрытие.

**SHIFT-AT-012:** При нуле активных посещений и выполнении остальных обязательных проверок смену можно закрыть.

**SHIFT-AT-013:** При освобождении последнего стола смена автоматически не закрывается.

**SHIFT-AT-014:** Повтор команды закрытия не создаёт второго отчёта.

**SHIFT-AT-015:** После закрытия новая отправка пакета в рамках прежней смены запрещена.

## 15.4. Отчёты

**SHIFT-AT-016:** После закрытия автоматически формируется локальный отчёт.

**SHIFT-AT-017:** Отчёт включает сотрудника, время, операции и поддерживаемые финансовые показатели.

**SHIFT-AT-018:** Для формирования отчёта не требуется интернет.

**SHIFT-AT-019:** Отчёт доступен в истории POS.

**SHIFT-AT-020:** После синхронизации отчёт становится доступен в Owner Dashboard.

**SHIFT-AT-021:** При настроенной интеграции создаётся задание доставки Telegram-отчёта.

**SHIFT-AT-022:** Ошибка Telegram не отменяет закрытие смены.

## 15.5. Надёжность

**SHIFT-AT-023:** После перезапуска POS Desktop активная смена сохраняется.

**SHIFT-AT-024:** После перезапуска Local POS Server активная смена восстанавливается.

**SHIFT-AT-025:** Одновременные открытие стола и закрытие смены не нарушают целостность данных.

**SHIFT-AT-026:** Повторный запрос открытия не создаёт дубль.

**SHIFT-AT-027:** После восстановления интернета ранее сохранённый отчёт синхронизируется.

**SHIFT-AT-028:** Сбой в процессе закрытия не приводит к состоянию CLOSED без обязательного локального отчёта.

# 16. Границы MVP

## 16.1. Входит в MVP

- Одна активная кассовая смена на филиал.
- Открытие по логину и паролю.
- Закрытие по логину и паролю.
- Серверная проверка полномочий.
- Запрет ресторанных операций без активной смены.
- Сохранение сотрудника открытия.
- Сохранение сотрудника закрытия.
- Сохранение времени открытия и закрытия.
- Блокировка закрытия при активных посещениях.
- Отсутствие автоматического закрытия.
- Учёт подтверждённых заказов и зарегистрированных оплат.
- Формирование итогового отчёта.
- Просмотр истории.
- Синхронизация отчёта в облако.
- Отображение отчёта в Owner Dashboard.
- Отправка итогового уведомления через Telegram.
- Очередь доставки при отсутствии интернета.
- Защита от дублирования команд.
- Восстановление после перезапуска.

## 16.2. Не входит в MVP

- Учёт начального остатка физической кассы.
- Обязательный подсчёт денег при закрытии.
- Сверка фактических и ожидаемых наличных.
- Расчёт недостачи и излишков.
- Автоматическое закрытие смен по расписанию.
- Перенос активных посещений между сменами.
- Одновременная работа нескольких независимых кассовых рабочих мест.
- Сложные процедуры передачи денежной кассы между кассирами.
- Автоматическое подтверждение банковских транзакций.
- Автоматическое создание фискальных документов средствами Bashkar POS.

## 16.3. Архитектурно предусмотрено на будущее

- Передача незавершённых посещений между сменами.
- Несколько независимых кассовых рабочих мест.
- Индивидуальные кассовые смены.
- Расширенные финансовые отчёты.
- Кассовые внесения и изъятия.
- Учёт фактических наличных.
- Сверка денежного ящика.
- Настраиваемые политики завершения смен.

Эти функции не должны усложнять реализацию первоначальной версии.

# 17. Изменения в ARCH-001 v0.9

Для согласованности проектной документации необходимо внести следующие изменения в архитектурное ТЗ.

## 17.1. Раздел 11.2 — Открытие смены

В текущей редакции ARCH-001 предусматривается фиксация начального состояния кассы.

**Изменить на:**

«Открытие кассовой смены выполняется сотрудником с соответствующим разрешением после проверки логина и пароля.

При открытии фиксируются филиал, сотрудник, устройство и время.

В MVP ввод начального остатка наличных не требуется. Физический остаток денег в кассе не учитывается как обязательный показатель».

## 17.2. Раздел 11.4 — Закрытие смены

Исключить из обязательных проверок MVP:

- ожидаемые наличные в физической кассе;
- фактически пересчитанные наличные;
- кассовые расхождения.

**Изменить на:**

«Закрытие смены требует повторной проверки логина и пароля сотрудника с соответствующим разрешением.

Закрытие запрещено при наличии активных посещений столов.

После выполнения обязательных проверок сервер атомарно закрывает смену, сохраняет итоговый отчёт и регистрирует события его доставки.

Закрытие не зависит от доступности облачной инфраструктуры».

## 17.3. Дополнить требования к отчётности

ARCH-001 должен учитывать:

- локальное формирование отчёта после закрытия;
- сохранение истории смен;
- синхронизацию отчётов с Supabase;
- просмотр в Owner Dashboard;
- Telegram-уведомления владельца;
- повторные попытки доставки при сетевых сбоях;
- независимость локального закрытия от доставки уведомлений.

Telegram является дополнительной внешней интеграцией, а не компонентом критического пути кассовой операции.

Изменения должны быть внесены в следующую согласованную редакцию ARCH-001. Они не отменяют остальные требования Local-First Architecture.

# 20. Итоговые принципы

1. Кассовая смена определяет период операционной работы филиала.
2. В MVP на филиал допускается только одна активная смена.
3. Кассир открывает смену по логину и паролю.
4. Начальные наличные не вводятся.
5. Официанты могут выполнять ресторанные операции только при активной смене.
6. Столы, посещения и пакеты продолжают использовать ранее утверждённую бизнес-логику CORE-001 v0.4.
7. Закрытие требует повторной проверки логина и пароля.
8. Наличие хотя бы одного активного посещения запрещает закрытие.
9. Смена не закрывается автоматически при освобождении последнего стола.
10. Все критические проверки выполняются Local POS Server.
11. После успешного закрытия создаётся локальный итоговый отчёт.
12. Отчёт включает операции и зарегистрированные платежи.
13. Отчёт не утверждает фактический остаток наличных.
14. Отчёты синхронизируются в Owner Dashboard.
15. Владелец получает Telegram-уведомление при настроенной интеграции и доступной доставке.
16. Отсутствие интернета не блокирует кассовую работу.
17. Закрытые смены и их отчёты сохраняются в истории.
18. Сложные механизмы передачи смен и сверки физической кассы откладываются на Post-MVP.
