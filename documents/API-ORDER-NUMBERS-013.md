# API-ORDER-NUMBERS-013 — единый номер заказа в смене

Статус: реализовано в Local POS Server `0.12.0-cash-ux`, схема 13. Дата: 25.10.2026.

## Контракт

Для каждой пары `branchId + shiftId` используется одна последовательность **TABLE и COUNTER**: 1, 2, 3… Новый номер назначается при первом успешном подтверждении заказа. Открытие посещения TABLE, черновик и prepare/quote номера не расходуют. Дополнительный пакет сохраняет номер исходного заказа. Новая смена начинает с 1.

Публичное поле `orderNumber: number | null` добавлено в DTO заказа, общий список активных заказов, историю пакетов, новые серверные квитанции подтверждения/оплаты, новые снимки завершённых продаж и печатные задания. Внутренние UUID сохраняют прежнее назначение. Пример карточки: `С10 / Заказ №001`, `На вынос / Заказ №002`.

COUNTER сохраняет совместимость поля `counterNumber`: для новых заказов оно равно общему `orderNumber`; пропуски между последовательными COUNTER допустимы, если промежуточные номера получили TABLE. Поиск COUNTER по номеру по-прежнему требует исходную смену. Старый `counter_sequences` остаётся как историческая структура, новый runtime его не увеличивает. Новая возможность объявлена в `/system/version` как `sharedOrderNumbers`.

## Хранение и атомарность

Миграция 013 добавляет `order_sequences` и неизменяемую связь `order_numbers` (заказ, филиал, смена, номер). Уникальность — `(branch_id, shift_id, number)`, один номер на заказ. FK и триггер проверяют связку заказа/филиала/смены. Выдача номера и запись заказа выполняются внутри одной CommandBus-транзакции: ошибка обязательной записи откатывает номер, повтор исходной команды возвращает сохранённый результат. Клиент не генерирует и не резервирует номер.

## Переход с существующих данных

Существующие COUNTER получают отображение прежнего `counter_number`; следующий общий номер соответствующей смены устанавливается больше максимального из них. Старые TABLE остаются без публичного номера (`null`), в карточке — «Номер не присвоен». Неизменные старые чеки, снимки продаж и результаты команд не переписываются; старые результаты могут не содержать нового поля. Исторический COUNTER в UI использует `counterNumber` как fallback.

Обновление выполняется **явно**, прежний запрет миграции при OPEN-смене сохранён (`MIGRATION_OPEN_SHIFT`). Это не автоматическое обновление рабочего профиля. Тестирование перехода выполнено на изолированных копиях, включая сохранность данных и отказ при открытой смене. MANGO не мигрировалась.
