# 1. Назначение документа

## 1.1. Цель

Документ определяет бизнес-логику управления столами, посещениями гостей, заказами и пакетами заказов в ресторанной системе Bashkar.kg.

Основная цель — обеспечить единые и предсказуемые правила обработки заказов независимо от интерфейса, через который сотрудник работает с системой.

Бизнес-правила должны одинаково применяться при работе через:

- Bashkar POS Desktop;
- веб-интерфейс официанта;
- будущие мобильные приложения;
- дополнительные разрешённые интерфейсы.

Окончательное решение о выполнении бизнес-операций принимает Local POS Server.

Клиентские приложения не могут обходить серверные ограничения.

## 1.2. Область документа

11. Изменения цен при оформлении заказов.

# 2. Основные бизнес-сущности

## 2.1. Стол — Table

**Table** представляет физический стол ресторана.

Каждый стол принадлежит определённому филиалу.

Основные характеристики:

- `id` — уникальный идентификатор;
- `branch_id` — идентификатор филиала;
- `number` — номер или название стола;
- `zone_id` — зона расположения;
- `is_active` — доступность стола для использования.

Рабочее состояние стола определяется наличием активного посещения.

Один стол может обслуживать разные компании гостей в течение дня.

История предыдущих посещений сохраняется отдельно.

## 2.2. Посещение — Table Session

**Table Session** — отдельный случай обслуживания гостей за определённым столом.

Пример:

Стол №7 обслуживает гостей в 12:00, затем другую компанию в 15:00.

Это два разных посещения одного стола.

Каждое посещение содержит:

- `id` — идентификатор посещения;
- `table_id` — идентификатор стола;
- `shift_id` — смена, в которой открыто посещение;
- `opened_by_employee_id` — кто открыл стол;
- `responsible_waiter_id` — ответственный официант;
- `opened_at` — время открытия;
- `closed_at` — время закрытия;
- `status` — состояние посещения;
- `close_reason` — причина завершения, если применимо.

**Основное ограничение:** один стол не может одновременно иметь два активных посещения.

## 2.3. Заказ — Order

**Order** — общий заказ конкретного посещения, объединяющий подтверждённые позиции всех отправленных пакетов.

Для MVP устанавливается правило:

**Одно посещение → один основной заказ.**

Открытие посещения не обязательно создаёт заказ.

Основной заказ создаётся при первой успешной отправке пакета.

Если гости делают дозаказ, новый заказ не создаётся. Дополнительные позиции включаются в существующий заказ посредством нового пакета.

Заказ связан с:

- посещением;
- пакетами;
- позициями;
- финансовыми расчётами;
- зарегистрированными оплатами.

## 2.4. Пакет заказа — Order Batch

**Order Batch** — группа позиций, подтверждённая и отправленная сотрудником одним действием.

Пакет создаётся при успешном принятии команды Local POS Server.

Одно посещение может содержать неограниченное логикой количество пакетов.

Например:

- Пакет №1 — напитки.
- Пакет №2 — основные блюда.
- Пакет №3 — десерты.

Основные данные пакета:

- `id` — уникальный идентификатор;
- `order_id` — основной заказ;
- `table_session_id` — посещение;
- `submitted_by_employee_id` — отправивший сотрудник;
- `submitted_at` — время отправки;
- `command_id` — идентификатор команды;
- позиции пакета;
- сумма пакета;
- связанные задания кухонной печати.

Принятый пакет не редактируется как обычный черновик.

Изменения уже принятого пакета должны отражаться отдельными корректирующими операциями.

## 2.5. Позиция заказа — Order Item

**Order Item** представляет конкретную позицию блюда или товара.

Основные данные:

- `id`;
- `order_batch_id`;
- `menu_item_id`;
- `name_snapshot`;
- `quantity`;
- `unit_price_snapshot`;
- `modifiers_snapshot`;
- `comment`;
- `discount_snapshot`;
- `total_amount`;
- `status`.

Позиция обязательно сохраняет фактическую цену и наименование на момент принятия заказа.

Каждая позиция может иметь собственный комментарий.

## 2.6. Черновик — Draft

**Draft** — ещё не отправленный набор позиций.

Черновик создаётся во время сбора заказа официантом.

Для MVP черновики мобильного веб-клиента хранятся в IndexedDB браузера.

Черновик:

- не считается принятым заказом;
- не входит в текущий подтверждённый счёт;
- не направляется на кухню;
- может редактироваться сотрудником;
- не требует обращения к серверу при каждом добавлении блюда.

Черновик связывается с конкретным сотрудником, устройством, филиалом и посещением.

После успешного принятия сервером соответствующий черновик удаляется из активных черновиков или помечается завершённым.

## 2.7. Связь бизнес-сущностей

Логическая модель:

**Restaurant Branch**
- содержит Tables;
- содержит Employees;
- содержит Shifts.

**Table**
- содержит историю Table Sessions.

**Table Session**
- принадлежит одному Table;
- имеет сотрудника, открывшего стол;
- имеет ответственного официанта;
- может содержать один основной Order.

**Order**
- содержит один или несколько Order Batches.

**Order Batch**
- содержит одну или несколько Order Items;
- хранит отправившего сотрудника;
- связан с заданиями печати.

**Order Item**
- хранит товар, цену, количество, модификаторы и комментарий.

Эта схема используется в качестве концептуальной основы для DB-SCHEMA-001.

# 3. Бизнес-логика столов

## 3.1. Состояния столов

В MVP поддерживаются два рабочих состояния:

| Статус | Значение |
|---|---|
| `FREE` | Нет активного посещения |
| `OCCUPIED` | Существует активное посещение |

Состояние стола определяется по данным Local POS Server.

**BR-TABLE-001**

Стол считается свободным, если у него нет активного посещения.

**BR-TABLE-002**

Стол считается занятым, если у него существует активное посещение.

Состояние не должно изменяться исключительно на клиенте без подтверждения сервера.

Дополнительные состояния `RESERVED`, `BLOCKED`, `CLEANING` и другие не входят в текущий MVP.

## 3.2. Открытие стола

Основной сценарий:

1. Гости занимают свободный стол.
2. Официант открывает экран этого стола.
3. Нажимает «Открыть стол».
4. Телефон отправляет команду Local POS Server.
5. Сервер проверяет права сотрудника.
6. Сервер проверяет активную смену.
7. Сервер проверяет, что стол свободен.
8. Сервер создаёт новое посещение.
9. Стол становится занятым.
10. Подключённые клиенты получают уведомление.

### Бизнес-правила

**BR-TABLE-003**

Открывать стол может только авторизованный сотрудник с необходимым разрешением.

**BR-TABLE-004**

Открытие стола разрешено только при активной кассовой смене.

**BR-TABLE-005**

Нельзя создать новое посещение, если стол уже занят.

**BR-TABLE-006**

Посещение создаётся на Local POS Server и сохраняется в SQLite.

**BR-TABLE-007**

После успешного открытия стол должен отображаться занятым для всех подключённых клиентов.

**BR-TABLE-008**

Повторная отправка той же команды открытия не должна создавать второе посещение.

**BR-TABLE-009**

Одновременные команды открытия одного свободного стола не должны приводить к созданию двух посещений.

В случае конкурентного открытия только одна новая операция может быть успешной.

Остальным клиентам сервер сообщает, что стол уже занят, и возвращает его актуальное состояние.

# 4. Привязка официантов к столам

## 4.1. Основной принцип

В Bashkar.kg необходимо различать:

1. Сотрудника, который открыл стол.
2. Официанта, ответственного за стол.
3. Сотрудника, отправившего конкретный пакет.

Это три независимых характеристики.

## 4.2. Сотрудник, открывший стол

Поле:

`opened_by_employee_id`

Содержит идентификатор сотрудника, который выполнил операцию открытия посещения.

Значение фиксируется при создании посещения и впоследствии не изменяется.

**BR-TABLE-010**

Информация о первоначальном открывшем стол сотруднике сохраняется на протяжении всей истории посещения.

## 4.3. Ответственный официант

Поле:

`responsible_waiter_id`

Определяет сотрудника, за которым закреплено текущее посещение.

Если стол открывает официант, он автоматически становится ответственным.

Если стол открывает кассир или менеджер, при наличии официантов назначается ответственный сотрудник.

Если ответственный не назначен, операции официантов в режиме строгой привязки остаются ограниченными до назначения. Административные операции регулируются правами сотрудника.

В MVP ответственный официант не изменяется в течение посещения.

**BR-TABLE-011**

Добавление пакетов другими официантами в режиме совместной работы не должно менять ответственного за стол.

# 5. Настраиваемые режимы доступа к столам

## 5.1. Общий принцип

Bashkar.kg должен поддерживать два режима работы официантов:

- `STRICT` — строгая привязка;
- `SHARED` — совместная работа.

Режим определяется настройкой филиала:

`table_access_mode`

Настройка действует на все столы соответствующего филиала.

## 5.2. Режим STRICT

В режиме строгой привязки официант работает только со своими назначенными посещениями.

### BR-TABLE-012

Официант может видеть состояние всех столов: свободен или занят.

### BR-TABLE-013

Официант может просматривать подробную информацию и пакеты только своих назначенных посещений, если не имеет дополнительных разрешений.

### BR-TABLE-014

Официант не может отправлять пакеты в чужие посещения без соответствующего специального разрешения.

### BR-TABLE-015

Официант может открыть любой свободный доступный стол, если имеет право открытия столов.

После открытия стол закрепляется за ним.

### BR-TABLE-016

Менеджер, владелец и кассир могут выполнять операции с чужими посещениями в пределах индивидуально предоставленных разрешений.

### Пример

Официант №1 открыл стол №7.

Ответственный — официант №1.

Официант №2 видит, что стол №7 занят.

Однако он не может:

- просматривать детальные позиции чужого заказа;
- отправлять дозаказ;
- изменять позиции заказа;
- закрывать чужое посещение без разрешения.

## 5.3. Режим SHARED

В режиме совместной работы официанты могут обслуживать общие столы.

Первоначальная привязка при этом сохраняется.

### BR-TABLE-017

Все авторизованные официанты с необходимыми правами могут просматривать активные столы и их заказы.

### BR-TABLE-018

Любой такой официант может добавлять новые пакеты к активному посещению.

### BR-TABLE-019

Добавление пакета другим сотрудником не меняет `opened_by_employee_id`.

### BR-TABLE-020

Добавление пакета другим сотрудником не меняет `responsible_waiter_id`.

### BR-TABLE-021

Каждый пакет обязательно сохраняет фактического отправителя.

### Пример

Официант №1 открыл стол №7.

Ответственный — официант №1.

Пакет №1 отправил официант №1.

Через некоторое время официант №2 отправил пакет №2.

При этом:

- открыл стол — официант №1;
- ответственный — официант №1;
- пакет №1 отправил официант №1;
- пакет №2 отправил официант №2.

Система сохраняет все эти сведения отдельно.

## 5.4. Отображение столов

Для обоих режимов предусматриваются два логических представления:

**«Мои столы»**

Показывает активные посещения, ответственным за которые назначен текущий официант.

**«Все столы»**

Показывает все столы филиала.

В режиме STRICT чужие занятые столы отображаются без недоступных сотруднику подробностей.

В режиме SHARED официант может открывать подробную информацию чужих активных посещений.

Точное расположение вкладок определяется в WAITER-001.

## 5.5. Изменение режима доступа

**BR-TABLE-022**

Менять режим доступа может только сотрудник с необходимым административным разрешением.

**BR-TABLE-023**

Изменение режима сохраняется на Local POS Server.

**BR-TABLE-024**

Новый режим применяется к последующим операциям, включая действия с уже открытыми посещениями.

**BR-TABLE-025**

Изменение режима доступа не должно менять ответственных официантов и историю ранее отправленных пакетов.

# 7. Жизненный цикл посещения

## 7.1. Основные состояния

Для MVP предусматриваются состояния:

| Статус | Значение |
|---|---|
| `ACTIVE` | Посещение открыто |
| `CLOSED` | Посещение завершено |

Причина завершения фиксируется отдельно.

Примеры:

- `PAID` — счёт полностью закрыт;
- `EMPTY` — завершено без отправленных заказов;
- `CANCELLED` — все ранее принятые позиции отменены до оплаты;
- `ZERO_TOTAL` — нулевой расчёт с действующими позициями завершён без Payment.

Финансовое состояние заказа и состояние посещения должны учитываться раздельно.

## 7.2. Открытое посещение

Посещение ACTIVE позволяет:

- создавать первый пакет;
- добавлять дозаказы;
- просматривать отправленные пакеты;
- регистрировать соответствующие оплаты;
- выполнять разрешённые корректировки.

Все действия ограничиваются правами пользователя и текущим состоянием смены.

## 7.3. Пустое посещение

Гости могут занять стол, но не сделать заказ.

В этом случае посещение можно завершить без оплаты.

### BR-SESSION-001

Пустым считается посещение, в котором отсутствуют принятые пакеты заказа и зарегистрированные платежи.

### BR-SESSION-002

Пустое посещение может быть закрыто сотрудником с соответствующим разрешением.

### BR-SESSION-003

Закрытие пустого посещения фиксируется в истории с причиной `EMPTY`.

### BR-SESSION-004

После закрытия стол становится свободным.

## 7.4. Закрытие посещения с заказом

Посещение, содержащее заказ, закрывается после выполнения всех обязательных условий.

При успешной полной оплате закрытие посещения и освобождение стола выполняются автоматически в той же атомарной серверной транзакции. Отдельная команда закрытия стола после оплаты не требуется.

### BR-SESSION-005

Обычное закрытие посещения с заказом разрешено только при полностью погашенном остатке счёта.

Исключение составляют посещения, в которых до оплаты отменены все оставшиеся действующие позиции. Такое посещение закрывается с причиной `CANCELLED` без создания Payment или Settlement; исходные пакеты и отмены сохраняются в истории.

Если отмена одной позиции или группы позиций приводит к отсутствию оставшихся действующих позиций, Local POS Server обязан проверить отдельное право полной отмены заказа. Право отмены отдельных позиций не даёт права на такое закрытие независимо от количества позиций и способа их выбора.

### BR-SESSION-006

При закрытии должны отсутствовать незавершённые операции, препятствующие фиксации окончательной суммы.

### BR-SESSION-007

Закрытие выполняется на Local POS Server.

### BR-SESSION-008

Операция закрытия должна быть атомарной и защищённой от повторного выполнения.

### BR-SESSION-009

После успешного закрытия посещение получает статус CLOSED.

### BR-SESSION-010

Стол становится свободным.

### BR-SESSION-011

Закрытое посещение сохраняется в истории.

### BR-SESSION-012

Создание новых пакетов в закрытом посещении запрещено.

## 7.5. Незавершённый черновик при закрытии

На телефоне официанта может оставаться черновик, относящийся к посещению, которое уже закрыто кассиром.

### BR-SESSION-013

Сервер не должен принимать новый пакет в закрытое посещение.

### BR-SESSION-014

Клиент должен сообщать сотруднику, что посещение уже завершено.

### BR-SESSION-015

Черновик не должен автоматически переноситься в новое посещение того же стола.

## 7.6. Повторное открытие стола

После закрытия посещения стол может быть занят следующими гостями.

При новом открытии создаётся новый `table_session_id`.

Новый заказ не должен объединяться с заказом предыдущего посещения.

# 8. Бизнес-логика черновиков заказов

## 8.1. Создание черновика

Официант выбирает активное посещение и начинает собирать заказ.

В черновик могут добавляться:

- товары;
- количество;
- модификаторы;
- комментарии;
- другие поддерживаемые параметры.

## 8.2. Работа с черновиком

**BR-DRAFT-001**

Официант может редактировать черновик до успешной отправки.

**BR-DRAFT-002**

Черновик не должен изменять подтверждённую сумму заказа.

**BR-DRAFT-003**

Черновик не должен создавать кухонное задание печати.

**BR-DRAFT-004**

Черновик сохраняется локально в IndexedDB браузера.

**BR-DRAFT-005**

После перезагрузки страницы приложение должно пытаться восстановить существующий черновик.

**BR-DRAFT-006**

Перед отправкой клиент должен проверить доступность сервера.

**BR-DRAFT-007**

При потере Wi-Fi клиент не должен отображать черновик как успешно отправленный пакет.

## 8.3. Подтверждение заказа гостем

Бизнес-процесс предполагает, что официант перед отправкой уточняет заказ у гостей.

После подтверждения сотрудник нажимает «Отправить».

Отдельное цифровое подтверждение гостем для MVP не требуется.

## 8.4. Завершение черновика

Черновик считается отправленным только после подтверждения успешного принятия сервером.

Если результат отправки неизвестен, приложение должно сначала проверить исходную операцию.

Нельзя автоматически создавать новую команду отправки того же содержимого.

---

# 9. Создание и отправка пакетов заказов

## 9.1. Основной принцип

Пакет заказа является основной единицей подтверждения позиций заказа и передачи на кухню тех позиций, которым требуется печать.

**Один подтверждённый черновик → один принятый пакет → при наличии предназначенных для кухни позиций необходимое задание их печати.** Все позиции сохраняются в заказе.

Физических заданий печати может быть несколько, если в будущих конфигурациях пакет распределяется по кухонным принтерам.

## 9.2. Сценарий отправки

1. Официант собирает черновик.
2. Уточняет позиции у гостей.
3. Нажимает «Отправить».
4. Клиент формирует команду с уникальным `command_id`.
5. Команда отправляется Local POS Server.
6. Сервер проверяет права сотрудника.
7. Сервер проверяет режим доступа к столам.
8. Сервер проверяет активную смену.
9. Сервер проверяет состояние посещения.
10. Сервер проверяет все позиции.
11. Сервер проверяет актуальность цен.
12. Сервер рассчитывает итоговую сумму.
13. Сервер сохраняет пакет и позиции.
14. Сервер создаёт задание кухонной печати, если в пакете есть предназначенные для кухни позиции.
15. Сервер записывает событие синхронизации.
16. После успешной транзакции возвращает подтверждение.
17. Print Service начинает обработку созданного задания, если оно требуется.
18. POS получает информацию о новом пакете.

## 9.3. Правила отправки

**BR-ORDER-001**

Пакет может отправить только авторизованный сотрудник с соответствующим разрешением.

**BR-ORDER-002**

Отправка разрешена только при открытой кассовой смене.

**BR-ORDER-003**

Посещение должно иметь статус ACTIVE.

**BR-ORDER-004**

Пакет должен содержать не менее одной допустимой позиции.

**BR-ORDER-005**

Сервер проверяет актуальность всех товаров, цен и модификаторов.

**BR-ORDER-006**

Сервер самостоятельно рассчитывает стоимость пакета.

**BR-ORDER-007**

Клиентская сумма не является источником истины.

**BR-ORDER-008**

Каждая команда отправки содержит уникальный `command_id`.

**BR-ORDER-009**

Пакет, все его позиции, необходимые задания печати и событие синхронизации фиксируются одной транзакцией.

**BR-ORDER-010**

Пакет считается принятым только после успешного сохранения на сервере.

**BR-ORDER-011**

Предназначенные для кухни позиции принятого пакета автоматически поступают в очередь кухонной печати. Пакет без таких позиций сохраняется без кухонного задания.

**BR-ORDER-012**

Кассир не должен вручную подтверждать каждый обычный заказ официанта.

## 9.4. Авторство пакета

**BR-ORDER-013**

Каждый пакет должен содержать `submitted_by_employee_id`.

**BR-ORDER-014**

Идентификатор фактического отправителя определяется Local POS Server из авторизованной сессии.

**BR-ORDER-015**

Клиент не может произвольно указать другого сотрудника отправителем.

**BR-ORDER-016**

В одном посещении могут быть пакеты разных сотрудников.

**BR-ORDER-017**

Авторство пакетов не изменяется при смене режима доступа к столам.

## 9.5. Состояния отправки на клиенте

Клиент должен различать:

- `DRAFT` — черновик;
- `SENDING` — выполняется отправка;
- `ACCEPTED` — пакет принят сервером;
- `UNKNOWN` — результат неизвестен;
- `REJECTED` — сервер отклонил команду.

Эти состояния относятся к отправке команды и не заменяют отдельные состояния печати.

## 9.6. Защита от дублирования

**BR-ORDER-018**

Повторная передача одной команды с тем же `command_id` не должна создавать новый пакет.

**BR-ORDER-019**

Если команда ранее была успешно обработана, сервер возвращает сохранённый результат.

**BR-ORDER-020**

Если один `command_id` повторно используется с другим содержимым, сервер возвращает ошибку конфликта.

**BR-ORDER-021**

При потере ответа клиент должен повторно проверить результат ранее отправленной команды, а не создавать новый заказ автоматически.

# 10. Дозаказы и несколько пакетов

## 10.1. Основной принцип

В течение одного посещения гости могут делать несколько заказов.

Каждый подтверждённый дозаказ оформляется отдельным пакетом.

## 10.2. Правила

**BR-ORDER-022**

Одно посещение может содержать несколько пакетов.

**BR-ORDER-023**

Новый пакет относится к существующему заказу посещения.

**BR-ORDER-024**

Новый пакет не изменяет ранее отправленные пакеты.

**BR-ORDER-025**

Общая сумма заказа учитывает позиции всех принятых пакетов с соответствующими корректировками.

**BR-ORDER-026**

Кухня получает только новые позиции очередного пакета.

**BR-ORDER-027**

Каждый пакет сохраняет отдельное время отправки и фактического отправителя.

## 10.3. Пример

Посещение №2501, стол №7.

**Пакет №1 — 12:30**

Отправил официант №1:

- Капучино × 2 — 300 сом.
- Чизкейк × 1 — 250 сом.

Сумма пакета: 550 сом.

**Пакет №2 — 12:50**

Отправил официант №2:

- Плов × 2 — 600 сом.

Сумма пакета: 600 сом.

**Пакет №3 — 13:10**

Отправил официант №1:

- Чай × 1 — 100 сом.

Сумма пакета: 100 сом.

**Общая сумма заказа: 1 250 сом.**

Все три пакета относятся к одному посещению и одному основному заказу.

# 11. Комментарии к позициям блюд

## 11.1. Назначение

В системе необходимо поддерживать индивидуальные комментарии к позициям заказа.

Комментарии используются для передачи пожеланий гостя кухне.

Примеры:

- Без лука.
- Меньше соли.
- Не остро.
- Соус отдельно.
- Без сахара.
- Подать после горячего.

## 11.2. Структура комментария

Каждая позиция заказа имеет необязательное поле:

`comment`

Комментарий относится к конкретной позиции, а не ко всему пакету.

## 11.3. Бизнес-правила

**BR-ITEM-001**

Комментарий является необязательным.

**BR-ITEM-002**

У каждой позиции может быть свой комментарий.

**BR-ITEM-003**

Если одинаковые блюда имеют разные пожелания, они сохраняются отдельными позициями.

Пример:

- Плов × 1 — без лука.
- Плов × 1 — обычный.

**BR-ITEM-004**

Комментарий сохраняется вместе с принятой позицией.

**BR-ITEM-005**

Комментарий позиции, предназначенной для кухни, должен передаваться в кухонное задание печати.

**BR-ITEM-006**

На кухонном чеке комментарий выводится непосредственно под соответствующим блюдом.

**BR-ITEM-007**

Комментарий не должен автоматически изменять стоимость товара.

**BR-ITEM-008**

Платные дополнительные ингредиенты и модификаторы должны обрабатываться через механизм модификаторов, а не через свободный комментарий.

**BR-ITEM-009**

Пока пакет находится в черновике, сотрудник может изменять комментарии.

**BR-ITEM-010**

После принятия пакета первоначальный комментарий не должен изменяться без отдельной корректирующей операции.

## 11.4. Ограничения комментариев

Для MVP:

- максимальная длина: 300 символов;
- простой текст;
- без HTML;
- без исполняемых команд;
- поддержка русского и кыргызского языков;
- удаление или экранирование управляющих символов при печати.

Конкретные правила переноса строк определяются адаптером печати.

## 11.5. Отображение в пакете

Пример:

**Пакет №3**

Позиция №1:

- Название: Плов.
- Количество: 1.
- Комментарий: Без лука.

Позиция №2:

- Название: Чай.
- Количество: 2.
- Комментарий: Без сахара.

Комментарии сохраняются как часть исторических данных заказа.

# 12. Отправка на кухню

## 12.1. Основной процесс

После успешного принятия пакета Local POS Server создаёт задание печати, если пакет содержит предназначенные для кухни позиции. Все позиции пакета сохраняются в заказе.

Задание сохраняется в локальной БД.

Kitchen Print Service выполняет печать независимо от облачной синхронизации.

## 12.2. Требования

**BR-KITCHEN-001**

Пакет должен быть сохранён до начала его обработки принтером.

**BR-KITCHEN-002**

При успешном принятии пакета с предназначенными для кухни позициями создаётся постоянное задание печати; пакет без таких позиций принимается без кухонного задания.

**BR-KITCHEN-003**

Печатаются только предназначенные для кухни позиции конкретного пакета.

**BR-KITCHEN-004**

Предыдущие пакеты не должны повторно печататься при обычном дозаказе.

**BR-KITCHEN-005**

Каждая предназначенная для кухни позиция должна печататься со своим количеством и комментарием.

**BR-KITCHEN-006 — Новая редакция**

Кухонный чек должен содержать номер стола либо идентификатор заказа без стола, дату и время отправки, сведения об отправившем сотруднике, названия блюд, количество, модификаторы и комментарии.

Номер пакета заказа не отображается на бумажном чеке, но сохраняется во внутренней структуре данных и истории печати.

**BR-KITCHEN-007**

Отказ принтера не должен удалять принятый заказ.

**BR-KITCHEN-008**

Ошибка печати должна отображаться в POS.

**BR-KITCHEN-009**

Повторная печать должна выполняться контролируемо, чтобы уменьшить риск повторного приготовления блюд.

## 12.3. Состояния печати

Для заданий печати предусматриваются:

- `PENDING` — ожидает печати;
- `PROCESSING` — выполняется отправка;
- `COMPLETED` — драйвер или принтер подтвердил доступный этап выполнения;
- `FAILED` — произошла ошибка;
- `UNKNOWN` — результат отправки неопределён.

Статус COMPLETED не обязательно доказывает физическую выдачу бумаги.

## 12.4. Связь с POS

После принятия пакета он сразу должен появляться в POS.

Кассир видит:

- номер стола;
- номер пакета;
- сумму;
- отправившего сотрудника;
- позиции;
- состояние кухонной печати.

Ручное подтверждение обычного пакета кассиром не требуется.

# 13. Цены и изменения меню

## 13.1. Основной принцип

Local POS Server является авторитетным источником действующих цен ресторана.

Клиент официанта может использовать кеш меню, но сервер повторно проверяет цену при отправке пакета.

## 13.2. Правила

**BR-PRICE-001**

Каждая принятая позиция сохраняет снимок цены.

**BR-PRICE-002**

Историческая стоимость принятой позиции не меняется при обновлении меню.

**BR-PRICE-003**

При отправке сервер сравнивает данные черновика с действующей версией меню.

**BR-PRICE-004**

Если цена отличается, пакет не должен приниматься молча по изменённой стоимости.

**BR-PRICE-005**

Клиент получает новую цену и информацию об изменении.

**BR-PRICE-006**

Для продолжения требуется явное подтверждение сотрудника.

**BR-PRICE-007**

После подтверждения клиент отправляет обновлённую команду, а сервер повторно проверяет цены перед окончательной записью.

**BR-PRICE-008**

Если товар стал недоступен, сервер отклоняет соответствующую отправку и сообщает причину.

Конкретная политика фиксации цен на всё посещение может быть добавлена в дальнейшем.

Для MVP действует правило цены на момент принятия позиции сервером.

---

# 14. Параллельная работа официантов

## 14.1. Общий принцип

Local POS Server должен поддерживать одновременную работу нескольких официантов.

Особенно важно обеспечить корректную работу в режиме SHARED.

## 14.2. Одновременные дозаказы

Возможный сценарий:

Официант №1 отправляет новый пакет для стола №7.

Одновременно официант №2 тоже отправляет новый пакет для этого стола.

**BR-CONCURRENT-001**

Две разные допустимые команды отправки должны обрабатываться независимо.

**BR-CONCURRENT-002**

Каждая команда должна получить собственный уникальный пакет.

**BR-CONCURRENT-003**

Оба пакета должны войти в общий заказ.

**BR-CONCURRENT-004**

Итоговая сумма заказа должна рассчитываться с учётом обоих пакетов.

**BR-CONCURRENT-005**

Ни один пакет не должен быть потерян из-за одновременного выполнения другого запроса.

## 14.3. Закрытие посещения одновременно с дозаказом

**BR-CONCURRENT-006**

Проверка активности посещения и сохранение пакета должны быть согласованы одной транзакционной логикой.

**BR-CONCURRENT-007**

Если закрытие завершилось раньше обработки отправки, новый пакет должен быть отклонён.

**BR-CONCURRENT-008**

Если новый пакет принят раньше операции закрытия, закрытие должно учитывать его стоимость и остальные связанные ограничения.

## 14.4. Обновление экранов

После изменения посещения сервер отправляет событие подключённым клиентам.

Однако события WebSocket не являются единственным источником состояния.

После повторного подключения клиент получает актуальные данные с Local POS Server.

---

# 15. Ошибки и нестандартные ситуации

## 15.1. Отсутствует интернет

При отключении внешнего интернета:

- POS продолжает работу;
- официанты продолжают работу через локальную сеть;
- заказы сохраняются в SQLite;
- задания печати выполняются локально;
- облачная синхронизация откладывается.

## 15.2. Потеря Wi-Fi на телефоне

Если телефон потерял соединение во время сбора черновика, черновик остаётся локально, насколько позволяет браузер.

Если потеря произошла во время отправки, результат операции может быть неизвестен.

Клиент не должен автоматически сообщать об успешной отправке без подтверждения.

## 15.3. Повторная отправка

Повторение команды с тем же `command_id` не создаёт дублированный пакет.

Если первоначальный запрос был успешно обработан, сервер возвращает ранее сохранённый результат.

## 15.4. Стол закрыт другим сотрудником

Если посещение закрыто до отправки нового пакета, сервер отклоняет операцию.

Клиент показывает актуальный статус посещения.

Черновик не переносится автоматически в новое посещение.

## 15.5. Изменение режима доступа

Если режим переключился со SHARED на STRICT во время работы официанта, сервер проверяет новые права при следующей команде.

Неавторизованная отправка в чужое посещение отклоняется.

## 15.6. Отказ принтера

Принятый заказ остаётся в системе.

Задание печати сохраняется в очереди.

Кассир получает информацию об ошибке.

Повторная печать выполняется отдельно и контролируемо.

## 15.7. Перезапуск POS Desktop

Закрытие графического интерфейса POS не должно уничтожать заказы и посещения.

Local POS Server продолжает выполнять операции, если служба работает.

После повторного запуска интерфейс получает актуальное состояние.

# 16. Основной бизнес-сценарий

## UC-001 — Обслуживание стола несколькими официантами

### Условия

- Режим доступа SHARED.
- Кассовая смена открыта.
- Стол №7 свободен.
- Официанты №1 и №2 авторизованы.
- Local POS Server работает.

### Шаг 1. Открытие стола

Гости занимают стол №7.

Официант №1 открывает стол.

Сервер создаёт посещение №2501.

Фиксируется:

- `opened_by_employee_id = 1`;
- `responsible_waiter_id = 1`;
- `status = ACTIVE`.

Стол становится занятым.

### Шаг 2. Первый пакет

Официант №1 собирает заказ:

- Капучино × 2 — 300 сом.
- Чизкейк × 1 — 250 сом.

Гости подтверждают заказ.

Официант отправляет пакет.

Сервер создаёт основной заказ и пакет №1 на 550 сом.

Пакет поступает в очередь кухонной печати.

### Шаг 3. Дозаказ другим официантом

Гости вызывают официанта №2.

Он открывает занятый стол №7.

В режиме SHARED у него есть доступ к активному посещению.

Он собирает:

- Плов × 1 — 300 сом, комментарий «Без лука».
- Плов × 1 — 300 сом, без комментария.

После подтверждения гостей отправляет пакет №2.

Сервер сохраняет:

`submitted_by_employee_id = 2`

Пакет №2 поступает на кухню.

Ответственным за стол остаётся официант №1.

### Шаг 4. Третий пакет

Официант №1 добавляет:

- Чай × 1 — 100 сом.

Сервер создаёт пакет №3.

### Шаг 5. Общий счёт

Система объединяет:

- пакет №1 — 550 сом;
- пакет №2 — 600 сом;
- пакет №3 — 100 сом.

Итого: **1 250 сом**.

### Шаг 6. Оплата и закрытие

Кассир завершает оплату в соответствии с установленными бизнес-правилами. Local POS Server одной атомарной транзакцией регистрирует полный расчёт, закрывает посещение №2501 с причиной `PAID` и освобождает стол №7.

История сохраняет:

- первоначального открывшего стол сотрудника;
- ответственного официанта;
- все пакеты;
- отправителя каждого пакета;
- позиции;
- комментарии;
- цены;
- задания печати;
- финансовую историю.

# 17. Критерии приёмки

## 17.1. Столы и посещения

**CORE-AT-001:** Открытие свободного стола создаёт активное посещение.

**CORE-AT-002:** После открытия стол становится занятым на всех подключённых клиентах.

**CORE-AT-003:** Одновременное открытие одного стола не создаёт два активных посещения.

**CORE-AT-004:** При открытии сохраняется ID сотрудника.

**CORE-AT-005:** Ответственный официант сохраняется отдельно от сотрудника, открывшего стол.

**CORE-AT-006:** Пустое посещение можно закрыть разрешённой операцией.

**CORE-AT-007:** Закрытое посещение сохраняется в истории.

**CORE-AT-008:** Нельзя добавить пакет к закрытому посещению.

## 17.2. Режимы доступа

**CORE-AT-009:** В STRICT обычный официант не может отправить пакет в чужое посещение.

**CORE-AT-010:** В SHARED другой официант может отправить дозаказ.

**CORE-AT-011:** Отправка другим официантом не меняет ответственного за стол.

**CORE-AT-012:** Каждый пакет хранит фактического отправителя.

**CORE-AT-013:** После изменения режима доступа сервер использует новые правила.

**CORE-AT-014:** В MVP отсутствует операция передачи стола другому официанту.

## 17.3. Заказы и пакеты

**CORE-AT-015:** Черновик не влияет на подтверждённый счёт.

**CORE-AT-016:** При первой отправке создаётся основной заказ.

**CORE-AT-017:** Последующие отправки создают новые пакеты того же заказа.

**CORE-AT-018:** Повтор одной команды не создаёт второй пакет.

**CORE-AT-019:** Два разных пакета могут быть приняты одновременно.

**CORE-AT-020:** Все принятые пакеты учитываются в общей сумме.

**CORE-AT-021:** Изменение цены меню не изменяет историческую цену позиции.

**CORE-AT-022:** Устаревшая цена требует подтверждения актуальной стоимости.

## 17.4. Комментарии

**CORE-AT-023:** Комментарий сохраняется у конкретной позиции.

**CORE-AT-024:** Одинаковые блюда с разными комментариями сохраняются как отдельные позиции.

**CORE-AT-025:** Комментарии предназначенных для кухни позиций включаются в кухонное задание печати.

**CORE-AT-026:** Отсутствие комментария не препятствует отправке заказа.

**CORE-AT-027:** Комментарий не влияет на стоимость блюда.

## 17.5. Надёжность

**CORE-AT-028:** Заказ можно принять без доступа к интернету.

**CORE-AT-029:** При отключении принтера пакет сохраняется.

**CORE-AT-030:** При потере ответа от сервера повторная отправка не создаёт дубль.

**CORE-AT-031:** При перезапуске POS Desktop данные посещения остаются доступными.

**CORE-AT-032:** Новый пакет, принятый до закрытия посещения, учитывается при проверке закрытия.

**CORE-AT-033:** Сервер не принимает пакет в уже закрытое посещение.

# 18. Границы MVP и будущие возможности

## 18.1. Входит в MVP

- Просмотр свободных и занятых столов.
- Открытие стола.
- Привязка ответственного официанта.
- Отдельная фиксация сотрудника, открывшего стол.
- Настраиваемые режимы STRICT и SHARED.
- Просмотр «Мои столы» и «Все столы».
- Создание черновиков.
- Локальное хранение черновиков на телефоне.
- Отправка пакетов.
- Дозаказы.
- Фиксация отправителя каждого пакета.
- Индивидуальные комментарии к блюдам.
- Передача комментариев на кухню.
- Автоматическое создание необходимых заданий кухонной печати.
- Проверка цен.
- Защита от повторной отправки.
- Закрытие пустых посещений.
- Закрытие оплаченных посещений.
- Сохранение истории.

## 18.2. Подготовлено архитектурно, но не реализуется в MVP

- Передача стола между официантами.
- История передачи ответственного официанта.
- Объединение столов.
- Перенос пакетов между посещениями.
- Разделение заказа между несколькими независимыми счетами.
- Бронирование столов.
- Состояние уборки стола.
- Дополнительные нестандартные статусы стола.

## 18.3. Требует отдельного согласования

В последующих разделах CORE-001 необходимо определить:

- подробные правила кассовых смен;
- частичную и смешанную оплату;
- возвраты;
- скидки;
- сервисные сборы;
- отмену отправленных позиций;
- исправление ошибочных комментариев после отправки;
- условия закрытия посещения при проблемах кухонной печати;
- полномочия кассира и менеджера;
- правила округления денежных сумм.

До согласования этих правил не следует самостоятельно вводить противоречащую им бизнес-логику в POS и Local Server.

# 19. Итоговые принципы раздела

1. Стол является физической сущностью, а посещение — отдельным случаем обслуживания гостей.
2. Одно активное посещение может существовать у стола только в единственном экземпляре.
3. Одно посещение в MVP содержит один основной заказ.
4. Основной заказ может содержать множество пакетов.
5. Каждый пакет фиксирует сотрудника, который его отправил.
6. Ответственный официант и отправитель пакета могут отличаться.
7. В режиме STRICT применяется строгая привязка посещений к официантам.
8. В режиме SHARED разрешена совместная работа с сохранением привязки.
9. Черновик не становится подтверждённым заказом до принятия сервером.
10. Каждая позиция может содержать собственный комментарий.
11. Принятый пакет сохраняется до обработки кухонной печати.
12. Повторная передача одной команды не должна создавать второй пакет.
13. Цены исторических позиций не изменяются задним числом.
14. Закрытие посещения освобождает стол, но не удаляет историю.
15. Передача столов между официантами проектируется для будущих версий, но не реализуется в MVP.

## Дополнение 04.11.2026 — область действия MVP

В утверждённом MVP режим доступа к столам фиксирован как `SHARED` для всего филиала. Владелец и сотрудники не могут переключить его на `STRICT` через интерфейс или API. Проверки авторизации, объектного доступа, принадлежности к филиалу и действующих разрешений остаются обязательными; совместная работа не передаёт ответственность за стол другому официанту.

Разделы о `STRICT`, переключении режима и поведении уже открытых столов при таком переключении сохраняются как требования будущей версии. Они не являются доступными сценариями текущего MVP. Интеграционные испытания MVP проверяют `SHARED` и запрет переключения; сценарии `STRICT` хранятся отдельно как будущий контракт и не засчитываются как пройденные испытания MVP.
