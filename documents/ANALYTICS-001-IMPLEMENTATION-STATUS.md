# ANALYTICS-001 — состояние реализации и зависимости

Дата сверки: 03.11.2026. Исходное задание: страница веб-кабинета владельца «Аналитика → Обзор».

## Проверенное состояние проекта

- До ANALYTICS-001 в репозитории не было Owner Dashboard. После подтверждения пользователя добавлен `apps/owner-dashboard` с первым экраном «Аналитика → Обзор». `apps/platform-admin` и `apps/public-menu` сохраняют собственное назначение.
- Local POS Server хранит `settlements`, `payments`, `refunds`, `orders`, `order_corrections`, смены и сохранённые отчёты в SQLite. Список продаж POS ограничен последними 24 часами, но сами финансовые факты в SQLite сохраняются.
- Для облака подготовлена миграция `20261103000100_analytics_overview.sql`: таблица подтверждённых финансовых фактов, идемпотентный приём подписанных пакетов, статус синхронизации и Owner-scoped агрегат. Изменение Edge Function `menu-sync` подготовлено в коде. Эти компоненты ещё не развёрнуты в удалённом проекте.
- В действующей финансовой схеме нет операции `Payment Reversal`/исправления метода оплаты. Этот пункт исходного задания нельзя изображать как работающий. Расчёт использует действительные запечатанные Settlement/Payment и отдельные Refund.
- В POS Desktop добавлена локальная страница «Аналитика → Обзор» только для Owner. Она читает текущий филиал через защищённый `GET /api/v1/analytics/overview`, сохраняет фильтры при фоновом обновлении и использует фирменные мятно-бирюзовые цвета. Переключение филиалов остаётся задачей веб-кабинета.

## Сделанная серверная основа

`buildOverviewMetrics` — внутренний read-only расчёт по SQLite для одного филиала и произвольного периода. Он использует только запечатанные денежные расчёты, точные целые тыйыны, различает TABLE/COUNTER и способы оплаты, считает возвраты по времени регистрации, скидку из итогового снимка Settlement, отменённые заказы и почасовые/дневные точки. Пустые интервалы возвращают нули. Реализован без изменения существующих финансовых записей.

Новый сайт получает показатели только из облачного агрегата. Метка «Обновлено» берётся из подтверждённой синхронизации, а при её отсутствии показатели скрываются.

Desktop получает локальные показатели из тех же запечатанных фактов SQLite и отдельно показывает состояние Cloud: неподтверждённое количество финансовых записей, последнее успешное подтверждение и ошибку отправки. Давнее подтверждение само по себе не означает устаревшие облачные данные, если новых записей нет. Отправку выполняет Local POS Server в фоне независимо от открытой страницы. Текущий вход Owner через Cloud может требовать интернет для новой авторизации; уже авторизованная страница читает локальные данные.

## Следующий обязательный этап для рабочей страницы

1. Применить облачную миграцию и развернуть обновлённую Edge Function `menu-sync`, затем обновить и запустить Local POS Server для нужных филиалов.
2. На реальных двух филиалах проверить первоначальную загрузку истории, повтор после потери связи, сверку итогов со сменными отчётами, смену через полночь, отзыв доступа и корректность статуса актуальности.
3. Опубликовать Owner Dashboard после приёмки. В данном изменении удалённый проект не менялся.

До деплоя облачного слоя и приёмки на двух филиалах это рабочая реализация в репозитории, но не подтверждённая production-аналитика.
