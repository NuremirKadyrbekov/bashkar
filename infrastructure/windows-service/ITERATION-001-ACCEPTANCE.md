Статус: подготовлен, на Windows ещё НЕ выполнен. Дата: 21.10.2026.

## Условия и журнал

Использовать только одноразовую тестовую установку. Не применять к реальной базе филиала. Записать модель ноутбука/POS, CPU, RAM, версию/сборку/редакцию Windows, пользователя, версию/хеш пакета и runtime, свободное место, часовой пояс, наличие интернета. Для каждого пункта: PASS/FAIL/BLOCKED/NOT RUN, фактический результат, время и обезличенные логи. Статус Running без живого API не PASS. Бэкап файла без проверенного восстановления не доказывает сохранность.

Облачный проект, реестр и Edge function подключены; настоящая активация/Keychain/offline restart проверены на macOS. Текущий исходный код — schema 3, Windows LocalService CurrentUser DPAPI требует отдельной приёмки. Старый ZIP iteration-001 имеет schema 2 и НЕ подходит для нового облачного сценария; нужен новый пакет iteration-002. До активации нормальное состояние — NEEDS_ACTIVATION и ready 503. Тестовые Owner/приватные authority/fixture в поставку не входят. Для Windows выделить отдельный доступный филиал: уже активированный на Mac филиал использовать нельзя.

## A. Установка и независимость службы

1. Проверить SHA-256 архива по manifest рядом с пакетом; распаковать в новую папку.
2. Старые **тестовые** службы BashkarPOSPrototype/BashkarPOSLockTest явно остановить; не удалять их lock-файлы. Установщик не обновляет их и откажет при работающей старой тестовой службе или существующей новой установке.
3. Administrator: `powershell -ExecutionPolicy Bypass -File .\install-foundation-test.ps1`. Создаётся только BashkarPOSFoundationTest, ProgramFiles/ProgramData с таким же именем, новый data, порт 3212. Сохранить вывод. Не повторять после частичного отказа без расследования.
4. `Start-Service BashkarPOSFoundationTest`. Проверить `http://127.0.0.1:3212/api/v1/system/health/live` = 200; ready = 503, NEEDS_ACTIVATION, schema=3 в version. Это ожидаемо и не означает готовность продаж.
5. Запустить `Start-Desktop-Test.ps1` как обычный пользователь. Ожидается облачный вход Owner и постоянная отметка тестового филиала. Закрыть Desktop: live продолжает отвечать.
6. Остановить службу штатно: соединения освобождены, stopped в журнале, sentinel снят. Запустить повторно: тот же installation ID/БД.
7. Перезагрузка и выход Windows/работа до входа: служба и API доступны независимо от Desktop. Повторить на Windows 10/11 и POS с 4 ГБ.

## B. ACL, конкуренция, crash и обновление

1. Administrator и LocalService имеют только необходимые права; обычный пользователь запускает Desktop, но не может читать/изменять/удалять/переименовывать data, marker, lock, БД, audit или код ProgramFiles. Проверить дерево, наследование, родительские каталоги и hard-link/rename варианты. Общий LocalService SID — ограничение тестового прототипа; отдельная служебная identity для реального пилота требует security-review.
2. Пока служба работает, второй запуск с тем же data должен отказать INSTANCE_LOCK_UNAVAILABLE и не менять БД. Проверить старый/новый процесс и алиасы пути; старую версию на той же рабочей БД не запускать ради эксперимента — только на отдельном воспроизводимом тестовом стенде.
3. Принудительно завершить именно Node этой тестовой службы по проверенному PID/ExecutablePath. Не использовать общий `Stop-Process -Name node`. Наблюдать SCM, PID, live и log: ожидается перезапуск после 5 с; при следующем отказе после 15 с; затем прекращение попыток до reset окна. Проверить, что WinSW передаёт аварию ребёнка SCM. До результата не считать restart готовым.
4. После crash новая версия получает OS lock без ручного удаления файлов и заново проходит проверки. Неизвестный/частичный legacy sentinel остаётся BLOCKED, без автоочистки. На неподвижном тестовом стенде отдельно проверить замену lock/sentinel: процесс прекращает опасные операции, чужой replacement не удаляет при close. Эти проверки не заменяют ACL.
5. Обновление старой установленной версии: только stop/disable старого запуска, подтверждение отсутствия процессов/владельца данных, проверенная копия и изолированный тест миграции, совместимость схемы, контролируемый запуск новой. Этот пакет НЕ выполняет upgrade. Реальный update/rollback до принятого D11/D13 runbook запрещён. Никакого автоматического возврата старой БД.

## C. База, миграции и отказы

1. На отдельных установках: явная новая установка, повторный start, попытка повторного init — не затирает файлы.
2. Остановленная тестовая служба: отдельно отсутствующая БД, marker, несовпадающий ID, повреждение файла, future schema/checksum mismatch. Ожидается BLOCKED; исходные файлы сохранены; пустая БД не возникает. Не удалять данные реального филиала.
3. Старый Bootstrap schema 1 или предыдущая schema 2: обычный start сообщает SCHEMA_UPGRADE_REQUIRED и не меняет версию. Отдельный `node.exe main.js migrate-db` при остановленной службе даёт схему 3, сохраняет ID и исходные записи. Неверный checksum/future version отклоняется.
4. При ожидающем обновлении и OPEN-смене миграция запрещена, в том числе для 2→3. Проверять на отдельной копии, не закрывать смену и не удалять записи обходными SQL-командами.
5. Воспроизводимый полный диск/IO-error/readonly на отдельном тестовом диске: команда не подтверждается, обязательные данные не сохраняются частично, API становится BLOCKED. После расследования и штатного рестарта проверки заново. После power loss отдельно integrity/данные/WAL — испытание только на выделенном оборудовании.
6. Не выполнять автоматическое восстановление из копии. При утрате обеих идентификаций пустой каталог не доказывает первичность установки; требуется отдельная подтверждённая процедура.

## D. Настоящая активация — NOT RUN на Windows

1. Создать тестовый Supabase проект, Owner, организацию/филиал, проверяющий backend и атомарный server registry. Service role не в Desktop/конфиге/логе. Проверить чужую организацию, отозванную роль Owner, конкурентные регистрации, поддельную/просроченную/replayed квитанцию и device mismatch.
2. Подключить защищённую identity LocalService; перенести/скопировать БД без ключа — не должно давать READY. Проверить ACL/DPAPI, ротацию и процедуру замены с подтверждённым физическим выводом старого офлайн-сервера.
3. Настоящий UI облачного входа/выбора филиала/отдельного локального пароля/commit. Проверить crash между облачной регистрацией и local commit; повтор должен выяснить исходную регистрацию, а не создать второй узел/Owner.
4. После настоящей активации отключить интернет (сохранив локальный сервер/сеть): перезапуск, локальный вход, сотрудники, смена и меню работают без Supabase/Telegram. Локальная test authority или просто отсутствие сетевых вызовов в unit test этот пункт не закрывают.

## E. Сотрудники, сессии, права и Desktop

После D: Owner создаёт Manager/Cashier/Waiter, получает временный пароль один раз. Повтор команды после потери ответа не раскрывает его снова; явный reset выдаёт новый. До личного пароля рабочих действий нет. Минимум 8 символов, common-password отклоняется, состав символов не навязывается. Измерить Argon2id (64 MiB/3/4) и параллельные входы на 4 ГБ, responsiveness/CPU/RAM.

Проверить POS idle=30 мин, absolute=12 ч; фоновые запросы не продлевают. Waiter policy=60 мин тестируется отдельно от ещё не готового браузерного транспорта. Logout/смена пользователя/password/reset/suspend/deactivate отзывают сессии и не закрывают Shift. Manager не меняет себя/Owner; grant не снимает роль-запрет; делегирует лишь разрешённое Owner и имеющееся у себя. Отзыв применяется к следующей команде, включая replay. Повторный приём — новый ID/логин, старый архив сохранён.

Проверить protected Desktop storage в Windows, отсутствие токена в renderer/localStorage/URL/логах, CSP/IPC sender/Origin/Host/CORS, HTTP-body/password ошибки, отсутствие секретов в audit/outbox/commands/ответах ошибок. Отдельно потеря ответа, перезапуск Desktop и прежний command ID. Подтверждения reset/suspend/deactivate; RU/KY, клавиатура, фокус и обычный пользователь. Проверить список невыясненных команд, повтор исходного payload/ID после перезапуска и запрет выдачи результатов другому сотруднику.

## F. Смена, меню и расчёт

1. Open требует сессии, отдельного права и повторных логина/пароля того же исполнителя; нет начального остатка. Несколько одновременных distinct-ID команд — одна OPEN; same-ID — исходный результат. Состояние сохраняется при logout/Desktop close/service restart. Close пока явно недоступен — не создавать фиктивный отчёт.
2. Категории одного уровня; основной язык обязателен, переводы необязательны/fallback; архив category с действующим item не проходит. Цена 0 принимается, missing/negative — ошибка; вариант заменяет base price.
3. Модификаторы: min/max, платные/бесплатные, запрет дубля/чужой опции/недоступной опции. Отдельный stoplist товар/модификатор, право, CAS и аудит; Waiter не меняет. Публикация не сбрасывает отдельный stoplist.
4. Draft save/reopen, два конкурирующих редактора, целостная публикация: не смешиваются старые и новые цены; fail audit/commit — старая редакция целиком; повтор не создаёт редакцию заново. Архивирование/новая цена не меняют старый snapshot калькуляции; реальный order snapshot проверяется в последующем блоке заказов.
5. Деньги целыми тыйынами: выбранный размер+опции, ×quantity; 1…9999; price/total ≤999999999. Discount 0…subtotal. TABLE 2 сбора по 50% от базы 1 тыйын: каждый 1, итог 3; COUNTER — 1. Ставка сотыми процента 0…10000, общая ≤10000. Проверить overflow в позиции/сумме/сборах и stale menu revision. QUOTE_ONLY не является продажей/оплатой.
