# UPDATE-001: ТЗ на завершение Update Manager и подготовку Windows E2E

Статус: рабочее ТЗ, 2026-11-05. Область: Bashkar POS, Windows x64, обновление установленной версии A → B. Это ТЗ не является отчётом о прохождении Windows E2E.

## Цель и граница готовности

Собрать существующие механизмы в один исполняемый Update Manager. Он должен принять ограниченное одноразовое задание с подписанным релизом и Cloud-разрешением, проверить установщик, подготовить обслуживание и Backup Set, остановить службу, извлечь и проверить payload, переключить файлы, выполнить миграцию, проверить новую версию и завершить обновление. После сбоя Manager должен продолжать **ту же** операцию по журналу или перейти к доказанному восстановлению. Когда доказать безопасность нельзя, служба остаётся закрытой и требуется ручное разбирательство.

**Код готов к Windows E2E A → B**, когда production-команда Manager может пройти полный сценарий и оба пути восстановления в изолированных автоматических тестах, а Windows-пакет содержит все используемые команды. **Windows E2E пройден**, только когда результаты этих сценариев получены на ноутбуке №2 и зафиксированы отдельно.

Текущая база: журнал и маршрутизация находятся в `apps/local-server/src/recovery/update-journal.ts` и `manager-coordinator.ts`; `update-manager-entry.ts` допускает только `--preflight` и `--resume-status`. Путь восстановления до `MIGRATION_INTENT`, путь восстановления после него и два закрытых запуска перед обычным режимом имеют изолированные тесты. Карта действий `LocalService` подготовлена, но Task Scheduler, DPAPI, ACL и реальное SCM-поведение на Windows не подтверждены. Последняя локальная проверка: `pnpm run check` и 98 профильных тестов прошли.

## Непересекаемые границы безопасности

1. Только одноразовые тестовые профили. Не открывать и не изменять MANGO, рабочие базы, регистрации и открытые смены.
2. Подтверждённые заказы, платежи, смены и прочие бизнес-операции не могут исчезнуть из-за автоматического восстановления. Если сравнение текущих данных с Backup Set не доказывает их сохранность, остановить автоматический путь.
3. Backup Set расшифровывается только под SID `LocalService` (`S-1-5-19`); Manager и установка выполняются под `SYSTEM` (`S-1-5-18`). Нельзя передавать ключ или расшифрованную SQLite-базу через файл, stdout, аргументы процесса или переменные среды.
4. Не создавать незашифрованную временную копию SQLite и не требовать BitLocker. Проверки Backup Set выполняются в памяти; запись восстановленных файлов разрешена только в уже ограждённый конечный каталог после проверки отсутствия новых бизнес-операций.
5. Не обходить подписанный manifest, Authenticode, Cloud install grant, проверку payload и NSIS preflight. Истёкший grant нельзя запрашивать или подменять при возобновлении старой операции; её идентичность берётся из журнала и исходного подписанного задания.
6. Guard и закрытый режим сохраняются до доказанного здоровья. После `NEW_UPDATE_COMMITTED` или `RECOVERY_COMMITTED`, когда обычный POS мог принять продажи, автоматический откат базы запрещён.
7. Никаких commit, push, deploy, GitHub Actions и действий с production-ключами в рамках реализации этого ТЗ без отдельного указания.

## Пакет 1. Долговечная подготовка и сериализация

### 1.1. Неоднозначный результат maintenance IPC

- Добавить привязанный к `operationId` долговечный результат подготовки на стороне `LocalService`: состояние обслуживания, идентификатор и путь Backup Set, проверенную личность установки, схему и необходимые показатели восстановления. Записывать результат атомарно **до** отправки ответа Manager.
- Повтор запроса с тем же `operationId` должен возвращать тот же подтверждённый результат после его повторной проверки. Он не должен создавать второй Backup Set, повторно закрывать смену или менять бизнес-данные.
- Если ответ потерян и результат нельзя доказать, журнал остаётся в состоянии ручного разбирательства. Manager не создаёт новую операцию и не повторяет потенциально опасную подготовку вслепую.
- Тесты: потеря ответа до и после записи результата, повреждённый/чужой результат, повторный запуск процесса и совпадение Backup Set/instance/schema.

### 1.2. Один исполнитель на операцию

- Ввести межпроцессную блокировку Manager с владельцем, привязанную к одной операции. Второй экземпляр не должен одновременно запускать NSIS, SCM, миграцию или `LocalService`-задачу.
- После аварийного завершения блокировка должна освобождаться или восстанавливаться по проверяемому состоянию ОС; не считать один лишь устаревший lock-файл доказательством работающего процесса.
- Повторный запуск сверяет `update-job.json`, журнал, guard, каталог приложения и состояния службы до любого действия.
- Тесты: конкурентный запуск, завершение владельца, повтор с тем же и другим `operationId`, повреждённый lock.

## Пакет 2. Учётные записи и исполняющие обработчики

### 2.1. Граница `SYSTEM` → `LocalService`

- Завершить и проверить мост `local-service-task.ts`: только фиксированный список команд, один UUID операции, неизменяемые пути к подписанному стабильному Manager, ограниченное время, проверка владельца и состояния существующей задачи при возобновлении.
- Каждая дочерняя команда самостоятельно проверяет SID `LocalService`; родительский Manager самостоятельно проверяет SID `SYSTEM`. Успех Task Scheduler без ожидаемого перехода журнала считается ошибкой.
- Проверить права на `%ProgramData%\BashkarPOS` и `%ProgramFiles%\Bashkar POS Update Manager`: `LocalService` получает доступ только к нужным данным и Backup Set, не может подменить стабильные исполняемые файлы; посторонний пользователь не может создать задание Manager.
- Проверить возобновление, когда Manager прерван до запуска задачи, во время неё и после её успешного завершения до получения результата.

### 2.2. Реальные обработчики Manager

- Связать `ManagerAction` с существующими функциями и командами без дублирования логики: подготовка подписанного задания; проверка Backup Set под `LocalService`; остановка SCM и старый инвентарь; повторяемое NSIS-извлечение; проверка подписанного payload; переключение файлов; миграция; проверка и закрытый запуск новой версии; финализация; восстановление до и после `MIGRATION_INTENT`.
- Перед выполнением EXE повторять проверку размера, SHA-256, Authenticode и привязки к подписанному manifest. Перед переключением проверять извлечённый payload. Существующий частичный staging разрешается пересоздавать только для текущей ограждённой операции и остановленной службы.
- При ошибке миграции, пока фаза всё ещё `BINARY_SWITCHED`, разрешить проверенный возврат старых файлов и данных. После записи `MIGRATION_INTENT` использовать только путь проверки/восстановления данных под `LocalService`; один лишь возврат старого приложения запрещён.
- Завершать успешный новый релиз и восстановление старого релиза через существующие guard-пробу, два закрытых запуска, обычный перезапуск и проверку здоровья. При любой неоднозначности оставлять guard/службу в безопасном состоянии и возвращать код ручного разбирательства.
- Запуск production Manager из ограниченного задания должен иметь явный доверенный механизм под `SYSTEM`. POS UI не получает права на произвольную команду SYSTEM. До завершения всех критериев ниже `--run` не открывать.

## Пакет 3. Возобновление и тесты Manager

Написать изолированные интеграционные тесты с настоящими временными SQLite, Backup Set, журналом, подписями тестового payload и файловыми каталогами. Заменять только Windows SCM, Task Scheduler, DPAPI и сетевые границы управляемыми адаптерами. Не подменять сами переходы журнала записью нужной фазы в тесте полного сценария.

Обязательная матрица:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Полный A → B | `NEW_UPDATE_COMPLETED`; версия/схема B; исходные бизнес-строки сохранены; служба здорова |
| Сбой NSIS или переключения до `MIGRATION_INTENT` | Старое приложение и исходные данные подтверждены; `RECOVERY_COMPLETED`; при несовпадении — guard и ручной разбор |
| Сбой после `MIGRATION_INTENT` | Только проверенный `LocalService` restore, старое приложение и закрытые проверки; сохранность всех подтверждённых строк |
| Сбой после открытия обычного POS | Никакого автоматического отката базы; служба остановлена/ограждена и требуется ручной разбор |
| Прерывание на каждом критическом intent и после каждого файлового rename | Повтор использует прежний `operationId`, не выполняет опасное действие дважды и приходит к доказанному результату либо ручному разбору |
| Повреждённый journal/job/guard, чужой Backup Set, изменённая подпись, неверная учётная запись | Отказ до опасного действия; исходные данные сохранены |

Отдельно проверить создание **следующего** Backup Set после успешного восстановления: служебные маркеры не должны навсегда блокировать обычную эксплуатацию.

## Пакет 4. Сборка и приёмка на Windows

### Ноутбук №1: сборка

- Собрать A и B с отдельными **тестовыми** ключами и тестовой цепочкой доверия; зафиксировать версии, схемы, SHA-256 EXE, подписанные manifest/payload, состав Manager и NSIS stage.
- Проверить, что bundled команды запускаются из установленного стабильного Manager и нужные native-модули включены. Зафиксировать результат `pnpm run check`, профильных тестов, esbuild и самой Windows-сборки.
- Production Bunny/Cloud-ключи для этого теста не использовать. Если build script требует чистый checkout, подготовить отдельную чистую тестовую сборку без изменения рабочего дерева и без несанкционированного commit/push.

### Ноутбук №2: установка и A → B

- Использовать чистую одноразовую установку. В версии A создать контрольные заказы, платежи и закрытую смену; записать контрольные значения и хеши. Открытую смену обновление должно отклонить.
- Проверить чистую установку, службу WinSW под `LocalService`, права ACL, DPAPI Backup Set, test Cloud grant/job, скачивание или локально поданный тестовый EXE через тот же проверочный путь, обновление A → B и сохранность контрольных данных.
- Повторить сценарии до/после `MIGRATION_INTENT`, отключение питания/убийство процессов на критических фазах, частичную распаковку, падение Task Scheduler-задачи, два закрытых запуска, обычный старт, ручной fail-closed. Проверить, что во время quarantine продажи и действия официанта заблокированы.
- Зафиксировать команды, журналы, версии, схемы, состояние SCM и результат каждого шага в отдельном Windows E2E отчёте. Не считать `Running` доказательством здоровья без HTTP и проверки бизнес-данных.

## Условия открытия `--run` и завершения этапа №4

`--run` можно включить только когда пакеты 1–3 реализованы, весь список `ManagerAction` имеет реальные обработчики либо явное ручное окончание, а изолированные тесты проходят для успеха и обоих восстановлений с возобновлением. После включения повторить весь набор тестов и проверить состав Windows EXE. Этап №4 считается завершённым как **код, готовый к Windows E2E**, но не как пройденное обновление на Windows. Полноценное удалённое production-обновление дополнительно требует развернутого Cloud/Bunny, production-ключей и отдельной приёмки.
