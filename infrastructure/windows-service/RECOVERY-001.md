# Backup Set candidate for UPDATE-001

`apps/local-server/src/recovery/backup-set.ts` creates an isolated backup candidate. The Windows installer bundles `server/backup-cli.js` for `create` and `verify` under LocalService; creation takes the database lock. `restore-check` requires `BASHKAR_RECOVERY_DISPOSABLE_TEST=1` and is reserved for a disposable test runner. It opens a decrypted temporary copy through `Storage` and removes the copy before returning. This code does not replace a live database or mark an update as `BACKUP_VERIFIED`.

Creation rejects an open shift, checks the source database and `installation.json` identity, includes the known external configuration and DPAPI files, encrypts each file with AES-256-GCM, and protects the set key with LocalService CurrentUser DPAPI. The manifest records the operation ID, software and schema versions, installation and registration IDs, and file hashes. Normal verification authenticates and hashes each encrypted entry while decrypting it into a discard stream. The disposable `restore-check` additionally opens the restored database, checks its schema and identity, verifies signed activation against the device key when activated, compares PIN and web key fingerprints with SQLite bindings, and checks the saved TLS private key against its certificate.

On Windows, data and backups are restricted to `%ProgramData%/BashkarPOS/data` and `%ProgramData%/BashkarPOS/backups`. The existing service installer sets ACLs on their parent. Backup creation must run under LocalService after writers are quiesced. The Windows build compiles `memory-backup.exe` from the locked SQLite amalgamation using Visual Studio C++ Build Tools. It copies SQLite into a bounded in-memory database (maximum 256 MiB), checks its integrity, and streams the serialized snapshot directly into AES-256-GCM encryption. Normal creation and verification do not write plaintext snapshots. An interrupted operation may leave `.partial-*`; a later backup refuses to start while incomplete staging exists. Completed sets are named by `operationId`.

Windows volume encryption is not required. The explicit `restore-check` writes a temporary plaintext copy and must only run on a clean disposable Windows machine. The temporary directory is removed on normal exit; an abrupt power loss could leave it behind. It is not a production update gate.

The disposable Windows installer smoke test stops its newly installed server, runs a temporary LocalService recovery service, creates and verifies a backup, opens the restored copy through `Storage`, checks that an update guard blocks server startup, removes the temporary service, and restarts the server. It checks an unactivated installation and DPAPI wrapping of the Backup Set key. A later activated/PIN fixture is still required. This smoke test must run only on a clean disposable Windows runner.

The production server checks `%ProgramData%/BashkarPOS/config/update-intent.json` and `update-guard.json` before opening SQLite. Either file blocks startup even when damaged or incomplete. `beginGuardedOperation` writes the operation/backup identity to the intent file first, then writes the guard; a crash between the two writes still blocks the server. This primitive does not install a release, authorize a backup, or clear either file. A future Update Manager must own those decisions and durable state transitions. These checks cannot stop an older installed binary that lacks them; the one-time transition needs SCM/WinSW control and power-loss testing.

The in-process maintenance controller is wired to both Desktop and Waiter HTTP listeners. It rejects all new HTTP requests during draining, waits for accepted requests, rejects new business commands, checks for an open shift, stops the Waiter listener, realtime socket and background print/cloud jobs, drains the command bus, rechecks SQLite integrity and the shift, then keeps HTTP blocked until service restart. A failed preflight before background shutdown reopens normal operation. A failure after shutdown retains maintenance mode and requires controlled service restart. No ordinary POS API route can enter maintenance.

The maintenance controller creates and cryptographically verifies a Backup Set using the server's existing SQLite connection while it owns the installation lock. It returns the candidate operation ID and path only after creation and verification succeed; a failure after background shutdown retains maintenance mode until controlled restart. The standalone `backup-cli create` remains for the disposable stopped-service smoke test. `backup-acceptance.ts` adds a separate production gate: it authenticates the Backup Set again, decrypts its files into bounded RAM, opens restored SQLite in memory, checks schema, installation and registration identity, protected device/PIN/web/TLS keys, and decrypts and verifies every saved PIN. It writes no plaintext recovery file and does not require disk encryption. Only a matching candidate can advance to `BACKUP_VERIFIED`. The gate is not yet wired to an independent Windows Update Manager; real LocalService DPAPI and activated/PIN Windows acceptance remain open.

The production server now listens on the fixed local Windows pipe `\\.\pipe\BashkarPOSUpdateControl`. The control key is stored in `%ProgramData%/BashkarPOS/config/update-control.key`, under the installer-created restricted ACL. A client and server exchange fresh nonces and HMAC proofs; the key is never sent over the pipe. The only command prepares maintenance and returns its Backup Set candidate. An operation ID binds the request and response. The LocalService identity, pipe behavior, and inherited ACL need Windows E2E confirmation. The pipe does not authenticate an employee or release, create the persistent startup guard, stop the Windows Service, or install files; these remain Update Manager responsibilities.

The independent Update Manager journal primitive stores `update-operation.json` in the restricted config directory. Pre-`MIGRATION_INTENT` recovery now has a separate guarded path. `PRE_MIGRATION_RECOVERY_INTENT` precedes any old-directory reconciliation; `PRE_MIGRATION_BINARY_RESTORED` records the verified old inventory after the rename. A LocalService-only `update-verify-pre-migration.js` command decrypts the Backup Set only in memory, verifies its identity and credentials, compares every SQLite user table and protected non-database file with the stopped installation, and writes a small non-secret proof marker before `PRE_MIGRATION_DATA_VERIFIED`. A subsequent LocalService old-install check advances to the existing guarded service probe and two-quarantine-boot recovery finalizer. The proof marker is removed only after ordinary health and `RECOVERY_COMPLETED`, so a later Backup Set remains possible. Power loss between directory renames, between proof marker and journal write, during guard removal, and before marker cleanup is covered by isolated tests. Changed business rows, changed protected files, mismatched guards, damaged Backup Set and absent LocalService identity leave the service guarded for manual investigation. No SQLite plaintext copy is written.

The stopped old application inventory is captured at `SERVICE_QUIESCED` before NSIS extracts into staging.
