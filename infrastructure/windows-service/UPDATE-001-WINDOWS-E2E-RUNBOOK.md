# UPDATE-001: приёмка тестового Windows A → B

Статус: инструкция для двух подготовленных ноутбуков. Реальные результаты в этом файле пока не записаны. Использовать только одноразовую установку и отдельные **тестовые** ключи. Рабочие базы, регистрацию ресторана и открытые смены не переносить.

Исходники для Windows-проверки передаются веткой `codex/update-001-windows-e2e` основного GitHub-репозитория. На ноутбуке №1 после клонирования выполнить `git fetch origin` и `git switch --track origin/codex/update-001-windows-e2e`; зафиксировать полученный commit SHA. Не подменять его `main` и не переносить с Mac локальные базы, DPAPI-ключи или файлы регистрации. `apps/platform-admin` и `apps/public-menu` являются отдельными Git-репозиториями; их незакоммиченные локальные изменения не входят в эту ветку.

## Ноутбук №1 — сборка и проверка пакета

1. В отдельной тестовой копии исходников зафиксировать commit SHA, список изменённых файлов и хеш исходного архива, `pnpm`/Node версии и выполнить `pnpm install --frozen-lockfile`, `pnpm run check`, профильные Vitest-тесты UPDATE-001. Не использовать production Bunny/Cloud-ключи. Для B с незакоммиченными изменениями не указывать, что `gitCommit` в тестовом manifest точно описывает содержимое дерева; приложить отдельный хеш архива.
2. Подготовить два подписанных тестовых релиза A и B с различными версиями и ожидаемой схемой B. Собрать Windows EXE через `infrastructure/windows-service/build-installer.ps1 -TestSigned`, передав **тестовые** публичные ключи publisher/Cloud, отдельный тестовый Ed25519 private key, manifest draft с `test_` release ID и тестовый сертификат Authenticode согласно параметрам скрипта. Сертификат должен быть доверенным на ноутбуке №2; иначе `Get-AuthenticodeSignature` не даст `Valid`, и сценарий останется закрыт. Записать SHA-256 обоих EXE, signed release manifest, signed payload manifest и значение target schema. Production-режим по-прежнему требует чистый checkout и HTTPS timestamp.
3. Проверить каталог `manager-stage`: `node.exe`, `update-manager.js`, `update-trust.json`, `service-bootstrap.js`, команды `update-verify-backup.js`, `update-restore.js`, `update-verify-restore.js`, `update-verify-pre-migration.js`, `update-service-probe.js`, `update-new-service-probe.js`, `update-finalize-recovery.js`, `update-finalize-new.js`. В payload B проверить `server/update-migrate.js`, `server/version.json`, `server/recovery-quarantine.json`.
4. Проверить подпись EXE и сертификат командой `Get-AuthenticodeSignature`; проверить, что подписанный payload B совпадает с извлечённым NSIS stage. Любое несовпадение блокирует тест установки.
5. На одноразовой установке проверить PowerShell `service.ps1 -Mode Install`: создано задание `BashkarPOSUpdateManager` под `NT AUTHORITY\SYSTEM` с **одним** действием `node.exe update-manager.js --run`, interval 1 minute, policy IgnoreNew. Проверить ACL каталога Manager: LocalService читает/исполняет, не изменяет; обычный пользователь не может подменить команду. Проверить ACL `%ProgramData%\BashkarPOS`, включая `config`, `backups`, `updates`.

## Ноутбук №2 — чистая установка и контрольные данные

1. Установить A на пустую тестовую машину. Убедиться, что WinSW-служба `BashkarPOSLocalServer` работает под LocalService и имеет `Automatic` start. В тестовой регистрации создать закрытую смену, заказ, платёж и контрольные записи. Записать ID, суммы, количество строк, SHA-256 SQLite/контрольных файлов, версию и схему. Проверить, что открытая смена блокирует maintenance и не меняет данные.
2. Создать одноразовое подписанное Cloud install grant и `update-job.json` на A; загрузить тестовый EXE B через тот же проверяемый путь. Проверить `--preflight` и `--resume-status` под SYSTEM. Дождаться фиксированного задания Manager. Не запускать Manager от обычного пользователя и не менять task action вручную.
3. Наблюдать журнал `update-operation.json` и SCM: `WAITING_FOR_MAINTENANCE` → `BACKUP_CANDIDATE` → `BACKUP_VERIFIED` → `SERVICE_QUIESCED` → `BINARY_SWITCH_INTENT` → `BINARY_SWITCHED` → `MIGRATION_INTENT` → `MIGRATED` → проверки нового релиза → `NEW_UPDATE_COMPLETED`. После каждого перехода записать время, версию файлов, схему, статус службы и guard. Сверить контрольные заказы, платежи и закрытую смену после двух закрытых запусков и обычного рестарта.
4. Отдельно на новых одноразовых установках A повторить: частичное извлечение NSIS; остановку Manager до/после maintenance receipt; прерывание между двумя rename; отказ миграции до и после `MIGRATION_INTENT`; отказ LocalService task; выключение питания; отказ здоровья guarded/quarantine/обычного режима. Для каждого сценария зафиксировать, возобновилась ли **та же** операция, остались ли подтверждённые строки, снят ли guard только после доказанного здоровья. После обычного открытия POS автоматический откат данных запрещён.
5. Проверить DPAPI LocalService: SYSTEM не может расшифровать ключ Backup Set; восстановление выполняется только дочерней задачей LocalService. Проверить, что в логах/stdout/аргументах нет ключа или расшифрованной SQLite. Проверить, что следующий Backup Set создаётся после успешного восстановления старой версии.

## Фиксация результата

Для каждого прогона сохранить: хеши A/B EXE, signed manifest, `update-operation.json`, события Manager, результат Task Scheduler, SCM состояние и SID, ACL, HTTP `health/live` и `health/ready`, версию/schema, контрольные ID и суммы, результат сравнения данных. `Running` без HTTP и проверки бизнес-строк не означает успех. При неоднозначном состоянии оставить guard и остановленную службу; дальнейшее действие только после ручного анализа. Windows E2E считается пройденным лишь после фактического протокола этих прогонов.
